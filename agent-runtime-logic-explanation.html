💡 核心职责
  1. 桥梁作用：连接 Service 层和 AI Agent，将业务请求转换为 Agent 输入，将 Agent 输出转换为业务决策
  2. 工具编排：定义和管理 Agent 可调用的工具（search、sync、reply、show 等）
  3. AI 调用：使用 Agents SDK 调用 AI 模型，支持流式响应
  4. 决策提取：从 Agent 输出中提取决策（方案A：从工具参数提取）
  5. Fallback 机制：当 AI 调用失败时，提供简单的 fallback 实现

🤖 AgentsSdkDiscoveryAgentRuntime 主实现类

类架构（第884-967行）

初始化 __init__(fallback=StubDiscoveryAgentRuntime())
↓
核心方法 initial_decision(run_input) | run_turn(run_input, user_message, action_context)
↓
内部方法 _run_or_fallback() | _run_with_agents_sdk() | _run_streamed_agent()
↓
Fallback 机制 _should_use_agents_sdk() | _fallback_result()
💡 设计思路
  • 主入口：initial_decision 和 run_turn 是主入口，统一调用 _run_or_fallback
  • Fallback 机制：当 API key 缺失或 AI 调用失败时，自动降级到 Stub runtime
  • 异常处理：捕获异常并尝试恢复决策，如果失败则 fallback
  • 流式响应：使用 Runner.run_streamed 支持流式响应，记录 first_token_latency

    🚀 _run_with_agents_sdk 核心运行方法

    5 步流程（第981-1243行）

    1
    配置 Provider
    设置 OpenAI client、base URL、API key，选择 wire API（responses 或 chat_completions）

    💡 方案A：双工具输出（第1026-1094行）
    设计理念：Agent 通过调用不同的工具来表达不同的意图
    • reply_to_user：纯对话回复，不展示候选人卡片（phase: collecting_preferences）
    • show_candidates：展示候选人卡片（phase: results_shown 或 no_result）
    • 优先级：show > reply（展示优先）

    💾 sync_requester_persona_memory 偏好同步

    🔍 search_partner_candidates 核心搜索

    💬 reply_to_user 输出工具
    回复用户对话消息，不展示候选人卡片。用于对话收集偏好、解释推荐理由。

    返回：保存到 tool_state["show_payload"]
    💡 工具设计原则（Agent Native）
    • 单一职责：每个工具只做一件事，不做业务逻辑判断
    • 纯执行：工具只执行操作，返回原始数据，不包含 instruction/output_hint
    • 描述清晰：工具 description 描述能力和使用场景，Agent 自主决定何时调用
    • 输出工具：reply_to_user 和 show_candidates 是输出工具，Agent 通过调用它们来表达意图

    💡 核心设计理念
    1. Agent 是决策大脑：AI 自主理解用户意图，决定调用哪些工具，如何回复
    2. 工具是执行器：工具只做一件事，返回原始数据，不包含业务逻辑
    3. 方案A双工具输出：Agent 通过调用 reply_to_user 或 show_candidates 表达意图
    4. 单一真相来源：SOUL.md 定义角色，工具 description 描述能力，不重复定义规则
    5. Fallback 机制：当 AI 调用失败时，自动降级到 Stub runtime
    6. 证据优先：记录 Agent 实际行为，用于测试验证和改进决策
