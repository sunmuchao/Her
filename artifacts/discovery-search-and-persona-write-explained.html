给人看的版本

发现页搜索逻辑 + 画像写入逻辑

这份说明专门用大白话讲两件事： 第一，用户在发现页说一句话之后，系统到底怎么搜人。 第二，用户说过的话最后会写进哪张表，哪些会进画像，哪些会进摘要，哪些会进向量库。

先说最重要的一句： 当前系统里，发现页“边聊边写 persona”这条能力实际上是关掉的。 也就是说，用户在发现页实时对话时，系统会实时搜索，但不会实时把这些话写进 user_personas。 真正的沉淀写入，主要发生在“会话结束之后”的后台处理。

一句话理解发现页

发现页更像一个“带记忆的红娘会话”，不是一个死板的筛选表单。

一句话理解画像写入

系统会把“能量化的条件”写画像，把“说不清但很重要的感觉和偏好”写摘要和向量。

一句话理解当前现实

实时搜索和长期沉淀，是两条链路，不是同一条链路。

一、发现页内部的完整搜索逻辑

先用一个最容易懂的例子：

例子：用户在发现页说

“我想先看看无锡的，别太强势，最好工作别忙得没时间谈恋爱。”

你以为系统在做的是： “把这句话立刻写进用户画像，再拿画像去搜人。”

当前真实情况不是这样。

当前更接近： “先把这句话当成这次会话里的即时搜索线索，红娘当场拿这些线索去搜；等会话结束后，再决定哪些内容值得沉淀。”

前端进入发现页 → 恢复/创建 discovery session → agent 判断要不要搜 → 整理本轮条件 + 历史 working criteria + self profile → partner_search 执行搜索 → 返回候选人卡片 → 写入当前 session 视图和搜索记录

1. 用户刚进入发现页时，系统先干什么

1
先找有没有旧会话。

前端会先看 URL 里有没有 session id，再看本地缓存里有没有之前的 session id。

如果有，就恢复旧会话；如果没有，就新建一个 discovery session。

2
恢复的不是“只有聊天记录”，而是整套页面状态。

包括 timeline、推荐卡片、建议动作、criteria chips、输入框提示语等。

3
还会补充 collected preferences。

前端会额外拉一份 collected statements，把一些偏好 chips 展示出来。

注意：这个更多是 UI 层补充，不等于直接用它触发一次搜索。

2. 新建会话时，后端到底怎么决定“要不要开始搜”

后端新建 session 后，不是立刻固定跑某个 SQL。 它会进入一个 discovery runtime，也就是“红娘代理”的运行时。

它会拿什么信息做判断 大白话解释
session.phase 当前是在“收集偏好”阶段，还是已经适合直接给结果。
criteria_labels 页面上已经展示过哪些条件标签，比如“无锡”“本科以上”。
recent_timeline 最近这段对话里发生过什么，已经看过哪些候选人。
runtime_context 更完整的上下文，比如上一次搜索摘要、可见动作摘要等。
self_profile 用户自己的资料，搜索时会用来做互相匹配和一些风险判断。
一句话总结： 发现页不是“用户一句话直接变搜索参数”，而是“agent 看上下文后，决定这句话该不该触发搜索、要带哪些条件去搜索”。

3. 真正发起搜索时，条件是怎么来的

搜索条件主要来自 4 个地方：

  • 用户这一次刚说的话，被 agent 提炼出的 criteria
  • 这个 session 里之前已经积累的 working_criteria
  • 用户自己的 self_profile
  • 一些 runtime context 里的补充信息
例子：用户连续两轮说话

第一轮：“先看无锡的。”

第二轮：“学历最好本科以上，别太强势。”

系统不会只看第二轮，而是会把第一轮和第二轮拼起来， 形成一个更完整的会话内搜索条件。

大白话就是：红娘不会因为你第二句话没再提“无锡”，就立刻把“无锡”忘掉。

4. working_criteria 是什么

你可以把它理解成： 这一次发现页会话里，红娘临时记住的筛人要求。

它不是长期画像，更像“这场对话期间的临时便签”。

例子

用户说：“无锡优先。”

系统可能先记成：cities = ["无锡"]

后面用户又说：“其实苏州也可以。”

那这张临时便签就会改成更新的条件组合，而不是每次都从头来。

当前代码里，`working_criteria` 的合并逻辑还有一个具体修正： 如果用户传了 cities，旧的 city 会被清掉，避免两个字段互相打架。

5. partner_search 真正会做什么

发现页把条件整理好后，会调用 partner_search.search_profiles()。 这一步不是简单数据库筛选，而是一个多层处理流程。

模块 大白话解释
search_sources 先把候选人的 profile、照片、可能的 moderation 信息都加载出来。
search_profile_context 把用户自己的资料和搜索条件整理成统一格式。
search_matching 做硬筛选和软匹配，比如年龄、城市、学历、一些节奏偏好。
search_reciprocal 不只看“你喜不喜欢她”，还看“她那边能不能接受你”。
search_ranking 综合打分、排序、控制结果不要太像、去掉质量太差的尾部结果。
search_text_signals 处理关键词证据、notes 摘要、敏感文本脱敏。
search_trust 补认证、活跃度、可信度相关信息。
personality_traits_reader 给 discovery 卡片补人格测评上下文，比如 MBTI、依恋、价值观等。
为什么一张候选人卡片里会有这么多东西

因为卡片不是只来自 profiles 表的一行数据。

它是把这些东西拼起来的：

  • 基础资料：年龄、城市、职业、学历
  • 搜索命中理由：为什么把她推荐给你
  • trust 信息：认证、照片、活跃程度
  • 人格信息：测评可用性、values、MBTI、依恋等

6. 搜完之后，结果怎么回到页面

搜索结果回到 discovery service 后，不是直接扔给前端列表。

它会被包装成一整套 discovery view：

  • assistant_message：红娘说的话
  • result_group：这一批推荐卡片
  • criteria_chips：当前已经识别出的偏好条件
  • suggested_actions：比如“换一批”“看看更多”之类
  • composer 状态：输入框该怎么提示
所以发现页的本质不是“搜人页”，而是“会话化搜索页”。 搜索只是里面的一步，session 才是中心。

7. 发现页当前一个非常关键的现实限制

当前 discovery 实时阶段的 persona 同步是禁用的。

也就是 agent 虽然还能调用名为 sync_requester_persona_memory 的工具， 但这个工具现在会直接返回“disabled_for_testing”，不执行实际写入。

大白话就是：红娘会当场帮你搜，但不会边聊边把你的话正式记进长期画像。

二、画像、摘要、向量库的完整写入逻辑

这里也先用最容易懂的例子说。

例子：用户在一段会话里说了这些话

“我不接受异地。”

“最好是无锡或者苏州。”

“我挺慢热的，不喜欢暧昧拉扯，希望关系推进明确一点。”

“我很看重情绪稳定和愿意沟通。”

系统不会把这些话一股脑塞进同一张表。

它会先问自己两个问题：

  • 这句话里有没有能量化、能结构化的东西？
  • 这句话里有没有很重要，但很难变成硬字段的东西？
会话结束触发 → 重新加载这段会话里的用户原话 → LLM 提炼结构化摘要 → 分成“可量化”和“不可量化”两堆 → 可量化写 persona / observations → 不可量化写 conversation_summaries → 再把 summary 文本做 embedding 写入 Milvus

1. 什么时候触发写入

当前不是实时写，而是主要在会话结束相关场景触发：

  • 用户新开一个发现页会话时，后台处理上一个会话
  • 用户切换会话时，后台处理被切走的那个会话
  • 显式关闭会话时处理

而且不是每次都全量重跑，会看这个会话自从上次处理后有没有新增内容。 没新增，就跳过。

2. 它提炼的原材料是什么

很关键的一点： 后台提炼时，不是拿内存里现成对象，也不是拿助手说过的话， 而是重新从数据库里加载该 session 的消息。

而且只保留 用户原话。

为什么只看用户原话

假设用户说：“我不想异地。”

助手回复：“明白了，你更偏好同城。”

如果连助手复述也一起拿去提炼，系统就可能把同一个意思重复沉淀两次， 甚至把助手的转述当成新的事实。

所以当前实现只看用户原话，这个做法是对的。

3. LLM 提炼后会得到什么

LLM 会把整段用户原话总结成结构化字段，比如：

字段 例子 性质
personality_traits 慢热、理性、温和 不可量化
values 看重情绪稳定、重视沟通 不可量化
partner_expectation 希望对方认真推进关系，不暧昧 不可量化，但很重要
emotional_needs 希望对方愿意回应、不冷处理 不可量化
city 无锡 可量化 / 结构化
education 本科 可量化 / 结构化
mbti_type INTJ 可量化 / 结构化

4. 第一道分流：可量化 vs 不可量化

这里可以把系统想象成一个分拣员：

  • 能明确变成字段、范围、枚举、布尔值的，放到“画像盒子”
  • 更像感觉、偏好、节奏、人物特质的，放到“摘要/向量盒子”
同一句话，会拆成两部分

用户说：“我希望找无锡的，最好本科以上，情绪稳定一点，别暧昧。”

可能会拆成：

  • 可量化：target_cities = ["无锡"]、target_education_min = 本科
  • 不可量化：partner_personality_preference = 情绪稳定、partner_relationship_pacing = 不喜欢暧昧

5. 可量化信息怎么写入 user_personas

可量化数据会走 persona-memory-sync 引擎。

主顺序是：

1
先标准化 patch。

比如列表转 CSV、布尔值规范化、整数规范化、一些语义别名统一。

2
读取已有 persona。

看看这个用户之前已经记住了什么。

3
合并 persona。

新值和旧值对比，决定是 insert、update 还是 skip。

4
upsert 到 user_personas。

也就是把长期画像真源更新掉。

5
把这次变化写进 user_persona_observations。

这一步更像审计日志，记录“为什么改了、改了哪些字段”。

一个非常关键的当前现实：

现在 strong_inference 和 weak_inference 基本不会真正写进 user_personas，会被跳过。

当前真正能稳定持久化进 persona 的，主要是： explicit、profile_form、explicit_confirmation。

大白话就是：系统现在更信“用户明确说过的”，没那么信“系统自己猜出来的”。

6. user_persona_observations 到底记什么

你可以把它理解成： 画像改动的凭据账本。

记录项 大白话解释
field_name 这次说的是哪个字段，比如 target_accept_long_distance
field_value 这次提炼出的值是什么
source_type 是明确表达，还是推断
evidence_text 不是整段原始对话，而是压缩过的证据摘要
applied_to_persona 这次值最后有没有真的改到 persona
applied_to_profile 这次值有没有进一步同步到 profile

所以它不是给检索直接用的主画像，而是给溯源、审计、调试用的。

7. 不可量化信息怎么写入 conversation_summaries

如果系统觉得这段信息很重要，但不适合强行塞进 persona 字段， 就会写进 conversation_summaries。

典型适合进 summary 的内容
  • “我很慢热，不喜欢关系推进太快。”
  • “希望对方能正面沟通，不要冷处理。”
  • “我特别看重情绪稳定。”
  • “工作别太卷，下班后最好有时间相处。”

这些都很重要，但很难用一个简陋的枚举值表达完整，所以更适合写摘要。

写 summary 之前，还会做一次质量检查：

  • 太空泛的句子会被拒绝
  • 像“希望真诚沟通”“三观一致”“有共同话题”这种没展开的空话，会被拦掉
  • 只有足够具体的 summary 才会入库
这个设计很重要。 如果把全是空话的摘要写进向量库，后面召回会越来越糊，谁都像谁。

8. 向量库怎么写

写完 conversation_summaries 后，系统会继续做 embedding， 再写入 Milvus Lite 的 user_vectors 集合。

但不是“每来一句就直接 embedding 原句”，而是更谨慎：

  • 先查这个用户这个维度过去有没有历史摘要
  • 判断这次是补充、覆盖、还是重复
  • 合成一个更稳定的最终摘要文本
  • 再对这个最终文本做向量化
例子：同一个维度会合并，不是无限堆原句

第一次 summary：partner_relationship_pacing = 慢热，希望关系推进明确

第二次 summary：partner_relationship_pacing = 不喜欢暧昧拉扯，希望认真推进

系统不会简单保留两句互相重复的话， 而是会尝试合成一个更完整、更稳定的最终文本， 再写入摘要表和向量库。

9. 向量库里存的到底是什么

Milvus 里每条向量大致包含这些信息：

字段 大白话解释
user_id 这个向量属于谁
conversation_id 这次向量是从哪段会话来的
vector_type 这是性格向量、价值观向量，还是择偶节奏向量
vector_version 这是这个维度的第几个版本
raw_text 生成这个向量用的最终摘要文本
is_active 这个版本现在是否仍然生效

搜索相似用户时，还会考虑时间衰减。 比如“性格特质”和“价值观”衰减得慢，“情感需求”衰减得更快。

10. profiles 的写入，到底处在什么位置

很多人会误以为：所有画像最后都会同步到 profiles。 但当前真实实现没有这么激进。

当前现实：

discovery 会话结束后的主沉淀重点，是 user_personas、 user_persona_observations、 conversation_summaries、 向量库。

profiles 不是这条链路里每次都自动全量回写的主落点。

当前 persona-memory-sync 对 profile 的自动同步，只有在这些条件同时满足时才会发生：

  • apply_scope = persona_and_profile
  • sync_profile = true
  • source_type 是 profile_form 或 explicit_confirmation

就算走了 profile 同步，当前默认也是 public_only 模式， 重点是写公开安全字段，不是把所有内部画像原样倒回 profile。

11. profiles 当前主要会被写哪些公开字段

字段 作用
public_display_name 公开展示名，不直接暴露原始姓名
public_education 经过掩码或安全渲染后的学历信息
public_job 经过安全处理后的职业文案
public_personality 可公开展示的人格描述
public_values 可公开展示的价值观描述
public_notes 可公开展示的补充说明
例子：为什么内部负面标签不能直接公开

如果内部 matcher 里有“绿茶”“冷暴力风险”这种标签，不能直接给前台展示。

当前系统会更倾向于转译成更克制的公开文案，比如：

  • “关系边界需要进一步确认”
  • “沟通方式建议重点确认”

三、用一句用户输入，完整跑一遍

完整示例

用户在发现页说：

“我想先看无锡或者苏州的，最好本科以上，不接受异地。 我自己比较慢热，也不喜欢暧昧拉扯，希望对方情绪稳定、愿意沟通。”

实时搜索阶段，会发生什么

  • agent 先判断：这句话已经足够触发一次搜索了
  • 提炼出即时 criteria，比如城市、学历、异地接受度
  • 和当前 session 的 `working_criteria` 合并
  • 读取用户自己的 self_profile
  • partner_search 开始筛候选人、做互相匹配、排序、补 trust / personality 上下文
  • 页面展示一批推荐卡片

但这时还不会发生什么

  • 不会立刻把这段话正式写进长期 `user_personas`
  • 不会立刻把这段话同步写到 `profiles` 主画像
  • 不会立刻写向量库

等会话结束后，后台会怎么沉淀

  • 重新从数据库读取这段 session 的用户原话
  • LLM 提炼结构化摘要
  • 可量化部分可能拆成： target_cities、 target_education_min、 target_accept_long_distance
  • 这些会写进 persona / observation
  • 不可量化部分可能拆成： personality_traits、 partner_relationship_pacing、 partner_personality_preference
  • 这些会写进 conversation_summaries
  • 再根据 summary 生成 embedding 写进 Milvus

四、最容易踩坑的认知误区

误区 1

“发现页边聊边搜，所以也一定边聊边写 persona。”

错。当前实时 persona 写入是禁用的。

误区 2

“所有用户偏好都应该写进 user_personas。”

错。很多主观偏好更适合进 summary + 向量。

误区 3

“summary 就是聊天原句。”

错。summary 是 LLM 提炼后、再经过质检和合并的文本。

误区 4

“profiles 是所有沉淀信息的最终总表。”

错。当前更像公开安全投影层 + 搜索底座，不是所有沉淀的真源。

五、最后用一句最通俗的话总结

发现页实时阶段： 像红娘一边和你聊天，一边拿你刚说的要求先去筛人。

会话结束后的沉淀阶段： 像红娘晚上复盘笔记，把“能变成明确条件的”记进画像， 把“很重要但更像感觉和偏好的”记成摘要，再做成向量，方便以后更懂你。

文档基于当前仓库代码真实实现整理，重点反映“现在系统实际怎么跑”，不是理想设计稿。
