# 主动通知、代为开口、系统撮合的外部系统设计与分阶段路线图

## 1. 这份文档的定位

这份文档不是 `partner-search` skill 本身的设计文档。

它描述的是：

- 如果未来产品要做主动提醒
- 或者做代为开口
- 或者做系统撮合

应该在 `partner-search` 外面另外做一层系统。

一句话说清楚：

- `partner-search` 只负责 `画像 / 条件 -> 候选结果`
- 主动提醒、代问、撮合都属于外部产品系统

## 2. 先把边界写死

### 2.1 `partner-search` 负责什么

`partner-search` 只负责：

- 理解用户画像和搜索条件
- 读取资料库
- 计算候选匹配结果
- 返回排序后的候选人
- 解释为什么匹配、哪里有风险、哪些信息缺失

### 2.2 `partner-search` 不负责什么

下面这些能力都不应该直接耦合进 skill：

- 持续留意
- 定时重跑搜索
- 推荐历史
- 跳过 / 收藏 / 已联系状态
- 主动通知
- 站内消息
- 微信 / 短信 / 电话触达
- 代为开口
- 自动撮合
- 工作流编排
- 队列、任务调度、cron

### 2.3 正确的依赖方向

正确关系应该是：

```text
外部产品系统
    |
    +--> 保存用户状态
    +--> 保存搜索订阅
    +--> 保存推荐历史
    +--> 决定何时提醒
    +--> 决定是否代问
    |
    v
partner-search
    |
    v
候选结果
```

也就是：

- 外部系统调用 `partner-search`
- `partner-search` 不反过来知道外部系统的通知、撮合、状态机细节

## 3. 为什么一定要解耦

如果把主动提醒、代问、自动撮合都耦合进 `partner-search`，会出现 4 个问题：

- skill 从“匹配器”膨胀成“产品后端”
- 文档和代码的职责边界会越来越乱
- 每次改推荐逻辑都容易误伤通知和撮合流程
- 后续就很难复用 `partner-search` 做单次查询、人工筛人、批量实验

更合理的做法是：

- `partner-search` 只做纯匹配
- 外部系统把匹配结果用在不同场景里

## 4. 如果以后要做“持续留意”，应该怎么接

### 4.1 外部系统自己存订阅

外部系统可以自己维护：

- 谁开启了“继续帮我留意”
- 她最后一次明确搜索条件是什么
- 她是不是还在找对象
- 她愿意被怎样提醒

这些都不是 `partner-search` 的状态。

### 4.2 外部系统定时调用 `partner-search`

外部系统自己做：

1. 读取某个用户保存好的搜索条件
2. 调用 `partner-search`
3. 取回候选结果
4. 和历史推荐做比较
5. 判断有没有值得提醒的新结果

也就是说：

- “持续留意”本质上是外部系统反复调用一次“单次搜索”
- 不是让 `partner-search` 自己长出订阅、提醒、消息中心

### 4.3 外部系统自己判断要不要提醒

比如这些规则应该由外部系统处理：

- 这个候选以前推过没有
- 这个用户今天已经提醒过几次
- `skip` 后要不要冷却 30 天
- 现在是不是静默时段
- 应该发站内还是站外

这些都不属于 skill 内部逻辑。

### 4.4 查询结果为空时，怎么接“要不要我继续帮你留意”

这是一个很典型、也很适合放在外层系统里的动作。

正确做法不是：

- 把这句追问写进 `partner-search`

正确做法是：

1. 先正常调用一次 `partner-search`
2. 外层系统读取结构化结果
3. 如果 `has_match == false` 且 `result_count == 0`
4. 外层系统再问用户一句：
   - `是否需要如果有合适的我主动通知你？`
5. 如果用户同意
6. 外层系统把这次搜索请求保存成一条订阅
7. 后续由外层系统定时重跑同样的搜索
8. 发现新的高分结果后，再决定是否提醒用户

这里要强调：

- 这句追问属于“产品交互”
- 保存订阅属于“产品状态”
- 后续重跑属于“产品工作流”

它们都不属于 `partner-search` 的匹配职责。

### 4.5 同意之后，外层系统到底要保存什么

外层系统保存的不是“这次空结果本身”，而是“以后继续帮你找的委托”。

至少应该保存：

- `requester_id`
- `source`
- `criteria`
- `self_profile` 或 `self_id`
- `table_name`
- `photos_table_name`
- `limit`
- 订阅标题
- 刷新频率
- 每日提醒上限
- 静默时段
- `skip` 冷却期

这样下次重跑时，外层系统才能尽量复现这次搜索，而不是重新猜用户条件。

### 4.6 推荐的外层接口形态

推荐把这部分实现成 `partner-search` 外面的一个很薄的封装层，例如：

- `run_search_session(...)`
  - 负责调一次 `partner-search`
  - 返回正常搜索结果
  - 如果结果为空，同时返回：
    - `needs_opt_in_prompt = true`
    - `opt_in_prompt = "是否需要如果有合适的我主动通知你？"`
- `handle_opt_in_decision(...)`
  - 负责接收用户是否同意
  - 同意后创建 saved-search subscription
  - 不同意则什么都不创建

这样做的好处是：

- `partner-search` 完全不改产品职责
- agent / API / 业务服务都可以复用同一套外层封装
- 后续提醒、冷却、去重、消息投递都还能继续留在外层系统

## 5. 如果以后要做“代为开口”，应该怎么接

外部系统可以这样做：

1. 用户先通过 `partner-search` 看到候选结果
2. 用户在产品层点“替我去问”
3. 产品层创建自己的 `match_case`
4. 产品层用脱敏方式去联系对方

这里 `partner-search` 仍然只负责最前面的：

- 给出候选结果
- 给出匹配解释

它不负责：

- 建案件
- 发消息
- 跟进回复
- 推进状态

## 6. 如果以后要做“自动撮合”，应该怎么接

这也是外部系统能力。

外部系统可以自己做：

- 为用户维护是否同意自动撮合
- 定时调用 `partner-search`
- 选出高分候选
- 决定是否触发后续流程

但 `partner-search` 自己不应该包含：

- 自动触发逻辑
- 自动通知逻辑
- 自动推进逻辑

## 7. 对 `partner-search` 最合理的实现要求

既然这个 skill 只做纯匹配，那么最合理的要求是：

### 7.1 输入清晰

输入就是：

- 用户画像
- 结构化筛选条件
- 文本偏好
- 是否需要双向偏好判断

### 7.2 输出清晰

输出就是：

- 候选人列表
- 排序分数
- 匹配理由
- 风险点
- 信息缺失
- 需要确认的问题

### 7.3 不保存产品状态

skill 本身不应该负责存：

- 推荐订阅
- 推荐历史
- 用户操作状态
- 通知结果
- 撮合进度

### 7.4 可以被外部重复调用

最好的形态是：

- 人工一次性调用它，可以返回候选结果
- 外部系统批量调用它，也可以返回候选结果

它是一个稳定的“匹配能力”，不是一个长流程工作流。

## 8. 外部系统和 skill 的推荐接口关系

以后如果真要接产品层，推荐按下面的思路理解：

### 8.1 skill 层接口

skill 层只回答一个问题：

- “按这份画像和条件，现在库里有哪些合适的人？”

### 8.2 产品层接口

产品层再回答这些问题：

- “要不要持续帮你留意？”
- “要不要提醒你？”
- “这次要不要给你发消息？”
- “你点了跳过后多久别再推？”
- “要不要替你去问对方？”

不要把这两层混在一起。

## 9. 一个最简单的例子

假设用户说：

- 帮我找无锡、28 到 33 岁、不抽烟、认真恋爱的人

`partner-search` 负责的是：

- 跑一次搜索
- 返回前 10 个候选
- 解释为什么这 10 个排在前面

如果未来产品还想做：

- 过两天再帮她找一次
- 如果出现新的高分人选就提醒她

那正确做法是：

- 外部系统记住她的搜索条件
- 外部系统再调用一次 `partner-search`
- 外部系统自己比较新旧结果
- 外部系统自己决定要不要提醒

而不是让 `partner-search` 自己负责“记住她、盯着她、通知她”。

## 10. 一句话总结

`partner-search` 的职责应该被严格固定为：

“根据用户画像和条件，从资料库中返回匹配对象，并解释匹配原因。”

而主动提醒、代为开口、系统撮合，应该永远被视为：

“调用 `partner-search` 的外部产品系统能力，而不是 skill 本身。”

## 11. 分阶段路线图总览

整个路线图建议拆成 5 个阶段：

- Phase 1: 把 `partner-search` 做成稳定的纯匹配引擎
- Phase 2: 把 `partner-search` 做成更易复用、更好测试的匹配能力
- Phase 3: 在 skill 外面做“持续留意 / 新候选提醒”
- Phase 4: 在 skill 外面做“代为开口”
- Phase 5: 在 skill 外面做“自动撮合”

其中：

- Phase 1 和 Phase 2 属于 `partner-search` 本身
- Phase 3 到 Phase 5 属于外部产品系统

## 12. Phase 1: 纯匹配引擎定型

### 12.1 目标

把 `partner-search` 定型成一个清晰、稳定、可解释的纯匹配能力。

### 12.2 这一阶段必须完成的任务

- 明确输入边界
  - 固定哪些字段属于用户画像
  - 固定哪些字段属于搜索条件
  - 固定哪些字段是可选项，例如 `self-*`、`must-have`、`prefer`
- 明确输出边界
  - 固定返回的候选字段
  - 固定 `score / fit_score / confidence_score / risk_score`
  - 固定 `matched_on / reciprocal_on / missing_fields / self_profile_gaps / risk_flags / follow_up_questions`
- 固定 skill 职责
  - 文档明确只做 `画像 / 条件 -> 候选结果`
  - 不把提醒、代问、撮合状态耦合进来
- 保持 CLI 可用
  - `scripts/search_candidates.py` 仍然可以直接跑
  - 现有使用方式不被破坏
- 补齐核心测试
  - 基础结构化筛选测试
  - 双向偏好判断测试
  - 风险与缺失字段测试
  - no-match 场景测试
  - 敏感信息摘要测试
- 更新文档和示例
  - 让别人看到文档就知道 skill 的输入输出契约

### 12.3 这一阶段建议交付物

- 一个稳定的 `search_candidates.py`
- 一套可对外说明的输入字段定义
- 一套可对外说明的输出字段定义
- 与之对应的测试用例

### 12.4 这一阶段不做什么

- 不做数据库新表
- 不做推荐订阅
- 不做推荐历史
- 不做消息提醒
- 不做代问
- 不做自动撮合

### 12.5 验收标准

- 同一份输入在同一份数据快照下，结果结构稳定
- 结果里能清楚解释“为什么匹配”
- 没有把产品工作流状态耦合进 skill

### 12.6 Phase 1 开发清单（按文件）

这一阶段建议只动下面这些文件。

#### 文件 1：`scripts/search_candidates.py`

目标：

- 不改变 skill 的产品边界
- 稳定输入和输出契约
- 保持 CLI 继续可用

具体任务：

- 明确模块职责注释
  - 在文件头部或关键函数附近补简短说明
  - 明确这是“单次匹配脚本”，不是通知或撮合工作流
- 稳定输入处理
  - 检查 `build_criteria_from_args(...)` 的输出字段是否一致
  - 检查 `build_self_profile_from_args(...)` 对 `self-id` / `self-*` 的行为是否一致
  - 明确哪些字段缺省时会被省略，哪些会给默认值
- 稳定候选结果结构
  - 检查 `evaluate_candidate(...)` 的返回字段是否固定
  - 保证命中候选时始终返回统一字段集
  - 保证 `matched_on / reciprocal_on / missing_fields / risk_flags / follow_up_questions` 这些字段格式稳定
- 稳定 no-match 结果
  - 检查 `build_no_match_diagnostics(...)` 和 `format_no_match_text(...)`
  - 明确无结果时最少会返回哪些诊断信息
- 保持 CLI 行为不破坏
  - `main()` 的现有调用方式继续可用
  - `--help`、`--self-id`、`--source`、`--show-source` 等现有行为不回退

这一阶段不要做：

- 不抽大规模新模块
- 不新建推荐/通知表
- 不加入订阅或工作流状态
- 不把脚本改成服务端程序

#### 文件 2：`tests/test_search_candidates.py`

目标：

- 把 Phase 1 的输入输出契约变成测试

具体任务：

- 补输入契约测试
  - `build_criteria_from_args(...)` 的关键字段映射
  - `build_self_profile_from_args(...)` 的成功和报错路径
- 补结果结构测试
  - `evaluate_candidate(...)` 命中时必须包含哪些字段
  - `evaluate_candidate(...)` 失败时的行为是否稳定
- 补 no-match 测试
  - 空结果时的诊断结构
  - fallback 候选的文本输出
- 补输出安全测试
  - 敏感字段脱敏
  - source 显示时密码脱敏
- 补 CLI 回归测试
  - `main()` 正常输出
  - `main()` 无结果输出
  - `main()` 报错退出

这一阶段不要做：

- 不为了测试去引入外部通知状态
- 不为了未来 Phase 3/4/5 提前加测试夹具

#### 文件 3：`SKILL.md`

目标：

- 让 skill 使用者一眼看懂边界和调用方式

具体任务：

- 保持 `Scope` 和 `Non-Goals` 清晰
- 确保 Quick Start 仍然围绕“单次匹配”
- 如果 Phase 1 调整了输入或输出描述，同步更新示例

#### 文件 4：`references/profile-schema.md`

目标：

- 保证 schema 文档继续支撑“纯匹配”场景

具体任务：

- 检查字段说明是否足够支撑当前筛选和 reciprocal 判断
- 如果 Phase 1 发现某些字段名解释不清，在这里补清楚
- 不在这里加入推荐订阅、通知、撮合状态字段

### 12.7 Phase 1 建议执行顺序

建议按下面顺序做：

1. 先读 `tests/test_search_candidates.py`
   - 先知道当前已经承诺了哪些行为
2. 再整理 `scripts/search_candidates.py` 的输入输出边界
   - 不急着大改结构
   - 先稳住契约
3. 先补测试，再改逻辑
   - 特别是结果结构和 no-match 结构测试
4. 再做最小必要代码调整
   - 只修契约不清、字段不稳、输出不一致的问题
5. 最后同步 `SKILL.md` 和 `references/profile-schema.md`
   - 保证文档和代码一致
6. 跑 `bash scripts/run_tests.sh`
   - 用现有测试套件做最后回归

### 12.8 Phase 1 完成后应该达到的状态

Phase 1 完成后，`partner-search` 应该处于下面这个状态：

- 文档已经明确写死：它只做匹配
- CLI 继续可用
- 输入字段定义清楚
- 输出字段定义清楚
- 命中和 no-match 两种结果都稳定
- 测试能覆盖核心契约
- 还没有任何提醒、订阅、代问、撮合状态被耦合进来

## 13. Phase 2: 可复用接口、质量和可维护性

### 13.1 目标

让 `partner-search` 不只是“一个能跑的 CLI”，而是“一个可被其他系统稳定调用的匹配能力”。

### 13.2 这一阶段必须完成的任务

- 抽函数层
  - 从 `search_candidates.py` 中抽出核心匹配入口
  - 保持 CLI 只是外层包装
  - 避免外部系统只能 shell 跑脚本再解析文本
- 固定可调用接口
  - 例如定义一个明确的 Python 调用入口
  - 输入参数包括 `source / criteria / self_profile / limit`
  - 输出直接返回结构化结果，而不是只返回文本
- 拆清内部层次
  - 读取 source 的逻辑
  - criteria 组装逻辑
  - scorer 逻辑
  - formatter 逻辑
  - diagnostics 逻辑
- 增加结构化输出能力
  - 文本输出继续保留给人工阅读
  - 结构化输出保留给系统调用
- 完善测试层级
  - CLI 测试
  - 函数级测试
  - 回归测试
  - 典型画像样本测试
- 完善性能与稳定性文档
  - 哪些筛选可以走 MySQL 预过滤
  - 哪些字段依赖 Python 侧评分
  - 哪些索引是推荐配置

### 13.3 这一阶段建议交付物

- 一个可 import 的匹配入口
- 更清楚的内部模块边界
- 更稳定的结构化结果格式
- 更完整的回归测试

### 13.4 这一阶段不做什么

- 不做推荐订阅服务
- 不做推荐派发
- 不做用户动作持久化
- 不做代问工作流

### 13.5 验收标准

- 外部系统不需要解析文本，也能稳定调用匹配能力
- 改动 scorer 或 formatter 时，测试能及时发现回归
- `partner-search` 依然保持纯匹配边界

### 13.6 Phase 2 落地到当前代码

这一阶段在当前 skill 里，应该具体落成下面这些东西：

- `scripts/search_candidates.py`
  - 保留 CLI
  - 但把真正的执行入口固定成 request 驱动
  - 例如 `build_search_request(...)`、`execute_search_request(...)`
  - CLI 只是把命令行参数转成 request，再调用同一条执行链路
- `partner_search/api.py`
  - 提供正式的 Python 调用入口
  - 例如 `search_profiles(...)`、`search(...)`
  - 让外部系统直接拿结构化结果，不再需要 shell 跑脚本后解析文本
- `partner_search/__init__.py`
  - 暴露稳定的公共导入面
  - 让调用方直接 `from partner_search import search_profiles`
- `scripts/search_candidates.py` 继续保留文本输出
  - 但同时支持结构化 JSON 输出
  - 例如 `--output-format json`
- `tests/test_partner_search_api.py`
  - 覆盖 importable API
  - 覆盖结构化 JSON 输出
  - 覆盖 persona 风格样本请求
- `tests/test_search_candidates.py`
  - 继续锁住 scorer、formatter、diagnostics、CLI 回归

这样做完以后，Phase 2 的状态应该是：

- 人可以继续用 CLI 看文本结果
- 系统可以直接 import 调用
- 文本和结构化输出共用同一套搜索执行链路
- 结果 schema 更稳定
- 测试能同时盯住 CLI 和 API 两层

## 14. Phase 3: 外部系统做“持续留意 / 新候选提醒”

### 14.1 目标

在 `partner-search` 外部做一层最小推荐系统，让产品可以重复调用 skill 并对新结果做提醒。

### 14.2 这一阶段必须完成的任务

- 设计搜索订阅存储
  - 保存谁开启了“继续帮我留意”
  - 保存她最后一次明确的搜索条件
  - 保存她是否仍在找对象
- 设计推荐历史存储
  - 保存以前推过谁
  - 保存分数快照
  - 保存是否已提醒
  - 保存冷却状态
- 设计用户动作存储
  - `skip`
  - `save`
  - `direct_greet`
- 做定时刷新任务
  - 读取订阅
  - 调用 `partner-search`
  - 取 top-K 候选
  - 和历史结果比对
  - 判断什么算“新推荐”
- 做推荐派发规则
  - 每天最多提醒几次
  - `skip` 后冷却多久
  - 当前是否在静默时段
  - 先只做站内提醒
- 做最小推荐卡片
  - 展示候选摘要
  - 展示匹配理由
  - 给出基础动作按钮

### 14.3 这一阶段建议交付物

- `saved_search_subscriptions` 一类的订阅表
- `profile_recommendations` 一类的推荐历史表
- `recommendation_actions` 一类的动作表
- 定时刷新脚本
- 推荐派发脚本
- 站内推荐卡片

### 14.4 这一阶段不做什么

- 不做代问
- 不做自动撮合
- 不默认做站外触达

### 14.5 验收标准

- 外部系统能重复调用 `partner-search`
- 用户只会看到真正新的、值得提醒的候选
- 推荐频控和冷却生效
- `partner-search` 本身没有被状态逻辑污染

### 14.6 Phase 3 落地到当前代码

这一阶段现在已经在 repo 里作为独立外部系统落地，路径是：

- `external-systems/partner-recommendation-system/`

具体对应关系如下：

- `recommendation_system/storage.py`
  - 建 `saved_search_subscriptions`
  - 建 `profile_recommendations`
  - 建 `recommendation_actions`
  - 建 `in_app_recommendation_cards`
- `recommendation_system/service.py`
  - 刷新订阅
  - 调 `partner-search`
  - 做历史去重
  - 做 `skip` 冷却
  - 做每日提醒频控
  - 做静默时段控制
  - 生成站内推荐卡片
- `recommendation_system/search_client.py`
  - 通过 Phase 2 Python API 调 `partner-search`
- `scripts/create_saved_search_subscription.py`
  - 创建保存搜索订阅
- `scripts/refresh_saved_searches.py`
  - 跑“持续留意”刷新任务
- `scripts/deliver_in_app_recommendations.py`
  - 跑站内推荐派发任务
- `scripts/record_recommendation_action.py`
  - 记录 `skip / save / direct_greet`
- `tests/test_recommendation_system.py`
  - 锁住去重、冷却、频控、站内卡片等回归

这样以后如果产品层要做真正的“继续帮我留意”，应该直接扩这个外部系统，而不是把状态逻辑塞回 `partner-search`。

## 15. Phase 4: 外部系统做“代为开口”

### 15.1 目标

让用户在看到候选后，可以通过产品层触发“替我去问”。

### 15.2 这一阶段必须完成的任务

- 设计 `match_case` 一类的案件表
  - 谁发起
  - 问的是谁
  - 当前状态是什么
- 设计脱敏摘要
  - 在对方未同意前，只发安全摘要
- 设计状态流转
  - `pending_outreach`
  - `awaiting_reply`
  - `accepted`
  - `declined`
  - `timed_out`
  - `closed`
- 设计发送与回复处理
  - 给对方发起问询
  - 记录回复
  - 处理超时
- 设计和推荐历史的关系
  - 已进入代问流程的候选，推荐状态如何变化
  - 已拒绝后的冷却如何处理

### 15.3 这一阶段建议交付物

- `match_cases` 一类的案件表
- 代问触发按钮
- 脱敏问询模板
- 回复处理逻辑
- 超时关闭逻辑

### 15.4 这一阶段不做什么

- 不做自动撮合
- 不把 `match_case` 状态塞进 `partner-search`

### 15.5 验收标准

- 用户可以从推荐结果平滑进入代问流程
- 对方未同意前不会泄露敏感信息
- 案件状态流转清楚且可审计

## 16. Phase 5: 外部系统做“自动撮合”

### 16.1 目标

只在用户明确授权的前提下，让系统自动推进少量高分候选。

### 16.2 这一阶段必须完成的任务

- 设计自动撮合授权开关
  - 用户是否同意
  - 用户接受什么触达方式
- 设计高阈值规则
  - 什么分数才有资格自动推进
  - 什么风险条件会阻止自动推进
- 设计触发策略
  - 是每天扫描还是事件触发
  - 是否只推进最新高分候选
- 设计顺序和保护规则
  - 不同时惊动两边
  - 对拒绝和超时做更长冷却
  - 限制每日自动推进数量
- 设计审计和实验
  - 记录为什么触发
  - 记录触达结果
  - 小流量灰度验证

### 16.3 这一阶段建议交付物

- 自动撮合授权配置
- 高阈值规则
- 自动推进任务
- 审计日志和实验报表

### 16.4 这一阶段不做什么

- 不把自动决策逻辑放回 `partner-search`
- 不在没有明确授权的前提下自动推进

### 16.5 验收标准

- 只有明确授权用户会进入自动撮合
- 自动推进数量和风险都可控
- 出现问题时能回溯是哪个规则触发的

## 17. 推荐实施顺序

最推荐的落地顺序是：

1. 先完成 Phase 1
2. 再完成 Phase 2
3. 然后如果产品真的需要“持续留意”，再做 Phase 3
4. Phase 3 跑稳后，再做 Phase 4
5. 最后才考虑 Phase 5

不要跳步。

特别是：

- 没有完成 Phase 1 和 Phase 2，不要急着做提醒系统
- 没有跑稳 Phase 3，不要急着做代问
- 没有验证好 Phase 4，不要急着做自动撮合

## 18. 一句话版路线图

完整路线图可以压缩成一句话：

“先把 `partner-search` 做成稳定的纯匹配引擎，再把它作为底层能力被外部系统重复调用，之后才逐步在外层增加持续留意、代为开口和自动撮合。”
