# 主动通知、代为开口、系统撮合的外部系统设计与分阶段路线图

## 1. 这份文档的定位

这份文档不是 `partner-search` skill 本身的设计文档。

它描述的是：

- 如果未来产品要做主动提醒
- 或者做代为开口
- 或者做系统撮合

应该在 `partner-search` 外面另外做一层系统。

一句话说清楚：

- `partner-search` 只负责 `画像 / 条件 -> 候选结果`
- 主动提醒、代问、撮合都属于外部产品系统

## 2. 先把边界写死

### 2.1 `partner-search` 负责什么

`partner-search` 只负责：

- 理解用户画像和搜索条件
- 读取资料库
- 计算候选匹配结果
- 返回排序后的候选人
- 解释为什么匹配、哪里有风险、哪些信息缺失

### 2.2 `partner-search` 不负责什么

下面这些能力都不应该直接耦合进 skill：

- 持续留意
- 定时重跑搜索
- 推荐历史
- 跳过 / 收藏 / 已联系状态
- 主动通知
- 站内消息
- 微信 / 短信 / 电话触达
- 代为开口
- 自动撮合
- 工作流编排
- 队列、任务调度、cron

### 2.3 正确的依赖方向

正确关系应该是：

```text
外部产品系统
    |
    +--> 保存用户状态
    +--> 保存搜索订阅
    +--> 保存推荐历史
    +--> 决定何时提醒
    +--> 决定是否代问
    |
    v
partner-search
    |
    v
候选结果
```

也就是：

- 外部系统调用 `partner-search`
- `partner-search` 不反过来知道外部系统的通知、撮合、状态机细节

## 3. 为什么一定要解耦

如果把主动提醒、代问、自动撮合都耦合进 `partner-search`，会出现 4 个问题：

- skill 从“匹配器”膨胀成“产品后端”
- 文档和代码的职责边界会越来越乱
- 每次改推荐逻辑都容易误伤通知和撮合流程
- 后续就很难复用 `partner-search` 做单次查询、人工筛人、批量实验

更合理的做法是：

- `partner-search` 只做纯匹配
- 外部系统把匹配结果用在不同场景里

## 4. 如果以后要做“持续留意”，应该怎么接

### 4.1 外部系统自己存订阅

外部系统可以自己维护：

- 谁开启了“继续帮我留意”
- 她最后一次明确搜索条件是什么
- 她是不是还在找对象
- 她愿意被怎样提醒

这些都不是 `partner-search` 的状态。

### 4.2 外部系统定时调用 `partner-search`

外部系统自己做：

1. 读取某个用户保存好的搜索条件
2. 调用 `partner-search`
3. 取回候选结果
4. 和历史推荐做比较
5. 判断有没有值得提醒的新结果

也就是说：

- “持续留意”本质上是外部系统反复调用一次“单次搜索”
- 不是让 `partner-search` 自己长出订阅、提醒、消息中心

### 4.3 外部系统自己判断要不要提醒

比如这些规则应该由外部系统处理：

- 这个候选以前推过没有
- 这个用户今天已经提醒过几次
- `skip` 后要不要冷却 30 天
- 现在是不是静默时段
- 应该发站内还是站外

这些都不属于 skill 内部逻辑。

## 5. 如果以后要做“代为开口”，应该怎么接

外部系统可以这样做：

1. 用户先通过 `partner-search` 看到候选结果
2. 用户在产品层点“替我去问”
3. 产品层创建自己的 `match_case`
4. 产品层用脱敏方式去联系对方

这里 `partner-search` 仍然只负责最前面的：

- 给出候选结果
- 给出匹配解释

它不负责：

- 建案件
- 发消息
- 跟进回复
- 推进状态

## 6. 如果以后要做“自动撮合”，应该怎么接

这也是外部系统能力。

外部系统可以自己做：

- 为用户维护是否同意自动撮合
- 定时调用 `partner-search`
- 选出高分候选
- 决定是否触发后续流程

但 `partner-search` 自己不应该包含：

- 自动触发逻辑
- 自动通知逻辑
- 自动推进逻辑

## 7. 对 `partner-search` 最合理的实现要求

既然这个 skill 只做纯匹配，那么最合理的要求是：

### 7.1 输入清晰

输入就是：

- 用户画像
- 结构化筛选条件
- 文本偏好
- 是否需要双向偏好判断

### 7.2 输出清晰

输出就是：

- 候选人列表
- 排序分数
- 匹配理由
- 风险点
- 信息缺失
- 需要确认的问题

### 7.3 不保存产品状态

skill 本身不应该负责存：

- 推荐订阅
- 推荐历史
- 用户操作状态
- 通知结果
- 撮合进度

### 7.4 可以被外部重复调用

最好的形态是：

- 人工一次性调用它，可以返回候选结果
- 外部系统批量调用它，也可以返回候选结果

它是一个稳定的“匹配能力”，不是一个长流程工作流。

## 8. 外部系统和 skill 的推荐接口关系

以后如果真要接产品层，推荐按下面的思路理解：

### 8.1 skill 层接口

skill 层只回答一个问题：

- “按这份画像和条件，现在库里有哪些合适的人？”

### 8.2 产品层接口

产品层再回答这些问题：

- “要不要持续帮你留意？”
- “要不要提醒你？”
- “这次要不要给你发消息？”
- “你点了跳过后多久别再推？”
- “要不要替你去问对方？”

不要把这两层混在一起。

## 9. 一个最简单的例子

假设用户说：

- 帮我找无锡、28 到 33 岁、不抽烟、认真恋爱的人

`partner-search` 负责的是：

- 跑一次搜索
- 返回前 10 个候选
- 解释为什么这 10 个排在前面

如果未来产品还想做：

- 过两天再帮她找一次
- 如果出现新的高分人选就提醒她

那正确做法是：

- 外部系统记住她的搜索条件
- 外部系统再调用一次 `partner-search`
- 外部系统自己比较新旧结果
- 外部系统自己决定要不要提醒

而不是让 `partner-search` 自己负责“记住她、盯着她、通知她”。

## 10. 一句话总结

`partner-search` 的职责应该被严格固定为：

“根据用户画像和条件，从资料库中返回匹配对象，并解释匹配原因。”

而主动提醒、代为开口、系统撮合，应该永远被视为：

“调用 `partner-search` 的外部产品系统能力，而不是 skill 本身。”

## 11. 分阶段路线图总览

整个路线图建议拆成 5 个阶段：

- Phase 1: 把 `partner-search` 做成稳定的纯匹配引擎
- Phase 2: 把 `partner-search` 做成更易复用、更好测试的匹配能力
- Phase 3: 在 skill 外面做“持续留意 / 新候选提醒”
- Phase 4: 在 skill 外面做“代为开口”
- Phase 5: 在 skill 外面做“自动撮合”

其中：

- Phase 1 和 Phase 2 属于 `partner-search` 本身
- Phase 3 到 Phase 5 属于外部产品系统

## 12. Phase 1: 纯匹配引擎定型

### 12.1 目标

把 `partner-search` 定型成一个清晰、稳定、可解释的纯匹配能力。

### 12.2 这一阶段必须完成的任务

- 明确输入边界
  - 固定哪些字段属于用户画像
  - 固定哪些字段属于搜索条件
  - 固定哪些字段是可选项，例如 `self-*`、`must-have`、`prefer`
- 明确输出边界
  - 固定返回的候选字段
  - 固定 `score / fit_score / confidence_score / risk_score`
  - 固定 `matched_on / risk_flags / missing_fields / follow_up_questions`
- 固定 skill 职责
  - 文档明确只做 `画像 / 条件 -> 候选结果`
  - 不把提醒、代问、撮合状态耦合进来
- 保持 CLI 可用
  - `scripts/search_candidates.py` 仍然可以直接跑
  - 现有使用方式不被破坏
- 补齐核心测试
  - 基础结构化筛选测试
  - 双向偏好判断测试
  - 风险与缺失字段测试
  - no-match 场景测试
  - 敏感信息摘要测试
- 更新文档和示例
  - 让别人看到文档就知道 skill 的输入输出契约

### 12.3 这一阶段建议交付物

- 一个稳定的 `search_candidates.py`
- 一套可对外说明的输入字段定义
- 一套可对外说明的输出字段定义
- 与之对应的测试用例

### 12.4 这一阶段不做什么

- 不做数据库新表
- 不做推荐订阅
- 不做推荐历史
- 不做消息提醒
- 不做代问
- 不做自动撮合

### 12.5 验收标准

- 同一份输入在同一份数据快照下，结果结构稳定
- 结果里能清楚解释“为什么匹配”
- 没有把产品工作流状态耦合进 skill

## 13. Phase 2: 可复用接口、质量和可维护性

### 13.1 目标

让 `partner-search` 不只是“一个能跑的 CLI”，而是“一个可被其他系统稳定调用的匹配能力”。

### 13.2 这一阶段必须完成的任务

- 抽函数层
  - 从 `search_candidates.py` 中抽出核心匹配入口
  - 保持 CLI 只是外层包装
  - 避免外部系统只能 shell 跑脚本再解析文本
- 固定可调用接口
  - 例如定义一个明确的 Python 调用入口
  - 输入参数包括 `source / criteria / self_profile / limit`
  - 输出直接返回结构化结果，而不是只返回文本
- 拆清内部层次
  - 读取 source 的逻辑
  - criteria 组装逻辑
  - scorer 逻辑
  - formatter 逻辑
  - diagnostics 逻辑
- 增加结构化输出能力
  - 文本输出继续保留给人工阅读
  - 结构化输出保留给系统调用
- 完善测试层级
  - CLI 测试
  - 函数级测试
  - 回归测试
  - 典型画像样本测试
- 完善性能与稳定性文档
  - 哪些筛选可以走 MySQL 预过滤
  - 哪些字段依赖 Python 侧评分
  - 哪些索引是推荐配置

### 13.3 这一阶段建议交付物

- 一个可 import 的匹配入口
- 更清楚的内部模块边界
- 更稳定的结构化结果格式
- 更完整的回归测试

### 13.4 这一阶段不做什么

- 不做推荐订阅服务
- 不做推荐派发
- 不做用户动作持久化
- 不做代问工作流

### 13.5 验收标准

- 外部系统不需要解析文本，也能稳定调用匹配能力
- 改动 scorer 或 formatter 时，测试能及时发现回归
- `partner-search` 依然保持纯匹配边界

## 14. Phase 3: 外部系统做“持续留意 / 新候选提醒”

### 14.1 目标

在 `partner-search` 外部做一层最小推荐系统，让产品可以重复调用 skill 并对新结果做提醒。

### 14.2 这一阶段必须完成的任务

- 设计搜索订阅存储
  - 保存谁开启了“继续帮我留意”
  - 保存她最后一次明确的搜索条件
  - 保存她是否仍在找对象
- 设计推荐历史存储
  - 保存以前推过谁
  - 保存分数快照
  - 保存是否已提醒
  - 保存冷却状态
- 设计用户动作存储
  - `skip`
  - `save`
  - `direct_greet`
- 做定时刷新任务
  - 读取订阅
  - 调用 `partner-search`
  - 取 top-K 候选
  - 和历史结果比对
  - 判断什么算“新推荐”
- 做推荐派发规则
  - 每天最多提醒几次
  - `skip` 后冷却多久
  - 当前是否在静默时段
  - 先只做站内提醒
- 做最小推荐卡片
  - 展示候选摘要
  - 展示匹配理由
  - 给出基础动作按钮

### 14.3 这一阶段建议交付物

- `saved_search_subscriptions` 一类的订阅表
- `profile_recommendations` 一类的推荐历史表
- `recommendation_actions` 一类的动作表
- 定时刷新脚本
- 推荐派发脚本
- 站内推荐卡片

### 14.4 这一阶段不做什么

- 不做代问
- 不做自动撮合
- 不默认做站外触达

### 14.5 验收标准

- 外部系统能重复调用 `partner-search`
- 用户只会看到真正新的、值得提醒的候选
- 推荐频控和冷却生效
- `partner-search` 本身没有被状态逻辑污染

## 15. Phase 4: 外部系统做“代为开口”

### 15.1 目标

让用户在看到候选后，可以通过产品层触发“替我去问”。

### 15.2 这一阶段必须完成的任务

- 设计 `match_case` 一类的案件表
  - 谁发起
  - 问的是谁
  - 当前状态是什么
- 设计脱敏摘要
  - 在对方未同意前，只发安全摘要
- 设计状态流转
  - `pending_outreach`
  - `awaiting_reply`
  - `accepted`
  - `declined`
  - `timed_out`
  - `closed`
- 设计发送与回复处理
  - 给对方发起问询
  - 记录回复
  - 处理超时
- 设计和推荐历史的关系
  - 已进入代问流程的候选，推荐状态如何变化
  - 已拒绝后的冷却如何处理

### 15.3 这一阶段建议交付物

- `match_cases` 一类的案件表
- 代问触发按钮
- 脱敏问询模板
- 回复处理逻辑
- 超时关闭逻辑

### 15.4 这一阶段不做什么

- 不做自动撮合
- 不把 `match_case` 状态塞进 `partner-search`

### 15.5 验收标准

- 用户可以从推荐结果平滑进入代问流程
- 对方未同意前不会泄露敏感信息
- 案件状态流转清楚且可审计

## 16. Phase 5: 外部系统做“自动撮合”

### 16.1 目标

只在用户明确授权的前提下，让系统自动推进少量高分候选。

### 16.2 这一阶段必须完成的任务

- 设计自动撮合授权开关
  - 用户是否同意
  - 用户接受什么触达方式
- 设计高阈值规则
  - 什么分数才有资格自动推进
  - 什么风险条件会阻止自动推进
- 设计触发策略
  - 是每天扫描还是事件触发
  - 是否只推进最新高分候选
- 设计顺序和保护规则
  - 不同时惊动两边
  - 对拒绝和超时做更长冷却
  - 限制每日自动推进数量
- 设计审计和实验
  - 记录为什么触发
  - 记录触达结果
  - 小流量灰度验证

### 16.3 这一阶段建议交付物

- 自动撮合授权配置
- 高阈值规则
- 自动推进任务
- 审计日志和实验报表

### 16.4 这一阶段不做什么

- 不把自动决策逻辑放回 `partner-search`
- 不在没有明确授权的前提下自动推进

### 16.5 验收标准

- 只有明确授权用户会进入自动撮合
- 自动推进数量和风险都可控
- 出现问题时能回溯是哪个规则触发的

## 17. 推荐实施顺序

最推荐的落地顺序是：

1. 先完成 Phase 1
2. 再完成 Phase 2
3. 然后如果产品真的需要“持续留意”，再做 Phase 3
4. Phase 3 跑稳后，再做 Phase 4
5. 最后才考虑 Phase 5

不要跳步。

特别是：

- 没有完成 Phase 1 和 Phase 2，不要急着做提醒系统
- 没有跑稳 Phase 3，不要急着做代问
- 没有验证好 Phase 4，不要急着做自动撮合

## 18. 一句话版路线图

完整路线图可以压缩成一句话：

“先把 `partner-search` 做成稳定的纯匹配引擎，再把它作为底层能力被外部系统重复调用，之后才逐步在外层增加持续留意、代为开口和自动撮合。”
