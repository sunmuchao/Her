# 主动通知、代为开口、系统撮合的外部系统设计

## 1. 这份文档的定位

这份文档不是 `partner-search` skill 本身的设计文档。

它描述的是：

- 如果未来产品要做主动提醒
- 或者做代为开口
- 或者做系统撮合

应该在 `partner-search` 外面另外做一层系统。

一句话说清楚：

- `partner-search` 只负责 `画像 / 条件 -> 候选结果`
- 主动提醒、代问、撮合都属于外部产品系统

## 2. 先把边界写死

### 2.1 `partner-search` 负责什么

`partner-search` 只负责：

- 理解用户画像和搜索条件
- 读取资料库
- 计算候选匹配结果
- 返回排序后的候选人
- 解释为什么匹配、哪里有风险、哪些信息缺失

### 2.2 `partner-search` 不负责什么

下面这些能力都不应该直接耦合进 skill：

- 持续留意
- 定时重跑搜索
- 推荐历史
- 跳过 / 收藏 / 已联系状态
- 主动通知
- 站内消息
- 微信 / 短信 / 电话触达
- 代为开口
- 自动撮合
- 工作流编排
- 队列、任务调度、cron

### 2.3 正确的依赖方向

正确关系应该是：

```text
外部产品系统
    |
    +--> 保存用户状态
    +--> 保存搜索订阅
    +--> 保存推荐历史
    +--> 决定何时提醒
    +--> 决定是否代问
    |
    v
partner-search
    |
    v
候选结果
```

也就是：

- 外部系统调用 `partner-search`
- `partner-search` 不反过来知道外部系统的通知、撮合、状态机细节

## 3. 为什么一定要解耦

如果把主动提醒、代问、自动撮合都耦合进 `partner-search`，会出现 4 个问题：

- skill 从“匹配器”膨胀成“产品后端”
- 文档和代码的职责边界会越来越乱
- 每次改推荐逻辑都容易误伤通知和撮合流程
- 后续就很难复用 `partner-search` 做单次查询、人工筛人、批量实验

更合理的做法是：

- `partner-search` 只做纯匹配
- 外部系统把匹配结果用在不同场景里

## 4. 如果以后要做“持续留意”，应该怎么接

### 4.1 外部系统自己存订阅

外部系统可以自己维护：

- 谁开启了“继续帮我留意”
- 她最后一次明确搜索条件是什么
- 她是不是还在找对象
- 她愿意被怎样提醒

这些都不是 `partner-search` 的状态。

### 4.2 外部系统定时调用 `partner-search`

外部系统自己做：

1. 读取某个用户保存好的搜索条件
2. 调用 `partner-search`
3. 取回候选结果
4. 和历史推荐做比较
5. 判断有没有值得提醒的新结果

也就是说：

- “持续留意”本质上是外部系统反复调用一次“单次搜索”
- 不是让 `partner-search` 自己长出订阅、提醒、消息中心

### 4.3 外部系统自己判断要不要提醒

比如这些规则应该由外部系统处理：

- 这个候选以前推过没有
- 这个用户今天已经提醒过几次
- `skip` 后要不要冷却 30 天
- 现在是不是静默时段
- 应该发站内还是站外

这些都不属于 skill 内部逻辑。

## 5. 如果以后要做“代为开口”，应该怎么接

外部系统可以这样做：

1. 用户先通过 `partner-search` 看到候选结果
2. 用户在产品层点“替我去问”
3. 产品层创建自己的 `match_case`
4. 产品层用脱敏方式去联系对方

这里 `partner-search` 仍然只负责最前面的：

- 给出候选结果
- 给出匹配解释

它不负责：

- 建案件
- 发消息
- 跟进回复
- 推进状态

## 6. 如果以后要做“自动撮合”，应该怎么接

这也是外部系统能力。

外部系统可以自己做：

- 为用户维护是否同意自动撮合
- 定时调用 `partner-search`
- 选出高分候选
- 决定是否触发后续流程

但 `partner-search` 自己不应该包含：

- 自动触发逻辑
- 自动通知逻辑
- 自动推进逻辑

## 7. 对 `partner-search` 最合理的实现要求

既然这个 skill 只做纯匹配，那么最合理的要求是：

### 7.1 输入清晰

输入就是：

- 用户画像
- 结构化筛选条件
- 文本偏好
- 是否需要双向偏好判断

### 7.2 输出清晰

输出就是：

- 候选人列表
- 排序分数
- 匹配理由
- 风险点
- 信息缺失
- 需要确认的问题

### 7.3 不保存产品状态

skill 本身不应该负责存：

- 推荐订阅
- 推荐历史
- 用户操作状态
- 通知结果
- 撮合进度

### 7.4 可以被外部重复调用

最好的形态是：

- 人工一次性调用它，可以返回候选结果
- 外部系统批量调用它，也可以返回候选结果

它是一个稳定的“匹配能力”，不是一个长流程工作流。

## 8. 外部系统和 skill 的推荐接口关系

以后如果真要接产品层，推荐按下面的思路理解：

### 8.1 skill 层接口

skill 层只回答一个问题：

- “按这份画像和条件，现在库里有哪些合适的人？”

### 8.2 产品层接口

产品层再回答这些问题：

- “要不要持续帮你留意？”
- “要不要提醒你？”
- “这次要不要给你发消息？”
- “你点了跳过后多久别再推？”
- “要不要替你去问对方？”

不要把这两层混在一起。

## 9. 一个最简单的例子

假设用户说：

- 帮我找无锡、28 到 33 岁、不抽烟、认真恋爱的人

`partner-search` 负责的是：

- 跑一次搜索
- 返回前 10 个候选
- 解释为什么这 10 个排在前面

如果未来产品还想做：

- 过两天再帮她找一次
- 如果出现新的高分人选就提醒她

那正确做法是：

- 外部系统记住她的搜索条件
- 外部系统再调用一次 `partner-search`
- 外部系统自己比较新旧结果
- 外部系统自己决定要不要提醒

而不是让 `partner-search` 自己负责“记住她、盯着她、通知她”。

## 10. 一句话总结

`partner-search` 的职责应该被严格固定为：

“根据用户画像和条件，从资料库中返回匹配对象，并解释匹配原因。”

而主动提醒、代为开口、系统撮合，应该永远被视为：

“调用 `partner-search` 的外部产品系统能力，而不是 skill 本身。”
