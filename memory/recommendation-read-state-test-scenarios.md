# 推荐来信已读状态测试场景

## 核心问题
点击推荐来信卡片后，红色提醒和图标数字依旧显示，需要验证修复效果。

## 测试维度

### 1. 功能正确性测试

#### 场景 1.1：推荐卡片点击后立即标记已读
- **前置条件**：
  - 用户有 3 个未读推荐卡片
  - 徽章显示数字 3
- **操作步骤**：
  - 点击第 1 个推荐卡片
- **预期结果**：
  - ✅ 红色提醒立即消失
  - ✅ 图标数字立即变为 2
  - ✅ 后端 API `markRecommendationCardsRead` 被调用
  - ✅ `RECOMMENDATION_READ_EVENT` 事件被触发
  - ✅ 徽章计数刷新函数被调用
- **验证点**：
  - API 调用参数正确（profileId, cardIds）
  - 事件 detail 包含 profileId 和 cardIds
  - 徽章计数重新计算逻辑正确

#### 场景 1.2：多个未读卡片顺序点击
- **前置条件**：
  - 用户有 5 个未读推荐卡片
- **操作步骤**：
  - 依次点击 5 个卡片
- **预期结果**：
  - ✅ 每次点击后数字立即减少 1
  - ✅ 数字变化：5 → 4 → 3 → 2 → 1 → 0
  - ✅ 最后一个点击后，图标数字消失
  - ✅ 所有卡片红色提醒消失

#### 场景 1.3：被动推荐（有人想认识你）点击后不立即标记已读
- **前置条件**：
  - 用户有 2 个被动推荐（interest 类型）
  - 徽章显示数字 2
- **操作步骤**：
  - 点击第 1 个被动推荐卡片
- **预期结果**：
  - ✅ 进入详情页，但红色提醒不消失
  - ✅ 图标数字不减少（仍为 2）
  - ✅ `markRecommendationCardsRead` API 不被调用（因为是 ProxyIntroCase）
  - ✅ 只有回复（accept/decline）后才标记已读

#### 场景 1.4：被动推荐回复后标记已读
- **前置条件**：
  - 用户进入被动推荐详情页
  - 未回复状态（case_status === 'awaiting_reply'）
- **操作步骤**：
  - 点击"愿意认识"按钮
- **预期结果**：
  - ✅ 回复 API 被调用
  - ✅ 案件状态变为 'accepted'
  - ✅ 返回推荐来信页，红色提醒消失
  - ✅ 图标数字减少 1

### 2. 事件机制测试

#### 场景 2.1：事件触发正确性
- **验证点**：
  - ✅ `RECOMMENDATION_READ_EVENT` 事件名称正确
  - ✅ 事件 detail 包含 profileId 和 cardIds
  - ✅ 事件在 API 成功后触发（失败不触发）
  - ✅ 事件使用 CustomEvent 构造

#### 场景 2.2：事件监听正确性
- **验证点**：
  - ✅ `useBadgeCounts` 监听 `RECOMMENDATION_READ_EVENT`
  - ✅ 事件触发时调用 `refresh()` 函数
  - ✅ 组件卸载时移除监听器（内存泄漏检查）

#### 场景 2.3：多组件监听同一事件
- **验证点**：
  - ✅ 多个组件同时监听，都能收到事件
  - ✅ 事件触发后，所有徽章计数同步更新

### 3. 徽章计数逻辑测试

#### 场景 3.1：徽章计数计算正确性
- **验证点**：
  - ✅ `fetchInboxUnreadCount` 返回推荐卡片未读数
  - ✅ `fetchMyProxyIntroCases` 返回被动推荐未读数
  - ✅ 合并逻辑：totalInboxUnread = inbox + interestUnread
  - ✅ 过滤逻辑：role === 'candidate' && case_status === 'awaiting_reply'

#### 场景 3.2：徽章刷新时机
- **验证点**：
  - ✅ 初始化时刷新
  - ✅ window focus 时刷新
  - ✅ 每 30 秒轮询刷新
  - ✅ `RECOMMENDATION_READ_EVENT` 触发时刷新
  - ✅ `RELATIONSHIP_READ_EVENT` 触发时刷新

#### 场景 3.3：徽章状态持久化
- **验证点**：
  - ✅ 页面刷新后徽章计数重新计算（依赖后端状态）
  - ✅ 不会因前端状态丢失导致徽章错误

### 4. 边缘场景测试

#### 场景 4.1：API 失败处理
- **操作步骤**：
  - Mock `markRecommendationCardsRead` API 返回错误
- **预期结果**：
  - ✅ 事件不触发（失败不触发事件）
  - ✅ 徽章计数不更新
  - ✅ 错误提示显示"标记已读失败"
  - ✅ 红色提醒不消失

#### 场景 4.2：并发点击多个卡片
- **操作步骤**：
  - 快速连续点击 3 个卡片（不等待 API 返回）
- **预期结果**：
  - ✅ 每个 API 都被调用（并发请求）
  - ✅ 每个事件都被触发
  - ✅ 徽章计数最终正确（3 个请求都完成）
  - ✅ 所有红色提醒消失

#### 场景 4.3：网络延迟场景
- **操作步骤**：
  - Mock API 响应延迟 3 秒
- **预期结果**：
  - ✅ 点击后立即进入详情页（不等待 API）
  - ✅ API 完成后事件触发
  - ✅ 事件触发后徽章更新
  - ✅ 用户体验流畅（不阻塞）

#### 场景 4.4：组件卸载场景
- **操作步骤**：
  - 点击卡片后立即返回上一页（组件卸载）
- **预期结果**：
  - ✅ API 继续执行（不因组件卸载中断）
  - ✅ 事件触发，其他组件收到事件
  - ✅ 徽章计数更新
  - ✅ 无内存泄漏（监听器移除）

#### 场景 4.5：混合场景测试
- **前置条件**：
  - 用户有 2 个推荐卡片 + 1 个被动推荐
  - 徽章显示数字 3
- **操作步骤**：
  - 点击推荐卡片 A
  - 点击被动推荐 B（不回复）
  - 返回推荐来信页
  - 点击推荐卡片 C
  - 点击被动推荐 B，点击"愿意认识"
- **预期结果**：
  - ✅ 点击 A：数字 3 → 2
  - ✅ 点击 B（不回复）：数字仍为 2
  - ✅ 点击 C：数字 2 → 1
  - ✅ 点击 B（回复）：数字 1 → 0

### 5. 性能测试

#### 场景 5.1：大量未读卡片性能
- **前置条件**：
  - 用户有 100 个未读推荐卡片
- **验证点**：
  - ✅ 页面渲染性能正常（不卡顿）
  - ✅ 点击响应速度正常（< 200ms）
  - ✅ 徽章计算性能正常（< 500ms）
  - ✅ 无内存泄漏

#### 场景 5.2：高频刷新性能
- **操作步骤**：
  - 快速连续触发 10 次 `RECOMMENDATION_READ_EVENT`
- **预期结果**：
  - ✅ 每次刷新都执行
  - ✅ 无重复 API 调用（节流/防抖）
  - ✅ 性能正常

### 6. 跨页面同步测试

#### 场景 6.1：详情页返回后同步
- **操作步骤**：
  - 推荐来信页点击卡片进入详情页
  - 查看详情后返回推荐来信页
- **预期结果**：
  - ✅ 红色提醒消失
  - ✅ 图标数字减少
  - ✅ 推荐来信列表刷新（卡片状态更新）

#### 场景 6.2：多标签页同步
- **操作步骤**：
  - 打开两个浏览器标签页
  - 在标签页 A 点击推荐卡片
- **预期结果**：
  - ✅ 标签页 A 徽章更新
  - ✅ 标签页 B 徽章不自动更新（依赖 window focus）
  - ✅ 标签页 B 切换到前台时刷新徽章

### 7. 数据一致性测试

#### 场景 7.1：前端状态与后端状态一致性
- **验证点**：
  - ✅ `isRead` 状态判断逻辑：card.card_status === 'read'
  - ✅ 徽章计数依赖后端 API（不依赖前端本地状态）
  - ✅ 页面刷新后状态一致（重新加载）

#### 场景 7.2：事件丢失场景
- **操作步骤**：
  - 点击卡片，API 成功但事件未触发（Mock）
- **预期结果**：
  - ✅ 徽章计数不更新（依赖事件）
  - ✅ 依赖其他刷新机制：window focus / 30秒轮询
  - ✅ 最终一致性保证
