## 1. 简历式筛选的「降维打击」与动态相处的「崩塌」

| 维度 | 说明 |
|------|------|
| **现象** | 用户在前置筛选里经常被身高、学历、房产、户口、年薪等硬指标快速淘汰；即使表面条件匹配，见面后也可能「三句话就聊不下去」。 |
| **小红书典型** | “相亲贴”里充满 `180cm`、`985/211`、房车户口等门槛，只要一项不达标，连进入“聊天环节”的资格都没有。 |
| **本质** | 传统画像是静态的、标签化的，但相亲最看重的是动态相处中的三观、接梗能力、情绪价值。人被降维成条件表后，复杂性和魅力都会被抹平。 |
| **系统切入点** | `user_persona_observations` 若只记硬件条件会处于劣势；需能通过 LLM 提取「性格底色」和「沟通偏好」。 |

## 2. 货不对板的「低信噪比」与信任焦虑（杀猪盘与简历水分）

| 维度 | 说明 |
|------|------|
| **现象** | 照片过度修图、收入虚标、职业和婚况包装，甚至混入引流黑产和职业骗子。 |
| **小红书典型** | 用户刷到“高质量男性”贴，留言几百条，结果私聊发现是引流黑产或骗子。即使是真人，也会出现“见面即下课”的巨大心理落差。 |
| **本质** | 缺乏真实可信的背书机制，用户在建立联系前需要耗费巨大心智去「侦察」对方真实性，平台整体信噪比过低。 |
| **系统切入点** | 不做单一「信任分」，而是拆成两套能力：一套是反诈风控，尽早拦截杀猪盘；一套是资料可信度校验，降低「简历水分」和见面翻车概率。 |

### 完整方案

#### 2.1 先拆开两类问题

- **杀猪盘 / 职业骗子**：本质是安全问题，目标不是“帮用户判断”，而是平台尽量在接触前或接触初期就拦截。
- **简历水分 / 货不对板**：本质是信息可信度问题，目标不是证明一个人“绝对真实”，而是降低用户自行侦察的成本。

这两类问题如果混成一个总分，会有两个副作用：

- 风险极高的人，可能因为资料写得完整、照片好看而被“均分”掩盖。
- 普通用户即使没有诈骗风险，也可能因为某些信息未认证而被误伤。

#### 2.2 设计原则

1. **不输出抽象总分，只展示字段级可信度**
2. **高风险行为单独处理，不与推荐分混算**
3. **优先验证“对婚恋决策影响大”的字段，而不是追求全量认证**
4. **第三方反馈采用结构化回流，不做公开口碑墙**

#### 2.3 资料可信度方案

建议把用户资料拆成若干关键字段，并给每个字段标注来源与验证状态，而不是只显示一个“已认证”徽章。

可优先覆盖这些字段：

- **照片**：普通上传、照片认证、活体自拍视频
- **身份**：实名、年龄
- **学历**：学校 / 最高学历认证
- **职业**：公司、岗位或职业类别认证
- **城市**：常住城市 / 定居意向
- **婚恋关键条件**：婚史、是否有孩子、结婚意向
- **收入**：不验精确值，只验区间

前台展示方式应从“单徽章”改成“字段级说明”，例如：

- `照片：已真人视频认证`
- `学历：已认证`
- `职业：未认证`
- `收入：用户自填（未认证）`

这样用户看到的不是“这个人可信 82 分”，而是“哪些信息有依据，哪些只是自述”。

#### 2.4 反诈风控方案

对于杀猪盘，不应依赖用户自己辨别，而应建立独立风控事件流。

重点信号包括：

- 新账号短时间高频私聊、多对象重复开场
- 快速导流到微信、Telegram、外部投资群
- 频繁出现借钱、投资、带单、内幕、稳赚等高风险话术
- 长期拒绝视频、拒绝语音、拒绝线下可核验接触
- 多次被不同对象标记为“诱导转账 / 导流 / 虚假身份”
- 资料稳定性异常：频繁换照片、换职业、换城市叙述

命中后不只做提示，应有明确动作：

- 降低曝光
- 限制主动发起聊天
- 触发补充认证
- 进入人工复核
- 严重时直接冻结

也就是说，`风险处置` 要走平台安全逻辑，而不是交给用户在对话里自行试错。

#### 2.5 第三方反馈与系统观察

“第三方评价”这个方向有价值，但不适合做成开放评论区，否则很容易演变成情绪化攻击、报复性差评和隐私风险。

更可控的做法是只收集结构化回流：

- `见面后是否与资料一致`
- `是否守时`
- `是否存在明显隐瞒`
- `是否有借钱 / 投资引导`
- `是否愿意正常视频或线下见面`

这些反馈不直接作为公开文案展示，而是作为平台侧观察日志的一部分。只有在满足以下条件时，才影响前台信任表达或风控判断：

- 重复出现
- 跨多个对象一致出现
- 与系统行为信号互相印证

#### 2.6 与搜索、推荐、撮合的结合方式

信任能力不能只放在详情页里“解释”，而应前置到筛选和排序里。

可提供的筛选项包括：

- `最低认证等级`
- `仅看照片认证以上`
- `仅看实名 / 学历 / 职业已认证`
- `仅看近期活跃且通过基础核验`

推荐排序里也可以引入可信度维度，但要注意：

- **资料可信度** 可以作为加分项
- **反诈风险** 应作为硬性降权或拦截项

也就是说，可信度影响“优先推荐谁”，风险决定“能不能继续出现在池子里”。

#### 2.7 MVP 建议

第一阶段不必把所有认证都做重，建议先上最能缓解焦虑的三件事：

1. **认证分层前台化**：把当前的认证状态从后台能力变成用户可见的字段级信号。
2. **照片 / 视频真人核验**：优先解决“照骗”和基础身份不确定的问题。
3. **聊天期反诈风控**：对导流、借钱、投资话术做事件识别和处置。

如果第一阶段验证有效，再逐步追加：

- 学历 / 职业认证
- 见面后结构化反馈
- 线下核验或平台背书服务

#### 2.8 最终想解决的，不是“真假判断”，而是侦察成本

用户真正厌烦的并不是“平台里存在不真实的人”，而是每次建立联系前，都要自己完成一轮侦查、交叉验证和风险判断。

因此产品目标应该是：

- 让高风险对象更早消失
- 让关键资料的可信程度更透明
- 让用户把精力从“查案”转回“判断是否适合相处”

#### 2.9 任务拆解

为了避免方案停留在概念层，建议把这条线拆成 `P0 基础可信度`、`P1 风控闭环`、`P2 深度背书` 三期推进。

##### P0：先让用户少“查案”

这一阶段的目标不是把所有认证做完，而是先把现有可信度信息前台化，并补齐最基础的反诈入口。

**产品 / 设计**

- 梳理资料中的关键字段，确认哪些字段进入“可信度展示层”：
  - 照片、实名、年龄、学历、职业、城市、婚史、子女、收入区间、结婚意向
- 定义字段级状态枚举：
  - `未填写`、`用户自填`、`已基础认证`、`已真人核验`、`已线下核验`
- 设计前台展示组件：
  - 列表卡片的简版认证标签
  - 详情页的“资料可信度”模块
  - 认证说明文案与悬浮解释
- 设计搜索筛选项：
  - `最低认证等级`
  - `仅看照片认证以上`
  - `仅看实名 / 学历 / 职业认证`

**后端 / 数据**

- 统一现有 `verified_level` 分层定义，明确 `none / basic / photo / id / offline` 对应含义。
- 扩展候选人读模型，支持字段级可信度输出，而不是只返回单个认证标签。
- 在搜索 / 推荐接口中补齐可信度字段返回：
  - `verified_level`
  - `verification_items`
  - `photo_count`
  - `last_active_at`
- 为搜索条件补齐可信度筛选参数，并与现有 `verified_level_min` 能力对齐。
- 为推荐理由补一类“可信度理由”文案：
  - 例如 `已真人照片认证`、`实名认证`、`线下核验`

**前端 / 客户端**

- 在推荐列表卡片增加可信度轻标签，不打断浏览。
- 在详情页增加“哪些信息已验证、哪些只是自填”的可读模块。
- 在搜索页增加可信度筛选入口。
- 在聊天页增加举报 / 风险提示入口，先解决用户“出事了不知道去哪报”的问题。

**运营 / 审核**

- 明确认证素材和审核标准：
  - 什么算照片认证
  - 什么算职业认证
  - 收入为什么只做区间、不做精确值
- 定义认证失败和补件流程。
- 定义基础举报类型：
  - `疑似照骗`
  - `资料不符`
  - `导流站外`
  - `借钱 / 投资`

**P0 交付物**

- 字段级可信度字典
- 搜索 / 推荐接口字段扩展
- 列表页与详情页可信度展示
- 举报入口与基础举报类型

##### P1：把“发现风险”变成“处置风险”

这一阶段的重点是把杀猪盘识别从人工经验变成系统事件流和风控动作。

**产品 / 风控策略**

- 定义高风险信号清单：
  - 高频私聊
  - 重复开场
  - 快速导流站外
  - 借钱 / 投资话术
  - 长期拒绝视频 / 语音 / 线下核验
- 定义风险等级和处置策略：
  - `提醒`
  - `降权`
  - `限制主动发言`
  - `要求补认证`
  - `人工复核`
  - `冻结`
- 定义误伤兜底机制：
  - 被限制后的申诉入口
  - 人工复核 SLA

**工程 / 后端**

- 为风控引入独立事件类型，接入现有事件 / outbox 习惯：
  - `risk.signal.detected`
  - `risk.case.opened`
  - `risk.action.applied`
  - `member.report.submitted`
- 在聊天与推荐链路埋点风险信号：
  - 消息关键词命中
  - 站外导流行为
  - 重复模板式开场
  - 多人举报聚合
- 实现基础规则引擎：
  - 先做规则命中，不急着上复杂模型
- 在推荐排序和曝光控制里接入风险状态：
  - 风险高的账号直接降曝光或拦截

**审核 / 运营**

- 搭建风险审核队列。
- 形成审核 SOP：
  - 看什么证据
  - 什么情况直接封
  - 什么情况要求补认证
  - 什么情况只做警告
- 沉淀典型案例，反向更新规则库和关键词库。

**数据 / 分析**

- 建立风控漏斗看板：
  - 举报量
  - 命中量
  - 人工确认率
  - 误伤率
  - 处置后复发率
- 跟踪风险策略对推荐转化的影响，避免“安全做强了但可聊对象被误杀”。

**P1 交付物**

- 风险事件字典与状态机
- 基础规则引擎
- 风险审核后台 / 队列
- 风险信号接入推荐降权与聊天限制

##### P2：从“平台提示”升级到“平台背书”

这一阶段才去做更重的认证和反馈回流，目的是进一步减少见面翻车。

**认证扩展**

- 上线学历认证、职业认证、城市 / 定居认证等更重的能力。
- 探索婚史、子女、结婚意向等高敏感字段的审慎核验方式。
- 设计“收入区间认证”而非精确收入认证，降低隐私和作弊成本。

**反馈闭环**

- 上线见面后结构化反馈表单：
  - `是否与资料一致`
  - `是否守时`
  - `是否存在明显隐瞒`
  - `是否有借钱 / 投资引导`
- 设计反馈生效规则：
  - 单次反馈只入库，不直接公开
  - 多次重复、跨对象一致、与系统信号印证后才影响信任表达
- 将高置信反馈回流到用户画像、风险画像和推荐系统。

**平台背书能力**

- 评估是否提供 `线下核验` 或 `平台认证顾问` 类服务。
- 评估是否在高价值场景中提供“优先展示已深度认证用户”的模式。

**P2 交付物**

- 重认证能力
- 结构化见面后反馈
- 信任回流策略
- 平台背书服务评估结论

#### 2.11 当前真实结论：不是“都解决了”，而是“先把风险显性化并拦住一部分”

如果从真实用户体验出发，需要非常明确地区分 `已经缓解` 和 `尚未真正解决`。

**当前已经缓解的部分**

- **资料可信度不再被一个总分糊弄过去**：
  - 已经能把照片、实名、年龄、学历、职业、收入、婚况、子女、结婚意向拆成字段级状态。
  - 用户至少能看到“哪些信息是平台核验过的，哪些只是用户自填”。
- **推荐和搜索链路已经开始带出信任差异**：
  - 线下核验、实名、照片认证这类强信号会被更明确展示。
  - 职业、收入、学历等未单独认证字段，会被明确标成“资料填写”或“未单独认证”。
- **明显杀猪盘话术已经能形成最小闭环**：
  - 对导流站外、投资、转账等高风险话术，系统可自动命中规则。
  - 用户可补充举报，审核可形成风险案件，并执行 `警告 / 限聊 / 冻结` 等动作。
  - 一旦被限聊，继续发言应被系统拦下，而不是继续放任试错。

**当前还没有真正解决的部分**

- **照片过度修图 / 换脸 / 非本人问题还没有被系统自动识别**：
  - 现在更多是在展示“照片是否经过真人认证”，而不是识别“这张图有没有修得过头”。
  - 平台还缺活体自拍视频、同人一致性检测、修图强度识别等能力。
- **收入虚标目前只是被标成“未认证”，还没有被真正核验**：
  - 也就是说，系统已经能提醒“这条收入只是自填”，但还不能证明“这条收入是真的”。
  - 职业、学历、收入之间是否存在明显不匹配，目前也没有形成稳定规则。
- **职业骗子只拦住了“明显型”，还没有覆盖“高段位长期伪装型”**：
  - 关键词式诈骗话术可以抓一批。
  - 但对于前期不提敏感词、后期慢慢导流、跨账号反复作案的人，当前系统仍可能漏掉。

所以，这一阶段的准确表述不应是：

- `我们已经解决了照骗、收入虚标、职业骗子问题`

而应是：

- `我们已经把“哪些信息可信、哪些信息只是自述”前台化了`
- `我们已经把明显诈骗从“用户自己猜”变成“系统先拦一层”了`
- `但更深的真实性核验和高段位反诈，仍需要继续建设`

#### 2.12 下一阶段优先级：先补真问题，不做表面加分

为了避免下一轮投入继续停留在“徽章更好看”或“解释文案更多”，建议后续按 `高优先级必须做`、`中优先级增强`、`后续迭代` 来排。

##### A. 高优先级必须做

这部分解决的是“用户仍然最容易翻车的地方”，优先级应高于任何视觉包装或泛化推荐优化。

**1. 照片真实性能力升级**

- 把“照片认证”升级成更细的状态：
  - 普通上传
  - 真人自拍认证
  - 活体自拍视频认证
  - 线下核验
- 增加 `疑似照骗 / 照片与真人差异大` 的举报类型与审核证据结构。
- 在见面后反馈里，单独收集：
  - `照片是否与真人基本一致`
  - `是否存在明显修图 / 非本人感`

**2. 收入 / 职业 / 学历的字段级硬核验**

- 不再满足于“未认证”提示，而是逐步建设：
  - 学历认证
  - 职业类别认证
  - 收入区间认证
- 允许产品层明确区分：
  - `已认证`
  - `用户自填`
  - `声明与其他字段疑似不一致`
- 对收入与职业、城市消费水平、工作年限明显不匹配的资料，进入人工复核或补件流程。

**3. 诈骗风控从关键词升级为行为风控**

- 在“投资 / 转账 / 导流”关键词外，补充行为信号：
  - 新号短时间高频私聊
  - 多对象重复模板开场
  - 频繁索要站外联系方式
  - 长期拒绝视频 / 语音 / 线下可核验接触
  - 多个账号共享相似资料模式或作案路径
- 对高风险账号，不只是提示，而应默认：
  - 降曝光
  - 限制主动发起聊天
  - 要求补认证
  - 进入人工复核

**4. 前台风险提醒要更直接**

- 不是只让后台知道，而是让用户在关键节点直接看到：
  - `该用户哪些信息未核验`
  - `哪些信息仅为自述`
  - `为什么系统建议你谨慎继续`
- 对已命中中高风险信号但尚未冻结的对象，可探索更克制的前台提示：
  - 例如 `对方存在导流 / 投资类风险信号，请勿转账或离开平台沟通`

##### B. 中优先级增强

这部分不是“立刻不上线就出大事”，但会明显提升整体可信度和误伤控制。

**1. 建立更强的见面后结构化反馈**

- 不是让用户写长评论，而是做标准化表单：
  - `照片是否一致`
  - `资料是否有明显隐瞒`
  - `收入 / 职业是否明显夸大`
  - `是否有借钱 / 投资 / 导流`
- 反馈默认只入后台，不直接公开。
- 只有在重复出现、跨对象一致、与系统信号印证时，才真正影响风控或信任表达。

**2. 建立风控误伤兜底机制**

- 被限制后要有申诉与复核入口。
- 审核后台要能回看：
  - 命中的规则
  - 相关消息证据
  - 举报来源
  - 历史处置记录
- 建立误伤率、漏报率、复发率看板，不然规则会越堆越乱。

**3. 推荐系统纳入“可信度门槛”**

- 现在更多是展示差异，下一步应在推荐排序中更稳地使用：
  - 低核验资料不轻易占据高位
  - 高风险账号直接不进入重点推荐池
- 重点不是做成一个神秘总分，而是把可信度变成明确可解释的排序条件。

##### C. 后续迭代

这部分更重、更贵，适合在前两层跑通后再做。

**1. 照片与身份的智能识别增强**

- 评估接入：
  - 修图强度识别
  - 同人一致性检测
  - 活体与历史照片一致性校验
- 这类能力技术和合规成本都更高，适合作为后续增强，而不是第一波 MVP 目标。

**2. 多账号 / 团伙型诈骗识别**

- 引入设备、IP、行为路径、资料模板相似度等信号。
- 识别“单账号看着正常，但一组账号一起作案”的情况。

**3. 平台背书服务**

- 评估是否上线更重的服务：
  - 线下核验
  - 深度认证专区
  - 高可信用户优先展示
- 这类能力会显著提升信任，但成本高、流程重，应在基础闭环稳定后推进。

#### 2.13 一句话给团队定调

这条线的产品目标，不应被表述为：

- `把所有人真假彻底判断出来`

而应被表述为：

- `先把“哪些信息只是自述”讲明白`
- `先把明显骗子更早拦住`
- `再逐步提升照片、收入、职业、学历等高决策字段的可核验性`

换句话说，当前阶段最重要的不是“让平台看上去更安全”，而是实打实减少用户的侦察成本和踩坑概率。

#### 2.14 可直接建 Jira 的高优先级任务包

如果下一步要真正推进“照片真实性、收入虚标、职业骗子”这三类问题，建议不要再按零散小需求推进，而是直接拆成 4 个 Epic。

**Epic A：照片真实性升级**

**Jira 1：定义照片信任状态机与前后台字段**

- **任务目标**：把当前“有照片 / 照片认证”升级为更细的照片真实性层级。
- **建议产出**：
  - 照片状态枚举：`uploaded / human_verified / live_video_verified / offline_verified`
  - 前台文案规范
  - 搜索 / 推荐 / 详情页统一字段定义
- **依赖**：
  - 产品确认状态含义
  - 设计确认展示样式
- **验收标准**：
  - API 文档明确新增字段及取值
  - 搜索、推荐、详情页都能返回并消费同一套字段
  - 用户能区分“普通上传照片”和“活体真人核验照片”

**Jira 2：新增活体自拍视频认证流程**

- **任务目标**：把“照片是真的本人”这件事从弱信号升级成强信号。
- **建议产出**：
  - 活体自拍视频上传入口
  - 审核流或自动校验流
  - 认证通过 / 失败 / 补录状态
- **依赖**：
  - 客户端上传能力
  - 审核策略或第三方能力选型
- **验收标准**：
  - 用户可完成自拍视频认证提交流程
  - 后台可看到认证状态和审核结果
  - 前台可展示 `活体自拍视频认证` 状态

**Jira 3：新增“疑似照骗”举报类型与审核证据结构**

- **任务目标**：让用户在发现“照片和真人差很多”时有明确反馈入口。
- **建议产出**：
  - 举报类型：`疑似照骗`、`照片与真人差异大`
  - 审核证据字段
  - 审核动作建议
- **依赖**：
  - 举报入口已存在
  - 风险案件模型支持新增类型
- **验收标准**：
  - 聊天页 / 资料页可提交相关举报
  - 后台可区分这类举报，不与诈骗举报混在一起
  - 可形成单独风险案件或可信度回流记录

**Jira 4：见面后“照片一致性”结构化反馈**

- **任务目标**：把“照骗判断”从主观吐槽变成结构化回流。
- **建议产出**：
  - 见面后反馈表单增加：
    - `照片是否与真人基本一致`
    - `是否存在明显修图 / 非本人感`
  - 回流规则设计
- **依赖**：
  - 见面后反馈入口
  - 风控 / 信任回流策略
- **验收标准**：
  - 反馈数据可入库
  - 单次反馈不公开展示
  - 多次重复反馈可进入审核或影响可信度标签

**Epic B：学历 / 职业 / 收入区间硬核验**

**Jira 5：定义学历、职业、收入区间认证字典与补件规则**

- **任务目标**：先把“怎么认证、认证到什么程度、失败后怎么办”讲清楚。
- **建议产出**：
  - 学历认证标准
  - 职业类别认证标准
  - 收入区间认证标准
  - 补件和驳回规则
- **依赖**：
  - 运营 / 审核规则确认
  - 合规评估
- **验收标准**：
  - 三类字段均有明确认证口径
  - 能区分 `已认证 / 用户自填 / 未认证 / 待补件`
  - 收入只做区间，不要求精确值

**Jira 6：扩展资料字段级认证模型与 API 返回**

- **任务目标**：让学历、职业、收入不再只是文案，而是结构化字段。
- **建议产出**：
  - 用户资料表 / 读模型新增字段级认证状态
  - 搜索 / 推荐 / 详情 API 返回结构扩展
  - 认证状态映射逻辑
- **依赖**：
  - Jira 5 完成字段字典
- **验收标准**：
  - 学历、职业、收入区间可分别返回认证状态
  - 前端能明确展示“哪些已认证，哪些只是自填”
  - 不再把这 3 类字段混成一个总徽章

**Jira 7：资料不一致规则第一版**

- **任务目标**：把明显不合理的资料先筛出来，而不是等用户自己发现。
- **建议产出**：
  - 规则样例：
    - 收入区间与职业类别明显不匹配
    - 城市、工作年限、收入叙述明显冲突
    - 职业 / 学历 / 收入字段频繁修改
  - 命中后的处置策略
- **依赖**：
  - Jira 6 可提供字段级结构化数据
- **验收标准**：
  - 规则命中可形成后台风险信号
  - 不直接封禁，优先进入补件 / 人工复核
  - 命中记录可回放、可解释

**Epic C：诈骗风控从关键词升级到行为风控**

**Jira 8：补齐行为型风险埋点**

- **任务目标**：不再只盯聊天内容，而是盯账号行为模式。
- **建议产出**：
  - 风险埋点：
    - 新号短时间高频私聊
    - 多对象重复模板式开场
    - 频繁索要站外联系方式
    - 长期拒绝视频 / 语音 / 线下核验
    - 多次被不同对象举报
- **依赖**：
  - 聊天事件流
  - outbox / 风险事件模型
- **验收标准**：
  - 以上行为至少能记录为独立事件
  - 可按账号维度聚合查看
  - 可进入风控案件而非只停留在日志

**Jira 9：行为型风控规则引擎一期**

- **任务目标**：把“行为异常”变成可执行处置，不再靠人工盯日志。
- **建议产出**：
  - 行为规则第一版
  - 风险分层：
    - `提醒`
    - `降权`
    - `限制主动聊天`
    - `要求补认证`
    - `人工复核`
- **依赖**：
  - Jira 8 埋点完成
- **验收标准**：
  - 行为规则可自动命中
  - 命中后可形成风险案件
  - 不同行为等级对应不同动作，而不是全部一刀切

**Jira 10：风险动作接入曝光、聊天和补认证流程**

- **任务目标**：让风控不是“看见了”，而是“真的拦住了”。
- **建议产出**：
  - 高风险账号降曝光
  - 中高风险账号限制主动发起聊天
  - 高风险账号触发补认证
  - 严重风险账号进入冻结流程
- **依赖**：
  - Jira 9 风控规则可产出稳定结果
- **验收标准**：
  - 不同风险等级能触发不同处置
  - 聊天限制和推荐降权可联动
  - 处置结果可在后台追踪

**Epic D：前台风险提醒与审核闭环**

**Jira 11：前台谨慎提示组件**

- **任务目标**：让用户在关键节点直接知道哪里需要谨慎，而不是后台默默记一笔。
- **建议产出**：
  - 资料页“哪些字段未核验”模块
  - 聊天页中高风险提示条
  - 不离开平台、不转账的提醒文案
- **依赖**：
  - Jira 6 字段级认证状态
  - Jira 9 / 10 风险状态输出
- **验收标准**：
  - 用户能明确看到“哪些信息只是自述”
  - 命中中高风险信号时，聊天页有克制但明确的谨慎提醒
  - 提醒不影响正常用户阅读体验

**Jira 12：审核后台补齐误伤兜底与看板**

- **任务目标**：防止规则越做越重，但没人知道误伤了多少。
- **建议产出**：
  - 申诉入口
  - 审核回看面板
  - 风控看板：
    - 命中量
    - 人工确认率
    - 误伤率
    - 漏报率
    - 复发率
- **依赖**：
  - 风险案件、风险动作、举报数据已结构化
- **验收标准**：
  - 被限制用户有申诉入口
  - 审核员能回看规则命中和证据
  - 每周可稳定输出误伤率和复发率数据

#### 2.15 建议排期顺序

如果只能分两轮做，建议顺序如下：

**第一轮：先做“能立刻少翻车”的**

1. Jira 1：定义照片信任状态机与前后台字段
2. Jira 5：定义学历、职业、收入区间认证字典与补件规则

5. Jira 9：行为型风控规则引擎一期
6. Jira 11：前台谨慎提示组件

**第二轮：再做“能进一步减少漏网和误伤”的**

1. Jira 2：新增活体自拍视频认证流程
2. Jira 3：新增“疑似照骗”举报类型与审核证据结构
3. Jira 4：见面后“照片一致性”结构化反馈
4. Jira 7：资料不一致规则第一版
5. Jira 10：风险动作接入曝光、聊天和补认证流程
6. Jira 12：审核后台补齐误伤兜底与看板

如果资源只能再压缩成首批 4 个任务，建议直接选：

1. Jira 1：照片信任状态机
2. Jira 6：字段级认证模型与 API
3. Jira 9：行为型风控规则一期
4. Jira 11：前台谨慎提示组件

这 4 个任务做完，用户侧就能明显感受到：

- 平台不再把“自填信息”伪装成高可信信息
- 明显骗子不再只能靠用户自己猜
- 关键风险会被更早提醒出来

##### A. 照片过度修图 / 照骗问题

**当前已经做到**

- 已经能区分：
  - `普通上传照片`
  - `真人照片认证`
  - `活体自拍视频认证`
  - `线下核验照片`
- 搜索、推荐、可信度文案里已经能明确展示照片核验层级。
- 用户侧已经可以通过“更高照片核验门槛”把只会上传普通照片的人先筛掉一批。
- 聊天风控和见面后反馈链路已经支持把“照片与真人不符”回流成结构化风险信息。
- 已补上后端闭环：
  - 可提交 `suspected_fake_photo`、`photo_heavily_edited` 这类结构化举报信号
  - 举报 / 见面后反馈可绑定具体资料源和资料记录
  - 风险案件支持批量审核、申诉复核和回放证据
- 活体自拍视频链路已经不是纯人工兜底：
  - 提交后会先跑一层本地机器预审脚手架
  - 能给出 `动作活体`、`同人比对`、`动作完成度` 的评分和风险标记
  - 能自动分流成 `自动通过`、`要求补录`、`转人工复核`
  - 对高风险样本会额外给出 `升级强实名` 建议，而不是一上来全量强实名
  - 已补上 `实时动作 challenge` 后端承接层：
    - 服务端可先签发 challenge token
    - 前端可实时完成 `眨眼 / 张嘴 / 转头 / 抬头`
    - 再把动作结果和视频证据一并回传到同一条认证单
  - 已补上 `强活体 provider 接口层 + 语音口令校验层` 的第一期骨架：
    - 后端机器预审现在只允许走 `local_oss`，代码里不再保留 `mock / reported` 切换入口
    - 后端不再只看“前端说自己眨眼成功了”，还会额外校验 `spoken_prompt_rendered / audio_recorded / speech_challenge_result`
    - 对带随机数字口令的 challenge，后端会判断：`有没有音频`、`识别出的数字和 challenge 是否一致`、`口令是否发生在动作之后`

**当前还没做到**

- 还没有自动识别：
  - 修图是否过度
  - 是否为同一人
  - 是否存在换脸 / 盗图 / 非本人照片
- 现在这层“机器预审”还只是仓库内可替换的本地 provider，还没正式接入支付宝 / 腾讯云 / 阿里云这类真实第三方动作活体与同人比对服务。
- 还没有正式前端举报入口、审核面板和运营工作台。

**所以当前真实差距是**

- 现在已经不是“只有提示”，而是“后端已经能举报、审核、回放、处置”。
- 也已经不是“完全只能人工看视频”，而是“已经有自动分流骨架，只是还没换成真实第三方识别能力”。
- 但它仍然还不是“系统已经能稳定自动识别照骗”。
- 也就是说，平台已经能**降低照骗暴露面**，但还不能说**已经解决照骗识别本身**。

##### B. 收入虚标 / 职业包装 / 学历水分

**当前已经做到**

  - `已认证`
  - `资料填写`

  - `资料存在待复核或不一致信号`
  - `建议先确认职业、学历和收入区间是否真实`
- 对资料反复修改、字段不一致的情况，已经能进入风险提示和排序降权。
- 已补上字段级后端闭环：
  - `education` / `job` / `income` 已有补件策略、提交流程、驳回重提和审核通过
  - 审核通过后可把字段状态和核验值回写到资料源
  - 已有资料不一致案件、审核事件、处置动作和搜索 / 推荐联动

**当前还没做到**

- 还没有正式前端补认证入口、审核工作台和用户侧申诉页面。

**所以当前真实差距是**

##### F. 测试验证与真实世界校准

**当前已经做到**

- 已经补了真实用户、过度包装用户、诈骗用户这几类场景测试。
- 搜索、推荐、聊天、网关的核心链路都已经有回归测试覆盖。
- 当前相关实现已经通过本地串行全链路回归：
  - `external-systems/partner-chat-system/tests/test_chat_system.py`
  - `external-systems/partner-http-gateway/gateway_tests/test_gateway_wsgi.py`
  - `external-systems/partner-http-gateway/gateway_tests/test_realistic_user_flows.py`
  - `local-skills/partner-search/tests/test_partner_search_api.py`

**当前还没做到**

- 还没有基于真实线上数据去校准：
  - 哪些规则太松
  - 哪些规则太重
  - 哪些文案用户看不懂
- 还没有观察真实用户在“补认证、举报、谨慎提示”下的行为变化。

##### G. 一句话结论

如果要对外讲最准确的话，当前阶段应该表述为：

- `除前端、算法识别能力、线上真实数据校准之外，当前仓库内可继续落地的后端风险闭环已经补齐，并已完成本地测试验证`
- `平台已经把风险做成可见、可提示、可筛掉一部分、可拦住一部分`

而不应该表述为：

- `照片过度修图、收入虚标、职业骗子这些问题已经彻底解决`

更准确一点说：

- 照片问题：已经解决了“可信度分层与前置筛选”，还没解决“自动识别照骗”。
- 收入 / 职业问题：已经解决了“别再伪装成高可信”，还没解决“真正完成硬核验”。
- 杀猪盘问题：已经解决了“明显风险能被发现并部分拦截”，还没解决“复杂黑产与团伙型诈骗”。

###### Task 1. 照片真实性自动识别与活体识别引擎

- 任务目标：把“照片问题主要靠人工发现”升级为“系统先筛、人工复核兜底”，重点解决过度修图、同人一致性、换脸盗图、非本人照片和自动活体识别。
- 判断口径：
  - 已完成：指仓库内已经有代码、有接口、可本地体验、主链路能跑通。
  - 未完成：指还没有达到“强同人、强照片识别、强 deepfake、强盗图、强修图、完整照片风控平台”的完整版标准。
- 已完成版清单（截至 `2026-05-13`）：
  - 活体 challenge 已经不是纯动作题，服务端会同时下发随机动作和随机数字口令。
  - 前端保留 `MediaPipe` 实时动作检测，当前已能做 `blink / open_mouth / turn_left` 的随机顺序挑战。

  - 后端已锁定 `local_oss` 机审模式，不再允许切回 `mock / reported`。
  - 后端已接入 `Silent-Face-Anti-Spoofing`，能输出防照片 / 防屏幕翻拍 / 防明显回放攻击的第一版风险分数。
  - 后端已接入 `faster-whisper`，会直接从上传视频音轨识别本次 challenge 数字，而不是只信浏览器上报。
  - 后端已补上 `口型和声音强绑定` 第一版：会从音轨抽语音能量曲线、从视频抽嘴部运动曲线，回填 `audio_video_sync_score`，没有同步证据时不再直接判口令通过。
  - 后端已补上 `deepfake 检测` 第一版：会从活体视频脸部帧里计算时序抖动、边缘缝合、色彩/纹理不稳定等启发式风险，输出 `deepfake_risk_score`，高风险样本会转人工或升级强实名。
  - 后端已补上 `修图检测` 第一版：会拿资料照和活体视频的人脸细节做比对，计算磨皮、美颜、滤镜和脸型差异风险，输出 `photo_edit_risk_score`，修图过重样本不再直接自动通过。
  - 后端已补上 `静态资料照真实性自动识别引擎` 第一版：资料照触发复核时，后端会自动拉取整组资料照，做 `同组同人一致性 + 站内重复图/疑似盗图 + 静态 deepfake 风险 + 静态修图风险` 合并分析，输出 `photo_authenticity_score` 和明细风险分。
  - `静态资料照真实性自动识别引擎` 第一版已经接进 `/v1/profile-review/risk-cases/evaluate`：命中高风险时会直接生成资料照风险案件，并自动创建活体补录单，不再只是人工主观判断。
  - 后端已经会把 `动作挑战结果 + Silent-Face 结果 + faster-whisper 结果` 合并后，再给出 `approved / under_review / resubmission_required`。
  - 网关演示页和两条核心接口 `/v1/verifications/live-video-challenges`、`/v1/verifications/live-video-submissions` 已可用于体验整套活体视频第一版链路。

###### Task 2. 照片举报、补录、结果通知的产品闭环

- 任务目标：把照片问题从“后端可以处理”升级为“用户能方便举报、被要求补录的人能完成补录、审核结果能被追踪”。
- 完整解决方案：
  - 用户入口：在搜索卡片、资料页、聊天页、见面后反馈页提供统一的“照片与真人不符 / 疑似过度修图 / 疑似非本人”入口；支持选择具体照片、补充说明、补充截图或见面备注。
  - 补录流程：被命中的用户进入“补录中心”，系统明确告诉用户是补录静态真人照、活体自拍视频，还是重新提交整组资料照；补录时给出拍摄约束，例如光线、角度、无遮挡、指定动作。
  - 状态追踪：提供提交成功、审核中、补件中、已通过、已驳回、已冻结等状态页，并显示当前原因、下一步动作、预计处理时限。
  - 消息通知：通过站内信、push、短信或企业微信运营提醒把补录要求、审核结果、解封结果同步给用户；对举报人只回传“已受理 / 已处理”，不泄露被举报人隐私。
  - 后台承接：前端动作全部落到统一工单与审核案件上，串起资料照片、活体视频、举报记录、见面后反馈、模型打分、历史处置。
  - 体验细节：对轻风险用户先给温和补录提示；对高风险用户直接降曝光并限制关键动作，避免在审核前继续扩散风险。
  - 建议验收标准：照片举报入口覆盖关键页面，补录完成率、审核时效、举报后命中率、因流程不清导致的客服咨询量应可量化追踪。

###### Task 3. 学历、职业、收入的硬核验接入与字段级可信度升级

- 任务目标：把“字段级补件与复核”升级为“字段级权威核验”，让教育、职业、收入不再停留在用户自述或人工主观判断。
- 完整解决方案：
  - 学历核验：接入毕业证、学位证、学信类权威查询或合作方接口；先做 OCR 与字段抽取，再做姓名、学校、专业、毕业时间一致性比对；无接口场景保留人工复核兜底。
  - 职业核验：建立多通道核验。
    企业邮箱验证用于白领岗位快速核验。
    工牌、在职证明、名片、社保或公积金截图用于人工复核。
    对自由职业、创业者、个体经营者设计差异化证明材料，不强行套用单一规则。
  - 收入核验：不追求展示精确收入值，而是核验收入区间真实性；可接入税单、薪资流水、社保基数、银行工资流水、纳税证明等材料，只输出收入区间和可信度等级。
  - 规则引擎：为 `education`、`job`、`income` 各自维护核验状态、证据类型、证据有效期、复核次数、争议状态和到期重审策略。
  - 风险联动：字段核验失败、材料造假、长期拒绝补件、前后说法不一致时，自动触发 `require_verification`、`limited_exposure`、推荐降权和聊天侧谨慎提示。
  - 隐私与合规：敏感材料脱敏、分级授权、最小留存、明示使用目的；收入类材料只存必要摘要，不在搜索或资料页向外暴露原始证明。
  - 商业与供应链：权威数据接入需要提前确认供应商、成本、接口 SLA、失败兜底率、合规条款和跨地区可用性。
  - 建议验收标准：教育、职业、收入三类字段都应有“自述 / 待补件 / 审核中 / 已核验 / 驳回 / 已过期”状态；复核通过率、误判申诉率、核验完成周期应可稳定统计。

###### Task 4. 用户核验中心、补件中心、申诉中心的前台闭环

- 任务目标：把所有需要用户配合的风控与核验动作沉淀为一个统一的用户自助中心，降低困惑、投诉与流失。
- 完整解决方案：
  - 信息架构：在用户中心下新增 `核验中心`、`申诉中心`、`风险记录` 三个一级入口，统一承接资料核验、照片补录、聊天限制原因、申诉进度、历史处理结果。
  - 页面能力：每个任务要明确展示触发原因、需要提交什么、示例材料、审核时长、失败原因、重新提交入口和联系客服方式。
  - 申诉闭环：用户可以对冻结、限制聊天、降曝光、字段驳回发起申诉；申诉需支持补充材料、文字说明、再次提交；系统要能显示“已受理 / 复核中 / 结论已出”。
  - 教育引导：针对“为什么要核验收入”“为什么被要求补录活体”“为什么不能立即恢复曝光”提供简短 FAQ 与例子，减少对抗情绪。
  - 通知中心：把待补件、待申诉、审核结论、再次补件等消息统一收敛，不让用户靠多个零散触点理解规则。
  - 无障碍与风控平衡：需要兼顾移动端可用性、拍摄体验、隐私提示和风险威慑，避免页面过度恐吓导致正常用户放弃。
  - 建议验收标准：补件完成率、申诉资料提交完整率、因“看不懂原因”导致的客服单量、恢复通过后的留存与转化应被纳入评估。

###### Task 5. 设备、IP、行为模板、关系图谱的深度反诈引擎

- 任务目标：从“关键词和单账号行为风控”升级为“识别职业骗子、团伙号、工作室号、慢热型诈骗链路”的图谱化反诈系统。
- 完整解决方案：
  - 采集层：补齐设备指纹、IP 与网段、登录地变化、UA、会话稳定性、注册路径、头像与文案模板、外部联系方式变体、主动私聊节奏、聊天对象扩散图、举报关联图、见面后异常反馈图。
  - 图谱层：构建账号、设备、IP、图片、联系方式、支付线索、文案模板、举报事件之间的多实体关系图；支持实体归并、关联路径查询、团伙聚类和风险传播。
  - 检测层：组合使用规则、聚类、异常点检测、图算法。
    规则识别明显共用设备、批量注册、同模板开场。
    聚类识别相似画像批量复用、相似话术矩阵、相似导流路径。
    图算法识别高风险中心节点、桥接节点、异常扩散速度和复发群。
  - 决策层：为“账号风险分”和“团伙风险分”分别维护阈值；团伙命中后不仅处理单账号，还要联动相邻账号复检、限流、冻结和人工深挖。
  - 联动层：把团伙识别结果回流给注册审核、搜索曝光、推荐分发、聊天发起限制、人工撮合白名单和线下见面提醒。
  - 安全与合规：设备与网络信息属于高敏感信号，必须进行哈希化、最小留存和权限隔离；需要提前确认是否触达当地合规红线。
  - 建议验收标准：新增的图谱信号应显著提升高危案件命中率，并降低“同团伙反复复活”的复发率；同时对正常用户的误伤率必须可解释、可回查。

###### Task 6. 风险提示、举报、反馈、谨慎引导的前台产品化

- 任务目标：让当前已经存在的风险信息真正被用户感知和使用，而不是只停留在 API 和后端状态中。
- 完整解决方案：
  - 搜索与推荐页：把“已核验 / 待复核 / 自述为主 / 资料存在不一致信号 / 需谨慎交流”等标签稳定展示出来，并允许用户按核验强度过滤。
  - 资料页：将教育、职业、收入、照片核验状态拆开展示；明确哪些是自填、哪些是核验、哪些存在争议；对高风险资料给出明显但不过度打扰的警示。
  - 聊天页：在命中高风险时展示动态提醒，例如“建议先视频核验”“避免转账”“对方资料存在待复核字段”；对严重风险增加关键动作摩擦，例如限制直接索要站外联系方式。
  - 举报页：统一设计举报分类、举证上传、举报结果回执和防滥用策略；对恶意举报要有频控和信用回收。
  - 见面后反馈页：把“照片不符、收入职业夸大、借钱投资、言行越界、持续导流站外”等选项结构化，并允许用户标注严重程度和是否愿意接受回访。
  - 风险教育：设计轻量级安全教育组件，在关键节点解释平台为什么提示、用户该如何自保、什么情况应该立即停止沟通。
  - 建议验收标准：用户对风险标签的点击率、举报转化率、见面后反馈填写率、风险提示后的危险行为下降幅度都应进入产品看板。

###### Task 7. 审核运营后台、SOP 与质检体系

- 任务目标：把当前可用的后端风控能力沉淀成一个真正可运营的审核平台，而不是仅靠接口和脚本处理。
- 完整解决方案：
  - 后台能力：提供风险案件列表、批量审核、案件回放、资料对比、图片对比、关联账号查看、申诉队列、字段核验队列、周报看板、阈值配置和操作审计。
  - 角色权限：区分一线审核、复核专员、风控策略、客服申诉、管理员五类角色；不同角色可见范围、可执行动作、可查看敏感材料范围必须隔离。
  - SOP：为照片问题、资料造假、诈骗导流、线下见面投诉、误伤申诉建立标准操作手册，明确处理时限、升级条件、冻结条件、恢复条件和抽检要求。
  - 质检：建立复核抽样、错杀复盘、漏放复盘、审单一致性检查；把质检结果回流给审核培训和规则调优。
  - 协同：后台需要和客服系统、消息系统、法务或合规审批流打通，避免审核结论无法被用户感知，也避免高风险账号多头处理不一致。
  - 运维：关键动作要有审计日志、回滚能力、双人复核开关和异常操作告警。
  - 建议验收标准：一线审核时长、申诉处理时长、复核一致率、操作追溯完整率、误伤纠正周期应可稳定统计。

###### Task 8. 线上真实数据校准、灰度放量与 A/B 验证体系

- 任务目标：验证当前规则、阈值、文案和产品摩擦是否真的有效，避免“本地链路没问题，但线上效果不可控”。
- 完整解决方案：
  - 指标体系：明确主指标和护栏指标。
    主指标包括高风险命中率、误伤率、复发率、举报命中率、补件完成率、资料核验通过率、见面后负反馈率。
    护栏指标包括匹配转化、聊天开启率、留存、客服投诉量、封禁申诉率。
  - 数据埋点：在搜索曝光、标签点击、发起聊天、补件提交、审核结论、申诉提交、申诉通过、见面后反馈等关键节点补齐埋点，保证能把“提示 -> 用户动作 -> 风险结果”串起来。
  - 离线评估：每次策略调整前先跑历史样本回放，确认新规则对高风险召回和误伤影响，再进入线上灰度。
  - 灰度机制：按城市、流量桶、用户类型或新老用户分阶段放量；先小流量试运行，再扩大覆盖；任何核心指标异常都可一键回滚。
  - A/B 设计：对提示文案、展示样式、补件时机、限制强度、审核阈值分别做实验，不把多个变量混在同一次实验里。
  - 策略治理：建立阈值配置中心和版本化记录，明确每次调整的负责人、原因、实验编号、起止时间和结论。
  - 周期复盘：每周复盘误伤、漏放、用户流失、客服反馈和模型漂移；每月做跨模块复盘，决定是否改文案、改规则、改阈值、改流程。
  - 建议验收标准：任何新的风控策略或核验流程上线前，都必须经过离线回放、灰度观察和线上复盘三步，不允许直接全量发布。

##### I. 建议落地顺序

- 第一阶段：先做 `Task 2`、`Task 4`、`Task 6`、`Task 7`，把现有后端能力真正变成用户与运营可用的产品闭环。
- 第二阶段：推进 `Task 3` 和 `Task 5`，把字段硬核验与深度反诈信号补齐，提升处置质量。
- 第三阶段：在前两阶段积累了足够样本和操作数据之后，推进 `Task 1` 和 `Task 8`，做自动识别、线上校准、灰度优化与持续迭代。
- 排期原则：前台承接、运营工作台、数据埋点必须优先于纯算法冲刺；否则即使模型做出来，也缺少高质量样本、人工复核闭环和真实世界反馈。

## 4. 奇葩经历带来的「心理阴影」

| 维度 | 说明 |
|------|------|
| **现象** | 用户反复遇到价值观扭曲、极度自私、边界感差或带操控倾向的对象，逐渐对相亲池失去信心。 |
| **小红书典型** | 对方在相亲现场 `PUA`、追问私密隐私，或者在确认关系后发现对方同时与多人“置顶聊天”。 |
| **本质** | 用户担心的不只是“不合适”，而是“踩坑”。几次极差体验后，会形成“好的都被挑走了，剩下的都是奇葩”的负面心理暗示。 |
| **系统切入点** | 需要把这类“红旗体验”从主观吐槽转成结构化信号，例如越界问题、关系状态不透明、失礼行为、多人并线等，并通过举报、见面后反馈和撮合节奏控制回流。 |

## 6. 高昂的「沉没成本」与「反馈真空」

| 维度 | 说明 |
|------|------|
| **现象** | 用户费心费力准备见面，花了时间、精力和金钱，最后却只得到一句“不合适”或直接被拉黑。 |
| **小红书典型** | 用户常发帖求助：“我到底哪里表现不好？为什么见完面就没下文了？” |
| **本质** | 相亲是典型的高成本、黑盒化交易。用户有投入，却拿不到有效反馈和复盘建议，因此只能重复同样的失败模式。 |
| **系统切入点** | 建立「反馈回流闭环」：分析失败原因（谈吐、衣着、价值观冲突等），修正用户画像，并给出可操作的改进建议。 |
