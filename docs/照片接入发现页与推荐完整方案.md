# 照片接入发现页与推荐完整方案

## 1. 背景

当前系统的发现页、推荐系统、画像写入链路已经比较完整，但照片只参与了很浅的一层：

- 展示层会显示头像/照片
- 搜索层会使用 `photo_count`
- 搜索层会使用 `photo_verification_level`
- 系统不会根据照片内容、长相类型、眼缘偏好来匹配和排序

这和真实相亲流程有明显偏差。

真实相亲通常是：

1. 先看照片有没有眼缘
2. 再看条件合不合适
3. 最后才进入更深的聊天和长期匹配判断

所以照片应该进入匹配逻辑，但不能只做成“谁颜值高谁排前”。更合理的目标是：

- 用照片补足“第一眼兴趣”
- 用照片语义表达“长相类型”
- 用用户行为学习“这个用户喜欢什么长相”


## 2. 当前系统现状

### 2.1 发现页搜索链路

当前发现页通过 `discovery_system -> service_integrations -> partner_search` 调用统一搜索引擎。

关键事实：

- 发现页会加载用户 `profile + persona`
- 把本轮条件合并进 `working_criteria`
- 调用 `build_discovery_search_request()` 编译统一搜索请求
- 再调用 `partner_search.search_profiles()` 搜索
- 如果配置了向量筛选，目前只支持基于性格/摘要语义做 include/exclude，不支持基于长相或照片语义做筛选

相关代码：

- `external-systems/partner-discovery-system/discovery_system/service_integrations.py`
- `match_domain/criteria_compiler.py`
- `partner_search/search_matching.py`
- `match_domain/vector_filter.py`

### 2.2 当前排序逻辑

当前候选人排序核心是：

`score = fit_score + confidence_score - risk_score`

其中：

- `fit_score`：条件匹配分
- `confidence_score`：资料可信度/完整度分
- `risk_score`：风险和缺失字段扣分

已纳入的照片相关信号只有：

- `photo_count`
- `photo_verification_level`

未纳入的照片相关信号包括：

- 颜值分
- 长相类型
- 眼缘偏好
- 照片风格语义
- 用户历史审美偏好

### 2.3 推荐系统链路

推荐系统并没有单独维护一套不同的匹配引擎，而是同样复用统一搜索编译和搜索逻辑：

- `build_effective_search_request()`
- `run_partner_search()`
- `partner_search.search_profiles()`

这意味着：

**只要底层搜索和排序支持照片特征，发现页和推荐系统都会天然继承。**

### 2.4 当前画像写入现状

当前发现页实时写画像逻辑是硬禁用的：

- `sync_requester_persona_memory()` 直接返回 disabled
- 实时对话阶段不会把新的偏好 patch 写入 persona

当前稳定可用的画像写入路径是：

1. 会话结束后
2. LLM 对用户对话做结构化提炼
3. 可量化字段写 `user_personas`
4. 不可量化字段写 `conversation_summaries + 向量库`
5. 不写 `profiles`

这个现状很重要，因为照片能力也应该遵循同样的设计原则：

**照片分析结果属于派生特征，不应直接写进正式 `profiles` 主表。**


## 3. 方案目标

本方案希望解决三个问题：

### 3.1 第一眼兴趣问题

系统需要知道：

- 这个候选人整体第一眼吸引力如何
- 是否会明显影响点击和继续了解意愿

### 3.2 长相类型表达问题

系统需要知道：

- 这个人属于什么长相类型
- 更偏成熟、清爽、温柔、阳光、精致还是斯文

### 3.3 用户个体审美问题

系统需要知道：

- 某个用户过去更喜欢哪类长相
- 同一张照片在不同用户眼里分数不一样

因此照片能力最终应拆成三层：

1. `平台基准眼缘分`
2. `长相语义表达`
3. `个体化照片偏好分`


## 4. 总体设计原则

### 4.1 不直接用原始照片做匹配

不在搜索链路里传照片本身，而是先把照片转成派生特征：

- 分数
- 标签
- 文本描述
- 向量

### 4.2 不把照片能力塞进正式资料表

照片分析结果应作为派生层存储，而不是正式资料事实。

### 4.3 不把照片做成唯一总分

照片应强影响排序，但不应一票否决所有条件匹配。

### 4.4 平台统一分和用户个体分同时存在

必须同时有两类分：

- 全局基础分
- 用户偏好修正分

### 4.5 Agent 只做理解层，不做实时批量照片排序

不能把照片方案设计成：

- 每次发现页搜索时让 agent 重新看一遍候选人照片
- 每次推荐刷新时让 agent 重新逐个判断长相和眼缘

原因：

- 成本高
- 延迟高
- 结果不稳定
- 不适合批量候选人排序

正确的职责分工应是：

- 照片上传时分析一次
- 把分析结果落库
- 搜索和推荐时直接复用
- agent 只负责理解、解释、调度

一句话：

**agent 可以做照片分析员，但不能做每次匹配现场看图的裁判。**


## 5. 数据层设计

## 5.1 新增表建议

建议新增一张独立表：

`profile_photo_features`

建议字段如下：

- `id`
- `profile_id`
- `primary_photo_id`
- `photo_set_version`
- `face_score_global`
- `appearance_score_global`
- `photo_quality_score`
- `photo_authenticity_score`
- `mature_score`
- `clean_score`
- `gentle_score`
- `sunny_score`
- `stylish_score`
- `appearance_summary`
- `appearance_tags_json`
- `appearance_embedding_status`
- `created_at`
- `updated_at`

如果需要支持多张图逐张分析，可再补一张明细表：

`profile_photo_feature_items`

字段可包括：

- `profile_id`
- `photo_id`
- `face_score_global`
- `quality_score`
- `authenticity_score`
- `appearance_tags_json`
- `appearance_summary`
- `is_primary`

### 5.2 为什么单独建表

原因：

- 这是算法派生结果，不是用户手填事实
- 可重算
- 可替换模型
- 可保留版本
- 不污染 `profiles`
- 和当前“会话结束后写 persona / summary，而不写 profiles”的体系一致


## 6. 照片分析产出

每次用户上传或更新照片后，异步执行照片分析，产出四类数据。

### 6.1 全局基础分

用于表达大众视角下的大致第一眼吸引力：

- `appearance_score_global`

建议范围：

- `0-100`

这个分不是给用户看的，只用于内部排序。

### 6.2 质量和可信度分

用于控制低质量照片的干扰：

- `photo_quality_score`
- `photo_authenticity_score`

用途：

- 防止模糊图、网图、过度修图污染排序
- 作为附加加分/扣分，不主导眼缘

### 6.3 长相风格维度分

建议先做少量稳定维度：

- `mature_score`
- `clean_score`
- `gentle_score`
- `sunny_score`
- `stylish_score`

这些分的意义不是“绝对好坏”，而是“偏哪种感觉”。

### 6.4 口语化长相描述

生成一段可以向量化的描述，例如：

- `看起来干净清爽，偏成熟稳重型，整体比较利落`
- `属于温柔耐看那一类，给人亲和感比较强`
- `更偏阳光有活力，第一眼比较精神`

同时生成：

- `appearance_tags_json`
- `appearance_embedding`

### 6.5 触发时机

照片分析不应发生在搜索请求过程中，而应在这些时机异步触发：

1. 用户首次上传照片
2. 用户替换主图
3. 用户新增照片
4. 用户删除照片
5. 模型版本升级后需要重算

这样做的目的很明确：

- 搜索更快
- 推荐更稳
- 结果可复用
- 不需要每次重新看图

### 6.6 Agent 在照片分析层的职责

agent 可以参与照片分析层，但职责要收敛。

适合 agent 做的事：

1. 生成口语化长相描述
2. 生成更自然的风格标签表达
3. 理解用户说的照片偏好
4. 生成推荐解释文案

不适合 agent 做的事：

1. 每次发现页搜索时重看 50 个候选人的照片
2. 每次推荐刷新时重新打眼缘分
3. 替代底层稳定的批量评分服务


## 7. 向量设计

## 7.1 新增向量类型

建议扩展当前向量体系，新增两类：

- `appearance_profile`
- `appearance_preference`

说明：

- `appearance_profile`：候选人长相语义向量
- `appearance_preference`：用户审美偏好向量

### 7.2 为什么复用现有向量体系

当前系统已经有：

- 向量存储
- 向量搜索
- 时间衰减
- include/exclude 过滤逻辑

所以照片能力不需要新造一套基础设施，只要扩展现有向量类型即可。

### 7.3 当前向量筛选的改造方向

当前 `vector_filter` 主要围绕：

- `personality_traits`
- `values`
- `partner_expectation`
- `emotional_needs`

后续可增加：

- `appearance_profile`

这样用户说：

- “想找成熟一点的”
- “不要太幼态的”
- “喜欢看起来干净利落的”

就可以直接走语义筛选。

### 7.4 Agent 和向量系统的关系

agent 更适合使用向量系统，而不是替代向量系统。

推荐关系是：

- 底层向量系统负责存和查
- agent 负责把用户自然语言翻译成向量筛选意图

例如：

- 用户说“我想找成熟一点的”
- agent 把它翻译成 `appearance_profile` 的 include 条件
- 真正筛选仍由底层 `vector_filter` 执行


## 8. 排序设计

## 8.1 当前排序不动骨架

保留当前主结构：

`score = fit_score + confidence_score - risk_score`

不要重写整套 `partner_search`，只增加照片相关的 bonus。

### 8.2 新增照片分层

建议新增三个照片相关分：

1. `photo_quality_bonus`
2. `photo_global_bonus`
3. `photo_preference_bonus`

最终总分：

`final_score = existing_score + photo_quality_bonus + photo_global_bonus + photo_preference_bonus`

其中：

- `existing_score` = 当前 `fit_score + confidence_score - risk_score`
- `photo_quality_bonus`：控制照片质量和可信度
- `photo_global_bonus`：平台基础眼缘分
- `photo_preference_bonus`：用户个体审美分

### 8.3 分值建议

建议初版控制在这个量级：

- `photo_quality_bonus`: `0 ~ 6`
- `photo_global_bonus`: `0 ~ 15`
- `photo_preference_bonus`: `-10 ~ 20`

这样照片有明显影响，但不会压过年龄、城市、婚况、目标这些硬逻辑。

### 8.4 为什么个体分权重可以更高

因为真实相亲里最重要的不是“谁普遍更好看”，而是：

**这个人是不是你喜欢的类型。**

所以：

- 全局分负责冷启动
- 个体分负责长期准确性

### 8.5 搜索阶段不重新看图

排序阶段只允许使用已经沉淀好的照片特征：

- `appearance_score_global`
- `photo_quality_score`
- `photo_authenticity_score`
- `appearance_summary`
- `appearance_profile embedding`
- `appearance_preference embedding`

明确不建议的方式：

- 搜索结果出来后，再让 agent 逐个候选人临场重读原始照片

因为这会导致：

- 发现页开场变慢
- 推荐刷新变慢
- 结果不稳定
- 线上成本失控


## 9. 动态个体偏好方案

### 9.1 核心思想

同一个候选人，在不同用户眼里的分数应该不同。

例如：

- A 用户一直偏爱成熟型
- B 用户一直偏爱清爽型
- C 用户一直偏爱阳光型

那么同一候选人的照片分应被动态修正。

### 9.2 行为信号来源

建议接入这些行为：

- 是否点击候选卡
- 是否查看详情
- 是否停留更久
- 是否表达感兴趣
- 是否发起聊天
- 是否持续聊天
- 是否快速跳过
- 是否明确说“不喜欢”

### 9.3 用户偏好画像构建

基于正负反馈，生成：

- 用户显式偏好标签分布
- 用户隐式审美偏好向量 `appearance_preference`

### 9.4 个体分计算

候选人侧已有：

- `appearance_embedding`

用户侧会逐步形成：

- `appearance_preference_embedding`

然后计算两者语义相似度，转成：

- `photo_preference_bonus`

这就是“喜欢成熟型的人，成熟类型分更高”的落地点。

### 9.5 冷启动策略

新用户没有历史行为时：

- 不依赖 agent 主观猜测其审美
- 先只用 `photo_global_bonus`
- 或少量接入显式偏好

行为样本逐步变多后：

- 再逐渐提高 `photo_preference_bonus` 权重

这样更稳，也更符合真实数据积累过程。


## 10. 接入发现页的方案

### 10.1 不改发现页总体架构

发现页仍然保持当前流程：

1. `profile + persona + working_criteria`
2. 编译搜索条件
3. `partner_search` 搜索
4. 返回前 5 个候选人

### 10.2 改造点

改造点在 `partner_search` 候选人 enrich 和评分阶段：

1. 搜索结果记录上补充 `profile_photo_features`
2. 在 `evaluate_candidate()` 内增加照片相关 bonus
3. 最终 `score` 使用新总分

这样：

- 发现页首屏结果自动带入照片逻辑
- “换一批”逻辑无需改
- 搜索编译器无需重写

### 10.3 用户感知

开场语“先看看有没有眼缘”会真正成立，不再只是文案。


## 11. 接入推荐系统的方案

推荐系统当前和发现页共用统一搜索/排序底座，因此只要底层支持照片分，推荐系统会自动继承。

接入方式：

1. 推荐刷新时走原有 `build_effective_search_request()`
2. `run_partner_search()` 调用底层搜索
3. 搜索结果已经包含照片分
4. 推荐卡排序自然体现照片能力

好处：

- 不需要单独维护推荐版照片逻辑
- 发现页和推荐系统保持同一套眼缘口径


## 12. 画像回流设计

## 12.1 候选人侧回流

候选人照片特征本身是静态派生特征，主要在照片更新时重算。

### 12.2 用户侧回流

用户审美偏好画像应通过行为回流形成。

建议新增一层用户偏好聚合：

- 正向样本：点击、感兴趣、聊天、持续互动
- 负向样本：快速跳过、明确拒绝

聚合结果可写入：

- 新的偏好表
- 或用户向量库中的 `appearance_preference`

### 12.3 和当前发现页会话写入关系

当前发现页实时 `sync_requester_persona_memory()` 是禁用的，因此：

- 照片偏好不要依赖实时 patch 写入
- 优先走行为日志聚合
- 如果后续恢复实时画像写入，再考虑支持显式审美偏好字段

### 12.4 Agent 在偏好回流中的职责

agent 可以帮助理解用户显式表达的偏好，例如：

- “喜欢成熟一点的”
- “不要太幼态的”
- “喜欢干净清爽型”

但 agent 不应成为主回流来源。

主回流来源仍应是：

- 点击
- 停留
- 感兴趣
- 开聊
- 持续互动
- 跳过
- 明确拒绝

因为行为数据比口头表达更稳定，也更适合长期建模。


## 13. 建议新增的数据对象

### 13.1 候选人照片特征表

`profile_photo_features`

### 13.2 用户照片偏好表

建议新增：

`user_appearance_preferences`

建议字段：

- `user_key`
- `profile_id`
- `preferred_mature_score`
- `preferred_clean_score`
- `preferred_gentle_score`
- `preferred_sunny_score`
- `preferred_stylish_score`

- `negative_sample_count`

### 13.3 行为样本表

如果当前行为流水不够细，可以新增：

`appearance_feedback_events`

记录：

- `user_key`

- `event_weight`
- `scene`
- `created_at`


## 14. 算法流程

### 14.1 候选人侧流程

1. 用户上传或更新照片
2. 异步触发照片分析
3. 生成分数、标签、描述、向量
4. 存入 `profile_photo_features`

### 14.2 用户侧流程

1. 用户浏览发现页或推荐卡
2. 记录点击、停留、跳过、感兴趣、聊天等行为
3. 聚合为用户审美偏好画像
4. 生成 `appearance_preference_embedding`

### 14.3 搜索阶段流程

1. 结构化条件做硬筛
2. `partner_search` 读取候选人基础记录
3. enrich 候选人照片特征
4. 计算当前用户对候选人的个体照片偏好分
5. 合并到最终排序

### 14.4 Agent 参与流程

agent 应参与的位置：

1. 照片更新后，辅助生成口语化长相描述
2. 用户表达照片偏好时，把自然语言翻译成系统条件
3. 推荐解释时，基于已有照片特征生成话术

agent 不应参与的位置：

1. 每次搜索的底层批量候选人打分
2. 每次推荐刷新的实时照片分析

最终推荐流程应是：

1. 底层服务先准备好照片特征
2. 搜索排序服务直接算分
3. agent 最后决定如何理解和解释给用户听


## 15. 详细打分建议

### 15.1 平台基础眼缘分

输入：

- 候选人照片特征

输出：

- `appearance_score_global`

建议作用：

- 冷启动排序
- 同类候选人之间拉开差距

### 15.2 质量分

输入：

- 清晰度
- 真人度
- 照片数量
- 照片一致性

输出：

- `photo_quality_bonus`

### 15.3 用户偏好分

输入：

- 候选人 `appearance_embedding`
- 用户 `appearance_preference_embedding`

输出：

- `photo_preference_bonus`

建议优先级：

`用户偏好分 > 平台基础分`

因为真实相亲更看“对不对胃口”，不是统一审美。


## 16. 风险控制

### 16.1 不做公开颜值分

内部可以有基础眼缘分，但不要对用户展示。

### 16.2 不做敏感推断

不要把以下信息作为照片匹配标签：

- 种族
- 疾病/残障
- 宗教
- 贫富判断
- 极细的年龄判断

### 16.3 不做冒犯性描述

口语化长相描述必须克制。

允许：

- 干净
- 清爽
- 温柔
- 成熟
- 阳光
- 斯文
- 精致

避免：

- 普通
- 显老
- 土
- 丑
- 网红脸
- 不上镜

### 16.4 不让照片一票否决全部匹配

照片权重要强，但不能让系统退化成纯刷脸。

### 16.5 不让 agent 输出漂移的照片判断

需要约束：

- agent 可以复用已有照片描述
- agent 可以做语言转译
- agent 不应在没有特征底座时自由发挥“这个人长相如何”

否则容易出现：

- 同一个人多次描述不一致
- 推荐解释口径漂移
- 线上结果不可复现


## 17. 上线顺序

### 第一期：照片基础分和语义

目标：

- 新增候选人照片分析层
- 新增 `appearance_score_global`
- 新增 `appearance_summary`
- 新增 `appearance_embedding`
- 接入发现页和推荐排序

特点：

- 无个性化
- 先解决“系统完全不看图”的问题
- 不让 agent 进入实时排序主链路

### 第二期：用户动态偏好

目标：

- 接入点击/跳过/聊天行为
- 构建 `appearance_preference_embedding`
- 计算个体偏好分

特点：

- 让系统从“平台觉得谁顺眼”升级到“这个用户会喜欢谁”

### 第三期：照片语义检索和可解释偏好

目标：

- 支持“找成熟一点的”“不要太幼态”的语义筛选
- 支持审美偏好聚类和实验

### 第四期：Agent 驱动的解释和语义调度增强

目标：

- 支持用户自然语言表达照片偏好
- 让 agent 基于已有照片特征生成更像红娘的话术解释

注意：

- 这一期增强的是交互和表达
- 不是把底层照片排序重新交给 agent

### 18.1 数据层

### 18.2 搜索层

新增逻辑：

### 18.4 行为层

## 19. 最终结论

当前系统的问题不是“没有搜索引擎”，而是：

**已有完整的结构化匹配和向量能力，但缺少一层照片派生特征。**

最顺的方案不是重写匹配系统，而是：

1. 把照片变成 `分数 + 描述 + 标签 + 向量`
2. 把这些特征挂到候选人侧
3. 把用户行为沉淀成照片偏好画像
4. 在现有 `partner_search` 排序里增加照片 bonus
5. 让发现页和推荐系统自动复用
6. 让 agent 只负责理解、调度和解释，不负责每次现场看图打分

一句话总结：

**照片不应该直接进入匹配，应该先转成“眼缘分”和“长相语义”，再进入现有搜索、排序和向量系统；agent 负责使用这些结果，而不是替代这套底层能力。**
