# 照片接入发现页与推荐完整方案

## 1. 先说结论

当前系统已经不是“完全不看照片”了。

现在真实状态是：

- 画像主链路已经比较成熟
- 发现页和推荐系统共用一套搜索排序底座
- 照片分已经能进入排序
- 用户照片偏好也已经有最小闭环骨架

真正还没补齐的，不是“要不要把照片接进排序”，而是下面三件事：

1. 照片特征怎么稳定产出
2. 用户审美偏好怎么基于正负反馈持续重建
3. 照片语义向量怎么真正接入筛选和召回

一句大白话：

**现在系统已经有“吃照片分”的嘴了，但“稳定生产照片分”的厨房还没完全建好。**


## 2. 当前真实链路梳理

### 2.1 画像写入主链路

当前稳定在跑的画像写入，不是发现页实时 patch，而是“会话结束后统一提炼”。

主流程是：

1. 会话结束
2. 读取本轮增量消息
3. LLM 产出结构化总结
4. 可量化内容写 `user_personas`
5. 不适合结构化落字段的内容写 `conversation_summaries`
6. 再把摘要文本做合并和向量化

对应代码：

- `match_domain/session_end_processor.py`
- `match_domain/ai_merge_handler.py`
- `persona_memory_sync/persona_memory_lib.py`

### 2.2 数据分别写到哪里

现在画像相关数据不是只写一个地方，而是三层：

1. `user_personas`
2. `conversation_summaries`
3. 向量库

大白话理解：

- `user_personas` 放比较像“字段”的东西
- `conversation_summaries` 放比较像“摘要”的东西
- 向量库放“以后方便语义检索”的东西

### 2.3 是否同步回正式资料表

`apply_persona_patch()` 会 upsert `user_personas`，也会写 `user_persona_observations`。

但它不是默认什么都同步到 `profiles`，只有特定 scope 才会做有限同步。

这点很重要，因为照片分析结果也应该遵循同样原则：

**照片结果属于派生特征，不应该污染正式 `profiles` 主表。**

### 2.4 发现页搜索主链路

发现页不是单独写死推荐，而是先把用户当前搜索意图编译成统一请求，再走底层搜索。

主流程是：

1. 读取 `profile + persona`
2. 合并本轮 `working_criteria`
3. `build_discovery_search_request()`
4. 调 `partner_search.search_profiles()`
5. 返回排序后的候选人

对应代码：

- `match_domain/criteria_compiler.py`
- `external-systems/partner-discovery-system/discovery_system/service_integrations.py`
- `partner_search/search_runtime_helpers.py`

### 2.5 推荐系统主链路

推荐系统也不是另一套独立匹配引擎。

它走的是：

1. `build_effective_search_request()`
2. `run_partner_search()`
3. `partner_search.search_profiles()`

所以只要底层搜索排序支持照片，发现页和推荐系统都会一起继承。

对应代码：

- `match_domain/criteria_compiler.py`
- `external-systems/partner-recommendation-system/recommendation_system/subscriptions.py`


## 3. 当前照片能力真实状态

### 3.1 已经落地的部分

这部分不是设想，是仓库里已经有的代码。

#### 3.1.1 表结构已经有了

已新增三张表：

- `profile_photo_features`
- `user_appearance_preferences`
- `appearance_feedback_events`

对应代码：

- `db_migrations/targets/persona/m0014_add_photo_matching_tables.py`

#### 3.1.2 访问层已经有了

现在已经支持：

- 读取候选人照片特征
- 读取用户审美偏好
- 写照片反馈事件
- upsert 用户审美偏好聚合结果

对应代码：

- `profile_service/api.py`

#### 3.1.3 搜索时已经会吃照片特征

`partner_search` 现在已经会：

- 按 `requester_id + persona_source` 加载当前用户照片偏好
- 给候选人 enrich 照片特征
- 在打分阶段把照片 bonus 加进总分

对应代码：

- `partner_search/search_candidates.py`
- `partner_search/search_runtime_helpers.py`
- `partner_search/search_matching.py`
- `match_domain/appearance_features.py`

#### 3.1.4 发现页正反馈已经回流

当前 `express_interest` 已经会：

- 记录 `appearance_feedback_events`
- 用当前候选人的照片特征重建一次用户照片偏好

对应代码：

- `external-systems/partner-discovery-system/discovery_system/service.py`

### 3.2 还没闭环的部分

这部分才是接下来真正该做的重点。

#### 3.2.1 缺照片特征生产任务

我没有看到完整的“上传照片后自动分析并写入 `profile_photo_features`”生产链路已经成熟落地。

也就是说：

- 表有了
- 排序入口有了
- 但稳定产出特征的任务还没真正闭环

#### 3.2.2 负反馈还不完整

现在最明确接上的是正反馈：

- `express_interest`

但还缺这些更关键的负向或弱正向信号：

- 跳过
- 快速划过
- 只看不点
- 看详情但没后续
- 聊了两句就断

#### 3.2.3 偏好重建还偏轻

当前偏好回流更像：

- 看到一次正反馈
- 立刻拿这次候选人的照片特征去更新偏好

这能跑，但还不够稳。

更成熟的做法应该是：

- 汇总历史事件
- 按事件强弱加权
- 定期重建偏好

#### 3.2.4 照片语义向量还没真正跑通

虽然文档和设计里已经提到：

- `appearance_profile`
- `appearance_preference`

但我没确认到它像摘要向量那样，已经完整接入现有向量类型、向量写入、筛选执行链路。


## 4. 对之前照片方案的修正

### 4.1 哪些方向还是对的

之前提的这几个大方向仍然是对的：

1. 给照片形成内部基础分
2. 把长相整理成口语化描述
3. 让用户形成动态审美偏好
4. 不让 agent 在每次搜索时现场看图裁判

### 4.2 哪些地方要改

之前方案最大的问题不是方向错，而是把现状看得太“从零开始”。

现在应该改成：

- 不是“从零把照片接进排序”
- 而是“在已有照片排序骨架上，把生产层和偏好闭环补齐”

一句大白话：

**不是重建房子，是先把已经盖好的楼层认清楚，再补没封顶的地方。**


## 5. 修正版整体方案

### 5.1 总目标

目标不是做“颜值决定一切”的系统。

目标是做三层照片能力：

1. 平台基础眼缘分
2. 长相风格语义表达
3. 用户个体审美偏好分

### 5.2 总体原则

#### 5.2.1 不在搜索时临场看原图

照片必须提前分析，搜索时只复用结果。

不能做成：

- 每次发现页搜索都让 agent 重看一遍照片
- 每次推荐刷新都重新判断谁更顺眼

#### 5.2.2 不把照片分析结果写进 `profiles`

这些东西都属于派生结果：

- 分数
- 标签
- 描述
- 向量

应该存派生表、摘要层、向量层，而不是正式资料事实层。

#### 5.2.3 照片强影响排序，但不能一票否决

真实相亲确实先看眼缘，但最终不能退化成纯刷脸。

所以照片分应该是强 bonus，不是唯一主分。


## 6. 推荐的目标形态

### 6.1 候选人侧沉淀什么

每个候选人最终都应该稳定沉淀这些照片特征：

- `appearance_score_global`
- `photo_quality_score`
- `photo_authenticity_score`
- `mature_score`
- `clean_score`
- `gentle_score`
- `sunny_score`
- `stylish_score`
- `appearance_summary`
- `appearance_tags_json`
- `appearance_profile_embedding`

### 6.2 用户侧沉淀什么

每个用户最终都应该沉淀这些照片偏好信息：

- 显式偏好维度
- 历史行为正负样本统计
- 维度加权后的偏好中心
- `appearance_preference_embedding`

### 6.3 搜索排序怎么用

当前总分骨架不用推翻。

现有主逻辑还是：

`score = fit_score + confidence_score - risk_score`

照片部分继续作为 bonus 叠加进去，只是后面要把 bonus 算得更完整。

建议拆成三类：

1. `photo_quality_bonus`
2. `photo_global_bonus`
3. `photo_preference_bonus`


## 7. 分阶段改进方案

### 7.1 第一优先级：补照片特征生产层

这是当前最该做的，不是因为它最炫，而是因为没有稳定生产层，后面一切都是空转。

要补的核心能力：

1. 照片上传/替换/删除后的异步触发
2. 主图选择
3. 基础质量和真实性评分
4. 长相风格维度评分
5. 口语化长相描述生成
6. 写入 `profile_photo_features`
7. 状态机和重算机制

### 7.2 第二优先级：补完整行为回流

现在只有最小正反馈，远远不够。

要补：

1. `skip`
2. `quick_pass`
3. `detail_view`
4. `chat_started`
5. `chat_continued`
6. `explicit_dislike`

这些事件不是都同权，必须有权重。

大白话：

“看了一眼就划走”和“聊了三天”不能算成同一种喜欢。

### 7.3 第三优先级：把偏好重建从即时改成历史聚合

建议不要只靠“来一次喜欢，就往那个人脸上靠一点”。

更稳的方式是：

1. 记录所有行为事件
2. 设定事件权重
3. 周期性聚合历史正负样本
4. 重建 `user_appearance_preferences`
5. 必要时生成 `appearance_preference_embedding`

### 7.4 第四优先级：补照片语义向量路径

后面用户一定会说这种话：

- 想找成熟一点的
- 喜欢干净清爽型
- 不要太幼态

这类需求只靠结构化分数不够。

所以要补：

1. `appearance_profile`
2. `appearance_preference`
3. `vector_filter` 对照片语义的 include/exclude
4. 对自然语言照片偏好的翻译能力

### 7.5 第五优先级：补 agent 理解和解释层

agent 后面应该主要做三件事：

1. 理解用户说的照片偏好
2. 翻译成系统可执行条件
3. 基于已有照片特征生成解释文案

agent 不应该做的是：

- 每次批量候选人实时看图排序


## 8. 动态分数该怎么理解

你前面提的想法是对的：

如果 A 用户一直喜欢成熟型，那成熟型在 A 这里就应该更高分。

更准确地说，不是“成熟本身更高分”，而是：

**成熟这个维度和 A 的历史偏好更接近，所以 A 看这个人时的 `photo_preference_bonus` 更高。**

大白话：

- 平台基础分回答“多数人第一眼觉得怎么样”
- 个体偏好分回答“这个用户会不会更喜欢”

所以同一个候选人，在不同用户那里，照片分本来就应该不一样。


## 9. 为什么现在这个方向合理

因为它和现有仓库结构是顺的。

### 9.1 顺画像体系

现在系统本来就是：

- 正式资料放事实
- persona 放结构化理解
- summaries 放摘要
- vector 放语义检索

照片能力加进来，也应该继续走“派生层 + 检索层”，而不是塞回 `profiles`。

### 9.2 顺发现页和推荐共用底座

既然发现页和推荐本来就共用 `partner_search`，那照片能力继续从底层搜索统一接入最省事，也最不容易分叉。

### 9.3 顺已经落地的照片骨架

现在已经有：

- 表
- 访问层
- 排序 bonus
- 最小正反馈

所以最合理的不是推翻重来，而是继续补闭环。


## 10. 风险控制

### 10.1 不做公开颜值分

内部可以有基础眼缘分，但不要对用户展示。

### 10.2 不做敏感属性推断

不要基于照片输出这些东西：

- 种族
- 疾病
- 宗教
- 贫富判断
- 过细的年龄推断

### 10.3 不做冒犯性描述

允许的描述应该偏中性、克制、可复用，比如：

- 干净
- 清爽
- 温柔
- 成熟
- 阳光
- 斯文
- 精致

不要出现：

- 丑
- 土
- 显老
- 普通
- 网红脸

### 10.4 不让照片压死硬条件

年龄、城市、婚况、关系目标这些硬条件，仍然要有足够权重。


## 11. 最终结论

当前系统已经不是“照片完全没参与匹配”，而是已经具备：

- 照片排序消费层
- 用户照片偏好读取层
- 最小正反馈闭环

真正缺的是：

- 照片特征生产层
- 更完整的用户正负反馈闭环
- 历史聚合后的偏好重建
- 照片语义向量筛选能力

所以后续重点不应该再放在：

- “要不要把照片接进排序”

而应该放在：

1. 照片特征如何稳定产出
2. 用户审美偏好如何持续重建
3. 照片语义能力如何补进现有向量系统

一句话总结：

**现在不是从零做照片匹配，而是在已经接入排序的基础上，把照片生产、偏好闭环和语义检索三层补完整。**

这一节补的是更上层的产品与检索方案。

## 13. 用户按外貌找人，应该拆成哪几类

用户基于外貌的搜索，不建议混成一个“颜值搜索”。

更合理的拆法是四类：

1. 找我觉得顺眼/漂亮的
2. 找像某个人的
3. 找某种明确五官或脸部属性的
4. 找某种整体气质或风格的

对应用户说法：

- “给我找好看的”
- “找像田曦薇的”
- “想找眼睛大的、偏幼态的”
- “想找阳光一点、清爽一点的”

这四类底层不是一套能力，不能混着做。

### 13.1 第一类：找顺眼/漂亮的

这一类的核心不是“客观美貌真理”，而是排序。

它应该由三层分数组成：

1. `photo_usability_score`
2. `appearance_score_global`
3. `appearance_preference_score`

分别回答三个问题：

- 这组照片能不能用于判断外貌
- 大众审美下第一眼大致顺不顺眼
- 这个用户自己会不会更喜欢

大白话：

- 第一层解决“照片糊不糊、假不假、脸都看不清”
- 第二层解决“普遍来看顺不顺眼”
- 第三层解决“你个人更偏爱哪一挂”

这里不建议产品上直接公开“颜值分”。

更稳妥的对内概念是：

- 平台基础外貌分
- 用户个体审美分

更稳妥的对外表达是：

- 眼缘分
- 外貌匹配度
- 你可能会喜欢

### 13.2 第二类：找像某个人的

这一类是标准的人脸相似检索。

适合这些请求：

- “找像田曦薇的”
- “找像刘亦菲的”
- “找像我发这张图的”

核心不是审美排序，而是：

**人脸 identity similarity。**

推荐链路：

1. 人脸检测与对齐
2. 人脸特征向量提取
3. 候选人多脸向量存储
4. Top-K 相似召回

推荐实现：

- 检测与关键点：`RetinaFace` 或 `MTCNN`
- 人脸 embedding：`InsightFace / ArcFace`
- 向量库：**统一使用现有 Milvus**（避免两套向量库冗余）
  - 新增 `face_embedding` 向量类型
  - 新增 `appearance_profile` 向量类型
  - 与现有 `conversation_summary` 向量类型共存
- 检索指标：`Cosine Similarity` 或 `L2`

这一类强烈建议支持两种输入：

1. 明星官方参考图库
2. 用户上传参考图

因为“像谁谁”的最终稳定输入，往往不是文本，而是图。

### 13.3 第三类：找五官或脸部属性

这一类不是“像某个人”，而是属性检索。

适合这些请求：

- “找眼睛大的”
- “找圆脸的”
- “找偏幼态的”
- “找成熟一点的”

这一类不建议直接复用第二类的人脸 identity embedding。

原因很简单：

- identity embedding 优先保留“是谁”
- 不保证“眼睛大”“鼻子高”“幼态感”这种局部或复合属性在向量空间里可稳定检索

这类更适合做成：

1. 显式属性分
2. 复合外貌标签分

建议沉淀的属性层：

- `eye_size_score`
- `face_roundness_score`
- `jaw_softness_score`
- `midface_fullness_score`
- `youthfulness_score`
- `mature_score`

其中“幼态”最好不要当成单一字段理解。

它本质上是一个复合标签，通常由这些信号共同构成：

- 眼睛占比
- 脸部比例
- 下颌线圆润度
- 面中饱满度
- 成熟感低
- 清透感高

所以“偏幼态”更适合产品化为：

- `幼态感分`
- `甜妹感分`
- `明媚感分`
- `清冷感分`

### 13.4 第四类：找整体气质或风格

这一类是当前仓库最容易顺接的方向。

适合这些请求：

- “找阳光一点的”
- “找清爽一点的”
- “找温柔挂的”
- “找有少年感的”

这一类的核心不是身份相似，而是：

**整体风格语义检索。**

最适合的底层表示是：

1. 风格维度分
2. 外貌摘要文本
3. 风格语义向量

这和当前仓库已经有的能力最接近：

- `clean_score`
- `gentle_score`
- `sunny_score`
- `stylish_score`
- `appearance_summary`
- `appearance_profile`


## 14. 发现页应该怎么给入口

发现页不应该只支持一个模糊的“上传图片搜索”按钮。

更好的做法是明确拆成两个用户入口：

1. `找像这张脸的`
2. `找这种感觉的`

### 14.1 找像这张脸的

用户预期是：

- 长得像
- 脸型像
- 五官组合像

底层走第二类链路：

- 人脸检测
- 对齐
- face embedding
- 相似召回

### 14.2 找这种感觉的

用户预期是：

- 整体气质像
- 风格像
- 拍照感觉像
- 妆发穿搭和氛围像

底层走第三类和第四类链路：

- 外貌属性提取
- 风格语义提取
- 属性筛选
- 风格向量检索

这样拆的好处是：

- 用户认知清楚
- 结果解释清楚
- 技术目标不会混掉

如果只给一个“上传图片搜索”，很容易出现：

- 用户以为在找长得像
- 系统实际上给的是风格像
- 最后用户会觉得“不准”


## 15. 完整数据与特征分层

外貌搜索建议拆成五层数据。

### 15.1 原始层

保存原始媒体事实：

- `profile_photos`
- `avatar_url`
- 原始上传记录
- 照片审核状态

这一层只保存事实，不保存判断。

### 15.2 质量层

回答“这张图能不能用”：

- 清晰度
- 人脸是否足够清楚
- 单人/多人
- 遮挡程度
- 真实性风险
- 是否适合做主图

建议字段：

- `photo_usability_score`
- `single_face_confidence`
- `face_visibility_score`
- `photo_authenticity_score`
- `primary_photo_candidate_score`

### 15.3 平台基础外貌层

回答“大众审美下第一眼大致怎样”：

- `appearance_score_global`
- `clean_score`
- `gentle_score`
- `sunny_score`
- `stylish_score`
- `mature_score`

必要时后续可扩展：

- `youthfulness_score`
- `sweetness_score`
- `coolness_score`
- `intellectual_score`

### 15.4 结构化属性层

回答“有没有某种具体脸部属性”：

- 眼睛大小
- 脸型圆润度
- 下颌线柔和度
- 面中饱满度
- 幼态感

这一层主要服务：

- 筛选
- 规则排序
- 明确条件解释

### 15.5 语义层

回答“系统怎么用人话描述这组照片”：

- `appearance_summary`
- `appearance_tags_json`
- `appearance_profile_embedding`

这一层主要服务：

- 用户自然语言搜索
- 风格检索
- Agent 解释文案


## 16. 完整召回与排序架构

外貌搜索不应该只有一层。

推荐拆成四段：

1. 基础候选池过滤
2. 外貌专项召回
3. 综合重排
4. 解释与反馈回流

### 16.1 第一段：基础候选池过滤

先走现有硬条件：

- 性别
- 年龄
- 城市
- 婚况
- 关系目标
- 活跃度
- 认证状态

这一层的作用是：

**先排除明显不合适的人。**

不能一上来就全库做人脸相似搜索再硬塞回前台。

### 16.2 第二段：外貌专项召回

根据用户请求类型选择召回器。

#### A. 顺眼/漂亮

不是单独召回器，更像候选池上的强排序信号。

#### B. 像某个人

使用人脸向量召回：

- 查询向量：参考图 face embedding
- 返回：Top-K 相似候选人

候选人有多张图时，候选人级别相似度建议取：

- `max_similarity`
或
- `top2_avg_similarity`

避免因为某一张偶然神似导致误召回。

#### C. 五官/脸部属性

使用属性筛选与属性排序：

- 显式阈值过滤
- 多属性加权排序

例如“眼睛大 + 偏幼态”：

- `eye_size_score >= threshold`
- `youthfulness_score >= threshold`
- 再按综合外貌分排序

#### D. 整体气质/风格

使用语义向量召回与标签召回：

- `appearance_profile` 向量检索
- `appearance_tags_json` 标签召回

### 16.3 第三段：综合重排

最终展示顺序，不能只看外貌专项分。

建议总分结构：

`final_score = base_match_score + appearance_bonus + preference_bonus + trust_bonus - risk_penalty`

拆开理解：

- `base_match_score`
  - 性别、年龄、城市、关系目标、婚况等基础适配
- `appearance_bonus`
  - 平台基础外貌分
  - 外貌专项检索分
- `preference_bonus`
  - 用户个体审美分
- `trust_bonus`
  - 认证、真实照片、资料完整度
- `risk_penalty`
  - 假图风险、多人图风险、资料风险

一句大白话：

**图像搜索负责把可能对的人捞出来，综合重排负责把真正适合展示的人排上来。**

### 16.4 第四段：解释与反馈回流

排序完成后，系统还要能解释为什么给你看这个人。

解释口径建议统一成三类：

1. 基础匹配解释
2. 外貌解释
3. 个体偏好解释

例如：

- “同城，关系目标一致”
- “照片整体更清爽、阳光”
- “长相类型更贴近你最近常点喜欢的那一挂”


## 17. 新用户和老用户的分层策略

“找漂亮的”这类需求，新用户和老用户不能同权处理。

### 17.1 新用户

新用户没有行为历史时：

- 主要吃 `photo_usability_score`
- 再吃 `appearance_score_global`
- 少量吃显式外貌偏好

也就是：

**平台基础外貌分权重大。**

### 17.2 老用户

老用户已经有足够正负反馈时：

- 继续保留基础外貌分
- 逐步提升个体审美分权重
- 允许“不是普遍最高颜值，但更符合这个用户口味”的人排上来

也就是：

**用户个体审美分权重逐渐变大。**


## 18. 用户行为回流应该怎么设计

为了让“顺眼”和“我喜欢这挂”越来越准，外貌反馈不应该只记录喜欢。

建议分成五类事件：

1. 强正反馈
2. 弱正反馈
3. 中性反馈
4. 弱负反馈
5. 强负反馈

### 18.1 强正反馈

- `express_interest`
- `save`
- `direct_greet`
- `chat_started`
- `chat_continued`

### 18.2 弱正反馈

- `detail_view`
- 长时间停留
- 看完多张图

### 18.3 中性反馈

- 只浏览一眼
- 没有明显动作

### 18.4 弱负反馈

- `skip`
- `quick_pass`

### 18.5 强负反馈

- `explicit_dislike`
- 明确标“不喜欢这类”

然后按事件强度做历史聚合，重建：

- `user_appearance_preferences`
- `appearance_preference_embedding`

### 18.6 候选卡片点击，需警惕”标题党”陷阱与幸存者偏差

**核心风险：点击率≠真实吸引力**

用户在发现页点击某个候选卡片，确实意味着：
- 这张卡第一眼吸引了她
- 至少愿意进一步看看

但如果直接将”点击”视为外貌正反馈，存在严重风险：

#### A. 幸存者偏差问题

实际业务中，点击率（CTR）高的封面图往往具备这些特征：
- **过度修图**：磨皮、美白、滤镜夸张
- **过度暴露**：衣着、姿势刻意吸引眼球
- **奇特构图**：非常角度、非常表情
- **标题党式呈现**：封面与真实长相差距大

如果将这些点击直接作为外貌偏好学习输入：
- 系统会迅速收敛到”给用户推荐修图最夸张的人”
- 正常、真实、不夸张的用户被边缘化
- 形成**劣币驱逐良币**：真实照片的人曝光越来越少

#### B. 改进方案：点击后行为校正

点击本身只作为”注意力信号”，必须结合后续行为进行加权校正：

| 行为组合 | 最终判定 | 理由 |
|---------|---------|------|
| 点击 + 停留 < 2秒 + 退出 | **弱负反馈** | 点击后发现”被骗”，快速逃离 |
| 点击 + 停留 2-5秒 + 简单浏览 | **中性信号** | 看了但不感兴趣 |
| 点击 + 停留 > 5秒 + 看多张图 | **弱正反馈** | 真实感兴趣，愿意多看 |
| 点击 + 停留 > 10秒 + 看完资料 | **中正反馈** | 认真感兴趣 |
| 点击 + 停留后 + express_interest | **强正反馈** | 明确喜欢 |

#### C. Quick Bounce 检测机制

建议引入”快速反弹”检测：

```
if click_and_exit_duration_ms < 2000:
    # 点击后停留少于2秒立刻退出
    feedback_type = “quick_bounce”
    feedback_weight = -0.3  # 弱负反馈
    feedback_reason = “封面吸引但内容不符预期”
```

这种情况说明：
- 封面图确实吸引了注意力（标题党成功）
- 但点进去后发现与预期不符（真实长相不够吸引）

系统应该学习：
- **负向信号**：这类封面图风格的”虚假吸引力”
- **而不是正向信号**：用户喜欢这类长相

#### D. 点击质量分层

建议将点击分为三层质量：

| 层级 | 定义 | 行为特征 | 学习权重 |
|------|------|---------|---------|
| **高质量点击** | 真实兴趣 | 停留 > 10秒 + 看多图 + 有后续动作 | +1.0 |
| **中质量点击** | 犹豫观望 | 停留 5-10秒 + 看完资料但无后续 | +0.3 |
| **低质量点击** | 快速反弹 | 停留 < 2秒 + 立刻退出 | -0.3 |

#### E. 防止劣币驱逐良币的机制

为避免系统过度推荐”标题党”封面图：

1. **封面图真实性评分**
   - 检测封面图的修图程度、滤镜强度
   - 过度修图的封面图，点击权重降级

2. **封面与详情一致性评分**
   - 比较封面图与详情页其他照片的一致性
   - 封面图与其他照片差异过大，点击权重降级

3. **用户反馈熔断机制**
   - 如果某用户多次出现”点击后Quick Bounce”
   - 系统应该降低该用户对类似封面图的敏感度

大白话：

**点击本身是”注意力信号”，不是”兴趣信号”。**
**只有点击后有持续行为，才是真实兴趣。**
**点击后快速退出，应该逆转为负反馈，避免系统学习”标题党”。**

### 18.7 未点击也有参考价值，但只能算弱负信号

“没有点击某个候选卡片”，确实往往意味着第一眼不够吸引。

但它不能被粗暴地直接解释为“用户不喜欢这类长相”。

因为未点击可能还有这些原因：

- 用户滑得很快
- 卡片位置靠后，根本没认真看到
- 同屏有更吸引的卡片
- 封面图不够好，但人本身未必不行

所以更合理的做法是：

- `点击` 视为弱正反馈
- `未点击` 视为弱负信号
- 只有在足够曝光且明显看过之后仍未点击，负向权重才上升

建议新增这些行为字段：

- `card_impression_count`
- `card_visible_duration_ms`
- `card_click`
- `detail_view_duration_ms`
- `photo_swipe_count`
- `return_view_count`

### 18.8 停留时长是重要的犹豫与兴趣信号

卡片停留时长和详情停留时长，都应该纳入外貌偏好学习。

它们往往说明的不是“明确喜欢”，而是：

- 第一眼有兴趣
- 正在认真看
- 有吸引力但还没下决定

建议解释方式：

- 极短停留：弱负信号
- 中等停留：中性或弱正信号
- 长停留并继续看图/看详情：中正反馈

一句大白话：

**停留时长代表“这个人有没有让我多看两眼”。**

### 18.9 行为学习不应该只有二元喜欢/不喜欢

最终不建议只做：

- 喜欢
- 不喜欢

而应该构建一个连续的外貌兴趣信号：

`appearance_interest_signal = exposure + dwell + click + detail_view + photo_depth + explicit_action`

这样系统学到的不是“你喜不喜欢某个人”，而是：

**你会不会被这类长相吸引、会不会愿意多看、会不会进一步行动。**


## 19. 发现页上传图片搜索的完整产品链路

这一节给一条完整的用户链路。

### 19.1 用户操作

用户在发现页点击：

- 上传图片搜索

然后选择模式：

1. 找像这张脸的
2. 找这种感觉的

### 19.2 系统处理

#### 模式一：找像这张脸的

1. 上传参考图
2. 做人脸检测与对齐
3. 抽 face embedding
4. 去 face 向量索引做 Top-K 召回
5. 拿回候选人 id 列表
6. 再走基础条件过滤与综合重排
7. 前台展示结果

#### 模式二：找这种感觉的

1. 上传参考图
2. 提取外貌风格分和语义摘要
3. 生成风格向量
4. 去 `appearance_profile` 做语义召回
5. 再叠加基础条件与个体偏好重排
6. 前台展示结果

### 19.3 前台展示

结果页建议明确告诉用户当前模式：

- `当前按“像这张脸”搜索`
或
- `当前按“这种感觉”搜索`

这样用户不会把两种能力混淆。


## 20. 底层存储建议

### 20.1 现有结构应继续保留

当前仓库里已有这些对象：

- `profile_photo_features`
- `user_appearance_preferences`
- `appearance_feedback_events`
- `appearance_profile`
- `appearance_preference`

这部分应继续作为：

- 平台基础外貌分
- 风格语义层
- 个体偏好层

的主承载。

### 20.2 需要新增的人脸相似检索层

为了支持“像田曦薇”这类需求，建议新增候选人 face 向量索引。

建议拆成单独层，不和现有 `appearance_profile` 混用。

原因：

- `appearance_profile` 是风格语义
- face embedding 是身份相似

两者目标完全不同。

建议新增逻辑对象：

- `profile_face_embeddings`
- `reference_face_search_jobs`
- `candidate_face_vector_index`（**存储在现有 Milvus 中，新增向量类型**）

**关键原则**：

- **统一使用现有 Milvus 向量库**
- 新增向量类型：`face_embedding`、`appearance_profile`
- 与现有向量类型共存：`conversation_summary`、`appearance_preference`
- **避免两套向量库（Milvus + FAISS）冗余**
- **降低运维成本和数据同步复杂度**

### 20.3 需要新增的结构化属性层

为了支持“眼睛大”“幼态感强”这类需求，建议新增属性层。

建议对象：

- `profile_face_attributes`

其中保存：

- 显式属性分
- 复合外貌标签分
- 属性提取模型版本

### 20.4 需要新增的认证人脸锚点层

为了让外貌搜索更真实、更可信，建议把身份认证里的人脸单独沉淀成“真人锚点层”。

原因：

- 身份认证人脸真实性更高
- 身份认证人脸身份一致性更高
- 它虽然不一定最好看，但更接近“这个人真实长相的稳定表示”

建议新增逻辑对象：

- `verified_face_anchors`
- `verified_face_embeddings`
- `verified_face_metadata`

这一层不负责“展示最好看的照片”，而负责：

- 真实性锚定
- face embedding 的可信 reference
- 后续一致性校验

大白话：

**认证脸不是最精致的脸，但它是最可信的真人底座。**

### 20.5 资料照和认证锚点要分开存、分开用

建议明确区分两套表示：

1. `profile_photo_representation`
2. `verified_face_anchor`

前者负责：

- 第一眼展示
- 风格表达
- 外貌吸引力

后者负责：

- 真实性
- 身份一致性
- 更稳定的人脸底座

不建议用认证脸直接替代资料照片排序。

因为认证脸通常：

- 更素
- 光线更普通
- 用户未必有妆发与表达管理

所以认证脸更适合做”锚点”，不适合直接做”展示最优图”。

### 20.6 为什么统一使用 Milvus（架构简化关键决策）

**核心问题**：

如果采用两套向量库（FAISS + Milvus）并存，会带来这些问题：

| 问题维度 | 具体影响 |
|---------|---------|
| **运维成本** | 需要同时维护两套向量库的部署、监控、备份、升级 |
| **数据同步** | 新照片上线后需要同时写入两套向量库，同步逻辑复杂 |
| **故障排查** | 向量检索问题时需要排查两套系统，定位困难 |
| **资源浪费** | 两套向量库都需要内存和存储，资源利用率低 |
| **一致性风险** | 两套向量库数据不一致时，检索结果不可预测 |

**架构简化决策**：

| 决策点 | 之前方案 | 现在方案 | 理由 |
|--------|---------|---------|------|
| **向量库选型** | FAISS（十万级）+ Milvus（百万级） | **统一使用现有 Milvus** | 避免两套系统并存 |
| **向量类型管理** | 不同向量库管理不同类型 | **通过向量类型区分** | 同一向量库内隔离 |
| **运维复杂度** | 高（两套系统） | **低（一套系统）** | 降低运维成本 |
| **数据同步** | 需要双写逻辑 | **单写逻辑** | 降低同步复杂度 |

**Milvus 向量类型管理策略**：

```
现有向量类型：
├─ conversation_summary（对话摘要向量）
│  └─ 用于：会话历史语义检索
│
新增向量类型：
├─ face_embedding（人脸身份向量）
│  └─ 用于：”找像某个人”的人脸相似检索
│
├─ appearance_profile（外貌风格向量）
│  └─ 用于：”找阳光清爽”的风格语义检索
│
└─ appearance_preference（用户审美偏好向量）
   └─ 用于：用户偏好相似度计算
```

**关键架构原则**：

1. **向量类型隔离**：不同类型的向量数据存储在不同collection或分区
2. **索引参数可定制**：不同类型向量可以使用不同的索引参数（IVF、PQ等）
3. **检索接口统一**：所有向量检索通过统一的Milvus接口
4. **运维简单**：只需要维护一套Milvus集群

**性能保障措施**：

| 性能维度 | Milvus 方案 | 保障措施 |
|---------|------------|---------|
| **检索延迟** | < 100ms（十万级） | 分区索引、缓存优化 |
| **扩展性** | 支持百万级扩展 | Milvus分布式架构 |
| **并发能力** | 支持高并发检索 | Milvus连接池、负载均衡 |

大白话：

> **统一使用现有Milvus，不是”勉强妥协”，而是”架构简化”。**
>
> **通过向量类型管理，既能满足不同检索需求，又能避免两套系统的运维噩梦。**
>
> **一套系统，多种类型，简单可靠。**


## 21. 与当前仓库能力的衔接关系

这套方案不是推翻现有实现，而是在现有基础上分三段补强。

## 22. 风险与边界

### 22.1 不做公开颜值排名

内部可以有平台基础外貌分，但不要对用户公开展示“颜值分”。

### 22.2 不输出冒犯性描述

允许使用：

- 清爽
- 温柔
- 阳光
- 精致
- 幼态感偏强
- 成熟感偏强

不允许使用：

- 丑
- 土
- 显老
- 普通
- 网红脸

### 22.3 不做敏感属性推断

不要基于照片输出这些内容：

- 种族
- 疾病
- 宗教
- 贫富
- 敏感身份

### 22.4 不让外貌压死硬条件

不管外貌多像、多顺眼，仍然要服从：

- 性别
- 年龄
- 城市
- 婚况
- 关系目标
- 资料可信度

### 22.5 不惩罚正常打扮和上镜差异

资料照片和身份认证照片出现差异，本身并不等于风险。

正常差异包括：

- 化妆
- 发型
- 光线
- 轻度滤镜
- 表情管理

系统真正要识别的不是“比认证视频更好看”，而是：

- 是否还是同一个人
- 是否差异过大到影响信任
- 是否存在明显过度失真

所以一致性评估建议分三层：

1. `正常差异`
2. `可见美化但仍可信`
3. `差异过大，影响真实性判断`

不能把所有“打扮后更精致”的照片都当成负向风险。


## 23. 新增：认证人脸锚点与资料照一致性评估

这一节补的是外貌搜索里非常关键的一层：

- 为什么要利用身份认证的人脸
- 它应该怎么参与检索与排序
- 资料照和认证脸之间如何比对

### 23.1 为什么认证人脸必须纳入体系

身份认证阶段的人脸，相比资料照片，通常有两个优势：

1. 更真实
2. 更稳定

它虽然未必是这个用户最好看的状态，但它能回答：

- 这个人真实大概长什么样
- 资料照是不是仍然代表本人

所以认证人脸不是展示层素材，而是可信锚点。

### 23.2 认证人脸在系统里应该承担什么角色

建议让认证人脸承担四个角色：

1. 真实性 reference
2. 身份一致性 reference
3. face similarity 检索时的候选人级校正依据
4. 资料照失真程度评估依据

也就是说，系统可以：

- 用资料照做展示和风格吸引
- 用认证脸做真实性锚定

### 23.3 资料照与认证脸的一致性，要做成独立评分层

建议新增一致性评估层，核心分数包括：

- `face_consistency_score`
- `beautification_gap_score`
- `profile_photo_trust_level`

它主要回答三个问题：

1. 资料照和认证脸是不是同一个人
2. 资料照和认证脸差异有多大
3. 这种差异是否已经影响信任

### 23.4 动态阈值与环境去噪机制（关键改进）

**核心问题**：

认证照通常来自活体检测阶段的前置摄像头截图，存在这些特征：
- 光线昏暗（室内环境）
- 素颜或淡妆
- 没有表情管理
- 模糊度较高

资料照通常是精心准备的照片：
- 专业光线或自然光
- 有妆容、发型、穿搭
- 有表情管理
- 高清修图

如果设定**绝对阈值**直接对比，会导致：
- 化妆前后差异大的真人被误判为"低可信度风险"
- 光线差异导致的embedding距离被误读为"不是同一个人"
- 对正常用户造成误惩罚

**改进方案：引入环境与置信度去噪**

#### A. 认证照质量评分层

在一致性比对前，必须先对认证照做质量评估：

- `verified_photo_brightness_score`：光照度评分
- `verified_photo_blur_score`：模糊度评分
- `verified_photo_face_visibility_score`：人脸可见度评分
- `verified_photo_quality_confidence`：综合质量置信度

#### B. 动态阈值调整策略

根据认证照质量置信度，动态调整一致性判定阈值：

```
if verified_photo_quality_confidence >= 0.8:
    # 高质量认证照，可以严格判定
    consistency_threshold = 0.75
elif verified_photo_quality_confidence >= 0.5:
    # 中等质量，阈值放宽
    consistency_threshold = 0.65
else:
    # 低质量认证照，不做严格判定
    consistency_threshold = 0.55
    # 同时输出低置信度标记
    flag = "low_verification_quality"
```

#### C. 置信度权重降级

当认证照质量极差时，一致性评分的**置信度权重**应降级：

```
consistency_confidence_weight = verified_photo_quality_confidence * 0.7

final_consistency_signal = {
    score: face_consistency_score,
    confidence: consistency_confidence_weight,
    quality_flag: quality_flag
}
```

这样在排序时，系统会：
- 高质量认证照 → 一致性评分权重高
- 低质量认证照 → 一致性评分权重低（不误判）

#### D. 环境差异补偿

针对光线、妆发差异，建议引入**环境差异补偿因子**：

```
environment_gap_score = calculate_environment_gap(
    verified_photo_brightness,
    profile_photo_brightness,
    verified_photo Makeup_detected,
    profile_photo Makeup_detected
)

adjusted_consistency_score = raw_consistency_score + environment_gap_compensation
```

大白话：
- 如果认证照光线极暗，资料照光线极亮 → 补偿光线差异
- 如果认证照素颜，资料照有妆 → 补偿妆容差异

**关键原则**：

> **系统应该识别的是"是否还是同一个人"，而不是"是否同样好看"。**
>
> **认证照质量差不应成为惩罚用户的理由。**

### 23.5 一致性层建议输出哪些风险标签

建议输出这些标签：

- `same_person_confirmed`
- `mixed_identity_photos`
- `identity_gap_high`
- `mild_beautification`
- `heavy_beautification`
- `profile_photo_low_trust`

这样后续排序、风控、解释都能复用。

### 23.5 一致性层怎么影响搜索与排序

它不一定直接一票否决，但应该影响：

1. `photo_authenticity_score`
2. `trust_bonus`
3. `risk_penalty`
4. 图片搜索结果重排

例如：

- 某候选人的资料照很像参考图
- 但资料照与认证锚点差异过大

那系统可以：

- 保留这个候选人的召回资格
- 但在最终排序里打折

避免出现：

**系统按修饰过度的资料照把人召回得很准，但真实见面完全不是那个感觉。**

### 23.6 一致性层不应该替代资料照风格层

需要明确：

- 一致性层回答“像不像本人、失真大不大”
- 风格层回答“这组照片整体给人什么感觉”

两者都要有，不能互相替代。


## 24. 最终建议

最终建议不是“做一个统一的外貌搜索”。

而是做四套协同能力：

1. 平台基础外貌排序能力
2. 用户个体审美学习能力
3. 人脸相似检索能力
4. 风格与属性检索能力

发现页层面，建议新增一个明确的图片搜索入口，并拆成两个模式：

1. `找像这张脸的`
2. `找这种感觉的`

底层层面，建议保留并增强当前仓库已落地的照片风格语义链路，同时新增：

- face embedding 检索层
- 结构化脸部属性层
- 认证人脸锚点层
- 资料照与认证锚点一致性评估层

一句话总结：

**“找漂亮的”靠平台基础外貌分 + 个体偏好分 + 弱行为信号学习；“找像田曦薇的”靠人脸相似检索；“找眼睛大的、偏幼态的”靠属性层；“找阳光清爽的”靠现有风格语义层；认证人脸提供真实锚点，资料照与认证脸之间再做一致性校正。四类需求共用发现页入口，但底层不要强行混成一个模型。”**
