## 1. 静态条件的「精准」与动态相处的「崩塌」

| 维度 | 说明 |
|------|------|
| **现象** | 很多平台通过身高、薪资、房产匹配得非常完美，但见面「三句话就聊不下去」。 |
| **痛点** | 传统画像是静态的（标签化），但相亲最看重的是动态的（三观、接梗能力、情绪价值）。 |
| **系统切入点** | `user_persona_observations` 若只记硬件条件会处于劣势；需能通过 LLM 提取「性格底色」和「沟通偏好」。 |

## 2. 「货不对板」的信任焦虑（杀猪盘与简历水分）

| 维度 | 说明 |
|------|------|
| **现象** | 照片过度修图、收入虚标，甚至遇上职业骗子。 |
| **痛点** | 用户在建立联系前，需要耗费巨大心智去「侦察」对方的真实性。 |
| **系统切入点** | 不做单一「信任分」，而是拆成两套能力：一套是反诈风控，尽早拦截杀猪盘；一套是资料可信度校验，降低「简历水分」和见面翻车概率。 |

### 完整方案

#### 2.1 先拆开两类问题

- **杀猪盘 / 职业骗子**：本质是安全问题，目标不是“帮用户判断”，而是平台尽量在接触前或接触初期就拦截。
- **简历水分 / 货不对板**：本质是信息可信度问题，目标不是证明一个人“绝对真实”，而是降低用户自行侦察的成本。

这两类问题如果混成一个总分，会有两个副作用：

- 风险极高的人，可能因为资料写得完整、照片好看而被“均分”掩盖。
- 普通用户即使没有诈骗风险，也可能因为某些信息未认证而被误伤。

#### 2.2 设计原则

1. **不输出抽象总分，只展示字段级可信度**
2. **高风险行为单独处理，不与推荐分混算**
3. **优先验证“对婚恋决策影响大”的字段，而不是追求全量认证**
4. **第三方反馈采用结构化回流，不做公开口碑墙**

#### 2.3 资料可信度方案

建议把用户资料拆成若干关键字段，并给每个字段标注来源与验证状态，而不是只显示一个“已认证”徽章。

可优先覆盖这些字段：

- **照片**：普通上传、照片认证、活体自拍视频
- **身份**：实名、年龄
- **学历**：学校 / 最高学历认证
- **职业**：公司、岗位或职业类别认证
- **城市**：常住城市 / 定居意向
- **婚恋关键条件**：婚史、是否有孩子、结婚意向
- **收入**：不验精确值，只验区间

前台展示方式应从“单徽章”改成“字段级说明”，例如：

- `照片：已真人视频认证`
- `学历：已认证`
- `职业：未认证`
- `收入：用户自填（未认证）`

这样用户看到的不是“这个人可信 82 分”，而是“哪些信息有依据，哪些只是自述”。

#### 2.4 反诈风控方案

对于杀猪盘，不应依赖用户自己辨别，而应建立独立风控事件流。

重点信号包括：

- 新账号短时间高频私聊、多对象重复开场
- 快速导流到微信、Telegram、外部投资群
- 频繁出现借钱、投资、带单、内幕、稳赚等高风险话术
- 长期拒绝视频、拒绝语音、拒绝线下可核验接触
- 多次被不同对象标记为“诱导转账 / 导流 / 虚假身份”
- 资料稳定性异常：频繁换照片、换职业、换城市叙述

命中后不只做提示，应有明确动作：

- 降低曝光
- 限制主动发起聊天
- 触发补充认证
- 进入人工复核
- 严重时直接冻结

也就是说，`风险处置` 要走平台安全逻辑，而不是交给用户在对话里自行试错。

#### 2.5 第三方反馈与系统观察

“第三方评价”这个方向有价值，但不适合做成开放评论区，否则很容易演变成情绪化攻击、报复性差评和隐私风险。

更可控的做法是只收集结构化回流：

- `见面后是否与资料一致`
- `是否守时`
- `是否存在明显隐瞒`
- `是否有借钱 / 投资引导`
- `是否愿意正常视频或线下见面`

这些反馈不直接作为公开文案展示，而是作为平台侧观察日志的一部分。只有在满足以下条件时，才影响前台信任表达或风控判断：

- 重复出现
- 跨多个对象一致出现
- 与系统行为信号互相印证

#### 2.6 与搜索、推荐、撮合的结合方式

信任能力不能只放在详情页里“解释”，而应前置到筛选和排序里。

可提供的筛选项包括：

- `最低认证等级`
- `仅看照片认证以上`
- `仅看实名 / 学历 / 职业已认证`
- `仅看近期活跃且通过基础核验`

推荐排序里也可以引入可信度维度，但要注意：

- **资料可信度** 可以作为加分项
- **反诈风险** 应作为硬性降权或拦截项

也就是说，可信度影响“优先推荐谁”，风险决定“能不能继续出现在池子里”。

#### 2.7 MVP 建议

第一阶段不必把所有认证都做重，建议先上最能缓解焦虑的三件事：

1. **认证分层前台化**：把当前的认证状态从后台能力变成用户可见的字段级信号。
2. **照片 / 视频真人核验**：优先解决“照骗”和基础身份不确定的问题。
3. **聊天期反诈风控**：对导流、借钱、投资话术做事件识别和处置。

如果第一阶段验证有效，再逐步追加：

- 学历 / 职业认证
- 见面后结构化反馈
- 线下核验或平台背书服务

#### 2.8 最终想解决的，不是“真假判断”，而是侦察成本

用户真正厌烦的并不是“平台里存在不真实的人”，而是每次建立联系前，都要自己完成一轮侦查、交叉验证和风险判断。

因此产品目标应该是：

- 让高风险对象更早消失
- 让关键资料的可信程度更透明
- 让用户把精力从“查案”转回“判断是否适合相处”

#### 2.9 任务拆解

为了避免方案停留在概念层，建议把这条线拆成 `P0 基础可信度`、`P1 风控闭环`、`P2 深度背书` 三期推进。

##### P0：先让用户少“查案”

这一阶段的目标不是把所有认证做完，而是先把现有可信度信息前台化，并补齐最基础的反诈入口。

**产品 / 设计**

- 梳理资料中的关键字段，确认哪些字段进入“可信度展示层”：
  - 照片、实名、年龄、学历、职业、城市、婚史、子女、收入区间、结婚意向
- 定义字段级状态枚举：
  - `未填写`、`用户自填`、`已基础认证`、`已真人核验`、`已线下核验`
- 设计前台展示组件：
  - 列表卡片的简版认证标签
  - 详情页的“资料可信度”模块
  - 认证说明文案与悬浮解释
- 设计搜索筛选项：
  - `最低认证等级`
  - `仅看照片认证以上`
  - `仅看实名 / 学历 / 职业认证`

**后端 / 数据**

- 统一现有 `verified_level` 分层定义，明确 `none / basic / photo / id / offline` 对应含义。
- 扩展候选人读模型，支持字段级可信度输出，而不是只返回单个认证标签。
- 在搜索 / 推荐接口中补齐可信度字段返回：
  - `verified_level`
  - `verification_items`
  - `photo_count`
  - `last_active_at`
- 为搜索条件补齐可信度筛选参数，并与现有 `verified_level_min` 能力对齐。
- 为推荐理由补一类“可信度理由”文案：
  - 例如 `已真人照片认证`、`实名认证`、`线下核验`

**前端 / 客户端**

- 在推荐列表卡片增加可信度轻标签，不打断浏览。
- 在详情页增加“哪些信息已验证、哪些只是自填”的可读模块。
- 在搜索页增加可信度筛选入口。
- 在聊天页增加举报 / 风险提示入口，先解决用户“出事了不知道去哪报”的问题。

**运营 / 审核**

- 明确认证素材和审核标准：
  - 什么算照片认证
  - 什么算职业认证
  - 收入为什么只做区间、不做精确值
- 定义认证失败和补件流程。
- 定义基础举报类型：
  - `疑似照骗`
  - `资料不符`
  - `导流站外`
  - `借钱 / 投资`

**P0 交付物**

- 字段级可信度字典
- 搜索 / 推荐接口字段扩展
- 列表页与详情页可信度展示
- 举报入口与基础举报类型

##### P1：把“发现风险”变成“处置风险”

这一阶段的重点是把杀猪盘识别从人工经验变成系统事件流和风控动作。

**产品 / 风控策略**

- 定义高风险信号清单：
  - 高频私聊
  - 重复开场
  - 快速导流站外
  - 借钱 / 投资话术
  - 长期拒绝视频 / 语音 / 线下核验
- 定义风险等级和处置策略：
  - `提醒`
  - `降权`
  - `限制主动发言`
  - `要求补认证`
  - `人工复核`
  - `冻结`
- 定义误伤兜底机制：
  - 被限制后的申诉入口
  - 人工复核 SLA

**工程 / 后端**

- 为风控引入独立事件类型，接入现有事件 / outbox 习惯：
  - `risk.signal.detected`
  - `risk.case.opened`
  - `risk.action.applied`
  - `member.report.submitted`
- 在聊天与推荐链路埋点风险信号：
  - 消息关键词命中
  - 站外导流行为
  - 重复模板式开场
  - 多人举报聚合
- 实现基础规则引擎：
  - 先做规则命中，不急着上复杂模型
- 在推荐排序和曝光控制里接入风险状态：
  - 风险高的账号直接降曝光或拦截

**审核 / 运营**

- 搭建风险审核队列。
- 形成审核 SOP：
  - 看什么证据
  - 什么情况直接封
  - 什么情况要求补认证
  - 什么情况只做警告
- 沉淀典型案例，反向更新规则库和关键词库。

**数据 / 分析**

- 建立风控漏斗看板：
  - 举报量
  - 命中量
  - 人工确认率
  - 误伤率
  - 处置后复发率
- 跟踪风险策略对推荐转化的影响，避免“安全做强了但可聊对象被误杀”。

**P1 交付物**

- 风险事件字典与状态机
- 基础规则引擎
- 风险审核后台 / 队列
- 风险信号接入推荐降权与聊天限制

##### P2：从“平台提示”升级到“平台背书”

这一阶段才去做更重的认证和反馈回流，目的是进一步减少见面翻车。

**认证扩展**

- 上线学历认证、职业认证、城市 / 定居认证等更重的能力。
- 探索婚史、子女、结婚意向等高敏感字段的审慎核验方式。
- 设计“收入区间认证”而非精确收入认证，降低隐私和作弊成本。

**反馈闭环**

- 上线见面后结构化反馈表单：
  - `是否与资料一致`
  - `是否守时`
  - `是否存在明显隐瞒`
  - `是否有借钱 / 投资引导`
- 设计反馈生效规则：
  - 单次反馈只入库，不直接公开
  - 多次重复、跨对象一致、与系统信号印证后才影响信任表达
- 将高置信反馈回流到用户画像、风险画像和推荐系统。

**平台背书能力**

- 评估是否提供 `线下核验` 或 `平台认证顾问` 类服务。
- 评估是否在高价值场景中提供“优先展示已深度认证用户”的模式。

**P2 交付物**

- 重认证能力
- 结构化见面后反馈
- 信任回流策略
- 平台背书服务评估结论

## 3. 社交力匮乏导致的「无效匹配」

| 维度 | 说明 |
|------|------|
| **现象** | 匹配成功，但双方只会发「你好」「在干嘛」「吃了吗」。 |
| **痛点** | 很多人具备结婚条件，但不具备破冰和维护关系的能力。 |
| **系统切入点** | 推荐引擎不能只推卡片；可提供「相亲助攻」——例如提示：「对方最近在看《三体》，你可以聊聊里面的物理学梗」。 |

## 4. 推荐机制的「信息茧房」与「选择超载」

| 维度 | 说明 |
|------|------|
| **现象** | 算法总是推同一类人，或推的人太多，用户产生「下一个会更好」的错觉，无法沉下心了解一个人。 |
| **痛点** | 「刷题式相亲」，看谁都像商品，失去对人的尊重感和好奇心。 |
| **系统切入点** | 引入「冷却与聚焦」机制：一旦双方进入深度沟通，可减少该用户曝光，引导「深耕」当前匹配。 |

## 5. 极高的「沉没成本」与「反馈缺失」

| 维度 | 说明 |
|------|------|
| **现象** | 花了钱、见了面，对方一句「不合适」就失联，用户不知道自己错在哪。 |
| **痛点** | 相亲高挫败感，用户需要复盘和成长。 |
| **系统切入点** | 建立「反馈回流闭环」：分析失败原因（谈吐、衣着、价值观冲突等），修正用户画像，并给出可操作的改进建议。 |
