发现页对话完整内部逻辑

这份 HTML 不是产品愿景图，而是按当前仓库代码把发现页对话的真实执行链路串起来：前端如何恢复会话、用户输入如何进入 gateway、DiscoveryService 如何做状态分流、什么时候走反馈重筛、什么时候弹资料更新、以及“愿意认识”如何流向推荐与牵线系统。

前端入口：DiscoverPage + useDiscoverySession 网关入口：/v1/discovery/sessions* 核心状态：collecting_preferences / results_shown / no_result 额外分支：rejection feedback / profile update / express interest
1. 总览主链路 2. 前端会话层 3. 后端状态机 4. 换一批反馈逻辑 5. View 渲染结构 6. 愿意认识出口 7. 持久化与审计 8. 代码锚点

1. 总览主链路

当前发现页本质上是一个“服务端驱动 view 的会话机”，前端不自己推导阶段，只负责恢复 session、提交 turn、映射 timeline。

主调用链 服务内决策 条件分支 结果输出 异常/拒绝
flowchart TD A[DiscoverPage 挂载] --> B[useDiscoverySession.loadSession] B --> C{URL 或 localStorage 里有 sessionId 吗} C -->|有| D[GET /v1/discovery/sessions/{id}] C -->|无| E[POST /v1/discovery/sessions] D --> F[Gateway.discovery_routes] E --> F F --> G[DiscoveryService.create_session / get_session_view] G --> H[返回 session.view] H --> I[mapDiscoveryView] I --> J[前端渲染 timelineItems + chips + suggested_actions] J --> K[用户输入文字 或 点击 action] K --> L[POST /v1/discovery/sessions/{id}/turns] L --> M[DiscoveryService.process_turn] M --> N{文本 / action 分流} N -->|文本| O[run_turn 或特殊分支] N -->|action| P[消费 action 后 run_turn 或特殊分支] O --> Q[_apply_runtime_result] P --> Q Q --> R[更新 session.view timeline] R --> S[返回最新 view] S --> T[前端全量重映射 UI]

2. 前端会话层

前端关键点是“恢复已有 session 优先，映射服务端 timeline 优先，用户消息只做乐观插入”。

初始化

  • 先看 URL 参数 `session`，再看 `readStoredDiscoverySessionId(profileId)`。
  • 有 session 就 `getDiscoverySession`，404 会清掉本地缓存再重新建会话。
  • 没有 session 就 `createDiscoverySession({ profileId })`。
  • 同时并行加载 `fetchCollectedStatements(profileId)`，仅在 session 还没给出 chips 时补齐偏好标签。

提交 turn

  • 输入文字时，先在 timeline 本地插入一条 `kind=message type=user` 的乐观消息。
  • 点击快捷动作时，提交 `action_id`，不再要求用户输入文字。
  • 服务端返回后，不做局部 patch，而是重新 `mapDiscoveryView(data.view)` 覆盖整个时间线。
  • 失败时回滚乐观消息，并把原文字放回输入框。
前端状态 来源 作用
timelineItems mapDiscoveryView(view.timeline) 统一渲染消息、候选人组、资料更新提示、测评结果、快捷动作
currentPrefs criteria_chips 或 collected statements 顶部“当前条件”标签
composerPlaceholder view.composer.placeholder 输入框提示语
composerDisabled view.composer.disabled 输入区禁用态
isSubmittingTurn 本地状态 打字中动效、提交按钮 loading

3. 后端状态机

`DiscoveryService` 是整个发现页对话的唯一编排核心。建会话和处理 turn 都会先更新 session，再写 turn、snapshot、tool call 审计。

flowchart TD A[process_turn] --> B{必须且只能传 user_message 或 action_id 一个} B -->|不满足| B1[DiscoveryInvalidTurnInputError] B --> C[加载 session] C --> D{session.status == active} D -->|否| D1[DiscoverySessionClosedError] D --> E[_build_runtime_input] E --> F{用户发文字?} F -->|是| G[先把 user_message 写入 new_items] G --> H[parse_rejection_feedback_from_text] H --> I{命中“换一批”追问逻辑?} I -->|是| J[_build_batch_refresh_prompt_result] I -->|否| K{正在等待 rejection feedback 且本句可解析} K -->|是| L[_force_rejection_feedback_turn] K -->|否| M[runtime.run_turn] F -->|否，是 action| N[读取 action] N --> O{不存在 / 已消费 / 已过期} O -->|是| O1[action not found 或 expired] O -->|否| P[mark_action_consumed] P --> Q{action_kind} Q -->|show_more_candidates| J Q -->|rejection_feedback| L Q -->|其他| M J --> R[_apply_runtime_result] L --> R M --> R R --> S[_update_rejection_feedback_waiting_state] S --> T[save_session] T --> U[create_turn] U --> V[persist_view_snapshot] V --> W[record_tool_calls] W --> X[return session_payload]

建会话

  • 初始 phase 固定为 collecting_preferences。
  • 默认 create mode 为 profile_first。
  • 会立即跑一轮首屏搜索，不等用户第一句输入。

首屏 profile-first

  • 直接搜 5 个候选人。
  • 有结果就进入 results_shown，输出首屏候选组。
  • 没结果就保持 collecting_preferences，给用户引导动作。

状态来源

  • 最终 phase 来自 runtime decision，而不是前端推断。
  • 当前实现的核心 phase：collecting_preferences、results_shown、no_result。
  • searching 若没有真实 search_response，会被强制回收成收集中状态。

4. “换一批”反馈逻辑

这部分是发现页当前最特殊的隐藏状态机。它不是简单地再搜一次，而是先争取用户给出拒绝原因，再把原因转成 search override。

flowchart TD A[用户说 换一批 / 再看看 / 不太合适] --> B{session.awaiting_rejection_feedback ?} B -->|否| C[_build_batch_refresh_prompt_result] C --> D[助手追问 上一批哪里不太合适] D --> E[下发 rejection_feedback actions] E --> F[session.state.awaiting_rejection_feedback = true] B -->|是| G[parse_rejection_feedback_text] G --> H{识别为 rejection feedback ?} H -->|否| I[继续走普通 run_turn] H -->|是| J[_force_rejection_feedback_turn] J --> K[submit_rejection_feedback / skip_rejection_feedback] K --> L[_feedback_search_override] L --> M[重新 search_partner_candidates] M --> N[_dedupe_feedback_search_results] N --> O{有结果?} O -->|是| P[phase = results_shown] O -->|否| Q[phase = no_result] P --> R[输出 按你刚才的反馈重新给你换一批] Q --> R
反馈类型 系统动作 默认 override
location_distance 偏向同城重筛 把 cities 收紧到用户自己城市
age_gap / criteria_age 年龄更接近 默认收成用户年龄上下约 3 岁
occupation_mismatch 职业方向调整 文案上更强调职业匹配，criteria patch 可来自解析结果
work_life_balance 作息稳定方向重筛 可写入 prefer / must_not_have 补丁
skip_feedback 直接记录“跳过反馈” 不问细节，直接按当前条件再搜

5. View 渲染结构

服务端实际返回的是 view model，前端只做映射。时间线是单数组，消息和候选组按顺序交错存在。

timeline item 类型

  • assistant_message → 前端 kind=message type=matchmaker
  • user_message → 前端 kind=message type=user
  • result_group → 候选人卡片组
  • profile_update_prompt → 资料更新确认卡
  • assessment_result → 测评结果卡
  • feedback_options → 预留的反馈选项块

_apply_runtime_result 会做什么

  • 先用 decision 更新 criteria_chips。
  • 有 search_response 时，先持久化 search run，再构造候选卡片。
  • 总是先追加 assistant message，再追加 profile update prompt，再追加 result group。
  • 最后刷新 view.suggested_actions 和 view.composer。
服务端字段 前端展示 备注
view.criteria_chips[] 顶部“当前条件”标签 若 session 自己没有，前端才会用 collected statements 补
view.suggested_actions[] 对话底部快捷动作 每次 turn 会替换，不是追加
result_group.cards[] 候选人卡片 含头像、城市、匹配理由、人格说明等字段
prompt.status 资料更新卡状态 可变为 pending / confirmed / rejected
view.composer 输入框 placeholder / disabled 当前实现通常回写成“继续告诉红娘你的要求”

6. “愿意认识”出口

发现页里的候选人不是终点。点击“愿意认识”会从 discovery 跨到 recommendation 和 matchmaking，形成正式牵线单。

flowchart TD A[前端调用 express-interest] --> B[Gateway 校验 session owner] B --> C[DiscoveryService.express_interest] C --> D{session active 且 last_search_run_id 存在?} D -->|否| D1[返回不可发起认识] D --> E[读取最新 search_run] E --> F{candidate 在最新 search_run 里吗} F -->|否| F1[candidate not found] F --> G[提取 criteria / self_profile / self_id] G --> H[recommendation.create_subscription] H --> I[recommendation.upsert_recommendation] I --> J[matchmaking.create_match_case] J --> K[matchmaking.dispatch_match_case_outreach] K --> L[返回 subscription_id + case]

前置约束

  • 必须基于最近一次 discovery search run。
  • 只能对最近搜索结果里的候选人发起意愿。
  • 如果 search run 丢失或过期，会提示重新让红娘搜一轮。

输出结果

  • 会记录 last_created_subscription_id、last_interest_candidate_id。
  • 返回值包含 subscription_id 和 case。
  • 后续链路继续进入 recommendation inbox / proxy intro / chat 体系。

7. 持久化与审计

发现页不是无状态聊天。每轮都会存 session、turn、search run、view snapshot、tool call，并打 metrics、funnel、audit 事件。

会话层

  • save_session 持久化 view、phase、state。
  • get_session_view 支持用最新 snapshot 恢复 view。
  • 前端可跨刷新继续回到同一 session。

回合层

  • create_turn 记录 request_kind、user_message、consumed_action、agent_decision。
  • request_kind 主要有 session_opened、user_message、action_click。
  • 每轮都写 view_snapshot。

工具与搜索

  • search_partner_candidates、sync_requester_persona_memory、propose_requester_profile_update 等都有 tool-call 审计。
  • 真实搜索结果会落成 search_run，供 express-interest 和订阅复用。
  • 反馈重筛也会重新生成搜索结果链路。
