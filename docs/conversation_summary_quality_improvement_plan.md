# conversation_summaries 摘要质量改进方案

## 1. 背景

当前 `conversation_summaries` 表中写入的摘要存在两类明显问题：

1. 可量化字段误写入摘要表  
   例如 `mbti_type`、`income`、`age`、`city` 这类结构化信息，本应写入 `profiles` / `user_personas` / `user_persona_observations`，但实际有时会进入 `conversation_summaries`。

2. 摘要文本过于空泛  
   例如“希望性格合拍”“需要稳定关系”“希望真诚沟通”。  
   这类文本后续会进入向量库，但因为缺乏具体偏好和区分度，即使召回成功，也没有实际匹配价值。

本方案的目标是：  
只让“对向量召回真正有价值的语义偏好摘要”进入 `conversation_summaries` 和向量库，同时把结构化事实彻底分流回资料表。

---

## 2. 改造目标

### 2.1 主目标

1. 可量化字段不再进入 `conversation_summaries`
2. 摘要字段必须具备：
   - 具体性
   - 区分度
   - 可检索性
   - 对匹配召回有实际价值

### 2.2 结果目标

改造后：

- `profiles` / `user_personas` 存结构化事实
- `conversation_summaries` 存高信息密度语义偏好
- 向量库只接收高质量摘要，不接收空泛文本

---

## 3. 问题根因

### 3.1 生成顺序问题

当前流程本质上是：

1. LLM 先自由生成结构化 JSON
2. 后端再根据字段名做分流

这会导致两个后果：

- 如果字段名与白名单不完全匹配，结构化字段会被误分流到摘要表
- 如果摘要文本生成得过于空泛，后端没有能力再把它“救回来”

### 3.2 可量化字段白名单不够硬

`split_by_quantifiability()` 依赖 `QUANTIFIABLE_FIELDS` 判断字段归属。  
如果白名单和 LLM 输出字段不完全一致，例如 `mbti_type`、`income` 等字段未被完整覆盖，就会被错误写入摘要表。

### 3.3 Prompt 对摘要质量约束过弱

当前 Prompt 的核心问题不是“提取错”，而是“提取得太空”。

模型会倾向于输出：

- “希望性格合拍”
- “需要稳定关系”
- “希望真诚沟通”

这些文本对人类阅读看似没错，但对向量召回几乎没有实际价值。

### 3.4 缺少落库前质量校验

当前流程里，只要 LLM 输出了摘要文本，通常都会直接写入 `conversation_summaries`。  
缺少一层判断：

> 这条摘要到底值不值得进向量库？

---

## 4. 改造后的目标架构

建议将整条链路改造成以下 5 步：

1. 读取聊天记录
2. LLM 按固定 schema 生成结果
3. 字段级分流
4. 摘要质量校验
5. 分别落库
   - 结构化字段 -> `profiles` / `user_personas`
   - 高质量摘要 -> `conversation_summaries`
   - 只有高质量摘要才允许进入向量库

核心原则：

> 先判断这是不是该写的内容，再决定写到哪里。

---

## 5. 字段层改造方案

### 5.1 结构化字段

以下字段只允许进入 `profiles` / `user_personas`，禁止进入 `conversation_summaries`：

- `mbti_type`
- `age`
- `height`
- `city`
- `education`
- `marital_status`
- `has_children`
- `smoking`
- `drinking`
- `income`
- 以及所有范围型、枚举型、事实型字段

设计原则：

- 只要能结构化存储，就不要进入摘要表
- 只要后续搜索和筛选可直接使用字段完成，就不要变成文本摘要

### 5.2 摘要字段

以下字段才允许进入 `conversation_summaries`：

- `personality_traits`
- `values`
- `partner_expectation`
- `life_attitude`
- `emotional_needs`
- `negative_preferences`

设计原则：

- 必须是语义型偏好
- 必须具备匹配价值
- 必须能帮助区分不同用户

---

## 6. LLM 输出方案

### 6.1 固定 JSON Schema

不要再让模型自由发挥输出形态，而是强制固定字段结构：

- 结构化字段：只提取明确事实
- 摘要字段：只保留具体、可匹配、可召回的偏好表达

### 6.2 Prompt 核心原则

Prompt 应明确约束模型：

1. 这些摘要会进入向量库用于匹配和召回
2. 目标不是写“通顺总结”，而是保留“高信息密度偏好”
3. 抽象词不能单独出现
4. 如果写“稳定”“真诚”“合拍”，必须展开成具体特征、行为、节奏或限制条件
5. 如果没有足够具体的信息，就输出空字符串 `""`

### 6.3 必须禁止的空泛输出

以下表达不能直接作为摘要入库：

- 希望性格合拍
- 希望真诚沟通
- 需要稳定关系
- 希望三观一致
- 希望有共同话题
- 希望被理解
- 需要情绪价值
- 希望相处舒服
- 想找合适的人

这些表达的问题是：

- 适用于绝大多数人
- 区分度极低
- 无法支撑有效召回

### 6.4 正确输出示例

错误示例：

- 希望性格合拍

正确示例：

- 希望对方情绪稳定、遇事愿意直接沟通、不冷处理问题
- 希望对方工作别太忙，下班后有时间陪伴和经营关系
- 希望对方温和不强势，关系推进节奏清晰
- 不喜欢长期暧昧和反复试探，倾向认真推进关系

---

## 7. 摘要质量校验层

### 7.1 目标

在摘要写入 `conversation_summaries` 之前，增加一层质量校验：

- 结构化字段禁止入摘要表
- 空泛摘要禁止入摘要表
- 只有具体、可检索、可区分的摘要才允许入库

### 7.2 质量分级

建议返回三档：

- `valid`
- `weak`
- `invalid`

落库建议：

- `valid` -> 可写入 `conversation_summaries`
- `weak` -> 默认不写，先打日志
- `invalid` -> 直接丢弃

### 7.3 规则 1：结构化字段拦截

如果字段属于结构化字段白名单，直接禁止写入摘要表：

```python
if field_name in QUANTIFIABLE_FIELDS:
    return "invalid"
```

### 7.4 规则 2：空文本丢弃

```python
if not text.strip():
    return "invalid"
```

### 7.5 规则 3：空泛词未展开则无效

抽象词黑名单建议包含：

- 合拍
- 真诚
- 稳定
- 靠谱
- 成熟
- 三观一致
- 共同话题
- 被理解
- 情绪价值
- 舒服
- 合适
- 有感觉
- 好相处

如果文本命中抽象词，但没有任何具体展开，则判 `invalid`。

示例：

- “希望性格合拍” -> `invalid`
- “需要稳定关系” -> `invalid`
- “希望真诚沟通” -> `invalid`

### 7.6 规则 4：必须包含至少一个具体锚点

具体锚点包括：

1. 性格/行为特征  
   例如：情绪稳定、温和、不强势、慢热、主动表达、有边界感

2. 沟通方式  
   例如：愿意沟通、有事直说、不冷处理、会回应、不敷衍

3. 关系节奏  
   例如：认真推进、不长期暧昧、关系明确、愿意长期投入

4. 工作/生活节奏  
   例如：工作别太忙、别太卷、生活规律、作息规律、下班后有时间

5. 现实限制  
   例如：同城、不能异地、行业偏好、婚育接受度、消费观限制

如果一条摘要没有任何具体锚点，则至少应判为 `weak`，多数情况下应判 `invalid`。

### 7.7 字段级专属门槛

#### partner_expectation

必须至少包含以下之一：

- 对方性格特征
- 沟通方式
- 工作/生活节奏
- 关系推进方式
- 城市/距离接受度
- 行业偏好或排斥
- 婚育接受度

否则直接判 `invalid`。

#### emotional_needs

必须体现“关系中的具体需要”，例如：

- 及时回应
- 不冷处理
- 下班后有时间陪伴
- 冲突时正面沟通
- 关系推进明确

如果只有：

- 需要安全感
- 需要被理解
- 需要情绪价值

则判 `invalid`。

#### life_attitude

必须体现具体生活方式或生活节奏，例如：

- 喜欢规律作息
- 偏稳定生活
- 不喜欢太卷
- 喜欢低消耗相处

如果只有：

- 热爱生活
- 积极向上

则判 `invalid`。

---

## 8. 向量入库规则

向量库不应直接接收所有摘要文本，应增加准入条件：

1. 只有通过质量校验的 `valid` 摘要才允许向量化
2. `weak` / `invalid` 摘要不生成 embedding
3. 结构化字段一律不参与摘要向量化

核心原则：

> 凡是不能提升召回质量的摘要，都不应该进入向量库。

---

## 9. 数据库层建议

建议在 `conversation_summaries` 增加以下辅助字段：

- `summary_quality`
  - `valid`
  - `weak`
  - `invalid`

- `quality_reason`
  - `too_generic`
  - `missing_concrete_signal`
  - `quantifiable_field_blocked`
  - `empty_text`

- `vector_eligible`
  - 是否允许进入向量库

- `source_model_version`
  - 记录是哪版 prompt / 提炼逻辑生成的

这样可以支持：

- 查询低质量摘要
- 区分新旧版本摘要
- 精准挑选需要重跑的记录

---

## 10. 历史数据修复方案

当前库里已经存在历史脏数据，建议拆成三类处理。

### 10.1 可量化字段误入摘要表

例如：

- `mbti_type`
- `income`
- `age`
- `city`

处理方案：

1. 从 `conversation_summaries` 中识别这些记录
2. 回填到 `profiles` / `user_personas`
3. 从摘要表中删除
4. 如果已进入向量库，则删除对应向量

### 10.2 空泛摘要

例如：

- 希望性格合拍
- 需要稳定关系
- 希望真诚沟通

处理方案：

1. 标记为 `invalid`
2. 不再参与向量化
3. 若已有向量则删除
4. 如果原始聊天记录还在，则按新 prompt 重跑摘要

### 10.3 半有效摘要

例如：

- 希望真诚稳定
- 希望认真一点

处理方案：

1. 标记为 `weak`
2. 默认不进入向量库
3. 后续可使用新规则重跑

---

## 11. 回填策略

不建议一次性全量重跑，建议分三步：

### 11.1 先修在线写入逻辑

先阻止系统继续产生新的脏数据。

### 11.2 再清理历史摘要表

先把明显错误的记录标记或删除。

### 11.3 最后分批重跑高价值历史会话

优先重跑：

- 最近活跃用户
- 近期参与匹配行为的用户
- 重点城市样本用户

---

## 12. 测试方案

### 12.1 分流测试

输入包含：

- `mbti_type`
- `income`
- `city`
- `personality_traits`
- `partner_expectation`

断言：

- 结构化字段不进入 `conversation_summaries`
- 只写 `profiles` / `user_personas`

### 12.2 摘要质检测试

断言以下为 `invalid`：

- 希望性格合拍
- 希望真诚沟通
- 需要稳定关系
- 希望被理解

断言以下为 `valid`：

- 希望对方情绪稳定，遇事愿意直接沟通，不冷处理问题
- 希望对方工作别太忙，下班后有时间相处
- 不喜欢长期暧昧和反复试探

### 12.3 向量准入测试

断言：

- `valid` 摘要允许生成 embedding
- `weak` / `invalid` 摘要不会进入向量库

### 12.4 历史修复测试

断言：

- 错误摘要能被识别
- 可量化字段可迁回正确表
- 脏向量能被删除

---

## 13. 上线顺序

推荐上线顺序如下：

1. 增加新的摘要 Prompt
2. 增加摘要质量校验层
3. 修正字段分流规则
4. 增加向量准入规则
5. 对新数据灰度观察
6. 再处理历史数据

不建议一开始就全量重跑，否则难以区分是 Prompt、分流还是质检规则起了作用。

---

## 14. 观察指标

上线后建议重点观察：

1. 新写入摘要中 `valid / weak / invalid` 占比
2. 结构化字段误入摘要表的数量
3. 每个用户平均有效摘要条数
4. 向量入库成功率
5. 向量召回后的人工主观质量
6. 空泛摘要命中率是否显著下降

最关键的业务指标是：

> 召回结果是否更具体、更有区分度、是否更接近用户真实偏好。

---

## 15. 一句话结论

本次改造的核心不是“把摘要写得更好看”，而是：

> 把结构化事实和语义偏好彻底分开，只让“具体、可区分、可召回”的摘要进入 `conversation_summaries` 和向量库。

如果一条摘要不能帮助系统更准确地找到“这个用户真正想要的人”，它就不应该入库。
