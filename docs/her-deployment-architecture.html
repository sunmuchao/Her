Step 1

浏览器 + 本地 Next.js

你通常不是把前端也放在 Docker 里，而是在 frontend/her-app 目录下直接跑 pnpm dev。

实际入口

http://localhost:3000

前端职责

页面渲染、登录态存储、通过 /api/gateway/* 代理调用后端。

HTTP
/api/gateway/*
Step 2

Docker Gateway Public

前端代理最终打到宿主机 127.0.0.1:8080，对应容器里的 gateway-public。

主要职责

统一入口：/v1/auth/*、/v1/discovery/*、/v1/recommendation/*、/v1/chat/*

你最近遇到的典型报错

401 Invalid or missing API credentials / 数据库连接池等待超时

内部调用
/v1/*
Step 3

业务子系统 + 共享领域内核

Gateway 不是业务本体。真正处理账号、发现页、推荐卡片、撮合、聊天的，是后面的多个系统和根目录共享包。

业务系统

chat / recommendation / matchmaking / discovery

共享根包

match_domain / partner_search / profile_service / relationship_ledger

状态读写
SQL / Redis / Media
Step 4

Docker 数据层

最终状态落到 Docker 里的 MySQL / Redis / MinIO，不是天然落到你宿主机本地的旧库，除非你手动同步过。

结构化数据

mysql:3306 → her、her_chat、her_discovery、her_matchmaking、her_recommendation

状态 / 媒体

redis 负责缓存/推送；minio 负责语音/媒体对象

访问入口层

对人、浏览器、运营人员真正可见的入口。

本地 Next.js 前端

最常见开发入口。浏览器访问 localhost:3000，由前端 BFF 代理所有后端请求。

宿主机 :3000

Compose Frontend

当前推荐直接用 docker compose up -d 启整套本地环境，前端默认包含在内。

默认启用

Gateway Public / Ops

用户面和运营面 HTTP 入口。public 对 app 用户，ops 对工作台和运维读接口。

:8080 / :8083

网关层

同一套 gateway 代码，被拆成三个“逻辑面”，通过环境变量控制挂哪些接口。

gateway-public

处理 auth、发现页、推荐卡片、聊天、资料、关系等用户面 REST 接口。

SURFACE=public

gateway-ops

处理 /v1/ops/*、规则配置、工作台、运维查看类接口。

SURFACE=ops

gateway-internal

只对内网开放；给 scheduler / script / 内部调用使用，启用 /jsonrpc。

SURFACE=internal
前端只应直连 gateway-public
gateway-ops 不是用户页面入口
gateway-internal 不暴露宿主机端口
三个面共用一套业务代码，不是三个独立系统
你看到的很多报错，是入口对了但下游状态没对齐

业务层

真正做业务决策和数据处理的地方。

partner-chat-system

短信登录、用户会话、聊天消息、语音生成、账号状态。

partner-recommendation-system

推荐卡片、推荐动作、规则配置、推荐解释、实验桶。

partner-matchmaking-system

撮合案件、代理介绍、关系推进、case 维度状态。

partner-discovery-system

发现页 session、小雅回复、条件收集、搜索运行、视图快照。

共享内核层

这些不是“边缘工具包”，而是业务层背后的通用领域支撑。

match_domain

跨系统领域逻辑、会话结束处理、关系状态推进。

partner_search

候选人搜索、条件筛选、排序与可信度整合。

persona_memory_sync / profile_service

资料归集、画像写回、资料聚合读取。

relationship_ledger

关系账本、阶段、跨域时间线和审计读模型。

数据层

所有业务最终都要落到这里；只要这里的状态和你理解的不一致，上层就会出现 401、空数据、语音缺失、推荐异常等连锁反应。

her

主资料库，含 profiles 等基础数据。

her_chat

账号、登录、消息、会话、语音相关记录。

her_discovery

发现页 session、turn、view snapshot、search run。

her_matchmaking

case、撮合状态、代理介绍过程数据。

her_recommendation

推荐卡片、动作、规则配置、订阅等。

Redis / MinIO

一个负责状态协同，一个负责媒体对象。

后台与监控层

系统不是“请求来了才工作”，大量稳定性来自后台任务和监控。

bootstrap

一次性初始化任务，负责 schema / 启动前准备。

sse-server

内网实时推送通道，接收 Gateway push，再向前端推送 SSE。

task_scheduler

定时任务、outbox 消费、订阅刷新、后台维护任务。

Prometheus / Grafana

观测层，负责抓指标和做可视化面板。

最容易混淆的 4 个坑

这四个坑最近几乎贯穿了所有排障。如果你后面还要继续联调，这一块比长文字说明更值得反复看。

坑 1：前端并不总在 Docker 里

你很多时候是本地跑 pnpm dev。所以 cookie、localStorage、BFF 代理都发生在本机，不是在容器里。

坑 2：:8765 和 :8080 容易串线

只要浏览器里留着旧 token，或者 env 改过又没重登，就会出现“前端像连这套，日志却落到另一套”的错觉。

坑 3：Docker MySQL 默认不是宿主机 :3307

如果没有显式同步或改 DSN，Docker 后端读的是容器里的 MySQL 卷，不是你宿主机本地旧库。

坑 4：Gateway 只是门面，不是业务本体

401、语音缺失、发现页没按钮、推荐卡片超时，很多时候真正坏的并不是 Gateway 本身，而是下游子系统、连接池、对象存储或数据库状态。
