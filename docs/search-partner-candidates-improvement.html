🛠️ search_partner_candidates 改进建议（大白话对比）

🎯 核心问题（一句话）
Tool 层做了不该做的事（业务逻辑），违反了 Agent Native 设计原则。
🍕 用大白话比喻：餐厅的故事
❌ 现在的问题设计
  • 厨师：负责炒菜（搜索数据）
  • 服务员（Tool）：负责端菜（返回数据）
  • ❌ 但是！服务员还在做这些事：
  • ❌ 决定菜怎么摆盘（性格推荐理由）
  • ❌ 决定给哪桌客人推荐什么菜（性格匹配度排序）
  • ❌ 决定要不要给客人推荐红酒（性格加分）
  • 问题：服务员做了店长（Agent）该做的事！
    • ✅ 正确的设计
  • 厨师：负责炒菜（搜索数据）
  • 服务员（Tool）：只负责端菜（返回原始数据）
  • 店长（Agent）：负责决策：
  • ✅ 决定菜怎么摆盘（AI 自主生成推荐理由）
  • ✅ 决定给哪桌客人推荐什么菜（AI 自主排序）
  • ✅ 决定要不要推荐红酒（AI 自主判断）
  • 正确：店长决策，服务员只端菜！
    • 对比 1：性格特质增强（最核心问题）
    🤔 为什么这是问题？
    性格推荐理由、性格加分是业务逻辑（软约束），应该由 Agent（AI）自主决定，而不是在代码中硬编码模板。
    ❌ 改进前（问题设计）
    Tool 层包含业务逻辑：
    • ❌ 硬编码性格推荐理由模板："依恋都偏安全型，相处会更稳"
    • ❌ 硬编码性格加分算法：价值观加分 + 依恋加分 + MBTI加分
    • ❌ 硬编码性格排序逻辑：base_score + personality_bonus
    # ❌ Tool 层在生成性格推荐理由（业务逻辑）
    reasoning = _build_personality_reasoning(user_traits, candidate_traits)
    # 硬编码模板："依恋都偏安全型，相处会更稳"
    candidate["personality_reasoning"] = reasoning

    # ❌ Tool 层在计算性格加分（业务逻辑）
    bonus = _compute_personality_bonus(user_traits, candidate_traits)
    # 硬编码算法：价值观 +5分，依恋 +4分
    candidate["personality_bonus"] = bonus

    # ❌ Tool 层在排序候选人（业务逻辑）
    candidate["score"] = base_score + bonus
    results.sort(key=lambda c: c["score"])
    ✅ 改进后（正确设计）
    Tool 层只返回数据：
    • ✅ 只返回性格特质原始数据（MBTI、依恋风格、价值观）
    • ✅ 不生成推荐理由（由 Agent 自主生成）
    • ✅ 不计算加分（由 Agent 自主判断）
    • ✅ 不排序候选人（由 Agent 自主决定）
    # ✅ Tool 层只返回原始数据
    candidate_traits = load_traits_for_profiles(source, candidate_ids)

    # ✅ 只附加原始数据，不生成推荐理由
    for candidate in results:
        traits = candidate_traits.get(candidate["id"])
        candidate["personality_traits"] = traits.to_dict()

    # ✅ 返回原始数据，供 Agent 参考
    return {"candidates": results, "personality_traits": candidate_traits}

    # Agent（AI）自主决定：是否生成推荐理由？怎么写？是否排序？
    ⬇️ 改进后的效果
    🎉 改进后的好处
    1️⃣ AI 更聪明
    AI 可以根据对话上下文自主生成推荐理由，不再千篇一律。
    例如：用户问"为什么推荐她"，AI 会根据性格特质 + 对话历史生成个性化回复。
    2️⃣ 职责清晰
    Tool 只做数据查询，Agent 只做决策。
    代码更简单，维护更轻松。
    3️⃣ 更灵活
    改推荐理由不需要改代码，只需改 Prompt。
    产品经理可以直接调整推荐策略，不需要程序员介入。

  • 1 Tool 层：limit = max(1, min(limit, 10))

    • ❌ 改进前（重复校验）

    normalized_limit = max(1, min(limit, 10))

    # Service Integrations 层（service_integrations.py）
    normalized_limit = max(1, min(int(limit or 5), 10))

    ✅ 改进后（只校验一次）
    # Tool 层（最外层）

    对比 3：并行加载（性能优化）
    🤔 为什么这是问题？
  • 1 ThreadPoolExecutor 在同步函数中使用
  • 2 executor.submit + .result() 会阻塞
  • 3 实际上不是真正并行，只是线程池包装
  • 4 在高并发场景下性能瓶颈明显
    • ❌ 改进前（伪并行）
    # ❌ 同步函数中使用 ThreadPoolExecutor
    with ThreadPoolExecutor(max_workers=2) as executor:
        future1 = executor.submit(load_requester_profile, ...)
        future2 = executor.submit(load_persona_for_discovery, ...)

    # ❌ .result() 会阻塞，不是真正并行
    self_profile = future1.result()
    persona_row = future2.result()
    ✅ 改进后（真正并行）
    # ✅ 异步并发（asyncio.gather）
    async def search_partner_candidates_with(...):
        self_profile, persona_row = await asyncio.gather(
            load_requester_profile_async(...),
            load_persona_for_discovery_async(...),
        )

    # ✅ 真正并行执行，不阻塞！
    🎯 总结：一句话记住
  • 📌 Tool 层只做一件事：返回原始数据
  • 🤖 Agent（AI）负责所有决策：推荐理由、排序、加分
  • ⚡ 硬约束只校验一次：在 Tool 层（最外层）
  • 🚀 真正并行：用 asyncio.gather，不用 ThreadPoolExecutor
  • 🎨 业务逻辑在 Prompt：不在代码中硬编码模板
