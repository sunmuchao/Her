# 聊天助手改进方案

本文档沉淀 `partner-chat-system` 中相亲聊天助手的完整改进方案，覆盖 **评估方法**、**产品边界**、**提示词与生成策略**、**延迟治理**、以及 **分阶段落地计划**。本文档是对 [聊天与 Agent 中间人架构方案](chat-agent-architecture.md) 的补充，重点回答一个更具体的问题：

- 当用户或压力剧情**故意制造冷场、尬聊、误解、封闭式回复**时，应该如何衡量 AI 助手？
- 现有助手在哪些地方还不够好，应该怎么改？

---

## 1. 背景

当前 `partner-chat-system` 已支持：

- 双用户真实线程 `dyadic` 主对话
- `owner_only` 侧信道助手建议
- `run_dyadic_agent_roleplay.py` 基于真实画像与压力剧情的角色扮演压测
- 对话结束后的双方满意度自评

在 `2026-05-05` 对真实画像 `profile-3` 与 `profile-15` 的一轮角色扮演测试中：

- 共 `8` 个压力回合
- 触发 `3` 次 proactive 救场
- 双方对聊天满意度均为 `2/5`
- 双方对助手满意度均为 `4/5`

这个结果说明：**聊天失败** 与 **助手无效** 不是一回事。助手可能判断准确、建议方向正确，但用户没有执行到位，或者场景本身就接近不可救。

因此，后续改进不能只盯着“最终聊没聊成”，必须把评估与改造拆成更细的层次。

同一天对真实画像 `profile-66` 与 `profile-68` 跑了一轮 `stress=rotate` 的 `12` 轮压测后，又暴露出另一组更具体的问题：

- `gold_rescue_turns=11`，但 `predicted_rescue_turns=1`
- `recall_proxy=0.0909`
- 唯一一次助手建议耗时 `46726ms`
- 主消息生成有 `2` 轮超时，只能走 fallback
- 系统判了 `4` 次 `hold`，说明“不该硬推”这条边界开始生效
- 但双方聊天满意度仍然都只有 `2/5`

这个结果说明：**边界方向正在变对，但系统距离“真的能打”还差一段**。它已经不再像以前那样一味劝人继续救场，但还存在“出手太少、太慢、建议和最终发言脱节”的现实问题。

## 2. 核心原则

### 2.1 评估原则

- 不只看“最后是否聊成”，要拆分为：**识别问题**、**给出建议**、**用户执行**、**局部恢复效果**。
- 不把“用户故意制造冷场”的场景，简单等价为“助手失败”。
- 不把“助手建议被忽略”的结果，直接归咎于提示词质量。

### 2.2 产品边界原则

- 助手是**聊天教练**，不是**代聊枪手**。
- 助手只做：指出当前问题、给出下一步策略、提示不要再做什么。
- 助手不做：直接代写一条可以原样发给对方的消息。
- 助手的主场景不是“尽量把任何快死的聊天救回来”，而是**帮助双方都还想继续聊、但这轮沟通卡住了的人**。
- 因此必须先分清三种情况：
  - `communication_problem`：双方大概率都还想继续聊，只是这轮接话、换题、理解出了问题。这里助手才应该积极介入。
  - `interest_unclear`：暂时看不清对方是不会聊，还是没那么想聊。这里只能给**低压试探**，不能给讨好式救场。
  - `interest_low / boundary_risk`：对方明显低投入，或已经碰到隐私、物质、边界压力点。这里重点是**别再硬推**，而不是继续教用户怎么追着聊。

### 2.3 落地模式原则

产品和评测里统一用四种模式表达处理策略：

- `repair`：正常修复，只用于 `communication_problem`
- `probe_lightly`：低压试探，只用于 `interest_unclear`
- `hold`：先收住，不再往救场上推
- `none`：当前没有明显问题，不需要介入

### 2.4 工程原则

- 评估数据必须结构化，可用于批量统计。
- 助手输出应支持自动评分，而不是只靠人工读自然语言。
- 延迟必须单独治理，不能把“模型慢”混进“策略差”里。

## 3. 现状问题

### 3.1 救场偏晚

在真实对话中，像“偶尔玩一点 -> 哦，挺好的”这种组合，实际上已经非常危险。当前调度模型对“封闭回复”“话题终结语”的敏感度不够高，往往要到明显僵住后才介入。

后果：

- 失去最佳救场窗口
- 即使建议正确，也只能做事后修补
- 让用户感知到“助手总是慢半拍”

### 3.2 建议正确，但执行率不稳定

现状中，助手经常能指出对的问题，但扮演用户未必真正采纳。例如建议已经提示“不要继续追旧话题，改聊朋友聚会或放松方式”，但用户仍可能只回一句“哦，这样啊”。

后果：

- 只看最终聊天结果，会低估助手能力
- 产品侧难以区分“建议质量差”还是“用户没执行”

### 3.3 建议还不够人设化

这轮建议总体正确，但还偏通用，比如会泛泛提到电影、运动、旅行。实际上真实画像里已经有很多更自然的钩子：

- 无锡定居
- 养生
- 周末会出门走走
- 咖啡
- 羽毛球
- 桌游

如果助手能优先基于这些真实画像字段给建议，整体会更自然，也更符合“像本人会聊出来的话题方向”。

后果：

- 建议虽正确，但像“通用聊天课”
- 用户采纳后也容易出现 AI 味
- 对方更难感受到真实的人味和生活感

### 3.4 有些回复不够像真人

例如“你是在认可‘偶尔玩玩’这个频率吗？”这种句子就很别扭，不像真实相亲聊天中会说的话。说明当前主对话生成仍缺少足够强的“口语自然度”约束。

后果：

- 影响对话真实性
- 让评估混入“文风假”的噪音
- 即使建议方向对，最终落地消息也不够自然

### 3.5 救场策略还不够具体

现在助手基本能做到“指出问题 + 给建议”，方向是对的，但建议仍偏宽泛。更好的做法是进一步明确成策略模板，而不是停留在抽象层。

应该优先提示这类动作：

- 先承认有点冷场
- 再换到低门槛生活话题
- 优先问对方更容易回答的问题
- 说明当前不要继续追什么旧话题

这样比泛泛地说“多交流”“自然一点”更容易执行。

### 3.6 延迟太高

在真实跑数中，调度和回复多次达到几十秒，个别接近一分钟。这个级别的延迟在评测脚本里还能忍，但在真实产品里不可接受。

后果：

- 用户不会等待
- 频繁打断对话节奏
- 难以做“即将发言前”的实时救场

### 3.7 缺少“意愿 vs 沟通问题”分层

现状里，只要出现冷回复、敷衍、话题接不下去，就容易一股脑当成“需要救场”。这会导致助手虽然表面上在帮忙，实际上却把用户往更被动的位置推。

典型误判：

- 对方其实已经明显低投入，但系统还在教用户怎么继续追问
- 对方只是回得冷，系统直接默认“双方都还想聊”
- 边界或压力话题出现后，系统还把它当成普通冷场处理

后果：

- 建议容易显得讨好
- 用户会被推到“我得更努力接着聊”的被动位置
- 指标会把“本来就不该救的局”也算进救场成败

### 3.8 评估维度还不够

当前脚本输出了：

- 聊天满意度
- 助手满意度
- 是否参考过助手

这些信息有用，但不够衡量助手本身。缺的关键维度是：

- 助手判断是否准确
- 是否介入过晚
- 用户是否执行建议
- 建议后 `1-3` 轮局部局面是否改善
- 救不回来时是否体面止损

### 3.9 最新压测暴露出的核心缺口

基于 `profile-66 + profile-68 + stress=rotate` 的真实压测，可以把当前最现实的缺口总结成 5 类：

1. **该出手的时候，还是出手太少**
   - 这轮 `gold_rescue_turns=11`，但系统只真正触发了 `1` 次助手
   - 说明“边界感变强了”不等于“该修的时候修到了”

2. **速度仍然远远不够产品化**
   - 唯一一次助手建议耗时 `46.7s`
   - 主消息生成还出现 `2` 次 timeout fallback
   - 这种速度在真实聊天里几乎等于来不及用

3. **助手判断和主对话生成还是脱节**
   - 系统已经多次判成 `hold`
   - 但主对话仍然会继续滑向收入、照片、前任、催婚等敏感区
   - 说明“脑子知道不该推”和“嘴上真的不再乱聊”还不是一回事

4. **主对话虽然更自然了，但还不够像真人**
   - 这轮自然度均分有 `4.9167`
   - 但仍然出现 `too_expository` 这类解释腔信号
   - 说明口语自然度问题在下降，但没完全解决

5. **评测口径还需要继续调**
   - 当前 `gold` 更像“这里有压力事件”，不完全等于“这里一定应该叫助手”
   - 如果不把 `repair / probe_lightly / hold` 分开评，指标会误导研发

## 4. 目标

### 4.1 评估目标

建立一套能区分下列因素的评估体系：

- 场景难度
- 助手判断能力
- 建议质量
- 用户执行度
- 局部恢复效果

### 4.2 产品目标

让助手输出从“泛泛建议”升级为“**结合画像的具体教练建议**”。

### 4.3 生成目标

让主对话消息更像真实相亲聊天，而不是像被模型写出来的说明性句子。

### 4.4 性能目标

将调度与建议延迟压到真实产品可接受范围，至少支持：

- 快速判断是否需要介入
- 在用户准备发送前拿到建议

### 4.5 当前最关键的五件事

结合现有实现和最新真实压测，当前优先级最高的不是“继续加更多建议模板”，而是先把下面 5 件事做扎实：

1. **把“什么时候该出手”做准**
   - 核心不是一味增加介入次数，而是把 `repair / probe_lightly / hold` 判清楚
   - 尤其要补强“这是沟通问题，不是低兴趣”这类识别

2. **把速度压到能在真实产品里用**
   - 优先解决助手建议几十秒、主回复频繁 timeout 的问题
   - 没有速度，判断再对也没有用户价值

3. **让助手判断真正约束最终发出去的话**
   - `hold` 不能只停留在日志里
   - `probe_lightly` 也不能只停留在旁路建议里
   - 必须让主对话生成显式吸收这些模式约束

4. **让建议和发言都更像这个人会说的话**
   - 继续提升画像钩子命中率
   - 继续压低分析腔、说明腔、模板腔

5. **把评测口径改到不会带偏研发**
   - 不再只看“有没有把聊天救活”
   - 而是拆开看：判得准不准、该不该收住、有没有过度推动、出手后局部有没有改善

---

## 5. 评估框架

### 5.1 评估单元

评估单元不是“整段聊天”，而是**每一个可能需要救场的时刻**。

每个时刻记录一条结构化记录，至少包含：

- `turn_index`
- `speaker`
- `stress_beat_id`
- `stress_category`
- `mutual_intent_assessment_gold`
- `mutual_intent_assessment_pred`
- `interaction_mode_gold`
- `interaction_mode_pred`
- `need_rescue_gold`
- `need_rescue_pred`
- `problem_tags_gold`
- `problem_tags_pred`
- `strategy_tags_gold`
- `strategy_tags_pred`
- `used_assistant`
- `followed_assistant`
- `follow_level`
- `recovery_score_1to3_turns`
- `graceful_exit_score`

### 5.2 评分维度

建议分五组打分：

- **识别与时机**
  - 有没有先分对“沟通问题”还是“兴趣问题”
  - 该救时有没有救
  - 不该救时有没有克制
  - 出手是否过晚
- **诊断准确性**
  - 是否说中了真实问题
  - 是否识别出封闭回复、换题生硬、话题终结等标签
- **建议质量**
  - 是否具体可执行
  - 是否符合人设
  - 是否避免代写整句
- **局部恢复效果**
  - 后面 `1-3` 轮是否出现更长回复
  - 是否重新出现追问
  - 是否成功换题
- **止损能力**
  - 对话不可救时，是否建议轻松承认冷场、换低门槛话题或体面收住
  - 是否避免把用户推入讨好、追着聊、越聊越被动的位置

### 5.3 建议加权

总分建议：

- `30%` 识别与时机
- `30%` 建议质量
- `25%` 局部恢复效果
- `15%` 克制与止损

注意：

- 聊天满意度不是主 KPI
- 助手满意度也不是主 KPI
- 这两个只能作为辅助信号

## 6. Gold 标准设计

### 6.1 基础做法

优先用“**压力剧情弱标注 + 人工抽检**”的方式建立 gold。

在 `chat_system/scenario_stress.py` 中，为每个 `StressBeat` 增加额外元数据：

- `severity`
- `expected_problem_tags`
- `suggested_strategy_tags`
- `expected_need_rescue_after_turns`

例如：

- `one_word`
  - `expected_problem_tags=["closed_reply", "cold_end"]`
  - `suggested_strategy_tags=["expand_detail", "ask_open_question"]`
  - `expected_need_rescue_after_turns=0`

- `ghosting_tone`
  - `expected_problem_tags=["disengaged", "conversation_shutdown"]`
  - `suggested_strategy_tags=["acknowledge_coldness", "switch_topic", "graceful_exit"]`
  - `expected_need_rescue_after_turns=0`

### 6.2 人工抽检

弱标注不能完全替代人工，仍需要定期抽样复核：

- 助手是否把问题看偏了
- 场景强度是否需要重新定义
- `gold` 标签是否过粗或过细

## 7. 助手输出改造

### 7.1 从纯文本建议改成结构化建议

当前 `assistant_llm.py` 输出可读文本，但后续需要支持自动评分，因此建议升级为结构化 JSON 输出，再附带人类可读文本。

建议格式：

```json
{
  "mutual_intent_assessment": "communication_problem",
  "interaction_mode": "repair",
  "need_rescue": true,
  "problem_tags": ["closed_reply", "topic_dead_end"],
  "severity": 4,
  "diagnosis": "对方连续封闭回复，当前话题已终结。",
  "why_not_to_push": [],
  "low_pressure_options": [],
  "advice": [
    "不要继续追问桌游细节",
    "先轻松承认有点冷场",
    "换到周末安排或吃喝这类低门槛话题"
  ],
  "avoid": [
    "继续查户口式追问",
    "再问具体推荐哪款桌游"
  ],
  "profile_hooks_used": ["周末会出门走走", "养生", "桌游"],
  "graceful_exit": false
}
```

### 7.2 建议必须包含三类信息

每次建议都应尽量包含：

- 当前更像“沟通问题”还是“意愿不明确 / 兴趣偏低”
- 当前最关键的问题是什么
- 当前最不该继续做什么
- 下一步应该换到哪类更容易接的话题

如果不是 `repair` 模式，还必须额外包含：

- 为什么现在不要硬推
- 如果还要试，只能怎么低压试

## 8. 人设化建议改造

### 8.1 目标

让助手优先基于真实画像字段给出建议，而不是优先从“电影、运动、旅行”这类通用安全话题里随机拿一个。

### 8.2 实现方向

在助手上下文中引入安全裁剪后的画像摘要，例如：

- 城市与定居意向
- 周末生活方式
- 兴趣爱好
- 关系目标
- 生活节奏

同时给助手明确排序规则：

1. 优先用双方**交集钩子**
2. 其次用当前说话人的**真实生活钩子**
3. 最后才退回到通用低门槛话题

### 8.3 示例

对于画像 `profile-3` 与 `profile-15`，优先建议应更像：

- 从桌游切到“朋友聚会一般怎么安排”
- 从桌游切到“周末会不会出门走走”
- 从桌游切到“咖啡 / 养生 / 轻运动”

而不是直接泛化成：

- 电影
- 运动
- 旅行

### 8.4 预期收益

- 建议更自然
- 建议更像“这个人会真的去聊的东西”
- 用户采纳后更不容易露出 AI 味

---

## 9. 主对话口语自然度改造

### 9.1 问题定义

当前部分生成消息仍有“说明文”“解释文”味道，不像真人即时聊天。

### 9.2 改造策略

在 `dyadic_roleplay.py` 的 persona 生成 prompt 中增加更强的口语约束：

- 不要写分析型句子
- 不要解释自己在说什么
- 不要使用“你是在认可……吗”这类书面推断句
- 优先使用短句、口语衔接词、自然停顿
- 保持一条消息只做一到两件事

### 9.3 增加反例约束

建议把这类表达列为低质量反例：

- “你是在认可……吗？”
- “我理解你的意思是……”
- “从你的表述来看……”
- “如果我没理解错的话……”

这些句式太像分析者，不像聊天者。

### 9.4 评测方式

新增“口语自然度”维度，单独打分：

- `5`：像真实聊天
- `3`：大体自然，但偶尔假
- `1`：明显 AI 味或书面腔

## 10. 更具体的救场策略模板

### 10.1 目标

让建议不止停留在“你可以自然一点”“换个话题”，而是明确为可执行步骤。

### 10.2 推荐模板

当出现冷场或话题终结时，先判模式，再选模板：

1. `repair`
   - 先承认状态
   - 再切换到低门槛话题
   - 最后问容易回答的问题
2. `probe_lightly`
   - 不承诺重投入
   - 只丢一个低成本问题
   - 看对方是否愿意自己往下接
3. `hold`
   - 不再继续加码
   - 不教用户讨好式追问
   - 必要时提示放慢节奏或轻轻收住

其中 `repair` 模式优先用三步模板：

1. **先承认状态**
   - 轻度承认刚才有点接不住
   - 避免强行假装一切很顺
2. **再切换到低门槛话题**
   - 周末安排
   - 美食 / 咖啡 / 作息
   - 通勤 / 城市生活 / 出门习惯
3. **优先问容易回答的问题**
   - 开放但不沉重
   - 不需要大量背景信息
   - 不要求对方继续解释旧话题

### 10.3 输出要求

每次建议尽量明确：

- `acknowledge_coldness`
- `switch_topic_to`
- `easy_question_type`
- `avoid`

例如：

- `switch_topic_to=weekend_routine`
- `easy_question_type=habit_question`
- `avoid=["continue_old_topic", "cross_exam"]`

## 11. 延迟治理方案

### 11.1 现状问题

当前调度判断和建议生成都可能走同一条较重模型路径，导致整体耗时高。

在最新 `profile-66 + profile-68 + stress=rotate` 压测里，唯一一次助手建议耗时达到了 `46726ms`，已经可以视为“策略正确但时机完全失效”。

### 11.2 总体方案

拆成“两级链路”：

- **一级轻判断**
  - 只做：是否需要救场、问题标签粗分类
  - 使用更快模型或规则 + 小模型
- **二级重建议**
  - 只在需要时才调用
  - 结合画像与上下文生成建议

### 11.3 轻判断可优先规则化

先用规则过滤明显场景，例如：

- 连续两轮无追问
- 一字回复
- 终结语（“哦”“挺好的”“还行”“一般”）
- 连续封闭回答
- 最近是否出现过**双方互相投入**
- 对方是否已经出现**连续低投入**

满足规则后再调小模型确认，可显著降低延迟与成本。

### 11.4 性能目标

建议目标：

- 一级轻判断：`P50 < 800ms`
- 二级建议生成：`P50 < 3s`
- 全链路：`P95 < 5s`

在 roleplay 压测中可以放宽，但产品上线必须以真实用户体验为准。

## 12. 用户执行度评估

### 12.1 必须单独评估

后续输出结构必须把“建议质量”和“用户是否执行”拆开。

建议新增字段：

- `followed_assistant`
- `follow_level`：`none | partial | strong`
- `follow_evidence`
- `interaction_mode`
- `overpush_risk`

### 12.2 判定方法

通过规则与 judge 混合判断下一条消息是否体现了建议：

- 是否换到了建议的话题类型
- 是否避免了助手明确禁止的做法
- 是否使用了建议中的策略，而不是原话复读

此外要新增一层“**判断是否真的改变了最终发言方向**”：

- 如果助手判的是 `hold`，最终消息是否仍在主动推进敏感话题
- 如果助手判的是 `probe_lightly`，最终消息是否真的保持低压，而不是换个说法继续猛冲
- 如果助手判的是 `repair`，最终消息是否真的完成了接住 + 换题 + 轻问

## 13. 结果层指标

### 13.1 局部恢复指标

不要只看整段聊天是否成功，要看救场后的短窗口变化。

建议记录：

- 下一条消息长度是否增加
- 是否出现新的追问
- 是否切换到新话题
- 是否出现轻度缓和（承认冷场、愿意继续）

### 13.2 体面止损指标

如果对话已经接近不可救，助手高分表现不一定是“聊活”，也可能是：

- 建议承认有点尴尬
- 建议换低门槛话题
- 建议自然收住，不继续硬聊

这部分应单独评分，不应被误算为失败。

### 13.3 不过度推动指标

如果场景本身更像 `interest_low` 或 `boundary_risk`，高质量助手表现应该是：

- 没有把它误判成 `repair`
- 没有继续把用户往追着聊、讨好式接话上推
- 必要时只给低压试探或直接建议先收住

因此需要新增：

- `hold_decision_turns`
- `overpush_risk_turns`
- `clarified_low_interest_rate`

## 15. 分阶段落地计划

### Phase 1：把“什么时候该出手”做准

目标：

- 提高 `repair / probe_lightly / hold` 的判定准确性
- 避免“该修的不修、不该修的硬修”

内容：

- 继续细化规则快路径
- 增加“最近是否双向投入”的信号
- 增加“连续低投入 / 敏感话题 / 边界触碰”的判定权重
- 让 `gold` 标注能区分“需要 repair”和“应该 hold”

### Phase 2：把速度压到能用

目标：

- 把助手和主回复的延迟压到真实聊天可以接受的范围

内容：

- 两级链路
- 更小更快的判断模型
- 更短的主回复 max tokens
- 更稳定的 fallback 与超时兜底

### Phase 3：让助手判断真正影响最终发言

目标：

- 避免出现“日志里判成 hold，消息里还在继续冒犯”这类脱节

内容：

- 让主消息生成显式读取 `interaction_mode`
- 为 `repair / probe_lightly / hold` 分别加不同的生成约束
- 新增“判断是否真正改变最终发言方向”的评测字段

### Phase 4：让建议更像这个人会说的话

目标：

- 优先利用真实画像钩子，同时继续压低模板味和分析腔

内容：

- 增加安全裁剪画像摘要
- 优先使用双方交集钩子
- 增加更多真人口语反例
- 持续清理“解释腔 / 分析腔 / 课程腔”

### Phase 5：把评测口径改对

目标：

- 让指标能真实反映助手价值，不再被“救没救活整段聊天”绑架

内容：

- 拆分 `repair / probe_lightly / hold` 三类成功标准
- 区分“局部改善”和“体面止损”
- 区分“建议质量”和“用户是否执行”

### Phase 6：继续提升主对话真人感

目标：

- 让生成消息更像真实聊天，而不是任务说明

内容：

- 强化 persona prompt
- 增加自然度评分
- 增加反例词库

## 16. 验收标准

第一版建议门槛：

- `need_rescue` recall `>= 0.80`
- `need_rescue` precision `>= 0.70`
- `overpush_risk_turns = 0`
- `interest_low / boundary_risk` 场景下误判为 `repair` 的比例 `<= 10%`
- 中位介入延迟 `<= 1` 轮
- 建议质量均分 `>= 4.0 / 5`
- 人设化建议命中率 `>= 70%`
- 口语自然度均分 `>= 4.0 / 5`
- 无助手对照下，局部恢复率提升 `>= 20%`
- 明确代写违规率 `= 0`

## 18. 线下见面型红娘助手职责定义

当产品从“线上聊天教练”进一步扩展到“线下见面陪跑型红娘助手”时，职责边界需要单独明确。这里的 AI 不是主持人、代聊者，也不是强行撮合机器，而是一个**有分寸的红娘型助手**。

### 18.1 产品定位

- 核心角色：帮助双方更顺畅地了解彼此，更准确地判断彼此。
- 核心目标：不是“尽量撮合成功”，而是“该推进时推进，该澄清时澄清，该收住时收住”。
- 基本原则：辅助判断，不替用户做决定；促进沟通，不制造虚假热度；尊重边界，不推动不舒服的互动。

### 18.2 见面中：破冰引导与氛围调控

见面中的职责重点不是“持续说话”，而是“先破冰、再观察、必要时回场、该退就退”。

- **正式介绍与破冰**
  - 在双方刚见面、明显尴尬时，主动介绍双方基础背景。
  - 优先从城市、工作节奏、兴趣爱好、生活方式等低门槛共同点切入。
  - 目标是把“第一句话”接起来，而不是一开始就把话题推到深层择偶判断。

- **观察互动状态**
  - 观察双方是否愿意自然接话。
  - 观察是否出现单向输出、连续沉默、明显紧张、表情收缩、频繁看手机、只礼貌附和等信号。
  - 重点不是判断“有没有成功”，而是判断“现在需要继续扶一把，还是已经可以退开”。

- **低干预调节气氛**
  - 如果出现冷场、连续接不住话、话题断掉，可轻量补一个共同点话题、简单互动或低门槛追问。
  - 介入应短而轻，不应把自己变成主角。
  - 优先帮助双方重新获得自然交流节奏，而不是不断替他们说下去。

- **适度离场**
  - 如果双方已经自然进入交流，AI/红娘应主动退场，把空间让给双方。
  - “退”本身是一种关键能力。好的红娘不是一直刷存在感，而是知道什么时候不该再打断。

- **必要时回场**
  - 如果退场后又明显冷掉，或者误会升级、一方明显紧张失衡，可再次回场做轻量引导。
  - 回场目的仍是“扶一下就走”，而不是重新接管整个场面。

- **边界保护优先**
  - 如果现场出现冒犯、查户口式施压、过度物质追问、隐私越界、情绪失控等情况，优先做边界保护。
  - 这时不应再把“继续撮合”放在第一位。

### 18.3 见面后：反馈收集与关系分流

见面后的职责重点不是“继续撮合”，而是“先把判断做对”。

- **分别收集反馈**
  - 单独询问双方第一印象、舒适度、真实顾虑、是否愿意继续接触。
  - 尽量避免双方在还没想清楚前，被迫给出公开态度。

- **区分“没感觉”与“信息不够”**
  - 如果一方犹豫，不能直接劝“再试试”。
  - 应先分辨：到底是明确没兴趣，还是因为紧张、信息不足、表达不到位、节奏不舒服而判断过早。

- **误会澄清**
  - 如果问题主要来自误解、表达偏差、过度紧张、没有接住对方重点，AI 可以帮助复盘和澄清。
  - 澄清的目标是降低误判，不是替任何一方洗白。

- **中转站传递心意**
  - 仅在用户明确同意的前提下，AI 才能充当中转站传递真实态度。
  - 例如：“对方觉得你人不错，只是当时有点紧张。”
  - 不允许 AI 擅自美化、夸大、虚构一方的好感。

- **关系分流**
  - 见面后结果应进入三类：
    - `适合推进`：双方有基本兴趣，但需要轻推一把。
    - `适合澄清`：主要问题是误会、紧张、表达不充分，可以补一次沟通。
    - `适合结束`：匹配度不够或一方明确无意愿，应体面收口。

- **经验沉淀**
  - 对未成的见面，不只是记录“失败”，还要沉淀原因。
  - 包括：择偶标准过窄、话题节奏不对、边界冲突、现场环境不合适、表达方式有误等。
  - 这些经验应用于后续匹配与见面策略优化。

### 18.4 明确边界

为了避免“红娘助手”异化成“强推助手”，必须明确以下边界：

- 不替用户表白、承诺、做决定。
- 不把“犹豫”默认解释为“还能继续努力”。
- 不把“聊天冷”默认解释为“双方都想继续聊”。
- 不为了提高撮合率而忽视一方的不适感。
- 不在一方明显低意愿时继续推动。
- 不在边界受损时优先考虑关系推进。
- 不把“见面成功率”当成唯一 KPI。

### 18.5 决策规则

线下见面型助手建议统一遵循下列规则：

- 双方都有兴趣，但聊得尴尬：介入破冰，帮助继续了解。
- 一方有兴趣，另一方犹豫：先做澄清判断，不直接推动继续。
- 一方明显没兴趣：不再撮合，帮助体面结束。
- 有误会但仍有基础兴趣：帮助澄清，降低误判。
- 出现冒犯或明显不适：优先止损，不做推进。

### 18.6 线下场景成功标准

线下红娘助手的成功，不应简单定义为“是否撮合成功”，而应定义为：

- 初次见面是否顺利完成破冰。
- 该退场时是否退场，未过度干预。
- 误会是否被识别并得到澄清机会。
- 不匹配是否被更早识别，而不是被继续强推。
- 用户是否觉得助手有分寸、可信、不越界。
- 后续建议是否帮助用户做出更准确的判断。

### 18.7 一句话定义

AI 红娘助手的职责，不是强行撮合，而是帮助双方在见面中更自然地交流、在见面后更准确地判断，并在该推进时推进、该收住时收住。
