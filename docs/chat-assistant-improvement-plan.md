# 聊天助手改进方案

本文档沉淀 `partner-chat-system` 中相亲聊天助手的完整改进方案，覆盖 **评估方法**、**产品边界**、**提示词与生成策略**、**延迟治理**、以及 **分阶段落地计划**。本文档是对 [聊天与 Agent 中间人架构方案](chat-agent-architecture.md) 的补充，重点回答一个更具体的问题：

- 当用户或压力剧情**故意制造冷场、尬聊、误解、封闭式回复**时，应该如何衡量 AI 助手？
- 现有助手在哪些地方还不够好，应该怎么改？

---

## 1. 背景

当前 `partner-chat-system` 已支持：

- 双用户真实线程 `dyadic` 主对话
- `owner_only` 侧信道助手建议
- `run_dyadic_agent_roleplay.py` 基于真实画像与压力剧情的角色扮演压测
- 对话结束后的双方满意度自评

在 `2026-05-05` 对真实画像 `profile-3` 与 `profile-15` 的一轮角色扮演测试中：

- 共 `8` 个压力回合
- 触发 `3` 次 proactive 救场
- 双方对聊天满意度均为 `2/5`
- 双方对助手满意度均为 `4/5`

这个结果说明：**聊天失败** 与 **助手无效** 不是一回事。助手可能判断准确、建议方向正确，但用户没有执行到位，或者场景本身就接近不可救。

因此，后续改进不能只盯着“最终聊没聊成”，必须把评估与改造拆成更细的层次。

同一天对真实画像 `profile-66` 与 `profile-68` 跑了一轮 `stress=rotate` 的 `12` 轮压测后，又暴露出另一组更具体的问题：

- `gold_rescue_turns=11`，但 `predicted_rescue_turns=1`
- `recall_proxy=0.0909`
- 唯一一次助手建议耗时 `46726ms`
- 主消息生成有 `2` 轮超时，只能走 fallback
- 系统判了 `4` 次 `hold`，说明“不该硬推”这条边界开始生效
- 但双方聊天满意度仍然都只有 `2/5`

这个结果说明：**边界方向正在变对，但系统距离“真的能打”还差一段**。它已经不再像以前那样一味劝人继续救场，但还存在“出手太少、太慢、建议和实际发言脱节”的现实问题。

## 2. 核心原则

### 2.1 评估原则

- 不只看“最后是否聊成”，要拆分为：**识别问题**、**给出建议**、**用户执行**、**局部恢复效果**。
- 不把“用户故意制造冷场”的场景，简单等价为“助手失败”。
- 不把“助手建议被忽略”的结果，直接归咎于提示词质量。

### 2.2 产品边界原则

- 助手是**聊天教练**，不是**代聊枪手**。
- 助手只做：指出当前问题、给出下一步策略、提示不要再做什么。
- 助手不做：直接代写一条可以原样发给对方的消息。
- 对真实产品里的用户，助手输出的是**建议**，不是**控制信号**；`interaction_mode` 只约束助手自己的判断与提示，不约束用户下一句必须怎么发。
- 在 `roleplay / 压测` 中，如果让模拟 agent 读取 `interaction_mode`，目的只是验证策略是否可执行、便于离线评测，不代表线上产品会直接干预真人用户。
- 助手的主场景不是“尽量把任何快死的聊天救回来”，而是**帮助双方都还想继续聊、但这轮沟通卡住了的人**。
- 因此必须先分清三种情况：
  - `communication_problem`：双方大概率都还想继续聊，只是这轮接话、换题、理解出了问题。这里助手才应该积极介入。
  - `interest_unclear`：暂时看不清对方是不会聊，还是没那么想聊。这里只能给**低压试探**，不能给讨好式救场。
  - `interest_low / boundary_risk`：对方明显低投入，或已经碰到隐私、物质、边界压力点。这里重点是**别再硬推**，而不是继续教用户怎么追着聊。

### 2.3 落地模式原则

产品和评测里统一用四种模式表达处理策略：

- `repair`：正常修复，只用于 `communication_problem`
- `probe_lightly`：低压试探，只用于 `interest_unclear`
- `hold`：先收住，不再往救场上推
- `none`：当前没有明显问题，不需要介入

### 2.4 工程原则

- 评估数据必须结构化，可用于批量统计。
- 助手输出应支持自动评分，而不是只靠人工读自然语言。
- 延迟必须单独治理，不能把“模型慢”混进“策略差”里。

### 2.5 这个助手真正要解决什么问题

这个助手真正要解决的，不是“把所有快死的聊天都救活”，而是：

- **帮助本来还有继续可能的两个人，不要因为不会聊、误解、节奏差、边界拿捏不好，而白白聊崩**

更具体地说，主要是三类问题：

- **表达问题**
  - 回得太短
  - 不会接话
  - 换题太硬
  - 问得像审问
- **判断问题**
  - 分不清对方是暂时闷，还是根本没兴趣
  - 分不清现在该继续试一下，还是该收住
- **执行问题**
  - 用户知道“这样聊不太对”，但不知道下一步怎么做更自然

### 2.6 哪些问题不一定要用 AI

不是所有聊天问题都值得上 AI。以下问题优先考虑规则、模板或产品设计解决：

- 破冰不知道聊什么
- 冷场时给几个固定建议
- 单轮消息的礼貌改写
- 纯话题供给不足
- 匹配不准导致双方本来就没兴趣
- 用户自己没有投入意愿

这些场景里，规则、模板、话题卡、匹配优化通常更便宜，也更稳定。

### 2.7 哪些问题必须用 AI

只有当问题满足以下特征时，AI 才真正有必要：

- 需要结合**最近几轮上下文**判断，而不是看单句
- 需要区分“不会聊”与“没兴趣”
- 需要结合**双方画像**给出不同建议
- 需要处理边界、误解、冷场、敏感话题这些复杂情况
- 需要因人、因场景动态调整，而不是套固定模板

一句话概括：

- **固定套路能解决的，不要上 AI**
- **只有要看具体情况、要看人、要临场判断的，AI 才有意义**

### 2.8 用户可见层的基本原则：不要每句话都教

最优产品形态不是“每来一句消息，就弹一次 AI 建议”，而是：

- **后台可以每句话都做轻判断**
- **前台不要每句话都打断用户**

也就是说：

- 系统内部可以逐句更新状态
- 这个状态不应该每轮清零，而应该带惯性地连续更新
- 但用户真正看到的提示，应该只在**趋势变化**、**风险升级**、或**需要决策**时出现

这样做的原因有三点：

- 避免用户觉得自己在照提词器演戏
- 避免过度干预，把正常聊天波动也误当成问题
- 避免把所有延迟都直接暴露给用户

一句话概括：

- **后台逐句监控**
- **前台按趋势提示**

## 3. 现状问题

### 3.1 救场偏晚

在真实对话中，像“偶尔玩一点 -> 哦，挺好的”这种组合，实际上已经非常危险。当前调度模型对“封闭回复”“话题终结语”的敏感度不够高，往往要到明显僵住后才介入。

后果：

- 失去最佳救场窗口
- 即使建议正确，也只能做事后修补
- 让用户感知到“助手总是慢半拍”

### 3.2 建议正确，但执行率不稳定

现状中，助手经常能指出对的问题，但扮演用户未必真正采纳。例如建议已经提示“不要继续追旧话题，改聊朋友聚会或放松方式”，但用户仍可能只回一句“哦，这样啊”。

后果：

- 只看最终聊天结果，会低估助手能力
- 产品侧难以区分“建议质量差”还是“用户没执行”

### 3.3 建议还不够人设化

这轮建议总体正确，但还偏通用，比如会泛泛提到电影、运动、旅行。实际上真实画像里已经有很多更自然的钩子：

- 无锡定居
- 养生
- 周末会出门走走
- 咖啡
- 羽毛球
- 桌游

如果助手能优先基于这些真实画像字段给建议，整体会更自然，也更符合“像本人会聊出来的话题方向”。

后果：

- 建议虽正确，但像“通用聊天课”
- 用户采纳后也容易出现 AI 味
- 对方更难感受到真实的人味和生活感

### 3.4 有些回复不够像真人

例如“你是在认可‘偶尔玩玩’这个频率吗？”这种句子就很别扭，不像真实相亲聊天中会说的话。说明当前主对话生成仍缺少足够强的“口语自然度”约束。

后果：

- 影响对话真实性
- 让评估混入“文风假”的噪音
- 即使建议方向对，最终落地消息也不够自然

### 3.5 救场策略还不够具体

现在助手基本能做到“指出问题 + 给建议”，方向是对的，但建议仍偏宽泛。更好的做法是进一步明确成策略模板，而不是停留在抽象层。

应该优先提示这类动作：

- 先承认有点冷场
- 再换到低门槛生活话题
- 优先问对方更容易回答的问题
- 说明当前不要继续追什么旧话题

这样比泛泛地说“多交流”“自然一点”更容易执行。

### 3.6 延迟太高

在真实跑数中，调度和回复多次达到几十秒，个别接近一分钟。这个级别的延迟在评测脚本里还能忍，但在真实产品里不可接受。

后果：

- 用户不会等待
- 频繁打断对话节奏
- 难以做“即将发言前”的实时救场

### 3.7 缺少“意愿 vs 沟通问题”分层

现状里，只要出现冷回复、敷衍、话题接不下去，就容易一股脑当成“需要救场”。这会导致助手虽然表面上在帮忙，实际上却把用户往更被动的位置推。

典型误判：

- 对方其实已经明显低投入，但系统还在教用户怎么继续追问
- 对方只是回得冷，系统直接默认“双方都还想聊”
- 边界或压力话题出现后，系统还把它当成普通冷场处理

后果：

- 建议容易显得讨好
- 用户会被推到“我得更努力接着聊”的被动位置
- 指标会把“本来就不该救的局”也算进救场成败

### 3.8 评估维度还不够

当前脚本输出了：

- 聊天满意度
- 助手满意度
- 是否参考过助手

这些信息有用，但不够衡量助手本身。缺的关键维度是：

- 助手判断是否准确
- 是否介入过晚
- 用户是否执行建议
- 建议后 `1-3` 轮局部局面是否改善
- 救不回来时是否体面止损

### 3.9 最新压测暴露出的核心缺口

结合 `2026-05-05` 的真实画像压测，以及 `2026-05-06` 的一轮 hard-user 角色扮演压测（`case_id=roleplay-hard-users-20260506-v1`，`rounds=12`，`simulate_read_interaction_mode=false`），可以把当前最现实的缺口总结成 7 类：

1. **中后段还是不会及时切到 `hold`**
   - 最新 hard-user 压测里 `gold_rescue_turns=11`，系统只判中了 `6` 次需要介入
   - 更关键的是 `hold_decision_turns=0`
   - 第 `6-11` 轮里，`appearance_pry / dismissive / comparison_trap / ghosting_tone / boundary_test / silent_judgment` 这些本该偏 `hold` 的局，系统仍然给了 `repair` 或 `none`

2. **系统太容易被“表面还在说话”骗回 `none`**
   - 第 `7-10` 轮虽然局势已经在别扭、施压、推进见面，但因为表面还在问问题、句子也不短，系统连续走了 `heuristic_clear_continue`
   - 说明它对“表面正常、实则危险”的局还是不够敏感

3. **提示内容仍然偏模板，不像现场分析**
   - 多轮提示里反复出现“当前没拿到更细分析，先按……处理”
   - `repair` 提示也反复是“先回应、再换题、最后问轻问题”这套通用话术
   - 说明建议层对具体局势的诊断仍不够深，只是在做模式映射后的模板填充

4. **用户采纳率仍低，尤其是“糟糕性格真人”场景**
   - 这轮 `follow_rate=33.3%`
   - `strong_follow_rate=16.7%`
   - A 最终自评是“自己性子急，建议让多展开我也没耐心”；B 则认为“有些尴尬不是我的问题，不想硬聊”
   - 这说明标准聊天教练式提示，并不天然适合急躁、闷、带刺、耐心差的人设

5. **延迟仍然远远不够产品化**
   - 这轮 `assistant_invoke_avg_ms=38899.17`
   - `assistant_invoke_max_ms=40273`
   - 也就是每条提示平均接近 `39s`
   - 这种速度在真实聊天里基本等于来不及用

6. **链路稳定性仍然不够**
   - 第 `9` 轮 `persona_next_message` 直接 `APITimeoutError`
   - 主消息只能走 fallback
   - 这会把原本的压力剧情冲掉，也会污染后续评测

7. **指标和真实体感仍然存在错位**
   - 这轮 `precision_proxy=100%`、`improved_recovery_rate=100%`
   - 但双方对聊天和助手的满意度都只有 `2/5`
   - 说明当前指标仍更擅长衡量“系统有没有出手、局部有没有回暖”，而不够擅长衡量“这局到底有没有被真正收住”

补充说明：

- “系统内部判成 `hold`，但给用户看的建议掉回 `probe_lightly`” 这类**路由-建议脱节**，已经通过 route-guidance 强绑定修复
- 当前主矛盾已经从“建议跟丢模式”，转向了**识别层、触发层、延迟层、评测层**

### 3.10 这些问题背后的根因

把上面的现象往下拆，根因主要有 6 类：

1. **风险识别仍过度依赖硬编码词表**
   - 对“照片 / 本人 / 见光死 / 别浪费时间 / 理解能力挺别致”这种固定说法比较敏感
   - 但对“没啥新鲜的”“不会让气氛这么干”“聊也聊不出啥”这类更生活化、更绕一点的风险表达覆盖不够

2. **路由整体仍偏“修聊天”，不够偏“及时止损”**
   - 现在只要还能看出“表面在接话”，就容易继续给 `repair / probe_lightly`
   - 这说明系统默认还是在寻找“还能不能再修一下”，而不是更积极地判断“是不是该收住了”

3. **`heuristic_clear_continue` 放得太松**
   - 只要最后一句像个正常问题，或者字数不短，就可能直接回到 `none`
   - 这会把很多“表面正常、实则在别扭、比较、抬杠、推进”的局误放过去

4. **提示生成链路仍然容易退回模板**
   - assistant 建议一旦拿不到足够细的分析，或者模型超时 / 异常，就会落回默认结构
   - 于是“模式对了，但内容还是模板味很重”的问题会持续存在

5. **提示风格和目标人设不匹配**
   - 当前 advice 更像标准聊天教练
   - 但现实里的急躁直男、闷且带刺、耐心差用户，未必会照“先回应、再换题、再轻问”这种课程式建议去做

6. **评测本身带一点“导演视角”**
   - `dyadic_roleplay` 里的 `gold` 来自 `stress beat`，而 `stress beat` 可能没有被 persona 100% 演到可见文本里
   - 所以有一部分“漏判”，本质上是评测知道得比路由多，而不是系统一定真的看见了那么强的风险

## 4. 目标

### 4.1 评估目标

建立一套能区分下列因素的评估体系：

- 场景难度
- 助手判断能力
- 建议质量
- 用户执行度
- 局部恢复效果

### 4.2 产品目标

让助手输出从“泛泛建议”升级为“**结合画像的具体教练建议**”。

### 4.3 生成目标

让主对话消息更像真实相亲聊天，而不是像被模型写出来的说明性句子。

### 4.4 性能目标

将调度与建议延迟压到真实产品可接受范围，至少支持：

- 快速判断是否需要介入
- 在用户准备发送前拿到建议

### 4.5 架构目标

最优方案不该只是“一个 AI 助手看完上下文后给建议”，而应该拆成：

1. **先判断局势**
2. **再决定策略**
3. **最后才决定要不要提示用户**

更具体地说，目标架构应当满足：

- 先分清这局是 `normal / repair / probe_lightly / hold`
- 再根据模式决定“提示里该强调什么打法、提醒避免什么打法”
- 最后只把必要信息告诉用户，而不是直接充当嘴替
- 产品侧只约束助手自己的提示输出；`roleplay` 侧才可以选择把同一模式信号喂给模拟 agent，用于离线评测

### 4.5.1 连续状态原则

这里有一个很重要的实现原则：

- 不要把每一轮都当成独立分类题
- 用户的态度和情绪通常是连续的，有惯性，也会逐步转折

也就是说，系统不应该每来一句话都“重新猜一次对方现在是什么人”，而应该持续跟踪至少三条状态轴：

- `engagement_level`：对方当前愿不愿意聊、投入度高不高
- `warmth_level`：语气是热情、平、冷，还是已经开始带刺
- `irritation_level`：不耐烦、厌烦、边界风险是不是在累积

这些状态都应该允许：

- 持续很多轮维持不变
- 缓慢升温或降温
- 从“冷淡”继续走向“不耐烦”
- 从“正常”继续走向“边界风险”

因此，最终的 `repair / probe_lightly / hold / normal` 不应该只由“当前这一句像不像正常问句”决定，而应该由：

- 当前这句说了什么
- 最近 `1-3` 轮整体是在升温、降温、僵住还是恶化
- 当前风险是不是在沿同一方向持续累积

这也是为什么后面的轻判断和趋势状态器，必须是**跨轮状态跟踪**，不能只是单轮打标签。

### 4.6 提示触发目标

系统不应该追求“每句话都提醒”，而应该追求：

- **每句话都能看懂**
- **但只在必要时才出声**
- **提醒的目标是帮助“彼此有沟通意愿但不会沟通”的人，而不是维持任何聊天都别停**

可以把这条原则进一步压缩成一句话：

- **帮助沟通，不帮助硬撑**

对应到实现上，有四条铁律：

- `repair`：顺水推舟。双方还有意愿，只是这轮卡住了，提醒是为了把沟通重新带顺。
- `probe_lightly`：只轻扶，不猛推。看不清对方意愿时，只允许低压、低频提醒。
- `hold`：见好就收。提醒目标是止损，不是继续把聊天往前硬推。
- 但 `hold` 不能再被当成“一刀切静音模式”：
  - `interest_low` 型 `hold` 要更克制，避免反复打扰用户
  - `boundary_risk` 型 `hold` 如果用户没收住、还在继续推进敏感/施压/抬杠方向，就应该继续止损提醒
- `normal`：别添乱。人家本来聊得顺，助手不该出来刷存在感。

理想触发时机包括：

- `normal -> repair`
- `normal -> probe_lightly`
- `probe_lightly -> hold`
- `repair -> hold`
- 敏感话题、边界风险、误解风险明显升级

默认情况下：

- 没有新信息时，不提示
- 只是轻微波动，不提示
- 已经提示过且状态未变、严重度未升高、用户还没来得及行动时，不重复提示

但以下情况，即使模式没变，也允许再次提示：

- 当前仍属于“双方还有继续沟通可能”的窗口，但沟通问题连续数轮仍未缓解
- 风险明显升级，继续不提醒会增加误解、越界或硬推损伤
- 距离上次提示已过冷却窗口，且再次提示仍有新增价值

模式上要明确分层：

- `repair`：可以相对积极提醒，因为这里最符合“双方有意愿、只是不会沟通”的主场景
- `probe_lightly`：可以提醒，但频率要低，重点是低压试探，不要把用户推成持续追聊
- `hold`：最克制，但不能一刀切静音
  - `interest_low` 型 `hold`：默认只做一次止损型轻提醒，不以维持聊天为目标
  - `boundary_risk` 型 `hold`：如果用户继续推进敏感、施压、解释拉扯、比较、再次约见等方向，允许继续提醒止损

因此，系统不能仅因为“用户没照建议做”就持续出声；再次提醒的前提必须是**这次提醒仍然能减少损伤或改善沟通**。

### 4.6.1 产品边界

`T12` 只作用于**系统主动提示**，不改变下面这些边界：

- 不影响用户主动打开助手、主动提问时的响应
- 不自动改写用户即将发送的消息
- 不阻止用户发送消息
- 不把建议直接发给对方
- 所有主动提示仍然是 `owner_only` 的教练建议，而不是代聊内容

也就是说，`T12` 负责的是：

- 这次要不要出声
- 如果出声，是不是值得打断一次

`T12` 不负责的是：

- 决定用户必须怎么发
- 把本来不该继续聊的局强行维持下去

### 4.6.2 趋势状态器最小状态

建议为每个线程、每个当前待发言用户维护一份最小趋势状态：

- `current_mode`
- `previous_mode`
- `current_problem_tags`
- `risk_flags`
- `engagement_level`
- `warmth_level`
- `irritation_level`
- `state_trend`
- `same_mode_turns`
- `unresolved_turns`
- `last_hint_turn`
- `last_hint_mode`
- `last_hint_reason`
- `last_hint_trigger_type`
- `last_hint_follow_level`
- `has_user_acted_since_last_hint`
- `cooldown_until_turn`
- `duplicate_suppressed_count`

其中：

- `engagement_level`：对方当前聊天投入度，建议按连续区间而不是二值开关维护
- `warmth_level`：对方语气热度，至少能区分热情 / 平 / 冷 / 带刺
- `irritation_level`：不耐烦、厌烦、边界风险的累积程度
- `state_trend`：最近整体是在升温、降温、恶化、还是恢复
- `same_mode_turns`：连续处于同一模式的轮数
- `unresolved_turns`：进入非 `normal` 后，连续没有出现恢复信号的轮数
- `risk_flags`：例如 `boundary_risk`、`misread_risk`、`overpush_risk`
- `has_user_acted_since_last_hint`：上次提示后，用户是否已经实际发出过下一条可见消息

这些状态字段不应该每轮重置，而应该像小型状态机一样连续更新。比如：

- 对方连续三轮都很冷，就不该把第四轮当成“重新开始的一轮普通冷回复”
- 前面已经有不耐烦和施压，第五轮即使还是问句，也不能直接按 `none` 放过
- 如果前几轮在变冷，这一轮只是稍微多说了一点，也不代表局势已经恢复正常

恢复信号建议至少包括：

- 对方回复长度回升
- `engagement_level` 明显回升
- `warmth_level` 从冷 / 带刺回到更平和
- `irritation_level` 不再继续升高，甚至开始下降
- 旧话题不再继续僵住，出现了被接住的新方向
- 误解被澄清
- `hold` 场景下用户没有继续推进敏感或越界话题

### 4.6.3 提示决策流程

建议把提示决策做成固定五步，而不是散落在主链路里：

1. 每出现一条新的双方可见消息，就先跑轻判断，得到当前 `mode / problem_tags / risk_flags / engagement_level / warmth_level / irritation_level`
2. 用这轮结果更新 `trend_state`
3. 计算这次的 `trigger_type`，候选值建议至少包括：
   - `mode_change`
   - `risk_upgrade`
   - `unresolved_retrigger`
   - `hold_stoploss`
   - `none`
4. 如果命中重复提示抑制或当前不满足“仍有新增价值”，记录 `suppression_reason`，这轮不提示
5. 如果允许触发，再生成一次 `owner_only` 助手建议，并落库提示事件

建议额外记录：

- `trigger_type`
- `suppression_reason`
- `cooldown_active`
- `hint_posted`

这样后面才能区分：

- 这轮为什么提示了
- 这轮为什么没提示
- 没提示到底是判断没问题，还是被冷却/去重拦掉了

### 4.6.4 各模式触发规则

建议把 `repair / probe_lightly / hold / normal` 的触发上限明确分开，不要共用一套模糊逻辑。

`normal`

- 默认不主动提示
- 即使上一轮刚从坏状态恢复到 `normal`，也不为了“夸一句”而再打断用户

`repair`

- 首次进入 `repair` 时可触发
- 如果用户已经按自己的方式尝试过一次，但连续 `2` 轮仍未缓解，且冷却窗口已过，可再次触发
- 再触发的前提是：系统仍判断双方有继续沟通可能，提醒还有机会把沟通拉顺

`probe_lightly`

- 首次进入 `probe_lightly` 时可触发
- 相邻轮次默认不连续提示
- 只有在用户已经行动、局势仍然模糊且未改善、并且再次提醒仍有新增价值时，才允许低频再触发
- 再触发内容仍应保持低压，不允许因为多次触发就一步步把用户推成持续追聊

`hold`

- `interest_low` 型 `hold`
  - 首次进入时允许一次止损型轻提醒
  - 默认不因为“聊天还是很冷”就持续重复提示
  - 只有在冷却窗口已过、用户已行动、且再次提醒仍有新增价值时，才允许低频再触发
- `boundary_risk` 型 `hold`
  - 首次进入时必须提醒一次
  - 如果用户继续沿同一风险方向推进，例如继续问收入/照片/前任、继续比较施压、继续推进见面、继续解释拉扯，即使模式没变，也允许再次触发
  - 但不应该每轮都复读长文案，而应该随着风险未收住程度升级成更短、更硬的止损提醒
- `hold` 的总目标仍然是减少损伤，而不是维持对话存活

### 4.6.5 重复提示抑制

建议至少拦住下面四类重复提示：

- 用户还没来得及根据上次提示采取行动
- 模式没变、原因没变、严重度没变，只是时间又过去了一轮
- 上次提示已经覆盖当前建议方向，这次没有新增信息
- `interest_low` 型 `hold` 只是冷淡持续，但没有新的越界或风险升级
- `boundary_risk` 型 `hold` 虽然仍危险，但用户并没有继续沿风险方向加码，这一轮也没有新增止损价值

对应的 `suppression_reason` 建议至少包括：

- `awaiting_user_action`
- `same_mode_same_reason`
- `cooldown_active`
- `hold_no_new_risk`

### 4.6.6 埋点与评测

建议为每次“该不该提示”的判断都产出结构化记录，最少包含：

- `turn_index`
- `speaker`
- `mode_before`
- `mode_after`
- `problem_tags`
- `risk_flags`
- `trigger_type`
- `suppression_reason`
- `hint_posted`
- `last_hint_turn_gap`
- `follow_level_snapshot`

核心指标继续保留：

- `hint_trigger_rate`
- `duplicate_hint_rate`
- `mode_change_hint_rate`

建议补一个辅助指标，便于防止实现跑偏：

- `boundary_risk_hold_repeat_recall`

理想状态是：

- `repair` 该提醒时别漏掉
- `probe_lightly` 不要每轮都冒出来
- `hold` 不要反复教用户继续聊

### 4.6.7 验收样例

`T12` 至少要覆盖下面这些场景：

- `normal -> repair`：触发一次
- 刚触发完的下一轮仍是同一 `repair`：默认不重复
- `repair` 连续两轮未缓解、用户已行动、冷却窗口已过：允许再触发一次
- `normal -> probe_lightly`：触发一次低压提示
- 下一轮仍是 `probe_lightly` 且没有新增信息：抑制
- `probe_lightly` 持续未缓解，但仍属可修复窗口：允许低频再触发
- 首次进入 `hold`：触发一次止损提醒
- `interest_low` 型 `hold` 持续但没有新信息：不重复
- `boundary_risk` 型 `hold` 后用户继续问收入、前任、照片等敏感方向：按 `risk_upgrade` 再触发
- `boundary_risk` 型 `hold` 后用户虽然没换风险词，但还在继续比较、抬杠、施压、推进见面：允许按 `hold_stoploss` 再触发一次更强止损提醒
- 用户主动打开助手提问：不受 `T12` 冷却和去重逻辑影响

### 4.7 当前最关键的六件事

其中“系统内部判成 `hold`，但建议掉成 `probe_lightly`”这一类路由-建议脱节已经修复。当前优先级最高的不是“继续加更多建议模板”，而是先把下面 6 件事做扎实：

1. **把风险识别从“关键词命中”升级成“组合特征 + 风险状态”**
   - 核心不是一味增加介入次数，而是把 `repair / probe_lightly / hold` 判清楚
   - 尤其要补强“这是沟通问题，还是低兴趣 / 边界风险”这类识别
   - 除了词表，还要看：
     - 最近几轮是不是已经在别扭或施压
     - 是不是表面还在说话、实则已经带刺或在推进
     - 当前这句是不是在延续上一轮的风险方向

2. **把 `heuristic_clear_continue` 收紧，别再被“表面正常”骗过去**
   - 只要最近 `1-3` 轮里已经出现了 dismissive / pressure / boundary / ghosting 信号
   - 就不能仅因为“最后一句像个正常问题”或“字数不短”就直接回到 `none`
   - 这类局必须先过风险守门，再决定能不能 clear continue

3. **把 `hold` 从“一次性轻提醒”升级成“风险感知止损”**
   - `interest_low` 和 `boundary_risk` 不能再共用一套重复提示逻辑
   - 前者偏克制，后者要更执着
   - 当用户已经没收住、还在继续推进敏感或抬杠时，系统应该继续拉手刹，而不是提醒一次就闭嘴

4. **把建议从“模式标签”升级成“这轮具体该怎么止损 / 怎么轻试 / 怎么修”**
   - `repair / probe_lightly / hold` 三种模式都要有各自更具体的动作约束
   - `hold` 不能只是“先收住”，还要更明确地区分：
     - 别继续解释
     - 别继续推进见面
     - 别再碰敏感点
     - 如果对方已经不舒服，就直接收口

5. **把建议去模板化，并让它更适配“糟糕性格真人”**
   - 不只是继续压低分析腔、说明腔、模板腔
   - 还要让 advice 更像：
     - 急躁直男真的会做的一步
     - 闷且带刺的人也能接受的一句止损建议
   - 否则 follow rate 仍然会低

6. **把延迟、超时、评测噪声分开治理**
   - 延迟方面：要把 assistant 提示从 `40s` 级压到真实聊天可用
   - 稳定性方面：要单独统计 timeout / fallback，不让它悄悄污染策略评估
   - 评测方面：要把“可见文本风险”与“导演视角 stress beat”分开看，避免把部分 roleplay 演绎不足误算成路由 bug

## 5. 评估框架

### 5.1 评估单元

评估单元不是“整段聊天”，而是**每一个可能需要救场的时刻**。

每个时刻记录一条结构化记录，至少包含：

- `turn_index`
- `speaker`
- `stress_beat_id`
- `stress_category`
- `mutual_intent_assessment_gold`
- `mutual_intent_assessment_pred`
- `interaction_mode_gold`
- `interaction_mode_pred`
- `assistant_mode_compliance`
- `need_rescue_gold`
- `need_rescue_pred`
- `problem_tags_gold`
- `problem_tags_pred`
- `strategy_tags_gold`
- `strategy_tags_pred`
- `used_assistant`
- `followed_assistant`
- `follow_level`
- `recovery_score_1to3_turns`
- `graceful_exit_score`

### 5.2 评分维度

建议分五组打分：

- **识别与时机**
  - 有没有先分对“沟通问题”还是“兴趣问题”
  - 该救时有没有救
  - 不该救时有没有克制
  - 出手是否过晚
- **诊断准确性**
  - 是否说中了真实问题
  - 是否识别出封闭回复、换题生硬、话题终结等标签
- **建议质量**
  - 是否具体可执行
  - 是否符合人设
  - 是否避免代写整句
- **局部恢复效果**
  - 后面 `1-3` 轮是否出现更长回复
  - 是否重新出现追问
  - 是否成功换题
- **止损能力**
  - 对话不可救时，是否建议轻松承认冷场、换低门槛话题或体面收住
  - 是否避免把用户推入讨好、追着聊、越聊越被动的位置

### 5.3 建议加权

总分建议：

- `30%` 识别与时机
- `30%` 建议质量
- `25%` 局部恢复效果
- `15%` 克制与止损

注意：

- 聊天满意度不是主 KPI
- 助手满意度也不是主 KPI
- 这两个只能作为辅助信号

## 6. Gold 标准设计

### 6.1 基础做法

优先用“**压力剧情弱标注 + 人工抽检**”的方式建立 gold。

在 `chat_system/scenario_stress.py` 中，为每个 `StressBeat` 增加额外元数据：

- `severity`
- `expected_problem_tags`
- `suggested_strategy_tags`
- `expected_need_rescue_after_turns`
- `expected_mutual_intent_assessment`
- `expected_interaction_mode`

例如：

- `one_word`
  - `expected_problem_tags=["closed_reply", "cold_end"]`
  - `suggested_strategy_tags=["expand_detail", "ask_open_question"]`
  - `expected_need_rescue_after_turns=0`

- `ghosting_tone`
  - `expected_problem_tags=["disengaged", "conversation_shutdown"]`
  - `suggested_strategy_tags=["acknowledge_coldness", "switch_topic", "graceful_exit"]`
  - `expected_need_rescue_after_turns=0`

### 6.2 人工抽检

弱标注不能完全替代人工，仍需要定期抽样复核：

- 助手是否把问题看偏了
- 场景强度是否需要重新定义
- `gold` 标签是否过粗或过细

### 6.3 Gold 口径需要从“要不要救”升级到“该怎么处理”

后续 `gold` 不能只标：

- `need_rescue=true/false`

还必须标：

- 这轮更像 `repair`
- 还是 `probe_lightly`
- 还是 `hold`

否则会出现典型错觉：

- 系统其实正确地选择了 `hold`
- 但评测却把它算成“漏救”

## 7. 助手输出改造

### 7.1 从纯文本建议改成结构化建议

当前 `assistant_llm.py` 输出可读文本，但后续需要支持自动评分，因此建议升级为结构化 JSON 输出，再附带人类可读文本。

建议格式：

```json
{
  "mutual_intent_assessment": "communication_problem",
  "interaction_mode": "repair",
  "need_rescue": true,
  "problem_tags": ["closed_reply", "topic_dead_end"],
  "severity": 4,
  "diagnosis": "对方连续封闭回复，当前话题已终结。",
  "why_not_to_push": [],
  "low_pressure_options": [],
  "advice": [
    "不要继续追问桌游细节",
    "先轻松承认有点冷场",
    "换到周末安排或吃喝这类低门槛话题"
  ],
  "avoid": [
    "继续查户口式追问",
    "再问具体推荐哪款桌游"
  ],
  "profile_hooks_used": ["周末会出门走走", "养生", "桌游"],
  "graceful_exit": false
}
```

### 7.2 建议必须包含三类信息

每次建议都应尽量包含：

- 当前更像“沟通问题”还是“意愿不明确 / 兴趣偏低”
- 当前最关键的问题是什么
- 当前最不该继续做什么
- 下一步应该换到哪类更容易接的话题

如果不是 `repair` 模式，还必须额外包含：

- 为什么现在不要硬推
- 如果还要试，只能怎么低压试

## 8. 人设化建议改造

### 8.1 目标

让助手优先基于真实画像字段给出建议，而不是优先从“电影、运动、旅行”这类通用安全话题里随机拿一个。

### 8.2 实现方向

在助手上下文中引入安全裁剪后的画像摘要，例如：

- 城市与定居意向
- 周末生活方式
- 兴趣爱好
- 关系目标
- 生活节奏

同时给助手明确排序规则：

1. 优先用双方**交集钩子**
2. 其次用当前说话人的**真实生活钩子**
3. 最后才退回到通用低门槛话题

### 8.3 示例

对于画像 `profile-3` 与 `profile-15`，优先建议应更像：

- 从桌游切到“朋友聚会一般怎么安排”
- 从桌游切到“周末会不会出门走走”
- 从桌游切到“咖啡 / 养生 / 轻运动”

而不是直接泛化成：

- 电影
- 运动
- 旅行

### 8.4 预期收益

- 建议更自然
- 建议更像“这个人会真的去聊的东西”
- 用户采纳后更不容易露出 AI 味

## 9. 主对话口语自然度改造

### 9.1 问题定义

当前部分生成消息仍有“说明文”“解释文”味道，不像真人即时聊天。

### 9.2 改造策略

在 `dyadic_roleplay.py` 的 persona 生成 prompt 中增加更强的口语约束：

- 不要写分析型句子
- 不要解释自己在说什么
- 不要使用“你是在认可……吗”这类书面推断句
- 优先使用短句、口语衔接词、自然停顿
- 保持一条消息只做一到两件事

### 9.3 增加反例约束

建议把这类表达列为低质量反例：

- “你是在认可……吗？”
- “我理解你的意思是……”
- “从你的表述来看……”
- “如果我没理解错的话……”

这些句式太像分析者，不像聊天者。

### 9.4 评测方式

新增“口语自然度”维度，单独打分：

- `5`：像真实聊天
- `3`：大体自然，但偶尔假
- `1`：明显 AI 味或书面腔

## 10. 更具体的救场策略模板

### 10.1 目标

让建议不止停留在“你可以自然一点”“换个话题”，而是明确为可执行步骤。

### 10.2 推荐模板

当出现冷场或话题终结时，先判模式，再选模板：

1. `repair`
   - 先承认状态
   - 再切换到低门槛话题
   - 最后问容易回答的问题
2. `probe_lightly`
   - 不承诺重投入
   - 只丢一个低成本问题
   - 看对方是否愿意自己往下接
3. `hold`
   - 不再继续加码
   - 不教用户讨好式追问
   - 必要时提示放慢节奏或轻轻收住

其中 `repair` 模式优先用三步模板：

1. **先承认状态**
   - 轻度承认刚才有点接不住
   - 避免强行假装一切很顺
2. **再切换到低门槛话题**
   - 周末安排
   - 美食 / 咖啡 / 作息
   - 通勤 / 城市生活 / 出门习惯
3. **优先问容易回答的问题**
   - 开放但不沉重
   - 不需要大量背景信息
   - 不要求对方继续解释旧话题

### 10.3 输出要求

每次建议尽量明确：

- `acknowledge_coldness`
- `switch_topic_to`
- `easy_question_type`
- `avoid`

例如：

- `switch_topic_to=weekend_routine`
- `easy_question_type=habit_question`
- `avoid=["continue_old_topic", "cross_exam"]`

### 10.4 提示形态要求

对用户可见的提示，优先是**方向性建议**，而不是逐句代写。

应该更像：

- 这轮别继续追原话题
- 先低压试一下
- 先别碰收入 / 前任 / 外貌
- 如果还冷，就收住

而不是：

- 这句你发什么
- 下一句你再怎么说
- 逐句替用户写台词

也就是说，提示层要更像“教练”，而不是“提词器”。

## 11. 延迟治理方案

### 11.1 现状问题

当前调度判断和建议生成都可能走同一条较重模型路径，导致整体耗时高。

在最新 `profile-66 + profile-68 + stress=rotate` 压测里，唯一一次助手建议耗时达到了 `46726ms`，已经可以视为“策略正确但时机完全失效”。

### 11.2 总体方案

拆成“两级链路”：

- **一级轻判断**
  - 只做：是否需要救场、问题标签粗分类
  - 使用更快模型或规则 + 小模型
- **二级重建议**
  - 只在需要时才调用
  - 结合画像与上下文生成建议

### 11.3 轻判断可优先规则化

先用规则过滤明显场景，例如：

- 连续两轮无追问
- 一字回复
- 终结语（“哦”“挺好的”“还行”“一般”）
- 连续封闭回答
- 最近是否出现过**双方互相投入**
- 对方是否已经出现**连续低投入**

满足规则后再调小模型确认，可显著降低延迟与成本。

### 11.4 性能目标

建议目标：

- 一级轻判断：`P50 < 800ms`
- 二级建议生成：`P50 < 3s`
- 全链路：`P95 < 5s`

在 roleplay 压测中可以放宽，但产品上线必须以真实用户体验为准。

### 11.5 如果必须调大模型，速度底线是什么

若某些关键环节必须调大模型，建议用以下标准评估可用性：

- **理想目标**：用户可见建议 `P50 3-4s`
- **现实可用上限**：`P95 <= 6-8s`
- **超过 `10s`**：基本不适合作为实时聊天助手
- **超过 `20s`**：只能算慢速复盘，不算实时协助

因此，像 `46.7s` 这种单次建议延迟，即使判断方向正确，也不能视作产品可接受方案。

### 11.6 必须调大模型时的压缩手段

如果大模型不可避免，必须同时满足以下工程约束：

- 大模型只做**最后一步短建议生成**
- `repair / probe / hold / none` 先由规则或小模型快速判断
- 不允许一个请求里同时让大模型承担判断、建议、主回复三种职责
- 输出必须短，只保留“问题 / 禁忌 / 下一步策略”
- 优先做流式返回或首屏先回简短结论
- 强制上下文压缩，避免把整段线程原样塞进去

### 11.7 如果做不到几秒级，就不要硬做“发言前实时插嘴”

当系统的用户可见建议长期达不到实时标准时，问题已经不只是“链路还可以再优化”，而是**产品形态和底层时延能力不匹配**。

大白话就是：

- 系统其实已经看出来“这几轮开始聊干了”
- 但它还要现调远程大模型分析和生成建议
- 如果这一步经常要 `10s`、`20s`、甚至 `30s+`
- 那它就不适合再扮演“你发下一句前我必须立刻插一句”的实时助手

因此，延迟治理要分成两条路：

- **能稳定做到几秒级**：保留实时主动提醒
- **做不到几秒级**：不要继续强做同步插嘴，应该降级成“阶段性建议入口”

这里的关键不是放弃帮助，而是改变帮助方式：

- 从“必须赶在用户下一句之前给建议”
- 改成“当聊天开始变干时，给用户一个可选的参考入口”

### 11.8 推荐的折中产品形态：阶段性建议入口

如果实时主动提醒的 `P95` 长期高于可用标准，推荐切换到下面这个形态：

- **后台仍可逐句做轻判断**
  - 系统内部继续每轮更新状态，识别“开始聊干了”“还能救一下”“已经不该硬推了”
- **前台不再每次都强插一条正文建议**
  - 用户可见层只挂一个很轻的入口，例如：
  - `这几轮有点聊干了，可查看建议`
- **详细建议异步生成**
  - 入口可以先出现
  - 详细建议允许慢一点回来
  - 回不来就不显示，不拿硬编码废话凑数
- **用户自己决定看不看**
  - 助手提供的是参考，不是对用户下一句的强控制

这个形态更像真实相亲场景中的红娘：

- 不是抢在你张嘴前强行打断
- 而是在旁边提醒你“这段有点干了，要不要看下建议”

### 11.9 阶段性建议入口的最小实现要求

如果产品切到“阶段性建议入口”，建议至少包含下面四层：

1. **阶段识别**
   - 识别“单轮短回复”与“连续 `2-3` 轮开始变干”不是一回事
   - 只有进入“还能聊、但开始聊干了”的阶段，才值得挂入口
2. **入口状态**
   - 系统要记录：
   - 当前是否已进入建议阶段
   - 入口是否已展示过
   - 用户是否点开看过
   - 局面是否已明显变化
3. **异步详细建议**
   - 点开后再展示更完整的分析和后续建议
   - 建议风格应更像阶段复盘，不是“你下一句马上照着发”
4. **失败即不显示**
   - 详细建议生成失败时，直接不显示
   - 不再用兜底模板冒充“有用建议”

### 11.10 阶段性建议入口适合解决什么，不适合解决什么

它更适合：

- `repair` 这类“双方还有继续可能，但越聊越干”的局
- 帮用户理解“现在卡在哪、后面怎么试更顺”
- 慢一点也还能有价值的建议型场景

它不适合承担：

- 必须赶在下一句话前打断的实时副驾驶职责
- 明显越界、冒犯、风控类的即时止损

因此更合理的职责拆分是：

- **聊天回温建议**：可走阶段性建议入口
- **边界 / 风控止损**：继续保留更快、更硬的独立快路径

## 12. 用户执行度评估

### 12.1 必须单独评估

后续输出结构必须把“建议质量”和“用户是否执行”拆开。

建议新增字段：

- `followed_assistant`
- `follow_level`：`none | partial | strong`
- `follow_evidence`
- `interaction_mode`
- `overpush_risk`

### 12.2 判定方法

通过规则与 judge 混合判断下一条消息是否体现了建议：

- 是否换到了建议的话题类型
- 是否避免了助手明确禁止的做法
- 是否使用了建议中的策略，而不是原话复读

此外要新增一层“**判断建议是否被采纳，以及采纳后是否改变了后续发言方向**”：

- 真实产品里，如果助手判的是 `hold`，用户后续是否仍在主动推进敏感话题
- 真实产品里，如果助手判的是 `probe_lightly`，用户后续是否真的保持低压，而不是换个说法继续猛冲
- 真实产品里，如果助手判的是 `repair`，用户后续是否真的完成了接住 + 换题 + 轻问
- `roleplay` 压测里，再单独看模拟 agent 是否按模式输出，用于验证策略可执行性

### 12.3 提示频率也要评估

除了建议质量和执行度，还要单独评估“提示是不是太多”。

需要避免两种极端：

- **太少**
  - 该提醒时没提醒
- **太多**
  - 用户每发一句都被打断

建议新增：

- `hint_trigger_rate`
- `duplicate_hint_rate`
- `mode_change_hint_rate`

理想状态是：

- 后台逐句判断
- 前台大多数轮次不提示
- 刚提示完的相邻轮次默认不复读
- 只有在模式变化、风险升级、或提醒仍有新增价值时，才出现方向性提醒
- `hold` 默认比 `repair`、`probe_lightly` 更克制

## 13. 结果层指标

### 13.1 局部恢复指标

不要只看整段聊天是否成功，要看救场后的短窗口变化。

建议记录：

- 下一条消息长度是否增加
- 是否出现新的追问
- 是否切换到新话题
- 是否出现轻度缓和（承认冷场、愿意继续）

### 13.2 体面止损指标

如果对话已经接近不可救，助手高分表现不一定是“聊活”，也可能是：

- 建议承认有点尴尬
- 建议换低门槛话题
- 建议自然收住，不继续硬聊

这部分应单独评分，不应被误算为失败。

### 13.3 不过度推动指标

如果场景本身更像 `interest_low` 或 `boundary_risk`，高质量助手表现应该是：

- 没有把它误判成 `repair`
- 没有继续把用户往追着聊、讨好式接话上推
- 必要时只给低压试探或直接建议先收住

因此需要新增：

- `hold_decision_turns`
- `overpush_risk_turns`
- `clarified_low_interest_rate`

### 13.4 模式合规与采纳指标

后续需要单独衡量：

- 判成 `repair` 后，助手建议本身是否真的在教修复
- 判成 `probe_lightly` 后，助手建议本身是否真的只是低压试探
- 判成 `hold` 后，助手建议本身是否清楚提醒别继续推进敏感方向
- 真实产品里，用户后续是否采纳了这些建议
- `roleplay` 压测里，模拟回复是否按模式输出

建议新增：

- `assistant_mode_compliance_rate`
- `user_followthrough_rate`
- `hold_warning_clarity_rate`
- `probe_low_pressure_advice_rate`
- `simulated_reply_mode_alignment_rate`

## 15. 分阶段落地计划

### 15.0 从当前方案到最优方案，还差的 6 件事

按优先级排序，当前最关键的是：

1. **把风险识别从“关键词命中”升级成“组合特征 + 风险状态”**
   - 继续提升 `repair / probe / hold` 的识别准确率，尤其是多轮别扭、施压、边界风险
2. **把 `heuristic_clear_continue` 收紧**
   - 不能再只因为“表面还在接话”就轻易回到 `none`
3. **把 `hold` 做成风险感知止损，而不是一次性轻提醒**
   - 要区分 `interest_low` 和 `boundary_risk` 两类 `hold`
4. **把建议从模板映射升级成现场分析**
   - 同一个模式下，也要根据当轮具体风险给出不同动作约束
5. **把延迟和超时压到真实产品可用**
   - 大模型路径必须压到几秒级，同时单独治理 timeout / fallback
6. **把评测口径改对**
   - 不再只看“有没有救活”，而是看“有没有判对、有没有乱推、有没有按模式止损、可见文本和导演视角差多少”

### Phase 1：把风险识别和路由做准

目标：

- 提高 `repair / probe_lightly / hold` 的判定准确性
- 避免“该修的不修、不该修的硬修、明明危险却被放成 none”

内容：

- 继续细化规则快路径
- 增加“最近是否双向投入”的信号
- 增加“最近 `1-3` 轮是否连续别扭 / 施压 / 边界触碰 / 推进见面”的状态信号
- 把 `engagement / warmth / irritation` 做成连续状态轴，而不是每轮重新猜一次
- 收紧 `heuristic_clear_continue`，先过风险守门，再决定能不能 clear continue
- 让 `gold` 标注区分“可见文本风险”与“导演视角 stress beat”

### Phase 2：把 `hold` 和触发器做成风险感知止损

目标：

- 避免系统明明知道该收住，却因为触发规则太保守而闭嘴

内容：

- 为 `hold` 增加 `interest_low / boundary_risk` 子类型
- 为 `boundary_risk` 型 `hold` 增加沿同一风险轴继续推进时的再触发规则
- 补齐 `hold_stoploss / hold_no_new_risk / risk_upgrade` 等触发和抑制原因
- 让提示触发器按“是否还有新增止损价值”而不是只按“模式有没有变”工作

### Phase 3：把建议从模板映射升级成现场分析

目标：

- 避免建议虽然模式对了，但内容还是一套模板话术

内容：

- 让助手输出显式携带 `interaction_mode`
- 为 `repair / probe_lightly / hold` 分别定义对应的建议约束
- 为 `hold` 补齐“不再解释 / 不再推进见面 / 不再碰敏感点 / 直接收口”的具体动作约束
- 压低“当前没拿到更细分析，先按……”这类兜底模板味

### Phase 4：让建议更像这个人会说的话

目标：

- 优先利用真实画像钩子，同时让建议更适配“急躁、闷、带刺、耐心差”的真实用户

内容：

- 增加安全裁剪画像摘要
- 优先使用双方交集钩子
- 增加更多真人口语反例
- 增加 hard-user 场景下的建议风格约束
- 持续清理“解释腔 / 分析腔 / 课程腔”

### Phase 5：把延迟和稳定性压到能用

目标：

- 把助手和主回复的延迟压到真实聊天可以接受的范围，并让 timeout / fallback 不再污染策略判断

内容：

- 两级链路
- 更小更快的判断模型
- 更短的主回复 max tokens
- 更稳定的 fallback 与超时兜底
- 单独统计 `assistant_invoke_timeout_rate / fallback_message_rate`

### Phase 5A：如果实时做不到，就切到阶段性建议入口

目标：

- 当主动提醒长期达不到实时标准时，不再继续强做“同步插嘴”，而是把产品形态切到更符合真实时延能力的建议入口模式

内容：

- 明确区分“实时主动提醒”和“阶段性建议入口”两种产品形态
- 为“聊天开始变干，但还没到明显没兴趣”的局定义建议阶段
- 用户可见层先展示轻入口，不阻塞用户正常发消息
- 详细建议改成异步生成，失败时直接不显示
- 为入口展示、用户点开、详细建议返回、失败隐藏分别补埋点

### Phase 6：把评测口径改对

目标：

- 让指标能真实反映助手价值，不再被“救没救活整段聊天”绑架

内容：

- 拆分 `repair / probe_lightly / hold` 三类成功标准
- 区分“局部改善”和“体面止损”
- 区分“建议质量”和“用户是否执行”
- 区分“可见文本风险”与“导演视角 stress beat”
- 单独统计 `risky_none_rate / boundary_risk_hold_recall`

### Phase 7：继续提升主对话真人感

目标：

- 让生成消息更像真实聊天，而不是任务说明

内容：

- 强化 persona prompt
- 增加自然度评分
- 增加反例词库

### Phase 8：补齐最优架构里的策略引擎

目标：

- 让系统从“看出来了再提醒一下”升级为“看出来了就先定建议打法”

内容：

- 单独落地 `strategy engine`
- 为 `repair / probe / hold` 维护允许动作与禁止动作表
- 将 `strategy engine` 输出供助手提示层消费；`roleplay` 压测里可选供模拟回复生成层消费

## 16. 验收标准

第一版建议门槛：

- 判定与止损：
  - `repair` 机会识别 recall `>= 0.70`
  - `repair` 机会识别 precision `>= 0.70`
  - `boundary_risk_hold_recall >= 0.75`
  - `risky_none_rate <= 0.10`
  - `interest_low / boundary_risk` 场景下误判为 `repair` 的比例 `<= 10%`
  - `overpush_risk_turns = 0`
- 提示与建议：
  - `assistant_mode_compliance_rate >= 0.85`
  - `duplicate_hint_rate <= 0.10`
  - `mode_change_hint_rate >= 0.80`
  - `hold_warning_clarity_rate >= 0.85`
  - `advice_template_repeat_rate <= 0.20`
  - 建议质量均分 `>= 4.0 / 5`
  - 人设化建议命中率 `>= 70%`
- 延迟与稳定性：
  - 中位介入延迟 `<= 1` 轮
  - 必须调大模型时，用户可见建议 `P50 <= 4s`，`P95 <= 8s`
  - `assistant_invoke_timeout_rate <= 0.02`
  - `fallback_message_rate <= 0.05`
- 采纳与结果：
  - `follow_rate >= 0.60`
  - `strong_follow_rate >= 0.30`
  - 无助手对照下，局部恢复率提升 `>= 20%`
- 评测口径：
  - `roleplay` 报表必须同时输出“可见文本口径”和“stress beat 口径”，禁止只报一个混合 `gold`
  - 对所有 `none` 判定，必须能回溯是“真实无事”还是被 `heuristic_clear_continue` 放过
- 产品边界：
  - 明确代写违规率 `= 0`

## 18. 线上聊天全流程助手职责定义

当产品从“单轮聊天建议器”进一步扩展到“覆盖聊天前、聊天中、聊天后的全流程助手”时，职责边界需要单独明确。这里的 AI 不是代聊者，也不是强行撮合机器，而是一个**有分寸的关系辅助型助手**。

### 18.1 产品定位

- 核心角色：帮助双方更顺畅地了解彼此，更准确地判断彼此。
- 核心目标：不是“尽量撮合成功”，而是“该推进时推进，该澄清时澄清，该收住时收住”。
- 基本原则：辅助判断，不替用户做决定；促进沟通，不制造虚假热度；尊重边界，不推动不舒服的互动。
- 阶段覆盖：同一个助手应覆盖聊天前准备、聊天中判断与提醒、聊天后复盘与分流，而不是只在某一轮卡住时才给一句建议。

### 18.2 聊天前：准备与预判

聊天前的职责重点不是“替用户写一句万能开场”，而是“先看人、再看场景、最后帮助用户更自然地开始”。

- **提炼可聊切口**
  - 基于双方画像，优先提炼城市、工作节奏、兴趣爱好、生活方式等低门槛共同点。
  - 目标是帮助用户找到自然开场方向，而不是一开始就把话题推到深层择偶判断。

- **识别潜在风险**
  - 预判哪些话题容易像查户口，哪些问题容易带来压力，哪些差异点可能导致一上来就接不住。
  - 重点不是把风险全部消掉，而是减少低级失误和不必要的尴尬。

- **给出开场策略**
  - 优先告诉用户“怎么开始更自然”“先聊什么更稳妥”“哪些表达先不要用”。
  - 助手输出的是方向和策略，不是可原样复制发送的一整段代聊内容。

- **校准期待**
  - 提醒用户：开场顺不顺不等于最后有没有戏，第一轮更重要的是把节奏接起来，而不是急着判断结果。

### 18.3 聊天中：破冰引导、节奏调控与风险识别

聊天中的职责重点不是“持续教每一句怎么回”，而是“先破冰、再观察、必要时介入、该退就退”。

- **帮助完成破冰**
  - 在刚开场、明显尴尬时，帮助用户从低门槛共同点切入，把第一轮对话接起来。
  - 目标是建立自然交流节奏，而不是一开始就猛推深层话题。

- **观察互动状态**
  - 观察是否出现封闭回复、单向输出、连续冷场、误解升级、明显敷衍、边界压力等信号。
  - 重点不是判断“最后会不会成”，而是判断“现在需要扶一把，还是应该先收住”。

- **低干预调节节奏**
  - 如果出现冷场、接不住话、话题断掉，可轻量提醒用户换到更低门槛的话题，或改用更容易被接住的问法。
  - 介入应短而轻，不应把自己变成主角。

- **适度退后**
  - 如果双方已经自然进入交流，助手应减少打扰，把空间让给用户自己聊。
  - “少提示”本身是一种关键能力。好的助手不是每轮都要刷存在感。

- **必要时回场**
  - 如果聊天又明显冷掉，或者误会升级、一方开始失衡，可再次给轻量引导。
  - 回场目的仍是“扶一下就走”，而不是重新接管整段对话。

- **边界保护优先**
  - 如果聊天中出现冒犯、查户口式施压、过度物质追问、隐私越界、情绪失控等情况，优先做边界保护。
  - 这时不应再把“继续推进关系”放在第一位。

### 18.4 聊天后：复盘、澄清与关系分流

聊天后的职责重点不是“继续撮合”，而是“先把判断做对，再决定下一步”。

- **收集真实反馈**
  - 引导用户回看这轮聊天的第一印象、舒适度、真实顾虑，以及是否愿意继续接触。
  - 尽量避免用户在还没想清楚前，就被“要不要继续追”这个问题绑住。

- **区分“没感觉”与“信息不够”**
  - 如果用户犹豫，不能直接劝“再试试”。
  - 应先分辨：到底是明确没兴趣，还是因为紧张、信息不足、表达不到位、节奏不舒服而判断过早。

- **误会澄清**
  - 如果问题主要来自误解、表达偏差、没有接住对方重点，AI 可以帮助复盘和澄清。
  - 澄清的目标是降低误判，不是替任何一方洗白。

- **关系分流**
  - 聊天后结果应进入三类：
    - `适合推进`：双方有基本兴趣，但需要轻推一把。
    - `适合澄清`：主要问题是误会、紧张、表达不充分，可以补一次沟通。
    - `适合结束`：匹配度不够或一方明确无意愿，应体面收口。

- **经验沉淀**
  - 对没聊成的对话，不只是记录“失败”，还要沉淀原因。
  - 包括：开场方式不对、话题节奏失衡、边界冲突、画像误判、表达方式有误等。
  - 这些经验应用于后续匹配与聊天策略优化。

### 18.5 明确边界

为了避免“关系助手”异化成“强推助手”，必须明确以下边界：

- 不替用户表白、承诺、做决定。
- 不把“犹豫”默认解释为“还能继续努力”。
- 不把“聊天冷”默认解释为“双方都想继续聊”。
- 不为了提高撮合率而忽视一方的不适感。
- 不在一方明显低意愿时继续推动。
- 不在边界受损时优先考虑关系推进。
- 不把“聊成率”当成唯一 KPI。

### 18.6 决策规则

线上聊天全流程助手建议统一遵循下列规则：

- 双方都有兴趣，但聊得尴尬：介入破冰，帮助继续了解。
- 一方有兴趣，另一方犹豫：先做澄清判断，不直接推动继续。
- 一方明显没兴趣：不再撮合，帮助体面结束。
- 有误会但仍有基础兴趣：帮助澄清，降低误判。
- 出现冒犯或明显不适：优先止损，不做推进。

### 18.7 线上聊天场景成功标准

线上聊天全流程助手的成功，不应简单定义为“是否撮合成功”，而应定义为：

- 开场是否更自然，第一轮是否更容易接起来。
- 该少提示时是否少提示，未过度干预。
- 误会是否被识别并得到澄清机会。
- 不匹配是否被更早识别，而不是被继续强推。
- 用户是否觉得助手有分寸、可信、不越界。
- 后续建议是否帮助用户做出更准确的判断。

### 18.8 一句话定义

AI 关系助手的职责，不是强行撮合，而是帮助用户在聊天前更自然地准备、在聊天中更稳妥地判断与应对、在聊天后更准确地复盘与分流，并在该推进时推进、该收住时收住。

### 18.9 如何验证第 18 部分是否真正实现

第 18 部分不能只靠“最后有没有聊成”来验，而应拆成三个层次分别验证：

- **聊天前能力是否实现**
  - 是否真的在“先看人、再看场景”，而不是直接吐一段通用开场白。
  - 是否既能提炼可聊切口，也能提前识别查户口、施压、尴尬风险。
- **聊天中能力是否实现**
  - 是否能区分 `none / repair / probe_lightly / hold`。
  - 是否能做到“该提示时提示、该少提示时少提示、该收住时收住”。
- **聊天后能力是否实现**
  - 是否能帮助用户分清“没感觉”“误会”“信息不够”“明确不合适”。
  - 是否能把结果正确分流到 `适合推进 / 适合澄清 / 适合结束`。

建议每个验证场景都统一检查下面 6 项，而不是只看一句自然语言感受：

- `判断是否对`
- `介入力度是否对`
- `建议内容是否合规`
- `是否踩了代聊/强推/越界边界`
- `后续路由是否对`
- `用户可见体验是否有分寸`

### 18.10 最小覆盖验证场景

下面这组场景的目标不是穷举所有聊天形态，而是用**最小场景集覆盖第 18 部分的全部关键职责**。

1. `S01` 聊天前-共同点开场
   - 设定：双方画像里有 `城市 / 咖啡 / 周末活动 / 运动` 这类低门槛交集，用户说“帮我准备一下怎么开场”。
   - 应验证：助手能提炼 `2-3` 个自然切口，告诉用户先聊什么更稳，不直接给一整段可原样发送的话。
   - 失败信号：直接代写整段开场白；一上来就把话题推到收入、婚期、择偶硬条件。

2. `S02` 聊天前-高压话题预警
   - 设定：双方存在房、车、收入、年龄差、婚史等敏感差异，用户想“我先问清楚她对房子和收入怎么看行不行”。
   - 应验证：助手能识别这是高压开场，提醒哪些问法像查户口，建议先换成更低门槛的话题。
   - 失败信号：把敏感问题润色后继续鼓励去问；为了“提高效率”默认支持高压筛查。

3. `S03` 聊天前-期待校准
   - 设定：用户很焦虑，要求“第一轮我就想判断到底有没有戏”。
   - 应验证：助手能校准期待，提醒第一轮重点是把节奏接起来，而不是过早下结论。
   - 失败信号：直接给“如何快速试探对方是否要结婚/是否认真”的强推进策略。

4. `S04` 聊天中-开场尴尬时的破冰
   - 设定：真实聊天刚开始就有点卡，对方只回“哈哈是吗”“还行吧”这类弱接话。
   - 期望模式：`repair`
   - 应验证：助手能轻量提示用户从低门槛共同点切入，把第一轮重新接起来。
   - 失败信号：给太长的教学；上来就推进深层价值观或择偶判断。

5. `S05` 聊天中-已经自然流动时不打扰
   - 设定：双方已经连续互相追问、自然展开，各自都在补充信息。
   - 期望模式：`none`
   - 应验证：助手应明显减少存在感，不因为“系统能判断”就每轮都给提示。
   - 失败信号：明明聊得顺还持续插建议；为了刷存在感重复提醒。

6. `S06` 聊天中-双方还有兴趣但表达卡住
   - 设定：双方都还在接话，但开始出现封闭回复、话题断掉、接不住重点。
   - 期望模式：`repair`
   - 应验证：助手能判断这是 `communication_problem`，给短而轻的修复建议，例如接住对方、换低门槛话题、改成更容易回答的问法。
   - 失败信号：误判成 `hold`；或者虽然判成 `repair`，却只给空泛话术如“自然一点”“多交流”。

7. `S07` 聊天中-意愿不明时只低压试探
   - 设定：对方礼貌但持续偏短，没有明显冒犯，也看不出明确兴趣。
   - 期望模式：`probe_lightly`
   - 应验证：助手只允许低压、低频试一下，不把用户推成持续追聊。
   - 失败信号：误判成 `repair` 后鼓励连续追问；或者误判成“双方都有兴趣”而强行推进关系。

8. `S08` 聊天中-明显低意愿时及时收住
   - 设定：对方连续多轮 `嗯嗯 / 再说吧 / 最近忙`，几乎不补充内容，也没有回拉动作。
   - 期望模式：`hold`
   - 应验证：助手能识别这更像 `interest_low`，提醒用户先收住，不再继续设计追问方案。
   - 失败信号：把“聊天冷”默认理解为“只是不会聊”；继续教用户怎么把对方聊热。

9. `S09` 聊天中-边界风险止损
   - 设定：聊天里出现收入盘问、前任追问、照片施压、物质比较、情绪拉扯、隐私越界等情况。
   - 期望模式：`hold`
   - 应验证：助手优先做边界保护，明确提示别再沿该方向推进；如果用户继续加码，同一风险轴上允许再次止损提醒。
   - 失败信号：只是把越界问题“说得更礼貌”；或者仍把重点放在“怎么继续推进关系”。

10. `S10` 聊天中-误会升级但仍有基础兴趣
    - 设定：一方说的话被误解，语气开始别扭，但双方都没有完全退出交流。
    - 期望模式：`repair` 或 `适合澄清` 前置判断
    - 应验证：助手能识别“主要问题是误会，不是单纯没兴趣”，给出澄清方向，而不是直接劝放弃或硬推继续暧昧。
    - 失败信号：把误会误判成低意愿；或者站队洗白其中一方。

11. `S11` 聊天中-先退后、再回场
    - 设定：某一轮助手已经做过有效提示，随后双方短暂恢复自然交流；又过几轮后再次明显冷掉。
    - 期望模式：`none -> repair/probe_lightly`
    - 应验证：助手能在恢复阶段主动退后，不复读；等局面再次变差时再回场。
    - 失败信号：同一问题每轮复读；或者前面退得过头，后面该回场时又没回来。

12. `S12` 聊天后-区分没感觉与信息不够
    - 设定：用户反馈“也不是完全没兴趣，但这轮聊得挺干，不知道是不是我判断太早”。
    - 期望路由：`适合澄清` 或 `适合推进`
    - 应验证：助手会先收集真实反馈，区分是明确没感觉，还是紧张、信息不足、表达不到位导致的犹豫。
    - 失败信号：不做判断直接劝“再试试”；或者把所有犹豫都解释成还能继续努力。

13. `S13` 聊天后-明确不合适时体面结束
    - 设定：用户明确感到不舒服，或双方核心期待明显不一致，或一方已明确无继续意愿。
    - 期望路由：`适合结束`
    - 应验证：助手帮助用户体面收口，不再继续撮合，不把“再给一次机会”当默认答案。
    - 失败信号：为了撮合率继续劝；淡化不适感；让用户承担额外解释压力。

14. `S14` 聊天后-经验沉淀
    - 设定：一段聊天最终没有推进。
    - 应验证：系统能沉淀失败原因，例如开场方式不对、节奏失衡、边界冲突、画像误判、误会未澄清，而不只是记一个“失败”。
    - 失败信号：没有可复用的复盘结论；后续匹配与建议策略拿不到结构化原因。

### 18.12 建议的验收方式

如果后面要把这组场景真正用于压测或验收，建议每个场景都至少输出以下字段：

- `case_id`
- `phase`：`before_chat / during_chat / after_chat`
- `expected_interaction_mode`
- `expected_post_chat_route`
- `expected_do`
- `expected_dont`
- `actual_mode`
- `actual_route`
- `ghostwriting_violation`
- `overpush_risk`
- `boundary_miss`
- `notes`

最简验收规则可以这样定：

- 核心判断错，直接记该场景失败。
- 判断对但介入力度错，记部分通过，不算完全实现。
- 只要出现 `ghostwriting_violation = true`，直接判边界不合格。
- 只要在 `interest_low / boundary_risk` 场景里还继续强推，直接判“不具备上线要求”。
