# 聊天助手改进方案

本文档沉淀 `partner-chat-system` 中相亲聊天助手的完整改进方案，覆盖 **评估方法**、**产品边界**、**提示词与生成策略**、**延迟治理**、以及 **分阶段落地计划**。本文档是对 [聊天与 Agent 中间人架构方案](chat-agent-architecture.md) 的补充，重点回答一个更具体的问题：

- 当用户或压力剧情**故意制造冷场、尬聊、误解、封闭式回复**时，应该如何衡量 AI 助手？
- 现有助手在哪些地方还不够好，应该怎么改？

---

## 1. 背景

当前 `partner-chat-system` 已支持：

- 双用户真实线程 `dyadic` 主对话
- `owner_only` 侧信道助手建议
- `run_dyadic_agent_roleplay.py` 基于真实画像与压力剧情的角色扮演压测
- 对话结束后的双方满意度自评

在 `2026-05-05` 对真实画像 `profile-3` 与 `profile-15` 的一轮角色扮演测试中：

- 共 `8` 个压力回合
- 触发 `3` 次 proactive 救场
- 双方对聊天满意度均为 `2/5`
- 双方对助手满意度均为 `4/5`

这个结果说明：**聊天失败** 与 **助手无效** 不是一回事。助手可能判断准确、建议方向正确，但用户没有执行到位，或者场景本身就接近不可救。

因此，后续改进不能只盯着“最终聊没聊成”，必须把评估与改造拆成更细的层次。

---

## 2. 核心原则

### 2.1 评估原则

- 不只看“最后是否聊成”，要拆分为：**识别问题**、**给出建议**、**用户执行**、**局部恢复效果**。
- 不把“用户故意制造冷场”的场景，简单等价为“助手失败”。
- 不把“助手建议被忽略”的结果，直接归咎于提示词质量。

### 2.2 产品边界原则

- 助手是**聊天教练**，不是**代聊枪手**。
- 助手只做：指出当前问题、给出下一步策略、提示不要再做什么。
- 助手不做：直接代写一条可以原样发给对方的消息。
- 助手的主场景不是“尽量把任何快死的聊天救回来”，而是**帮助双方都还想继续聊、但这轮沟通卡住了的人**。
- 因此必须先分清三种情况：
  - `communication_problem`：双方大概率都还想继续聊，只是这轮接话、换题、理解出了问题。这里助手才应该积极介入。
  - `interest_unclear`：暂时看不清对方是不会聊，还是没那么想聊。这里只能给**低压试探**，不能给讨好式救场。
  - `interest_low / boundary_risk`：对方明显低投入，或已经碰到隐私、物质、边界压力点。这里重点是**别再硬推**，而不是继续教用户怎么追着聊。

### 2.3 落地模式原则

产品和评测里统一用四种模式表达处理策略：

- `repair`：正常修复，只用于 `communication_problem`
- `probe_lightly`：低压试探，只用于 `interest_unclear`
- `hold`：先收住，不再往救场上推
- `none`：当前没有明显问题，不需要介入

### 2.4 工程原则

- 评估数据必须结构化，可用于批量统计。
- 助手输出应支持自动评分，而不是只靠人工读自然语言。
- 延迟必须单独治理，不能把“模型慢”混进“策略差”里。

## 3. 现状问题

### 3.1 救场偏晚

在真实对话中，像“偶尔玩一点 -> 哦，挺好的”这种组合，实际上已经非常危险。当前调度模型对“封闭回复”“话题终结语”的敏感度不够高，往往要到明显僵住后才介入。

后果：

- 失去最佳救场窗口
- 即使建议正确，也只能做事后修补
- 让用户感知到“助手总是慢半拍”

### 3.2 建议正确，但执行率不稳定

现状中，助手经常能指出对的问题，但扮演用户未必真正采纳。例如建议已经提示“不要继续追旧话题，改聊朋友聚会或放松方式”，但用户仍可能只回一句“哦，这样啊”。

后果：

- 只看最终聊天结果，会低估助手能力
- 产品侧难以区分“建议质量差”还是“用户没执行”

### 3.3 建议还不够人设化

这轮建议总体正确，但还偏通用，比如会泛泛提到电影、运动、旅行。实际上真实画像里已经有很多更自然的钩子：

- 无锡定居
- 养生
- 周末会出门走走
- 咖啡
- 羽毛球
- 桌游

如果助手能优先基于这些真实画像字段给建议，整体会更自然，也更符合“像本人会聊出来的话题方向”。

后果：

- 建议虽正确，但像“通用聊天课”
- 用户采纳后也容易出现 AI 味
- 对方更难感受到真实的人味和生活感

### 3.4 有些回复不够像真人

例如“你是在认可‘偶尔玩玩’这个频率吗？”这种句子就很别扭，不像真实相亲聊天中会说的话。说明当前主对话生成仍缺少足够强的“口语自然度”约束。

后果：

- 影响对话真实性
- 让评估混入“文风假”的噪音
- 即使建议方向对，最终落地消息也不够自然

### 3.5 救场策略还不够具体

现在助手基本能做到“指出问题 + 给建议”，方向是对的，但建议仍偏宽泛。更好的做法是进一步明确成策略模板，而不是停留在抽象层。

应该优先提示这类动作：

- 先承认有点冷场
- 再换到低门槛生活话题
- 优先问对方更容易回答的问题
- 说明当前不要继续追什么旧话题

这样比泛泛地说“多交流”“自然一点”更容易执行。

### 3.6 延迟太高

在真实跑数中，调度和回复多次达到几十秒，个别接近一分钟。这个级别的延迟在评测脚本里还能忍，但在真实产品里不可接受。

后果：

- 用户不会等待
- 频繁打断对话节奏
- 难以做“即将发言前”的实时救场

### 3.7 缺少“意愿 vs 沟通问题”分层

现状里，只要出现冷回复、敷衍、话题接不下去，就容易一股脑当成“需要救场”。这会导致助手虽然表面上在帮忙，实际上却把用户往更被动的位置推。

典型误判：

- 对方其实已经明显低投入，但系统还在教用户怎么继续追问
- 对方只是回得冷，系统直接默认“双方都还想聊”
- 边界或压力话题出现后，系统还把它当成普通冷场处理

后果：

- 建议容易显得讨好
- 用户会被推到“我得更努力接着聊”的被动位置
- 指标会把“本来就不该救的局”也算进救场成败

### 3.8 评估维度还不够

当前脚本输出了：

- 聊天满意度
- 助手满意度
- 是否参考过助手

这些信息有用，但不够衡量助手本身。缺的关键维度是：

- 助手判断是否准确
- 是否介入过晚
- 用户是否执行建议
- 建议后 `1-3` 轮局部局面是否改善
- 救不回来时是否体面止损

---

## 4. 目标

### 4.1 评估目标

建立一套能区分下列因素的评估体系：

- 场景难度
- 助手判断能力
- 建议质量
- 用户执行度
- 局部恢复效果

### 4.2 产品目标

让助手输出从“泛泛建议”升级为“**结合画像的具体教练建议**”。

### 4.3 生成目标

让主对话消息更像真实相亲聊天，而不是像被模型写出来的说明性句子。

### 4.4 性能目标

将调度与建议延迟压到真实产品可接受范围，至少支持：

- 快速判断是否需要介入
- 在用户准备发送前拿到建议

---

## 5. 评估框架

### 5.1 评估单元

评估单元不是“整段聊天”，而是**每一个可能需要救场的时刻**。

每个时刻记录一条结构化记录，至少包含：

- `turn_index`
- `speaker`
- `stress_beat_id`
- `stress_category`
- `mutual_intent_assessment_gold`
- `mutual_intent_assessment_pred`
- `interaction_mode_gold`
- `interaction_mode_pred`
- `need_rescue_gold`
- `need_rescue_pred`
- `problem_tags_gold`
- `problem_tags_pred`
- `strategy_tags_gold`
- `strategy_tags_pred`
- `used_assistant`
- `followed_assistant`
- `follow_level`
- `recovery_score_1to3_turns`
- `graceful_exit_score`

### 5.2 评分维度

建议分五组打分：

- **识别与时机**
  - 有没有先分对“沟通问题”还是“兴趣问题”
  - 该救时有没有救
  - 不该救时有没有克制
  - 出手是否过晚
- **诊断准确性**
  - 是否说中了真实问题
  - 是否识别出封闭回复、换题生硬、话题终结等标签
- **建议质量**
  - 是否具体可执行
  - 是否符合人设
  - 是否避免代写整句
- **局部恢复效果**
  - 后面 `1-3` 轮是否出现更长回复
  - 是否重新出现追问
  - 是否成功换题
- **止损能力**
  - 对话不可救时，是否建议轻松承认冷场、换低门槛话题或体面收住
  - 是否避免把用户推入讨好、追着聊、越聊越被动的位置

### 5.3 建议加权

总分建议：

- `30%` 识别与时机
- `30%` 建议质量
- `25%` 局部恢复效果
- `15%` 克制与止损

注意：

- 聊天满意度不是主 KPI
- 助手满意度也不是主 KPI
- 这两个只能作为辅助信号

## 6. Gold 标准设计

### 6.1 基础做法

优先用“**压力剧情弱标注 + 人工抽检**”的方式建立 gold。

在 `chat_system/scenario_stress.py` 中，为每个 `StressBeat` 增加额外元数据：

- `severity`
- `expected_problem_tags`
- `suggested_strategy_tags`
- `expected_need_rescue_after_turns`

例如：

- `one_word`
  - `expected_problem_tags=["closed_reply", "cold_end"]`
  - `suggested_strategy_tags=["expand_detail", "ask_open_question"]`
  - `expected_need_rescue_after_turns=0`

- `ghosting_tone`
  - `expected_problem_tags=["disengaged", "conversation_shutdown"]`
  - `suggested_strategy_tags=["acknowledge_coldness", "switch_topic", "graceful_exit"]`
  - `expected_need_rescue_after_turns=0`

### 6.2 人工抽检

弱标注不能完全替代人工，仍需要定期抽样复核：

- 助手是否把问题看偏了
- 场景强度是否需要重新定义
- `gold` 标签是否过粗或过细

## 7. 助手输出改造

### 7.1 从纯文本建议改成结构化建议

当前 `assistant_llm.py` 输出可读文本，但后续需要支持自动评分，因此建议升级为结构化 JSON 输出，再附带人类可读文本。

建议格式：

```json
{
  "mutual_intent_assessment": "communication_problem",
  "interaction_mode": "repair",
  "need_rescue": true,
  "problem_tags": ["closed_reply", "topic_dead_end"],
  "severity": 4,
  "diagnosis": "对方连续封闭回复，当前话题已终结。",
  "why_not_to_push": [],
  "low_pressure_options": [],
  "advice": [
    "不要继续追问桌游细节",
    "先轻松承认有点冷场",
    "换到周末安排或吃喝这类低门槛话题"
  ],
  "avoid": [
    "继续查户口式追问",
    "再问具体推荐哪款桌游"
  ],
  "profile_hooks_used": ["周末会出门走走", "养生", "桌游"],
  "graceful_exit": false
}
```

### 7.2 建议必须包含三类信息

每次建议都应尽量包含：

- 当前更像“沟通问题”还是“意愿不明确 / 兴趣偏低”
- 当前最关键的问题是什么
- 当前最不该继续做什么
- 下一步应该换到哪类更容易接的话题

如果不是 `repair` 模式，还必须额外包含：

- 为什么现在不要硬推
- 如果还要试，只能怎么低压试

## 8. 人设化建议改造

### 8.1 目标

让助手优先基于真实画像字段给出建议，而不是优先从“电影、运动、旅行”这类通用安全话题里随机拿一个。

### 8.2 实现方向

在助手上下文中引入安全裁剪后的画像摘要，例如：

- 城市与定居意向
- 周末生活方式
- 兴趣爱好
- 关系目标
- 生活节奏

同时给助手明确排序规则：

1. 优先用双方**交集钩子**
2. 其次用当前说话人的**真实生活钩子**
3. 最后才退回到通用低门槛话题

### 8.3 示例

对于画像 `profile-3` 与 `profile-15`，优先建议应更像：

- 从桌游切到“朋友聚会一般怎么安排”
- 从桌游切到“周末会不会出门走走”
- 从桌游切到“咖啡 / 养生 / 轻运动”

而不是直接泛化成：

- 电影
- 运动
- 旅行

### 8.4 预期收益

- 建议更自然
- 建议更像“这个人会真的去聊的东西”
- 用户采纳后更不容易露出 AI 味

---

## 9. 主对话口语自然度改造

### 9.1 问题定义

当前部分生成消息仍有“说明文”“解释文”味道，不像真人即时聊天。

### 9.2 改造策略

在 `dyadic_roleplay.py` 的 persona 生成 prompt 中增加更强的口语约束：

- 不要写分析型句子
- 不要解释自己在说什么
- 不要使用“你是在认可……吗”这类书面推断句
- 优先使用短句、口语衔接词、自然停顿
- 保持一条消息只做一到两件事

### 9.3 增加反例约束

建议把这类表达列为低质量反例：

- “你是在认可……吗？”
- “我理解你的意思是……”
- “从你的表述来看……”
- “如果我没理解错的话……”

这些句式太像分析者，不像聊天者。

### 9.4 评测方式

新增“口语自然度”维度，单独打分：

- `5`：像真实聊天
- `3`：大体自然，但偶尔假
- `1`：明显 AI 味或书面腔

---

## 10. 更具体的救场策略模板

### 10.1 目标

让建议不止停留在“你可以自然一点”“换个话题”，而是明确为可执行步骤。

### 10.2 推荐模板

当出现冷场或话题终结时，先判模式，再选模板：

1. `repair`
   - 先承认状态
   - 再切换到低门槛话题
   - 最后问容易回答的问题
2. `probe_lightly`
   - 不承诺重投入
   - 只丢一个低成本问题
   - 看对方是否愿意自己往下接
3. `hold`
   - 不再继续加码
   - 不教用户讨好式追问
   - 必要时提示放慢节奏或轻轻收住

其中 `repair` 模式优先用三步模板：

1. **先承认状态**
   - 轻度承认刚才有点接不住
   - 避免强行假装一切很顺
2. **再切换到低门槛话题**
   - 周末安排
   - 美食 / 咖啡 / 作息
   - 通勤 / 城市生活 / 出门习惯
3. **优先问容易回答的问题**
   - 开放但不沉重
   - 不需要大量背景信息
   - 不要求对方继续解释旧话题

### 10.3 输出要求

每次建议尽量明确：

- `acknowledge_coldness`
- `switch_topic_to`
- `easy_question_type`
- `avoid`

例如：

- `switch_topic_to=weekend_routine`
- `easy_question_type=habit_question`
- `avoid=["continue_old_topic", "cross_exam"]`

## 11. 延迟治理方案

### 11.1 现状问题

当前调度判断和建议生成都可能走同一条较重模型路径，导致整体耗时高。

### 11.2 总体方案

拆成“两级链路”：

- **一级轻判断**
  - 只做：是否需要救场、问题标签粗分类
  - 使用更快模型或规则 + 小模型
- **二级重建议**
  - 只在需要时才调用
  - 结合画像与上下文生成建议

### 11.3 轻判断可优先规则化

先用规则过滤明显场景，例如：

- 连续两轮无追问
- 一字回复
- 终结语（“哦”“挺好的”“还行”“一般”）
- 连续封闭回答
- 最近是否出现过**双方互相投入**
- 对方是否已经出现**连续低投入**

满足规则后再调小模型确认，可显著降低延迟与成本。

### 11.4 性能目标

建议目标：

- 一级轻判断：`P50 < 800ms`
- 二级建议生成：`P50 < 3s`
- 全链路：`P95 < 5s`

在 roleplay 压测中可以放宽，但产品上线必须以真实用户体验为准。

## 12. 用户执行度评估

### 12.1 必须单独评估

后续输出结构必须把“建议质量”和“用户是否执行”拆开。

建议新增字段：

- `followed_assistant`
- `follow_level`：`none | partial | strong`
- `follow_evidence`
- `interaction_mode`
- `overpush_risk`

### 12.2 判定方法

通过规则与 judge 混合判断下一条消息是否体现了建议：

- 是否换到了建议的话题类型
- 是否避免了助手明确禁止的做法
- 是否使用了建议中的策略，而不是原话复读

---

## 13. 结果层指标

### 13.1 局部恢复指标

不要只看整段聊天是否成功，要看救场后的短窗口变化。

建议记录：

- 下一条消息长度是否增加
- 是否出现新的追问
- 是否切换到新话题
- 是否出现轻度缓和（承认冷场、愿意继续）

### 13.2 体面止损指标

如果对话已经接近不可救，助手高分表现不一定是“聊活”，也可能是：

- 建议承认有点尴尬
- 建议换低门槛话题
- 建议自然收住，不继续硬聊

这部分应单独评分，不应被误算为失败。

### 13.3 不过度推动指标

如果场景本身更像 `interest_low` 或 `boundary_risk`，高质量助手表现应该是：

- 没有把它误判成 `repair`
- 没有继续把用户往追着聊、讨好式接话上推
- 必要时只给低压试探或直接建议先收住

因此需要新增：

- `hold_decision_turns`
- `overpush_risk_turns`
- `clarified_low_interest_rate`

## 15. 分阶段落地计划

### Phase 1：评测可分解

目标：

- 让输出结构能区分“判断准不准”“建议好不好”“用户有没有执行”
- 让输出结构能区分“这是沟通问题，还是兴趣问题”

内容：

- 扩展 `stress beat` 元数据
- 扩展 roleplay 输出结构
- 增加局部恢复与执行度字段
- 增加 `mutual_intent_assessment` 与 `interaction_mode`

### Phase 2：先判意愿，再判沟通

目标：

- 避免把低兴趣局误判成“用户再努力一点就能救”

内容：

- 规则快路径增加“最近是否有双方互相投入”的判断
- 调度模型输出 `repair / probe_lightly / hold / none`
- 加入 `overpush_risk_turns` 指标

### Phase 3：建议更具体

目标：

- 让助手稳定输出“当前问题 + 避免事项 + 换题类型 + 易回答问题类型”

内容：

- 改造助手 JSON 输出
- 引入建议模板
- 在 `probe_lightly` 下补足“为什么别硬推”“怎么低压试”的建议

### Phase 4：建议更人设化

目标：

- 优先利用真实画像钩子

内容：

- 增加安全裁剪画像摘要
- 优先使用双方交集钩子

### Phase 5：更像真人

目标：

- 提升主对话口语自然度

内容：

- 强化 persona prompt
- 增加自然度评分
- 增加反例词库

### Phase 6：延迟治理

目标：

- 让真实产品体验可接受

内容：

- 两级链路
- 规则前置
- 小模型优先判断

## 16. 验收标准

第一版建议门槛：

- `need_rescue` recall `>= 0.80`
- `need_rescue` precision `>= 0.70`
- `overpush_risk_turns = 0`
- `interest_low / boundary_risk` 场景下误判为 `repair` 的比例 `<= 10%`
- 中位介入延迟 `<= 1` 轮
- 建议质量均分 `>= 4.0 / 5`
- 人设化建议命中率 `>= 70%`
- 口语自然度均分 `>= 4.0 / 5`
- 无助手对照下，局部恢复率提升 `>= 20%`
- 明确代写违规率 `= 0`
