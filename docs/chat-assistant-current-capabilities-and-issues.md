更新时间：2026-05-15

## 1. 文档目的

这篇文档保留两件历史信息：

- 当时实验分支里已经实现了什么。
- 当时还能看到哪些真实问题。

不写未来规划，也不把改进方案里的目标或这份历史快照当成当前主干事实。

先说清两个边界：

- `interaction_mode` 只约束助手自己的建议，不直接约束真实用户下一句必须怎么回。
- `mode_hint` / `controlled` 只用于离线 `roleplay` 实验，不是线上产品行为。

## 2. 一句话说清当时的助手是什么

现在的 AI 助手，本质上是一个“相亲聊天私教”，不是代聊机器人。

它会看最近几轮双方可见对话，判断现在更像是：

- 需要修一下聊天节奏
- 只适合低压试一下
- 应该先收住别再推进
- 或者根本不用插手

然后给当前说话人一条仅自己可见的建议。用户自己改写后，才能真正发给对方。

## 3. 当时实验分支里的完整功能

### 3.1 四个核心入口

1. `assistant_query`

用户主动问助手“这轮怎么接”。

例子：

- 用户看到对方回了个“嗯”，自己点一下助手。
- 助手返回一条仅自己可见的建议，不会直接发给对方。

2. `assistant_proactive_hint`

系统主动提醒，但不是每轮都提醒。

它会先看当前局面，再结合趋势状态判断“这轮值不值得提醒”。

3. `assistant_mode_route`

只做局面判断，不生成建议。

适合调试、埋点、评测时单独看“它脑子里觉得现在是什么局”。

4. `adopt_draft`

用户确认并改写后，把内容正式发进双方聊天。

这里有一个硬约束：

- 助手建议不能原样转发。
- `body_override` 必须由用户自己改写，而且不能和助手草稿一模一样。

这保证了“助手给建议”和“用户真正怎么发”是两件事。

### 3.2 它现在怎么判断局面

现在不是只看最后一句，而是“最近几轮快判断 + 趋势状态”一起工作。

它先做一个快路由，输出这些结构化结果：

- `mutual_intent_assessment`
- `interaction_mode`
- `reason`
- `risk_axis`
- `hold_subtype`
- `engagement_level`
- `warmth_level`
- `irritation_level`
- `state_trend`

其中最核心的两层是：

1. `mutual_intent_assessment`

- `communication_problem`：双方可能还想聊，只是这轮接歪了、卡住了。
- `interest_unclear`：还不能确认对方有没有兴趣，先别重投入。
- `interest_low`：对方投入已经偏低了。
- `boundary_risk`：已经碰到边界、施压、比较、冒犯这类风险。
- `normal`：目前看还算自然，不用插手。

2. `interaction_mode`

- `repair`：修聊天，重点是接住、化解、换一个更容易接的话题。
- `probe_lightly`：低压试一下，只能轻轻试，不能连环追问。
- `hold`：先收住，别再推进。
- `none`：先别打断，自然往下聊。

### 3.3 它已经能区分两种 `hold`

现在的 `hold` 不是一刀切。

1. `interest_low`

意思是：对方主要是冷、淡、低投入。

这类场景下，助手更偏向提醒“别硬聊了，别讨好式救场”。

2. `boundary_risk`

意思是：已经碰到风险点了，比如：

- 照片/外貌
- 收入/条件
- 前任/隐私
- 过快推进见面
- 比较、抬杠、施压

这类场景下，助手会更像“止损提醒”，而不是继续教你推进。

### 3.4 它已经会看“风险轴”

现在系统会给风险归一条线，常见有：

- `appearance`：照片、外貌、胖瘦、见光死
- `income_condition`：收入、房车、条件
- `privacy_ex`：前任、婚史、隐私
- `meetup_push`：推进见面
- `pressure_compare`：比较、施压、抬杠

这件事的作用是：助手不只知道“有风险”，还知道“风险是沿哪条线在走”。

例如同样是 `hold`：

- 如果是 `appearance`，它会提醒“别继续追着照片、外貌差距这些点问”
- 如果是 `meetup_push`，它会提醒“别急着继续推进见面”

### 3.5 它已经会给结构化建议

助手输出的不是一句随便写写的话，而是一组结构化字段。常见包括：

- `current_problem`：这轮最核心的问题是什么
- `avoid`：这轮先别怎么聊
- `advice`：建议动作
- `topic_directions`：可换的话题方向
- `why_not_to_push`：为什么别硬推
- `rescue_flow`：建议顺序
- `graceful_exit_plan`：如果还是接不动，怎么体面收口
- `profile_hooks_used`：用了哪些画像钩子

还有两层保护：

1. 不代写可直接发送的整句

建议会尽量保持“方向性”，而不是直接替用户写一句完整台词。

2. `hold` 会做止损对齐

如果路由已经判成 `hold`，系统会尽量避免再给出“继续推进”“继续追问”这类冲突建议。

### 3.6 它已经支持画像钩子，但做了安全裁剪

助手会读取双方画像摘要和画像钩子，但不是全量生吞。

现在已经做了几件事：

- 只取安全摘要字段，比如城市、工作、关系目标、性格、生活方式、爱好
- 优先选择双方交集或当前说话人真实生活里的钩子
- 会过滤掉不适合拿来当聊天建议钩子的敏感项，比如收入、前任、照片、身高体重
- 如果没有特别好的钩子，会退回到一些低门槛兜底方向，比如“周末安排”“最近放松方式”

### 3.7 它已经有主动提醒机制，但不是每轮都弹

系统现在会给每个用户在每个线程上记一份趋势状态，里面至少有：

- 当前模式和上一轮模式
- 连续卡了多少轮
- 当前风险标记
- 当前风险轴
- `hold` 子类型
- 上次什么时候提醒过
- 上次提醒后，用户有没有行动过
- 当前是否还在冷却期

真正决定“这轮要不要提醒”的触发逻辑，已经不是简单的“判到了就弹”，而是看这些条件：

- 第一次进入风险模式
- 模式切换了
- 风险升级了
- `boundary_risk hold` 沿同一风险轴继续加码了
- 同一问题连续几轮没缓解，值得再次提醒

同时也会压住很多重复提示，比如：

- 用户还没来得及行动
- 还在冷却期
- 同一模式没有新增价值
- `hold` 没有出现新的风险升级

所以它现在的设计不是“每轮都说话”，而是“有价值才说”。

### 3.8 它已经有 `hold` 快路径、缓存和短提示词

为了解决建议太慢的问题，当前实现已经有几层提速：

1. `boundary_risk hold` 快路径

如果明显是边界风险类 `hold`，可以直接走规则止损，不一定要等大模型。

2. 更短的提示词

建议生成 prompt 已经压短，且只要求极短 JSON。

3. 响应缓存

同样的输入再次出现时，可以直接走缓存。

4. OpenAI client 复用

减少重复初始化开销。

### 3.9 它已经有最小风控闭环

除了聊天建议本身，系统现在还有一条独立的风控链路：

- 用户可以举报
- 系统会对 dyadic 消息做一版关键词规则命中
- 风险会聚合成 `chat_risk_cases`
- 运营可以做 `warn` / `limit_chat` / `freeze`
- 如果 case 已经被限制或冻结，相关用户会被阻止继续发双方可见消息

### 3.10 它已经有离线 roleplay、报表和基准测试

当前仓库里已经具备完整的离线评测链路：

1. 双智能体 roleplay

两个虚拟相亲用户在真实 `chat_threads` 上轮流聊天，可以加压力剧情、冷场、边界测试等。

2. 三种回复实验模式

- `free`：自由发挥
- `mode_hint`：模拟回复方能看到 `interaction_mode`
- `controlled`：模拟回复方尽量按建议方向执行

但后两者都只是离线实验，不是线上产品行为。

3. 报表已经把“提示是否合理”放到更前面

现在报表会优先看：

- 模式是否判对
- 危险局有没有被放成 `none`
- `hold` 是否及时抓到
- 是否有直接代聊式违规
- 超时、fallback 有多少

而不是先看“角色扮演有没有照做”。

4. 已有单独的延迟基准脚本

可以对比当前 prompt 和更老、更长 prompt 的耗时差异，也能看到缓存和快路径的效果。

## 4. 几个具体例子

### 4.1 `repair` 例子

对话：

```text
A: 你好，周末一般会做什么？
B: 看情况。
A: 嗯。你周末都干嘛
```

当前系统会更倾向判成：

- `mutual_intent_assessment=communication_problem`
- `interaction_mode=repair`

大白话就是：

- 不一定是对方彻底没兴趣
- 更像前面已经有点尬，接话一直没接顺
- 这时候应该“修聊天”，不是继续硬问原话题

当前建议风格大概会像：

```text
当前问题：对方上一句太短，旧话题快聊干了。
先别继续这样聊：不要继续追着已经聊干的话题硬问。
回复建议：
1. 先回应对方上一句里的具体信息。
2. 再把话题换到更容易接、门槛更低的方向。
3. 最后只问一个轻一点、对方容易回答的问题。
```

### 4.2 `probe_lightly` 例子

对话：

```text
A: 你平时会做饭吗？
B: 偶尔。
A: 那你更擅长中餐还是西餐？
```

当前系统会更倾向判成：

- `mutual_intent_assessment=interest_unclear`
- `interaction_mode=probe_lightly`

大白话就是：

- 对方没有明确拒绝
- 但投入也不高
- 这时候只能轻轻试一下，不能连着追问很多句

当前建议风格大概会像：

```text
如果只适合低压试探：
1. 先丢一个低门槛、对方一句就能接的问题试一下。
2. 如果对方还是冷，就别继续加码输出。
```

### 4.3 `hold_interest_low` 例子

对话：

```text
A: 今天过得怎么样？
B: 还行。
A: 最近工作忙不忙？
B: 就那样。
```

当前系统会更倾向判成：

- `mutual_intent_assessment=interest_low`
- `interaction_mode=hold`
- `hold_subtype=interest_low`

大白话就是：

- 对方已经连续低投入
- 现在不是“你再努力一点就能救回来”的局
- 更该提醒的是“别硬聊，先收住”

### 4.4 `hold_boundary_risk` 例子

对话：

```text
A: 你照片是本人吧？别差距太大。
B: 是本人。怎么，怕见光死？
```

当前系统会更倾向判成：

- `mutual_intent_assessment=boundary_risk`
- `interaction_mode=hold`
- `risk_axis=appearance`
- `hold_subtype=boundary_risk`

当前建议风格大概会像：

```text
当前问题：这轮已经碰到边界压力，不适合继续推进。
先别继续这样聊：
1. 不要继续解释动机。
2. 不要再抛新的泛聊天问题硬续上。
回复建议：
1. 别继续追着照片、外貌差距这些点问。
2. 别再证明自己，也别试图把话题拉回正常聊天。
```

### 4.5 用户确认发送的例子

假设助手给的是：

```text
先接住对方刚说“家里催相亲很烦”这个点，
再换一个门槛更低的话题，
别上来就继续推进见面。
```

那用户真正发出去的内容，应该是自己改写后的版本，比如：

```text
家里一直催这个确实挺烦的。我有时候也会被问得有点头大。
你一般下班后会怎么放空？
```

上面这句只是“用户自己改写后的示意”。

重点是：

- 助手给的是方向
- 真正发给对方的话，仍然要用户自己决定

## 5. 当前已经能看到的主要问题

### 5.1 非 `hold` 快路径场景还是太慢

这是现在最明显的问题。

基准脚本 `/tmp/assistant-latency-benchmark.json` 显示：

- `hold_fast_path`: `0.24 ms`
- `repair_current_uncached`: `41641.96 ms`
- `repair_current_cache_hit`: `1.04 ms`

大白话就是：

- 明显边界风险的 `hold`，现在可以非常快
- 但 `repair` / `probe_lightly` 这类更依赖大模型的场景，第一次命中还是可能等四十多秒
- 缓存只对“重复命中同样输入”有帮助，不能解决第一次就慢的问题

### 5.2 慢了之后，超时和 fallback 还是很重

最近一次 hard-user 连贯对话评测 `/tmp/hard-users-coherent-20260507-c.json` 里：

- `assistant_invoke_avg_ms = 39964.2`
- `assistant_invoke_timeout_rate = 0.6`
- `assistant_guidance_fallback_rate = 0.8`

大白话就是：

- 平均一次建议还是接近 40 秒
- 10 次里大约有 6 次助手调用超时
- 10 次里大约有 8 次最后只能靠 fallback 兜底

这会带来一个连锁问题：

- 助手不一定判错
- 但没等到模型结果，只能说更安全、更短、更通用的话
- 于是用户体感上会觉得“像模板”“不像现场分析”

### 5.3 fallback 现在虽然更安全了，但仍然会显得泛

同一份 `/tmp/hard-users-coherent-20260507-c.json` 里，多个 `hold` 回合都出现了近似重复的 fallback 建议：

```text
别急着继续推进见面。
这轮先收口，别再往前顶。
```

这说明当前 fallback 至少做对了一件事：

- 没再把 `hold` 场景往“继续试试”上带偏

但它也还有明显短板：

- 太像兜底话术
- 场景区分度不够细
- 模型一超时，建议就容易变得很像模板

### 5.4 仍然有一部分该提醒的局，被错放成了 `none`

最近这份 hard-user 评测里：

- `risky_none_rate = 0.25`
- `boundary_risk_hold_recall = 0.75`

大白话就是：

- 还有 25% 的危险局被误放成“没事，继续聊”
- 该进 `boundary_risk hold` 的局，抓到了 75%，但还没到完全稳

具体例子：

1. 第 2 轮漏判

```text
刚下班啊辛苦。我今天状态也一般，家里又打电话催相亲，有点烦。
```

gold 认为更像：

- `communication_problem`
- `repair`

但系统实际判成了：

- `normal`
- `none`

2. 第 10 轮漏判

```text
刚说周末经常去公司，这会儿又说随性，有点矛盾吧。
```

gold 认为更像：

- `boundary_risk`
- `hold`

但系统实际判成了：

- `normal`
- `none`

### 5.5 “为什么这轮没提醒”现在可能是设计如此，不一定是 bug

当前主动提醒不是每轮触发。

系统会主动压住很多重复提示，比如：

- `waiting_for_user_action`
- `cooldown_active`
- `same_mode_no_new_value`
- `hold_no_new_risk`

这套设计的好处是：

- 不会每轮都烦用户

但代价也很直接：

- 用户体感上可能会觉得“刚才还在提醒，这轮怎么突然不说了”

所以这个点需要产品和评测方统一认知：

- “没提醒”不一定是没看见
- 也可能是趋势触发器故意压住了重复建议

### 5.6 `follow_rate` 低，说明建议执行性还不够稳，但不能直接当成主结论

同样是最近这份 hard-user 评测：

- `follow_rate = 0.2`
- `strong_follow_rate = 0.0`

这说明一个现实问题：

- 有些建议就算方向对，难搞用户也未必愿意照做

但这项指标不能直接当成“助手一定做错了”，因为它还混着两层因素：

1. 建议本身是否容易执行
2. 角色扮演用户是否真的按提示演

所以现在报表已经把这类指标降成 `reference_only`，只作为参考，不当主结论。

### 5.7 离线评测和真实用户之间，仍然有一层天然差距

虽然当前 roleplay 已经支持：

- 压力剧情
- 连续情绪走势
- `free / mode_hint / controlled`
- 可见文本口径和 stress 口径拆分

但它仍然是“模拟人”。

这意味着：

- 它适合用来找链路问题、识别问题、提示质量问题
- 不适合直接把“模拟人有没有听话”当成真实世界的最终结论

这一点现在系统已经在报表层做了部分修正，但方法论上仍然要持续注意。

## 6. 一句话总结

现在的 AI 聊天助手，已经不是一个只会吐模板的壳子了。

它已经具备：

- 局面路由
- `repair / probe_lightly / hold / none` 四模式
- `hold` 风险止损
- 画像钩子
- 主动提醒趋势状态
- 用户改写后再发送
- 最小风控闭环
- 离线 roleplay、报表、延迟基准

但当前最主要的问题仍然是：

- 非快路径场景太慢
- 一慢就超时，一超时就 fallback
- 还有一部分局面会被误放成 `none`
- fallback 还不够像现场分析
- 角色扮演采纳度和真实世界之间仍有评测鸿沟
