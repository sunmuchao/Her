# 发现页图片发送链路梳理 A1-001

日期：2026-07-19

> 对应任务：[`A1-001 盘点当前发图主链路`](./发现页图片搜索AI%20Native任务拆分.md)
>
> 目标：把“用户在发现页上传图片并发送”这一条链路，从前端、Gateway、搜索执行层到 session 回写完整串清楚，并明确当前失败点与错误提示来源。

---

## 1. 结论先行

当前发现页“发图发送”链路的真实情况是：

1. 前端上传图片后，不是走统一 discovery turn，而是走独立的 `submitPhotoSearch()`
2. 前端把图片压缩成 base64 data URL 后，直接请求 `POST /v1/discovery/photo-search`
3. 这个请求仍然把 `mode` 作为顶层协议字段发给 Gateway
4. Gateway 当前只接受 `face / style / celebrity`，不接受 `auto`
5. 但前端默认模式仍然是 `auto`
6. 因此前端默认发图发送时，请求会在 Gateway 校验层被拒绝
7. 前端拿到 Gateway 错误后，没有把真实错误暴露给用户，而是统一展示：
   - `这张图我刚才没处理成功，你重新发一次，我继续帮你找。`

一句话版：

**当前主链路的第一断点不在视觉搜索模型层，而在“前端默认发 `mode=auto`，Gateway 不认 `auto`”这个协议冲突。**

## 2. 用户动作

### 2.1 入口动作

用户路径是：

1. 在发现页底部输入区上传一张图片
2. 图片经过前端压缩后挂到输入区
3. 用户点击发送
4. 前端进入 `submitPhotoSearch()`

关键代码：

- 图片处理入口：
  - [`discover-page.tsx:560`](../frontend/her-app/components/her/discover-page.tsx)
- 发图发送入口：
  - [`discover-page.tsx:591`](../frontend/her-app/components/her/discover-page.tsx)

### 2.2 前端本地先做了什么

`submitPhotoSearch()` 在真正请求前做了两件事：

1. 先乐观插入一条用户图片消息
2. 再插入一条“小雅处理中”消息

关键代码：

- 用户气泡：
  - [`discover-page.tsx:598`](../frontend/her-app/components/her/discover-page.tsx)
- 处理中气泡：
  - [`discover-page.tsx:611`](../frontend/her-app/components/her/discover-page.tsx)

这意味着：

- 用户即使还没请求成功，也会先看到消息已经发出
- 当前前端显示的是“先给用户即时反馈，再等待接口结果”

## 3. 前端请求

### 3.1 实际调用的接口

前端不是走统一 `submitTurn()`，而是独立调用：

- `searchDiscoveryByPhoto(...)`

关键代码：

- [`discover-page.tsx:626`](../frontend/her-app/components/her/discover-page.tsx)
- [`discovery.ts:170`](../frontend/her-app/lib/api/endpoints/discovery.ts)

### 3.2 请求字段

前端发送的请求体是：

```json
{
  "profile_id": "...",
  "session_id": "...",
  "mode": "...",
  "image_source": "...",
  "query_text": "...",
  "celebrity_name": "...",
  "top_k": 12,
  "attribute_filters": {}
}
```

关键代码：

- [`discovery.ts:180`](../frontend/her-app/lib/api/endpoints/discovery.ts)

### 3.3 当前默认行为

当前前端仍保留：

- `photoSearchMode`
- 默认值是 `auto`

所以当用户只是上传图片直接发送时，最常见情况是：

- `mode = auto`
- `image_source = 压缩后的 base64 图片`
- `query_text = 空`

这正是当前主链路的核心冲突来源。

## 4. Gateway 校验

### 4.1 Gateway 入口

后端入口是：

- `rest_discovery_photo_search(...)`

关键代码：

- [`discovery_routes.py:336`](../external-systems/partner-http-gateway/gateway/discovery_routes.py)

### 4.2 Gateway 读取的字段

Gateway 会读取：

1. `profile_id`
2. `mode`
3. `image_source`
4. `query_text`
5. `celebrity_name`
6. `session_id`

关键代码：

- [`discovery_routes.py:341`](../external-systems/partner-http-gateway/gateway/discovery_routes.py)

### 4.3 Gateway 的第一层拒绝条件

当前 Gateway 的顶层校验是：

```python
if mode not in {"face", "style", "celebrity"}:
    return _photo_search_error("mode must be one of: face, style, celebrity")
```

关键代码：

- [`discovery_routes.py:351`](../external-systems/partner-http-gateway/gateway/discovery_routes.py)

这意味着：

- `auto` 会直接被拒绝
- `hybrid` 也会直接被拒绝

### 4.4 其他参数校验

在 `mode` 通过后，还会继续校验：

1. `face/style` 必须带 `image_source`
2. `celebrity` 必须带 `celebrity_name` 或 `query_text`
3. 所有模式至少要有 `image_source`、`query_text`、`celebrity_name` 之一

关键代码：

- [`discovery_routes.py:353`](../external-systems/partner-http-gateway/gateway/discovery_routes.py)

### 4.5 当前真实断点

由于前端默认发 `mode=auto`，所以当前默认链路大多数情况下会死在：

- `discovery_routes.py:351`

也就是：

**请求还没进入真正搜索，就先在 Gateway 参数校验层被拒了。**

## 5. 搜索执行

### 5.1 只有通过 Gateway 校验才会往下走

如果 `mode` 通过校验，Gateway 会构建一个 `PhotoPreferenceIntent`，再调用：

- `execute_photo_preference_search(...)`

关键代码：

- [`discovery_routes.py:367`](../external-systems/partner-http-gateway/gateway/discovery_routes.py)
- [`discovery_routes.py:405`](../external-systems/partner-http-gateway/gateway/discovery_routes.py)
- [`photo_intent_agent.py:61`](../match_domain/photo_intent_agent.py)

### 5.2 当前兼容执行层的真实路由

`execute_photo_preference_search(...)` 仍是一个兼容层，当前行为是：

1. `celebrity`
   - 直接返回失败
2. `face`
   - 调 `search_similar_face_candidates(...)`
3. `style`
   - 调 `search_style_candidates(...)`
4. `hybrid`
   - 代码里支持，但 Gateway 顶层并不允许传进来

关键代码：

- `celebrity` 直接失败：
  - [`photo_intent_agent.py:109`](../match_domain/photo_intent_agent.py)
- `hybrid` 路由：
  - [`photo_intent_agent.py:128`](../match_domain/photo_intent_agent.py)
- `face` 路由：
  - [`photo_intent_agent.py:138`](../match_domain/photo_intent_agent.py)

### 5.3 底层搜索函数

当前底层能力是存在的：

1. `search_similar_face_candidates(...)`
   - 按脸相似搜
   - [`photo_discovery_search.py:184`](../match_domain/photo_discovery_search.py)

2. `search_style_candidates(...)`
   - 按风格/感觉搜
   - [`photo_discovery_search.py:268`](../match_domain/photo_discovery_search.py)

3. `search_hybrid_photo_candidates(...)`
   - 脸 + 风格双路融合
   - [`photo_discovery_search.py:330`](../match_domain/photo_discovery_search.py)

### 5.4 当前执行层的第二个结构性问题

即便先不看 `auto` 报错，当前链路还有一个结构性问题：

- Gateway 顶层只允许 `face/style/celebrity`
- 但执行层内部其实还有 `hybrid`
- 而且 `celebrity` 在执行层里其实已经是“兼容失败”状态

也就是说，当前这条链路顶层协议和底层能力并不一致。

## 6. session 回写

### 6.1 回写时机

如果请求里带了 `session_id`，Gateway 会在搜索结果生成后，把本轮图片搜索写回 discovery session。

关键代码：

- [`discovery_routes.py:439`](../external-systems/partner-http-gateway/gateway/discovery_routes.py)

### 6.2 回写内容

当前回写会向 timeline 追加三类内容：

1. 一条用户消息
   - 如果有图，会带 `media_type=image` 和 `media_url`
2. 一条助手总结消息
3. 一组结果卡片 `result_group`

关键代码：

- [`discovery_routes.py:224`](../external-systems/partner-http-gateway/gateway/discovery_routes.py)

### 6.3 回写文案

当前回写文案仍然带模式心智，例如：

1. `face`
   - `我按这张脸帮你找了一轮。`
2. `style`
   - `我按这张图的整体感觉帮你找了一轮。`
3. `hybrid`
   - `我先综合这张图里的脸和整体感觉帮你找了一轮。`

关键代码：

- [`discovery_routes.py:238`](../external-systems/partner-http-gateway/gateway/discovery_routes.py)

### 6.4 当前回写层的特点

当前回写不是统一 discovery turn 的自然消息回放，而是：

- photo-search 专用回写逻辑

这进一步证明：

**当前图片发送还没有真正进入统一 discovery 对话主链路。**

## 7. 错误分支

### 7.1 Gateway 错误如何变成前端异常

前端所有 Gateway 请求都走：

- `gatewayJson(...)`

如果 HTTP 状态不是 2xx，它会直接抛出 `GatewayClientError`。

关键代码：

- [`client.ts:60`](../frontend/her-app/lib/api/client.ts)
- [`client.ts:79`](../frontend/her-app/lib/api/client.ts)

### 7.2 前端如何吞掉真实错误

`submitPhotoSearch()` 里的 `catch` 不区分错误来源，统一做了三件事：

1. 去掉处理中消息
2. 插入统一错误助手消息
3. `notifyError(error, '照片搜索失败')`

关键代码：

- [`discover-page.tsx:667`](../frontend/her-app/components/her/discover-page.tsx)

统一错误文案是：

- `这张图我刚才没处理成功，你重新发一次，我继续帮你找。`

这就是为什么：

- 用户看到的是“图片处理失败”
- 但真实问题往往是“Gateway 不接受当前 mode”

### 7.3 当前错误分支结论

当前主链路的错误呈现有两个明显问题：

1. 协议冲突被伪装成“图片处理失败”
2. 用户无法从 UI 区分：
   - 图片坏了
   - 参数错了
   - 搜索为空
   - 服务异常

## 8. 当前链路的 3 个核心结论

### 8.1 结论一：当前主断点在 Gateway 顶层校验

最常见失败点不是图片模型，而是：

- 前端默认 `mode=auto`
- Gateway 不认 `auto`

### 8.2 结论二：当前发图仍是独立图片搜索链路

它不是统一 discovery turn，而是：

- 前端独立 `submitPhotoSearch()`
- Gateway 独立 `/v1/discovery/photo-search`
- session 独立 `_append_photo_search_to_discovery_session(...)`

### 8.3 结论三：当前错误提示会误导排障

前端把所有失败都翻译成：

- `你重新发一次`

这会掩盖真实问题，拖慢后续改造与排障。

## 9. 对后续任务的直接影响

### 9.1 对 `A1-002`

`A1-002` 的第一刀应该切在：

- Gateway 顶层 `mode` 校验

不是先去改底层搜索函数。

### 9.2 对第二阶段统一 turn 改造

当前链路已经证明：

- 图片发送必须从独立 `/photo-search` 心智，收口到统一 discovery turn

否则：

- 图片和普通聊天永远还是两条链

### 9.3 对第三阶段 visual memory

当前 session 回写只是在 timeline 中追加图片消息和结果组，

但还没有：

- 正式的 visual context memory

所以“上一张图继续找”能力后续必须单独补。

## 10. A1-001 完成标准核对

本任务已回答清楚以下三个问题：

1. **现在“发图发送”为什么会失败**
   - 因为前端默认发 `mode=auto`，Gateway 不接受 `auto`

2. **当前失败主要在前端、Gateway 还是搜索层**
   - 默认主断点在 Gateway 顶层校验

3. **后面统一多模态 turn 的第一刀该切哪一层**
   - 第一刀先切 Gateway 顶层协议心智
   - 再收口前端提交入口
   - 再收口 discovery runtime

一句话收尾：

**A1-001 的结论不是“图片搜索能力不行”，而是“当前发图主链路首先死在协议层，且错误展示掩盖了真实根因”。**
