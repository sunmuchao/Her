## Phase 1：工具层改造（3-4 天）

### 任务 1.1：改造 search_partner_candidates（Layer 1 + Layer 2）

| 属性 | 内容 |
|------|------|
| **任务 ID** | T-1.1 |
| **描述** | 改造现有 `search_partner_candidates` 工具，支持硬约束筛选 + 偏好表筛选，返回 `preference_coverage` |
| **工作量** | 中（1-1.5 天） |
| **依赖** | 无 |
| **负责人建议** | 后端开发 |

**具体子任务：**

1. 修改工具参数：
   - 新增 `preference_json` 参数（偏好表筛选条件）
   - 保留 `criteria_json` 参数（硬约束条件）
   - 修改 `limit` 参数上限（默认 20，最多 50）

2. 新增 `_filter_by_preference_table` 函数：
   - 实现偏好表查询逻辑
   - 支持 `include` 和 `exclude` 筛选
   - 处理偏好表字段缺失的情况（跳过筛选）

3. 新增 `_check_preference_coverage` 函数：
   - 检查用户要求的特征是否被偏好表覆盖
   - 返回 `covered_features` 和 `uncovered_features`

4. 修改返回结构：
   - 新增 `preference_coverage` 字段
   - 新增 `preference_tags` 字段（每个候选人的偏好表标签）

**验收标准：**

- [ ] 工具支持 `criteria_json` + `preference_json` 双参数
- [ ] 返回 `preference_coverage` 字段正确标识覆盖情况
- [ ] 硬约束筛选正常工作（年龄、城市等）
- [ ] 偏好表筛选正常工作（或正确跳过）

### 任务 1.3：实现脱敏处理模块

| 属性 | 内容 |
|------|------|
| **任务 ID** | T-1.3 |
| **描述** | 实现聊天记录脱敏处理模块，在交给 Agent 之前先脱敏 |
| **工作量** | 小（0.5 天） |
| **依赖** | T-1.2 |
| **负责人建议** | 后端开发 |

**具体子任务：**

1. 创建 `sanitize_chat_record` 函数：
   - 手机号脱敏：保留前3后4
   - 身份证号脱敏：保留前6后4
   - 地址脱敏：保留城市，具体地址替换
   - 银行卡号脱敏：保留后4位
   - 收入脱敏：转化为区间
   - 微信号/QQ号脱敏：完全移除
   - 邮箱脱敏：保留域名
   - 真实姓名脱敏：用"候选人"代替

2. 创建 `load_and_sanitize_chat_records` 函数：
   - 先查询原始聊天记录
   - 再脱敏处理
   - 返回脱敏后的聊天记录

**验收标准：**

- [ ] 所有敏感信息类型都被正确脱敏
- [ ] 脱敏后不影响 Agent 分析（保留语气、关键词频率）
- [ ] 脱敏规则硬编码执行，不依赖 Agent 判断

## Phase 2：偏好表设计与实现（5-7 天）

### 任务 2.1：偏好表结构设计

| 属性 | 内容 |
|------|------|
| **任务 ID** | T-2.1 |
| **描述** | 设计偏好表字段和数据结构 |
| **工作量** | 中（1 天） |
| **依赖** | 无 |
| **负责人建议** | 产品 + 数据架构师 |

**具体子任务：**

1. 定义偏好表字段：
   - 性格标签：温柔、绿茶、强势、内向、稳重等
   - 沟通风格：直接、含蓄、迎合型等
   - 价值观：家庭导向、事业导向、真诚等
   - 情绪倾向：稳定、焦虑、抑郁等
   - 关系期望：结婚导向、认真恋爱、玩玩等
   - 生活方式：宅家、规律作息、爱运动等

2. 定义数据结构：
   - `profile_id`：候选人 ID
   - 各字段：字符串数组或单值
   - `updated_at`：更新时间
   - `source`：提取来源（聊天记录、测评等）

3. 定义字段映射表：
   - 用户表达 → 偏好表字段映射
   - 例如："不要绿茶" → 性格标签.exclude = ["绿茶"]

**验收标准：**

- [ ] 偏好表字段覆盖常见性格特征（至少 20 个标签）
- [ ] 数据结构支持扩展
- [ ] 字段映射表完整

### 任务 2.3：偏好表离线提取逻辑实现

| 属性 | 内容 |
|------|------|
| **任务 ID** | T-2.3 |
| **描述** | 实现从聊天记录提取特征到偏好表的逻辑（核心任务） |
| **工作量** | 大（2-3 天） |
| **依赖** | T-2.2 |
| **负责人建议** | AI/算法开发 |

**具体子任务：**

1. 设计提取模型：
   - 选择合适的 LLM（Claude Sonnet 或 Qwen）
   - 设计 Prompt（输入聊天记录，输出性格标签）

2. 实现提取逻辑：
   - 批量提取：一次处理多个候选人
   - 单人提取：处理单个候选人
   - 特征融合：从聊天记录 + persona + 测评综合提取

3. 实现提取流程：
   - 查询候选人聊天记录
   - 调用 LLM 提取特征
   - 写入偏好表

4. 实现增量提取：
   - 只提取最近 N 天有新聊天记录的候选人
   - 避免重复提取

**验收标准：**

- [ ] 提取模型能准确识别性格特征
- [ ] 提取逻辑支持批量处理
- [ ] 提取结果写入偏好表
- [ ] 增量提取正确工作

## 风险与应对

| 风险 | 可能影响 | 应对措施 |
|------|---------|---------|
| 偏好表提取模型不准确 | 偏好表数据质量差 | 人工标注测试数据，验证提取模型准确率 |
| 偏好表覆盖率低 | Agent 工作量仍然大 | 持续扩充偏好表字段 |
| Agent 判断不准确 | 用户体验差 | Prompt 优化 + 用户反馈修正 |
| Token 消耗超预期 | 成本高 | 监控 Token 消耗，优化分析策略 |
