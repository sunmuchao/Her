## 二、核心问题分析

### 问题1：search_part 存在但不写入 working_criteria

**发现的问题**：
```
split_persona_patch 返回 search_part（包含搜索条件）
    ↓
但 sync_requester_persona_memory 已禁用
    ↓
所以 working_criteria 不会被写入
    ↓
Agent 无法从 session.state["working_criteria"] 读取搜索条件
```

**预期后果**：
```
场景：第10轮用户说"改成上海的"
    ├─ Agent 可能忘了第1轮说的"北京"（80条限制）
    ├─ 无法从 working_criteria 中读取
    ├─ 搜索结果可能返回北京的用户（错误）
    └─ 方案文档的"不插手"设计有问题
```

---

### 问题2：persona_part 不写入（可量化字段缺失）

**发现的问题**：
```
用户说："我是INTJ人格"
    ↓
split_persona_patch 提取 persona_part: {mbti_type: "INTJ"}
    ↓
但 sync_requester_persona_memory 已禁用
    ↓
所以 persona_part 不会被写入 user_personas 表
    ↓
下次对话 Agent 不知道用户是INTJ
```

**预期后果**：
```
场景1：第1轮用户说"我是INTJ"
    ├─ persona_part 不写入（禁用生效）
    ├─ 会话结束后提炼主观描述（性格温柔）
    └─ 但可量化字段（INTJ）没有记录

场景2：第2轮用户再来
    ├─ Agent 不知道用户是INTJ
    ├─ 搜索时无法使用 MBTI 筛选
    └─ 用户体验下降（需要重复说）
```

## 三、方案文档理想设计的漏洞

### 漏洞1：Agent 80条限制未考虑

**方案文档假设**：
```
"Agent 自己记住搜索条件，系统不插手"
    ↓
假设：Agent 能记住所有条件
    ↓
实际：Agent 80条限制，可能遗忘
    ↓
漏洞：方案文档没考虑真实约束
```

---

### 漏洞2：可量化字段需要立即生效

**方案文档假设**：
```
"所有画像沉淀在会话结束后统一写入"
    ↓
假设：会话结束后写入就够了
    ↓
实际：可量化字段（INTJ）需要立即生效
    ↓
漏洞：方案文档没考虑即时性需求
```

## 四、实测预期结果

### 如果搜索异常（预期）

**场景**：
```
第1轮："帮我搜北京的"
    → Agent 记在心里："北京"

第10轮："改成上海的"
    → Agent 可能忘了第1轮说的"北京"
    → 无法从 working_criteria 读取
    → 搜索结果可能返回北京的用户（错误）
```

**结论**：
```
❌ 方案文档的"不插手"设计有问题
✅ 需要 working_criteria 作为小本本
✅ sync_requester_persona_memory 是必要的
```

---

### 如果画像沉淀不完整（预期）

**场景**：
```
用户说："我是INTJ人格"
    → persona_part 不写入（禁用生效）
    → 会话结束后提炼主观描述
    → 但可量化字段（INTJ）缺失

下次对话：
    → Agent 不知道用户是INTJ
    → 无法使用 MBTI 筛选
    → 用户体验下降
```

**结论**：
```
❌ 会话结束后写入不够用
✅ 可量化字段需要实时写入
✅ 主观描述可以会话结束后提炼
✅ 需要分层处理（可量化实时，主观会后）
```
