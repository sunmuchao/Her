# 匹配打分重构方案

## 0. 当前落地状态

截至当前版本，下面这些已经落地：

- 收入 reciprocal 判断已从“只看是否在区间内”改成区分 `below_min / within_band / above_max`
- 收入高于对方上限不再默认硬淘汰，而是作为风险提示保留
- 年龄、身高已支持“命中 / 接近 / 有一定偏差 / 偏差过大”这类近似判断
- 学历已支持“略低但接近 / 有一定差距 / 差距较大”的软处理
- 当前城市未命中但定居城市命中的情况已可保留
- 结果已拆成 `strict / compatible / fallback` 三层展示
- 主匹配与 reciprocal 已都开始使用“接近度分值”而不是单纯二元通过/失败
- 城市梯度和收入曲线已接入集中配置入口

当前配置入口：

- [match_domain/search_scoring_config.py](/Users/sunmuchao/Downloads/Her/match_domain/search_scoring_config.py)

当前已配置化的参数类型：

- `income_curve`
- `city_curve`

这意味着后续如果要调：

- 收入低于下限多少算“略低”
- 高于上限时给多少保留分
- 当前同城、定居同城、定居目标命中分别给多少分

已经不需要直接改主业务判断代码，而是可以优先走配置层。

当前版本还没有完全做到的，是更完整的“连续打分制”：

- 城市还没有真正引入“邻城 / 通勤圈 / 长三角 / 跨省”这类地理关系数据
- 年龄/身高/学历的接近判断目前仍以轻量分段为主，不是完全连续曲线
- reciprocal 虽已接近统一打分方向，但部分 bonus 仍有字段特化逻辑

因此，这份方案后续的重点，不是再做一轮简单放宽，而是把现在已经落地的“兼容匹配”继续收束成统一打分框架。

## 1. 背景

当前匹配逻辑的核心问题，不只是“规则太严格”，而是整体思路偏向：

- 先大量硬过滤
- 再对剩余候选人排序

这种模式会带来两个明显问题：

1. 很多“并非最佳、但仍然可聊”的候选人被提前过滤
2. 结果页经常出现“无匹配”，但实际只是规则把人筛空了

更合理的方向应当是：

- 只用少量规则处理“绝对不能接受”的条件
- 对大多数条件使用“接近度打分”
- 最终按总分排序，而不是按是否踩中区间边界做二元判断


## 2. 目标

本方案目标是将现有匹配逻辑升级为：

- `硬门槛过滤`
- `多字段接近度评分`
- `双向偏好加权`
- `结果分层展示`

一句话概括：

**把系统从“筛简历”改成“做推荐”。**


## 3. 新的总体架构

建议把匹配逻辑拆成三层。

### 3.1 第一层：硬门槛层

只处理真正不能接受的条件。

### 3.2 第二层：接近度评分层

对年龄、身高、收入、学历、城市距离等字段，按“离理想值有多近”进行连续打分。

### 3.3 第三层：软偏好加分层

对性格、生活方式、价值观、表达感、聊天感、资料质量等做加分或轻扣分。


## 4. 哪些条件保留硬过滤

建议只有以下字段默认继续硬过滤：

- 性别
- 明确不接受婚史
- 明确不接受对方有孩子
- 明确不接受异地
- 明确不接受抽烟
- 明确不接受喝酒
- 用户明确标记为“必须满足”的条件

这些条件的特点是：

- 不是“更好更差”
- 而是“能不能接受”

因此直接过滤是合理的。


## 5. 哪些条件改成接近度评分

以下字段建议不再默认硬过滤，而改成“接近度分”：

- 年龄
- 身高
- 收入
- 学历
- 城市/距离
- 定居城市
- 结婚时间预期
- 房车等现实条件

这些字段的共同特点是：

- 更接近更好
- 但不应该是“只要差一点就直接淘汰”


## 6. 接近度打分的核心原则

旧逻辑：

- 在区间内 = 通过
- 不在区间内 = 失败

新逻辑：

- 命中理想范围 = 高分
- 略微偏离 = 小扣分
- 明显偏离 = 大扣分
- 严重偏离 = 极低分，必要时再淘汰

本质上，系统不再判断“是不是在框里”，而是判断：

**离用户理想要求到底有多近。**


## 7. 年龄评分方案

假设用户期望年龄区间为 `28-32`。

建议按以下方式评分：

- `28-32`：满分区
- `27`、`33`：轻微偏离，少扣分
- `26`、`34`：中度偏离，中等扣分
- `24-25`、`35-36`：明显偏离，大扣分
- 偏离更多：极低分，必要时可淘汰

推荐表达方式：

- 在理想区间内：100 分
- 差 1 岁：85-90 分
- 差 2 岁：70-75 分
- 差 3-4 岁：40-60 分
- 差 5 岁以上：很低

关键点：

- `27` 和 `22` 不能都被简单视作“区间外”
- 它们与理想目标的接近程度完全不同


## 8. 身高评分方案

假设用户期望身高区间为 `175-180`。

建议按以下方式评分：

- `175-180`：满分区
- `174`、`181`：轻微偏离
- `172-173`、`182-183`：中度偏离
- 偏差继续增大：逐步降分

### 8.1 身高建议做非对称评分

现实中很多用户对身高的偏好不是完全对称的：

- 低于下限通常比高于上限更敏感

因此建议：

- `低于下限` 扣分更快
- `高于上限` 扣分更慢

这样更符合真实用户心智。


## 9. 收入评分方案

收入最不适合做简单硬过滤。

假设用户期望收入区间为 `30-50万`。

建议按以下逻辑处理：

- `30-50`：高分
- `25-29`：略低，轻中度扣分
- `20-24`：明显偏低，中大扣分
- `50-70`：通常仍然不错，轻微扣分甚至不扣
- `70+`：视业务策略轻扣或仅提示

### 9.1 收入建议强烈采用非对称评分

收入的业务语义与年龄、身高不同。

现实中一般是：

- `低于下限`：负向更明显
- `高于上限`：不一定是负向

因此建议：

- `低于下限` 扣分更重
- `高于上限` 扣分更轻
- 某些场景甚至可以只提示、不扣分

### 9.2 收入不应默认被当成封顶线

很多用户填写收入区间的真实含义是：

- “最好在这个生活阶段”

而不是：

- “绝对不能高于这个数”

因此收入更适合表达为：

- 理想带
- 而不是硬上限


## 10. 学历评分方案

学历不适合做上下区间，更适合做等级差评分。

例如用户要求最低学历是 `本科`：

- `本科`：高分
- `硕士/博士`：高分或更高
- `大专`：中低分
- `高中及以下`：低分

学历的关键不是“是否超上限”，而是：

- 是否低于用户底线
- 低了多少个层级

因此学历建议采用“等级阶梯分”。


## 11. 城市 / 距离评分方案

城市不应只做：

- 同城
- 非同城

建议改成距离梯度评分：

- 同区 / 近距离：高分
- 同城不同区：次高分
- 周边通勤城市：中分
- 短途异地：较低分
- 长期异地：低分或硬过滤

### 11.1 距离与异地接受度要分层

需要区分两种语义：

1. `不接受异地`
   这是硬门槛

2. `希望同城`
   这是距离偏好，应进入接近度评分


## 12. 双向匹配如何改

当前 reciprocal 逻辑过于像“拦截器”。

建议改成：

- 真正不能接受的条件，仍然一票否决
- 年龄、身高、收入等不再简单判定 fail
- 改为“对方接受概率分”或“对方偏好接近度分”

也就是说，双向匹配不再只问：

- “你有没有卡进对方区间？”

而改成：

- “你离对方理想偏好有多近？”

这样 reciprocal 就从：

- 硬拦截器

变成：

- 双向加权评分器


## 13. 总分结构建议

建议最终总分由四部分构成。

### 13.1 硬门槛通过

只决定是否进入候选池，不直接计分。

### 13.2 基础条件接近度分

字段包括：

- 年龄
- 身高
- 收入
- 学历
- 城市/距离

这是主分。

### 13.3 双向匹配分

衡量：

- 对方是否也更可能接受你

### 13.4 软偏好与资料质量分

包括：

- 性格
- 价值观
- 生活方式
- 活跃度
- 照片
- 认证
- 资料完整度

### 13.5 推荐权重

可作为起始版本参考：

- 基础条件接近度：50%
- 双向匹配：25%
- 软偏好：15%
- 资料质量/活跃度：10%

这样排序会以“合不合适”为主，而不会过度被资料包装牵引。


## 14. 产品侧配置建议

为了让算法真正贴合用户意图，产品层最好支持每个字段配置“重要性”。

建议每个关键字段支持三种模式：

- `必须满足`
- `理想范围`
- `加分项`

例如：

- 年龄：理想范围 `28-32`
- 收入：理想范围 `30-50`
- 异地：必须满足，不接受异地

这样系统才能区分：

- 什么该硬卡
- 什么该按接近度评分
- 什么只是命中更好


## 15. 数据模型建议

当前很多字段只存一个区间，不能完整表达真实偏好。

建议未来关键字段尽量支持：

- `ideal_min`
- `ideal_max`
- `acceptable_min`
- `acceptable_max`
- `importance`

最少也应支持两层含义：

1. 理想范围
2. 可接受范围

例如收入可表达为：

- 理想收入：`30-50`
- 可接受最低：`25`
- 可接受最高：空

这能表达出：

- 最好在这个区间
- 高一点没关系
- 太低不太行

比单一的 `30-50` 更接近真实语义。


## 16. 结果展示建议

结果页不应只给一个混合列表，也不应只给“有/没有”。

建议分成三层展示：

### 16.1 高匹配

基础条件和双向偏好都比较接近。

### 16.2 可聊对象

存在一定偏差，但整体仍然值得聊。

### 16.3 风险较高

某些核心条件偏差较大，仅作为补充展示。

这样用户看到的将不再是：

- “没人”

而是：

- 很合适的有几个
- 还能聊的有几个
- 偏差主要在哪里


## 17. 与当前逻辑的主要区别

当前逻辑：

- 用大量区间边界做前置过滤
- reciprocal 经常直接 fail
- 结果经常被筛空

新逻辑：

- 只保留少量硬门槛
- 年龄、身高、收入、学历、城市都按接近度评分
- reciprocal 变成加权项，而不是简单 fail
- 最终看总分排序


## 18. 推荐的落地顺序

虽然本文件主要讨论方案，不讨论代码实现细节，但从策略上仍建议按以下顺序推进：

1. 先保留当前硬门槛
2. 先把收入改成接近度评分
3. 再把年龄、身高从区间判断改成连续评分
4. 再改 reciprocal，从硬失败改成双向评分
5. 最后升级产品配置与数据模型


## 19. 最终结论

本次匹配逻辑的最佳改进方向，不是简单“把硬筛放宽”，而是整体范式切换：

- 从区间卡边界
- 改成接近度打分

真正合理的模型应是：

**硬门槛过滤 + 多字段接近度评分 + 双向偏好加权排序**

其中：

- 性别、婚史、孩子、异地、抽烟喝酒等属于“是否接受”的问题，继续硬过滤
- 年龄、身高、收入、学历、城市属于“越接近越好”的问题，应按接近度评分
- reciprocal 不再主要承担“拦截器”角色，而应转成“双向接受概率加权”

这会让系统更符合真实婚恋匹配场景，也能明显减少“假无匹配”。
