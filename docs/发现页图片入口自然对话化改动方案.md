# 发现页图片入口自然对话化改动方案

> 目标：把发现页“发送图片”入口从模式选择式交互，改成“图片 + 自然口语描述”的对话式交互。
>
> 适用范围：发现页前端输入区、图片发送链路、后端照片检索编排层、埋点与验收。

## 0. 核心结论

这次改动的核心不是“新增一个图片搜索 tool”，而是把发现页里的图片找人能力，合并到现有搜索匹配 tool 中，作为统一搜索匹配能力的一种输入形式来承接。

用户侧的体验应该是：

- 发图
- 可选补一句自然话
- 小雅自己理解并完成搜索匹配

系统侧的实现应该是：

- 对外只暴露统一的搜索匹配入口
- 对内保留图像理解、文本理解、候选召回、融合重排、追问判断等模块化能力
- 不再把“按脸找 / 按感觉找 / 按明星找”做成前台模式，也不建议做成 agent 层并列 tool

一句话说：这次不是把“图片搜索”做得更明显，而是把它降级成搜索匹配里的自然对话输入条件。

## 1. 改什么

这次不是重做整套照片能力，而是只改发现页图片入口这一段交互和对应编排方式。

当前问题是：

- 用户点击发送图片后，会看到 `让小雅判断`、`找像这张脸`、`找这种感觉`、`像某明星`
- 上传图片后，还会看到“你可以直接发，让小雅自己判断你是想按脸找、按感觉找，还是按某个参考人物找”
- 这会把用户带进“先学会怎么操作图片搜索”的工具心智

目标状态是：

- 用户点击发送图片
- 图片挂到对话输入区
- 用户直接像聊天一样说一句自然话
- 小雅根据 `图片 + 文本 + 上下文` 自己理解并处理

一句话说，这次改动要把“图片搜索工具入口”改成“带图的自然对话入口”。

## 2. 为什么要改

现在的问题不是文案不够好，而是交互方向错了。

用户真实会说的是：

- `我喜欢这种感觉`
- `帮我找像她这种长相的`
- `不是明星脸，就是这种气质`
- `我想找笑起来很舒服的`

用户不会天然按产品预设去想：

- 我现在是在按脸找
- 还是按感觉找
- 还是按明星找

所以现有设计的问题是：

- 把系统内部分类暴露给用户
- 让用户替系统做理解工作
- 打断自然表达
- 让“发送图片”从聊天流里分叉成一个单独工具流程

## 3. 产品原则

这次改动要遵守四条原则：

1. 用户侧保持单入口，不要求先选模式
2. 图片只是表达上下文，不是独立工具页
3. 小雅负责理解意图，用户只负责发图和说人话
4. 系统内部可以有多种能力，但不能写成一棵硬编码模式树

## 4. 前端改动

### 4.1 要删掉的内容

上传图片后，移除这些用户可见元素：

- 模式选择 chips
- `让小雅判断`
- `找像这张脸`
- `找这种感觉`
- `像某明星`
- `图片已经挂进对话框了。你可以直接发，让小雅自己判断你是想按脸找、按感觉找，还是按某个参考人物找。`

### 4.2 要保留的内容

上传图片后，只保留：

- 图片缩略图预览
- 删除图片按钮
- 普通输入框

### 4.3 输入区行为

上传图片后：

- 输入框还是原来的同一个输入框
- 用户可以不写字直接发图
- 用户也可以补一句自然语言再发
- 回车和发送按钮行为与普通消息保持一致

不要把上传图片后的输入区改造成一个单独的图片搜索编辑器。

### 4.4 输入框提示文案

提示文案可以弱引导，但不能再教用户分流。

可接受方向：

- `可以直接说说你的感觉`
- `补一句你喜欢哪里也行`
- `直接发，或者说说你想找什么样的`

不可接受方向：

- `按脸找`
- `按感觉找`
- `按某个参考人物找`
- `让小雅判断你想走哪种模式`

## 5. 后端与 Tool 改动

### 5.1 总原则

后端不要把前台模式按钮删掉后，再在后台保留一套同样的硬编码分流。

不要写成：

- 用户说了 A 就一定走 face
- 用户说了 B 就一定走 style
- 用户提到明星就一定走 celebrity

这种本质上只是把硬编码从前台搬到后台。

### 5.2 Tool 归属原则

本次改动不建议为“图片入口自然对话化”单独新增一个图片搜索 tool，而应并入现有搜索匹配 tool，作为统一搜索匹配能力的一部分来承接。

原因是：

1. 从产品语义上看，用户无论是发纯文本、发图片，还是发图加一句自然语言，本质诉求都不是“使用某个图片工具”，而是“帮我找符合我偏好的人”。
2. 如果单独新增图片 tool，虽然前端去掉了模式选择，但 agent 层仍然可能退化成“看到图片就走图片 tool、看到文本就走文本 tool”的隐性模式分流。
3. 统一到搜索匹配 tool 后，外部调用语义会更一致。调用方只需要表达“这是一次搜索匹配请求”，而不需要提前判断它属于图片搜索、文本搜索还是混合搜索。

### 5.3 正确做法

对外应该保留一个统一的搜索匹配 tool，例如：

- `search_match`

这个 tool 的输入可以是：

- 纯文本
- 纯图片
- 图片 + 文本
- 图片 + 文本 + 会话上下文

这个 tool 的职责是：

- 理解本轮匹配意图
- 决定是否先看图、先看文本、还是图文联合理解
- 决定是否直接搜索，还是先追问一句
- 决定调哪些内部能力做召回和重排
- 返回候选结果和可解释的理解摘要

### 5.4 内部能力拆分

虽然不单开图片 tool，但内部仍应保留清晰的能力模块，例如：

- `analyze_reference_image`
- `extract_visual_preferences_from_text`
- `search_face_similarity_candidates`
- `search_style_candidates`
- `search_attribute_candidates`
- `search_reference_person_candidates`
- `rerank_visual_candidates`
- `ask_clarifying_question`

这些是搜索匹配 tool 内部可编排的能力集合，不是对上层暴露的固定模式。

真正要由 agent 自主决定的是：

- 先调哪个工具
- 要不要同时调多个工具
- 是否先追问一句
- 是否先做图像理解再做检索
- 是否需要把多路结果融合重排

### 5.5 后端理解的输入

后端每轮要综合理解：

1. 图片本身
2. 用户补充的自然语言
3. 当前发现页会话上下文

需要理解的重点是：

- 用户更在意长相相似，还是感觉相似
- 用户是在拿图做脸部参考，还是风格参考
- 用户有没有追加属性约束
- 用户是不是在表达混合需求
- 当前更适合直接搜，还是先追问

### 5.6 明确反模式

以下实现方式不符合本次方案目标：

- 看到图片就固定调用某个独立图片 tool
- 提到明星就直接映射 celebrity 模式
- 提到“感觉”“气质”就直接映射 style 模式
- tool 对外暴露多个“图片子模式”供 agent 二选一或三选一

这些写法都会让系统重新退回模式分流，只是从前台显式分流，变成后台隐式分流。

## 6. 接口改动

### 6.1 前端请求

前端统一提交附图消息，不再替用户指定明确模式。

建议保留的核心字段：

- `image_source`
- `query_text`
- `session_id`
- `profile_id`

如果为了兼容旧接口暂时还保留 `mode`，前端也只传：

- `auto`

### 6.2 接口语义

接口语义要从：

- `用户选择了一种图片搜索模式`

改成：

- `用户发来一张参考图，并附带一段自然语言需求`

### 6.3 与搜索匹配 Tool 的关系

接口层语义需要与统一搜索匹配 tool 保持一致：

- 前端表达的是一次搜索匹配请求
- 图片是这次请求的参考信息之一
- 文本是这次请求的自然语言补充信息
- 后端负责决定如何理解和编排

如果旧接口暂时保留 `mode` 字段，其语义也只能是兼容字段，不能再承载真实分流逻辑。

## 7. 结果展示改动

前台不要展示：

- `当前按某模式搜索`
- `当前走 face/style/celebrity`

前台应该展示的是“小雅怎么理解了这次需求”，例如：

- `我先按你这张图的整体感觉帮你找了一轮`
- `这轮我更偏按五官相似度和脸型去找`
- `我参考了这张图的清爽感，也把你补的“笑起来舒服”一起算进去了`

重点是解释理解过程，不是暴露内部分类。

## 8. 埋点改动

前端不再暴露模式，不代表后端不做观测。

建议记录：

- `photo_entry_source`
- `has_image`
- `has_query_text`
- `query_text_length`
- `agent_intent_summary`
- `tools_considered`
- `tools_called`
- `tool_call_order`
- `tool_call_reasons`
- `clarify_before_search`
- `clarify_reason`
- `result_fusion_strategy`
- `result_count`
- `user_followup_action`

重点记录的是 agent 的理解和能力调用过程，不是模式枚举值。

## 9. 验收标准

改完后至少要满足：

1. 用户上传图片后，界面上不再出现任何模式选择按钮
2. 用户上传图片后，界面上不再出现“按脸找 / 按感觉找 / 按明星找”的教学文案
3. 用户可以只发图，也可以发图加一句自然语言
4. 前端发送接口默认走统一入口，不要求用户侧决定模式
5. 后端是自主编排能力工具，不是命中规则树
6. 前台结果解释是口语化理解，不是内部分类说明
7. 埋点中能看到真实的工具调用与融合过程

## 10. 非目标

这次改动不包括：

- 重做底层照片特征体系
- 重做整套人脸向量索引
- 改写推荐系统全链路
- 替换现有发现页全部输入区交互

这次只聚焦：

- 发现页图片入口交互
- 图片消息的请求语义
- 搜索匹配 tool 内部编排方式
- 结果解释与埋点

## 11. 完整落地任务拆分

下面按可执行任务拆分，默认前提是：图片能力并入现有搜索匹配 tool，不单开新 tool。

### 11.1 产品与交互任务

1. 明确最终用户路径
   - 用户点击图片入口后，仍停留在普通对话输入流
   - 上传后页面只保留图片缩略图、删除按钮、原输入框、发送按钮
2. 删除旧交互元素
   - 下线 `让小雅判断`
   - 下线 `找像这张脸`
   - 下线 `找这种感觉`
   - 下线 `像某明星`
   - 下线所有“教用户选模式”的提示文案
3. 确认输入框提示语
   - 产出新的弱引导文案
   - 明确哪些表达可接受，哪些表达不可接受
4. 确认无文案场景
   - 明确只上传图片是否允许直接发送
   - 明确删除图片后是否恢复普通输入态
5. 确认结果解释口径
   - 解释理解过程
   - 不暴露内部模式名
   - 不出现 `face/style/celebrity`

### 11.2 前端任务

1. 改造发现页输入区 UI
   - 去掉上传图片后的模式 chips
   - 去掉图片模式说明文案
   - 保留图片预览、删除按钮、输入框、发送按钮
2. 改造输入状态管理
   - 支持纯文本
   - 支持纯图片
   - 支持图片 + 文本
   - 删除图片后完整回退状态
3. 统一发送逻辑
   - 带图消息走普通发送链路
   - 不再走模式化分支
4. 调整请求字段
   - 发送 `image_source`
   - 发送 `query_text`
   - 发送 `session_id`
   - 发送 `profile_id`
   - 如需兼容旧接口，仅传 `mode=auto`
5. 校验交互行为
   - 只发图是否可发送
   - 发图 + 文本时回车和发送按钮是否一致
   - 上传中、删除中、失败重试是否正常
6. 改造前端埋点
   - 新增 `photo_entry_source`
   - 新增 `has_image`
   - 新增 `has_query_text`
   - 新增 `query_text_length`
   - 废弃显式模式选择埋点
7. 补齐异常处理
   - 图片上传失败提示
   - 图片失效或解析失败提示
   - 图片过大或格式不支持提示
   - 发送失败重试逻辑

### 11.3 接口层任务

1. 统一请求语义
   - 把接口定义从“模式搜索请求”改为“带图自然对话搜索请求”
2. 处理旧字段兼容
   - 短期兼容 `mode=auto`
   - 中期移除对 `mode` 强依赖
   - 最终删除旧模式枚举
3. 明确空文本带图协议
   - 定义 `query_text` 为空时的传法
   - 明确后端如何识别“只发图”
4. 透传会话上下文
   - 保证后端能拿到 session 和历史上下文

### 11.4 搜索匹配 Tool 改造任务

1. 明确 tool 对外定位
   - 统一收口到 `search_match` 一类搜索匹配入口
2. 扩展 tool 入参模型
   - 支持文本
   - 支持图片
   - 支持图片 + 文本
   - 支持会话上下文
   - 支持用户 profile 信息
3. 保留内部模块化能力
   - 图像理解
   - 文本偏好提取
   - 长相相似召回
   - 风格/气质召回
   - 属性约束召回
   - 参考人物识别或映射
   - 结果融合重排
   - 追问判断
4. 改造编排逻辑
   - 支持先看图、先看文本、图文联合理解
   - 支持多路并行召回
   - 支持先追问再搜
5. 下线硬编码模式树
   - 排查并删除关键词直映模式逻辑
   - 排查并删除“有图即某模式”的默认分流逻辑
6. 升级输出结构
   - 返回候选结果
   - 返回内部理解摘要
   - 返回是否追问及原因

### 11.5 后端能力模块任务

1. 接入图像理解能力
   - 输出视觉摘要
   - 输出可用于搜索的特征描述
2. 接入文本理解能力
   - 识别偏长相还是偏感觉
   - 识别属性约束和否定条件
   - 识别混合需求
3. 梳理多路召回能力
   - 相似脸召回
   - 风格相似召回
   - 属性过滤
   - 参考人物映射
   - 混合召回
4. 实现融合重排策略
   - 定义图像信号和文本信号如何平衡
   - 定义用户补充文本如何参与重排
   - 定义上下文偏好如何参与重排
5. 实现追问策略
   - 图像信息弱时可先追问
   - 文本约束冲突时可先追问
   - 低置信度理解时可先追问
6. 生成可解释摘要
   - 为前台提供口语化理解素材

### 11.6 数据与埋点任务

1. 埋点字段落库
   - `photo_entry_source`
   - `has_image`
   - `has_query_text`
   - `query_text_length`
   - `agent_intent_summary`
   - `tools_considered`
   - `tools_called`
   - `tool_call_order`
   - `tool_call_reasons`
   - `clarify_before_search`
   - `clarify_reason`
   - `result_fusion_strategy`
   - `result_count`
   - `user_followup_action`
2. 定义核心指标
   - 图片入口发送率
   - 图片消息带文本比例
   - 首轮结果点击率
   - 首轮追问率
   - 二次补充率
   - 搜索成功率
   - 会话继续率
3. 设计对比实验
   - 对比旧模式分流入口和新自然对话入口
   - 重点观察发送转化、追问率、满意度和继续率

### 11.7 测试任务

1. 前端功能测试
   - 上传图片
   - 删除图片
   - 只发图
   - 发图 + 文字
   - 发送失败重试
   - 刷新恢复
2. 接口测试
   - 纯图片请求
   - 图片 + 文本请求
   - 空文本请求
   - 非法图片地址
   - 超长文本
   - 旧字段兼容
3. 搜索匹配 tool 测试
   - 偏长相请求
   - 偏气质请求
   - 明星参考请求
   - 混合需求请求
   - 低置信度追问
   - 图文冲突输入
4. 回归测试
   - 普通文本搜索匹配
   - 发现页原有聊天发送
   - 推荐链路其他入口
   - 老版本客户端兼容
5. 结果解释测试
   - 不出现技术模式词
   - 能正确反映本轮理解

### 11.8 上线任务

1. 准备灰度开关
   - 前端自然对话图片入口开关
   - 后端搜索匹配编排开关
2. 准备监控告警
   - 图片发送失败率
   - 搜索耗时
   - 空结果率
   - 追问率异常
   - tool 调用失败率
3. 准备回滚方案
   - 可分别回滚前端入口、后端编排、接口兼容逻辑

### 11.9 建议的项目任务标题

- 删除发现页图片上传后的模式选择 UI
- 删除图片模式教学文案并替换为弱引导提示
- 统一发现页图片消息发送链路
- 调整带图消息请求协议为自然对话语义
- 兼容旧 `mode` 字段并固定传 `auto`
- 改造搜索匹配 tool 支持图片/图文混合输入
- 下线搜索匹配中的模式硬编码分流逻辑
- 接入图像理解与文本偏好联合编排
- 实现多路召回融合与重排
