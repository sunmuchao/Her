# 人脸关键点检测接入主流程改进方案

## 1. 背景与问题

当前照片分析主流程已经会产出一批外貌相关字段，但其中有两类能力被混在了一起：

1. AI整体感知能力
   - 入口在 [match_domain/appearance_features.py](/Users/sunmuchao/Downloads/Her/match_domain/appearance_features.py:1283) 的 `build_photo_feature_patch(...)`
   - 会调用：
     - [match_domain/beauty_score_analyzer.py](/Users/sunmuchao/Downloads/Her/match_domain/beauty_score_analyzer.py:92)
     - [match_domain/appearance_description_generator.py](/Users/sunmuchao/Downloads/Her/match_domain/appearance_description_generator.py:92)
   - 产出 `beauty_score`、`appearance_summary`、`appearance_keywords`、`appearance_style_type`、`dominant_features`

2. 脸部细节属性能力
   - 当前写入 `profile_face_attributes` 的逻辑在 [match_domain/appearance_features.py](/Users/sunmuchao/Downloads/Her/match_domain/appearance_features.py:1505) 的 `_build_face_attribute_patch(...)`
   - 这里的 `eye_size_score`、`face_roundness_score`、`jaw_definition_score`、`smile_intensity_score`、`skin_clarity_score`、`youthfulness_score` 并不是基于真实人脸关键点检测算出来的
   - 这些值目前主要来自：
     - 前面 AI 整体打分字段
     - 稳定 hash
     - 一些固定公式

这会带来两个核心问题：

1. 字段语义不真实
   - `eye_size_score` 看名字像“真实量测”
   - 实际却是“根据整体印象大概推出来的数”

2. 搜索和推荐会被误导
   - 用户说“找眼睛小的女生”，系统如果按 `eye_size_score` 去筛，很容易筛出不符合直觉的人
   - 因为底层不是在看眼睛本身，而是在看一个间接估算结果

## 2. 现状确认

仓库里已经有一套真正的关键点提取器：

- [match_domain/face_attributes_extractor.py](/Users/sunmuchao/Downloads/Her/match_domain/face_attributes_extractor.py:48)

这套能力基于 `dlib` 68 点关键点，当前可以提取：

- `eye_size_score`
- `eye_distance_score`
- `nose_height_score`
- `nose_width_score`
- `lip_thickness_score`
- `lip_width_score`
- `face_shape_type`
- `jawline_definition_score`
- `forehead_height_score`
- `chin_prominence_score`
- `cheekbone_prominence_score`

但它目前没有真正接入主流程，`extract_face_attributes(...)` 现在没有被主链路调用。

另外，现有提取器还有一个工程缺口：

- 代码里使用 `cv2.imread(photo_url)` 读取图片
- 这更适合本地文件路径
- 现在线上主流程拿到的大多是 MinIO HTTP URL
- 所以即使把它强行接上，也会先卡在图片加载这一层

## 3. 改造目标

目标不是“再加一个新的打分器”，而是把“真实关键点检测”接入当前照片分析主流程，并明确分层：

1. `profile_photo_features`
   - 继续保存 AI 对照片整体观感的理解
   - 例如颜值、风格、整体描述、关键词

2. `profile_face_attributes`
   - 改为保存基于真实人脸关键点计算出来的几何属性
   - 例如眼睛大小、眼距、鼻梁高度、嘴唇厚度、下颌线清晰度、脸型

这样后续搜索、推荐、解释、排序，才可以真正依赖这些“脸部细节字段”。

## 4. 目标架构

建议把主流程拆成两条并行但职责清晰的能力链：

1. 整体外貌理解链
   - 输入：主图
   - 能力：视觉大模型
   - 输出：`beauty_score`、`appearance_summary`、`appearance_keywords`、`appearance_style_type`
   - 落表：`profile_photo_features`

2. 脸部结构量测链
   - 输入：同一张主图
   - 能力：人脸检测 + 68 点关键点 + 几何计算
   - 输出：`eye_size_score`、`eye_distance_score`、`nose_height_score`、`lip_thickness_score`、`face_shape_type` 等
   - 落表：`profile_face_attributes`

这两条链都分析“照片”，但不是一回事：

- 第一条回答“这个人整体看起来怎样”
- 第二条回答“这个人的五官结构具体怎样”

## 5. 主流程接入方案

### 5.1 当前主链路

当前主要路径是：

1. `refresh_profile_photo_features(...)`
2. `build_photo_feature_patch(...)`
3. `_sync_profile_face_side_tables(...)`
4. `_build_face_attribute_patch(...)`

现在的问题出在第 4 步：

- `_build_face_attribute_patch(...)` 没有调用真实关键点提取
- 而是在用估算逻辑拼一个伪属性 patch

### 5.2 改造后的主链路

建议改成：

1. `build_photo_feature_patch(...)`
   - 继续负责 AI 整体外貌分析
   - 不再承担“推断脸部细节属性”的职责

2. `_sync_profile_face_side_tables(...)`
   - 在写 `profile_face_attributes` 前，调用真实的人脸关键点提取器

3. `_build_face_attribute_patch(...)`
   - 从“公式估算器”改成“真实属性映射器”
   - 输入真实提取结果
   - 将提取结果标准化后落库

建议的新调用关系：

1. 选主图
2. 主图走 AI 整体分析
3. 同一张主图走 landmark 提取
4. 两边结果分别写入各自表

## 6. 代码级改造点

### 6.1 扩展 `face_attributes_extractor.py`

文件：

- [match_domain/face_attributes_extractor.py](/Users/sunmuchao/Downloads/Her/match_domain/face_attributes_extractor.py:48)

必须补齐以下能力：

1. 支持 HTTP/HTTPS/MinIO URL 图片加载
   - 不再直接用 `cv2.imread(photo_url)`
   - 改为：
     - 若是本地路径，继续本地读取
     - 若是 URL，先下载二进制，再 `cv2.imdecode(...)`

2. 输出结构标准化
   - 明确 `success`
   - 明确 `error_code`
   - 明确 `error_message`
   - 明确 `face_count`
   - 明确 `selected_face_index`
   - 明确 `extractor_version`

3. 多人脸处理策略
   - 默认选面积最大的人脸，而不是简单取第一个
   - 将总人脸数写入结果

4. 质量门槛
   - 图片太小、脸太斜、遮挡严重、关键点不稳定时，返回失败或低置信结果

建议新增内部函数：

- `_load_image_from_source(...)`
- `_select_primary_face(...)`
- `_compute_face_quality_signals(...)`
- `_normalize_attribute_payload(...)`

### 6.2 重写 `_build_face_attribute_patch(...)`

文件：

- [match_domain/appearance_features.py](/Users/sunmuchao/Downloads/Her/match_domain/appearance_features.py:1505)

改造方向：

1. 删除当前基于 `mature_score`、`gentle_score`、`sunny_score` 等字段推导 `eye_size_score` 的逻辑
2. 改为接收真实 landmark 提取结果
3. 直接映射到 `profile_face_attributes`

建议直接落库的字段：

- `eye_size_score`
- `eye_distance_score`
- `nose_height_score`
- `nose_width_score`
- `lip_thickness_score`
- `lip_width_score`
- `face_shape_type`
- `jawline_definition_score`
- `forehead_height_score`
- `chin_prominence_score`
- `cheekbone_prominence_score`
- `face_count`
- `dominant_face_index`
- `extractor_version`

对于当前表里已有但 landmark 暂时不直接提供的字段，建议分三类处理：

1. 可直接废弃的伪字段
   - 例如当前纯估算得出的 `youthfulness_score`
   - 若业务没有强依赖，建议停止写入或置空

2. 可以暂时保留但标注来源的字段
   - 例如 `smile_intensity_score`、`skin_clarity_score`
   - 这类字段未必适合当前 dlib 68 点直接稳定计算
   - 可先保留旧字段，但增加来源标记

3. 需要后续补充真实算法的字段
   - 如果产品强依赖，再单独做二期算法

### 6.3 改造 `_sync_profile_face_side_tables(...)`

文件：

- [match_domain/appearance_features.py](/Users/sunmuchao/Downloads/Her/match_domain/appearance_features.py:1548)

建议逻辑：

1. 根据主图 URL 调用 `extract_face_attributes(...)`
2. 如果成功：
   - 用真实结果生成 face attributes patch
   - `attribute_source = landmark`
3. 如果失败：
   - 不阻塞 `profile_photo_features` 主流程
   - `profile_face_attributes` 可选择：
     - 保留旧值不更新
     - 或写失败状态
   - 不建议再悄悄写一套伪造的新 `eye_size_score`

建议新增落库元信息：

- `attribute_source`
  - `landmark`
  - `heuristic_fallback`
  - `unavailable`
- `attribute_confidence`
- `attribute_error_code`
- `attribute_error_message`
- `analyzed_photo_url`
- `analyzed_photo_version`

## 7. 数据分层与字段职责

这是这次改造里最关键的一条原则。

### 7.1 `profile_photo_features` 负责什么

只负责 AI 对“整体观感”的理解，例如：

- 颜值分
- 整体气质
- 外貌总结
- 风格标签
- 主导特征描述

这些字段适合用于：

- 文案解释
- 粗排序
- 风格推荐

### 7.2 `profile_face_attributes` 负责什么

只负责“可量测的人脸结构属性”，例如：

- 眼睛大小
- 眼距
- 鼻梁高度
- 鼻翼宽度
- 唇厚
- 脸型
- 下颌线清晰度

这些字段适合用于：

- 精细筛选
- 条件搜索
- 结构化偏好匹配

### 7.3 不能再混用

后续任何“眼睛大/小”“脸圆/不圆”“鼻子高/不高”的查询，都应该优先走 `profile_face_attributes` 的真实量测字段，而不是继续从 `appearance_summary` 或整体气质标签里猜。

## 8. 搜索推荐链路如何跟着调整

改造完后，搜索推荐侧也要同步改，不然只是“写了真字段，但查询还在走旧逻辑”。

建议规则：

1. 用户明确提出结构型偏好
   - 如“小眼睛”“圆脸”“高鼻梁”“厚嘴唇”
   - 优先转成结构化过滤条件
   - 命中 `profile_face_attributes`

2. 用户提出风格型偏好
   - 如“温柔”“干净”“御姐”“元气”
   - 继续主要依赖 `profile_photo_features`

3. 两类偏好同时存在
   - 先做结构过滤
   - 再做整体风格排序

这能解决之前那种问题：

- 用户说“小眼睛”
- 系统却只是根据整体印象推荐“看起来合适的人”
- 最终推荐结果和用户肉眼判断完全不一致

## 9. 图片加载与基础设施要求

### 9.1 图片访问

主流程里的人脸关键点检测需要稳定拿到原图或足够清晰的缩略图。

建议要求：

1. 分析服务必须能访问 MinIO 内网地址
2. 下载超时、重试、最大文件大小都要有限制
3. 下载后统一转成 OpenCV 可处理的数组

### 9.2 模型依赖

`dlib` 方案要求：

1. 容器镜像内有 `dlib`、`opencv-python`
2. 启动时能找到：
   - `shape_predictor_68_face_landmarks.dat`
3. 服务启动时做一次自检
   - 缺模型直接告警
   - 缺依赖直接告警

### 9.3 运行资源

关键点检测是 CPU 密集型任务，不应继续无节制地和主推荐链路抢资源。

建议：

1. 单独队列
   - `photo_feature_refresh`
   - `face_landmark_refresh`

2. 单独并发限制
   - landmark 队列并发数单独控制

3. 单独 worker 或独立进程池
   - 避免把搜索推荐主线程打满

## 10. 容错与降级策略

原则：真实关键点提取失败时，不要拖死主流程，但也不要继续伪造一个“看起来像真值”的结果。

建议策略：

1. AI 整体分析成功、landmark 失败
   - `profile_photo_features` 正常写入
   - `profile_face_attributes` 记录失败状态或保持旧值
   - `attribute_source = unavailable`

2. landmark 成功但质量低
   - 写入结果
   - 同时写 `attribute_confidence`
   - 搜索时只在置信度达标时参与强过滤

3. 完全无脸、多人脸混乱、遮挡严重
   - 不产出结构化脸部结论
   - 只保留 AI 整体描述

不建议默认启用“heuristic fallback 继续写假值”，除非为了兼容老接口短期过渡，并且必须显式标记来源。

## 11. 历史数据回填方案

线上已有大量 `profile_face_attributes` 是旧估算值，必须回填，否则新老数据会混杂。

建议分三步：

1. 增加来源标记字段
   - 先区分老数据是 `heuristic`
   - 新数据是 `landmark`

2. 批量重跑
   - 读取有主图的历史 profile
   - 按批次执行 landmark 提取
   - 写回真实 face attributes

3. 分批切流
   - 当 `landmark` 覆盖率足够高后
   - 搜索推荐默认只依赖 `landmark` 数据

回填期间，搜索侧建议：

1. 优先使用 `attribute_source = landmark`
2. 对 `heuristic` 数据降低权重或不用于强过滤

## 12. 测试与验收

### 12.1 单元测试

至少覆盖：

1. 本地路径图片读取
2. URL 图片读取
3. 无脸场景
4. 多脸场景
5. 图片损坏场景
6. landmark 成功后的字段映射

### 12.2 集成测试

至少覆盖：

1. `refresh_profile_photo_features(...)` 跑完全链路
2. `profile_photo_features` 和 `profile_face_attributes` 同时更新
3. MinIO 图片可正常下载并解析
4. landmark 失败不会阻塞主分析

### 12.3 业务验收

抽样人工校验以下查询：

1. “眼睛小”
2. “眼距宽”
3. “圆脸”
4. “鼻梁高”

验收标准不是“字段写进去了”，而是：

1. 检索结果和人工肉眼判断大体一致
2. 同一批候选人的排序稳定
3. 明显优于现有 heuristic 结果

## 13. 上线步骤

建议分阶段上线：

### 阶段一：基础接通

1. 补齐 URL 图片加载
2. 主流程接入 `extract_face_attributes(...)`
3. 新增来源字段与失败字段
4. 先只对新分析数据生效

### 阶段二：搜索侧灰度

1. 搜索解析里识别结构型偏好
2. 灰度走 landmark 字段过滤
3. 对比新旧结果质量

### 阶段三：历史回填

1. 跑批重算老数据
2. 统计覆盖率与失败率
3. 修正阈值和质量门槛

### 阶段四：彻底切换

1. 下线旧 heuristic face attribute 生成逻辑
2. 搜索推荐默认使用真实 landmark 属性
3. 清理混淆字段和旧版本标记

## 14. 风险与注意事项

### 14.1 算法风险

`dlib` 68 点对以下场景会不稳定：

- 侧脸
- 大遮挡
- 重美颜
- 超低清晰度
- 多人同框

所以不能把它当成“任何照片都必定成功”的能力。

### 14.2 工程风险

最大工程风险有三个：

1. 镜像依赖重
   - `dlib` 在部分环境编译和运行要求较高

2. CPU 消耗高
   - 大批量历史回填容易打爆资源

3. 图片访问链路不稳
   - MinIO、网络、图片格式兼容都可能导致失败

### 14.3 产品风险

如果没有来源标记，前台和搜索层会继续把旧 heuristic 数据当成真值使用，导致结果逻辑前后不一致。

## 15. 最终建议

本次改造建议按下面原则落地：

1. 保留 AI 整体外貌分析
   - 它适合做整体观感和风格理解

2. 把真实人脸关键点检测接入主流程
   - 让 `profile_face_attributes` 真正代表五官结构

3. 搜索推荐分层使用
   - 结构型条件走 landmark
   - 风格型条件走 AI 整体理解

4. 明确来源、置信度、失败状态
   - 不再把“估算值”伪装成“真实测量值”

5. 将 landmark 任务从主推荐资源池中拆开
   - 避免再次出现照片分析抢占资源、拖慢搜索推荐主流程的问题

## 16. 验收结论

这次改造完成后的标志，不是“代码里多了一个关键点模块”，而是下面三件事同时成立：

1. 新分析出来的 `profile_face_attributes` 来自真实 landmark 提取
2. 用户说“小眼睛”“圆脸”这类需求时，系统能基于真实结构字段筛选
3. 照片分析任务不会再把搜索推荐主流程拖慢

只有这三点同时做到，才算真正完成“人脸关键点检测接入主流程”。
