🤖 四、Agent 决策核心逻辑

DISCOVERY_AGENT_SOUL.md 核心原则
  • 1. 学习式对话
    每次拒绝都是学习机会，不要只刷新，要理解原因。先答应用户请求，再顺带收集信号。
  • 2. 主动建议
    理解用户意图，不只是执行命令。当用户多次表达相似不满时，主动提出调整建议。
  • 3. 诚实透明
    推荐理由要可解释，调整策略要告知用户。当用户对某个维度表达不满时，应该解释该维度的匹配逻辑。
  • 4. 输出风格
    口语化、自然、像真人红娘。根据用户性格调整语气（急性子简洁，慢性子详细）。

Agent Native 特点对比

✅ 正确设计
  • Agent 根据 Prompt 自主理解用户意图
  • 工具 description 描述能力和使用场景
  • 单一真相来源：SOUL.md + 工具描述
  • 工具只返回原始 data（保留 component_type）
❌ 反模式（已废弃）
  • 触发词映射表（关键词 → 工具硬编码）
  • 工具返回 instruction/output_hint（模板化输出）
  • 工具包含业务逻辑（筛选、排序、评分）
  • 规则分散在多处（SOUL.md + 工具 + schemas）

🔧 五、工具调用链路

🔍 search_partner_candidates 核心工具
搜索候选人。当用户想看推荐、调整搜索条件、表达不满后重新搜索时调用。
Agent → search_partner_candidates(criteria_json, limit)
→ run_input.search_partner_candidates(criteria, limit)
→ service._search_partner_candidates(session, criteria, limit)
→ partner_search.search_profiles(source, criteria, self_profile, limit)
→ 返回搜索结果 summary
💾 sync_requester_persona_memory 偏好同步
将用户表达的择偶偏好同步到长期记忆（Persona Memory），后续推荐更精准。
Agent → sync_requester_persona_memory(patch_json)
→ run_input.sync_requester_persona_memory(patch)
→ service._sync_requester_persona_memory(session, patch, now)
→ persona_memory API
→ 返回同步结果
📝 propose_requester_profile_update 资料更新
提议更新用户资料（如年龄、城市变化），生成 profile_update_prompt 到 timeline，用户确认后才生效。
Agent → propose_requester_profile_update(patch_json, evidence_text)
→ run_input.propose_requester_profile_update(patch, evidence)
→ service._propose_requester_profile_update(session, patch, evidence, now)
→ 返回更新提议
💬 reply_to_user 输出工具
纯回复用户，不展示候选人卡片。用于对话收集偏好、解释匹配逻辑等场景。
Agent → reply_to_user(message, criteria_labels, suggested_actions)
→ tool_state["reply_payload"] = {...}
→ Agent Runtime 提取 reply_payload
→ 转换为 DiscoveryDecision
👥 show_candidates 输出工具
展示候选人卡片。用于搜索结果展示，包含 assistant_message + result_group + suggested_actions。
Agent → show_candidates(message, criteria_labels, result_group_title, suggested_actions)
→ tool_state["show_payload"] = {...}
→ Agent Runtime 提取 show_payload（优先级高于 reply）
→ 转换为 DiscoveryDecision
🔔 create_saved_search_subscription 订阅工具
创建订阅持续留意，当有新候选人匹配时推送通知。
Agent → create_saved_search_subscription_from_last_search(title)
→ service._create_saved_search_subscription(session, title, now)
→ 返回订阅创建结果
💡 工具返回结构（Agent Native 原则）
正确设计：工具只返回原始 data，包含 component_type 供前端渲染。
禁止：instruction/output_hint/summary 字段（职责错位，导致模板化输出）。
示例：
{ "success": true,
"data": {
"component_type": "MatchCardList", // ✅ 前端渲染需要
"candidates": [...], // ✅ 原始数据
"user_preferences": {...} // ✅ Agent 参考信息
}
}

🎯 八、关键特性总结

🧠 Agent Native 架构
AI 自主理解用户意图，无需硬编码关键词。单一真相来源：SOUL.md + 工具描述。
⚡ 流式响应
Runner.run_streamed 流式运行，前端显示 TypingIndicator，减少延迟感知。
🔄 会话管理
sessionId 持久化到 localStorage，页面刷新后恢复上次会话，支持多会话切换。
📊 测评集成
MBTI、价值观拍卖会等测评结果可融入对话流，成为对话的一部分。
💡 如何理解这个系统？
  1. 看架构：前端 → Hook → API → Gateway → Service → Agent → 工具 → 数据，分层清晰。
  2. 看初始化：页面加载 → 恢复/创建会话 → Agent 首次决策 → 展示候选人或欢迎消息。
  3. 看交互：用户输入/点击 → 乐观更新 → API调用 → Agent决策 → 工具执行 → 数据返回 → 渲染。
  4. 看Agent：SOUL.md 定义角色 → 工具描述能力 → AI自主理解意图 → 调用工具 → 输出决策。
  5. 看工具：工具只返回原始data，Agent根据数据自主决定如何回复，不使用模板。
  6. 看数据流：单向数据流，前端发起请求 → 后端处理 → Agent决策 → 返回数据 → 前端渲染。
